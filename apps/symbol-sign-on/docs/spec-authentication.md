# Symbol Sign-On v1 認証仕様

## 文書情報

| 項目 | 内容 |
| --- | --- |
| 文書種別 | アプリケーション仕様書 |
| 対象 | Symbol Sign-On v1 の認証要求・署名・識別子 |

本書は、認証要求とSymbol署名を結び付け、通常認証および強化認証を判定するための外部動作を定義する。Main/Childの公開状態は [spec-public-state.md](./spec-public-state.md)、対応サービスとの結果交換は [spec-sso-integration.md](./spec-sso-integration.md)、失効と障害は [spec-revocation-operations.md](./spec-revocation-operations.md) を正本とする。

## 1. 適用範囲と責任境界

### 1.1 対象

Symbol Sign-Onは、利用者がパスワードを提示せず、Symbolの認証鍵による署名で本人確認を行う。通常認証は単一の認証鍵で成立し、強化認証は任意のChild鍵とMain/Child公開状態の検証を組み合わせる。

通常認証は、ログインごとのSymbolトランザクション発行および常時のオンチェーン参照を必要としない。強化認証で必要となる公開状態の参照は、[spec-public-state.md](./spec-public-state.md) の規則に従う。

### 1.2 対象外

本書は次を定義しない。

- 秘密鍵の生成、保管、復元、バックアップおよびUI
- 標準DIDまたはDID Coreへの準拠
- サービス固有の認可、権限、プロフィール、セッションおよびデータ継続性
- Symbolトランザクションの作成、アナウンスまたはチェーン上の意味検証
- OAuth/OIDCの具体的なエンドポイントおよびトークン形式

### 1.3 秘密情報の責任境界

- 認証基盤および対応サービスは秘密鍵を受け取らず、保存せず、ログ・例外・デバッグ出力・監査記録へ平文で出力してはならない。
- v1の初期対応署名クライアントはSafelySignSymbolとする。ただし、必要な署名操作の実行可能性、提供主体、安全管理主体および継続利用責任は別途確認する。
- 署名クライアントが秘密鍵を認証基盤へ開示しないことを、v1提供前の確認項目とする。

## 2. 用語

| 用語 | 定義 |
| --- | --- |
| 認証主体 | 子鍵の追加・変更・失効後も同一利用者として扱う対象。サービス固有アカウントとは異なる。 |
| 認証主体識別子 | 認証主体を指定するSymbolアドレスまたはSymbolネームスペース。`did`形式は使用しない。 |
| Main | 強化認証においてChildとの関係を承認・変更・失効できる側のアカウント。 |
| Child | 任意で追加するログイン用の別鍵アカウント。 |
| 通常認証 | 単一の認証鍵によるオフチェーン署名認証。 |
| 強化認証 | Childの署名に加え、Main/Childの有効な公開状態を確認する認証。 |
| 認証要求 | 対象サービス、署名対象および有効条件を指定する、認証基盤が発行する要求。 |

## 3. 認証要求の論理モデル

認証要求は、少なくとも次の論理情報を持たなければならない。実際のフィールド名、wire format、文字コードおよびシリアライズ方式は未決定であり、適合実装間で同一のバイト列を再構成できる仕様として別途確定する。

| 論理情報 | 必須性 | 制約と意味 |
| --- | --- | --- |
| 対象サービス | 必須 | 認証結果を利用できるサービスを一意に識別する。 |
| 要求識別子 | 必須 | 認証要求と署名結果を関連付け、使用済み要求を判定する。 |
| Challengeまたは署名対象 | 必須 | 利用者が署名する値。認証基盤が発行した値でなければならない。 |
| 発行時点 | 必須 | 要求の発行順序または有効期間の判定に使用する。 |
| 有効期限 | 必須 | 期限経過後の署名を認証に使用しない。 |
| 対象ネットワーク | 必須 | TestnetとMainnetを混同しないために使用する。 |

認証要求に含める論理情報のうち、上流要件から必要性が導けない追加情報は標準項目にしてはならない。

## 4. 認証要求の発行と検証

1. 認証基盤は、許可された対応サービスを対象として認証要求を発行する。
2. 認証要求には、要求識別子、対象サービス、署名対象、有効条件および対象ネットワークを含める。
3. 利用者は、認証基盤へ秘密鍵を渡さず、署名クライアントを通じて署名を生成する。
4. 認証基盤は、署名を検証する前に、要求の存在、構造、対象サービス、対象ネットワークおよび期限を検証する。
5. 認証基盤は、署名が検証可能であり、検証済みの要求と対応し、未使用である場合だけ認証を成立させる。
6. 認証成立後、要求識別子または対応する署名を使用済みとして扱い、同じ要求を再利用して認証を成立させてはならない。

未発行、改変、期限切れ、対象サービス不一致、対象ネットワーク不一致、検証不能または使用済みの要求は拒否する。入力を推測で補正してはならない。

## 5. 署名仕様

### 5.1 署名の責務

Symbol署名は本人確認のために使用する。認証基盤は、署名が有効であることだけから、チェーン上のトランザクションが有効であること、利用者が処理を承認すべきこと、またはサービス固有の認可が成立したことを推論してはならない。

Symbolの署名方式、公開鍵および署名の検証は対象プロトコル版と署名クライアントの対応を確認して実施する。オフチェーン認証メッセージへ、根拠なくトランザクション固有のシリアライズ規則を適用してはならない。

### 5.2 署名対象バイト列

署名対象は、独立実装が同一のバイト列を再構成できるよう、次を確定しなければならない。

- 各論理フィールドの順序と必須性
- 文字列の文字コードとバイト表現
- 数値・時刻の表現
- Challenge、要求識別子、対象サービス、対象ネットワークの境界
- 公開鍵および署名の外部表現

本初版では、これらの具体値は上流資料だけから一意に導けないため未決定とする。署名対象バイト列が確定するまで、認証サービスを相互運用仕様として提供してはならない。

### 5.3 署名失敗

次のいずれかに該当する場合、認証を成立させてはならない。

- 署名対象の再構成に失敗した
- 公開鍵または署名の形式が不正である
- 署名検証に失敗した
- 署名者と認証主体またはChildの対応を確認できない
- 認証要求の対象サービスまたはネットワークと一致しない
- 認証要求が期限切れまたは使用済みである

## 6. 認証主体識別子

- 認証主体識別子は、SymbolアドレスまたはSymbolネームスペースのいずれか一方で指定する。
- アドレスとネームスペースの両方の指定を必須にしてはならない。
- 識別子は対象ネットワークを含めて正規化し、一意に比較できなければならない。
- ネームスペースを使用する場合、対象ネットワーク上で有効なSymbolアドレスへ解決できることを確認する。
- 解決結果が取得不能、対象ネットワーク不一致、参照時点不明または信頼不能の場合、解決結果を認証成功の根拠にしてはならない。
- 解決結果の変更を同一認証主体の継続として扱う条件は未決定である。確認なしに既存主体を別主体へ再割当てしてはならない。
- Childの追加、変更または失効によって認証主体識別子を変更してはならない。

Symbolアドレスのネットワーク情報およびネームスペース解決APIは、Symbol技術資料・OpenAPIを参照して対象バージョンとの整合性を確認する。ただし、APIの存在だけから認証上の信頼性や継続条件を導出してはならない。

## 7. 通常認証と強化認証

### 7.1 通常認証

- 通常認証は単一の有効な認証鍵による署名で成立する。
- 通常認証はChild設定を必須としない。
- 通常認証は、当該ログインごとのSymbolトランザクション発行および常時のオンチェーン参照を必要としない。
- 強化認証の公開状態が信頼不能または参照不能であることだけを理由に、通常認証を停止してはならない。

### 7.2 強化認証

- 利用者は通常認証を維持したまま、任意でChildを追加できる。
- Childによる署名に加え、Main/Childの有効な公開状態を確認する。
- Child側の自己申告だけで強化認証を成立させてはならない。
- Main側の承認、Childの制御確認および公開状態の確認が成立しない場合、強化認証を成立させてはならない。
- Childの変更・失効後の状態は [spec-public-state.md](./spec-public-state.md) と [spec-revocation-operations.md](./spec-revocation-operations.md) に従う。

## 8. エラー分類

呼び出し側が認証不成立の理由を区別する必要がある場合、少なくとも次の分類を使用する。具体的なwire error codeは未決定である。

| 分類 | 条件 |
| --- | --- |
| `INVALID_REQUEST` | 必須情報の欠落、形式不正、再構成不能 |
| `REQUEST_NOT_FOUND` | 未発行または存在を確認できない要求 |
| `REQUEST_EXPIRED` | 有効期限を経過した要求 |
| `REQUEST_REUSED` | 使用済み要求または署名の再利用 |
| `SERVICE_MISMATCH` | 対象サービスが現在の要求・結果と一致しない |
| `NETWORK_MISMATCH` | Testnet/Mainnetなど対象ネットワークが一致しない |
| `SIGNATURE_INVALID` | 署名または署名者を検証できない |
| `IDENTIFIER_UNRESOLVED` | 認証主体識別子を信頼できる対象へ解決できない |
| `CHILD_RELATION_INVALID` | Main/Child関係を確認できない |
| `PUBLIC_STATE_UNAVAILABLE` | 強化認証に必要な公開状態を確認できない |

## 9. 未決定事項・要確認事項

- 認証要求のwire format、Challenge形式、期限表現および再利用保持方式
- 署名対象の正確なバイト列、文字コード、署名クライアントとの交換形式
- 初回利用時の新規主体成立または既存主体への利用開始の扱い（OPEN-013）
- ネームスペース解決結果の変更時に継続性を認める条件（OPEN-016）
- SafelySignSymbolの提供・安全管理・継続利用責任と確認主体（OPEN-014）
- Symbolプロトコル、ノードおよびREST Gatewayの対応バージョン
