# Symbol Sign-On v1 SSO連携仕様

## 文書情報

| 項目 | 内容 |
| --- | --- |
| 文書種別 | アプリケーション仕様書 |
| 対象 | 認証結果を対応サービスへ提供する連携契約 |
| 対象チェーン | Symbol |
| 対象ネットワーク | 初期検証: Testnet、正式提供: Mainnet |
| 主な上流 | [requirements.md](./requirements.md)、[sso-memo01.md](./sso-memo01.md) |

本書は、認証基盤と対応サービスの責任境界、対象サービス限定、認証結果および契約変更を定義する。認証そのものは [spec-authentication.md](./spec-authentication.md)、失効結果は [spec-revocation-operations.md](./spec-revocation-operations.md) を参照する。

## 1. 適用範囲と対象外

### 1.1 対象

- 認証基盤から対応サービスへの認証成立・不成立の提供
- 認証結果と対象サービスの結び付け
- 認証とサービス固有の認可・権限・セッションの責任分離
- 認証関連HTTP通信のHTTPS要件
- 複数サービスで共通認証契約を使用する場合の版と変更責任

### 1.2 対象外

- サービス固有のログイン後セッション、ロール、権限およびアカウント管理
- サービス間のアカウント統合、共通識別子共有およびデータ移行
- OAuth/OIDCの採否を根拠なく確定すること
- TLSの具体的な暗号スイート、証明書運用またはインフラ構成

## 2. 責任境界

### 2.1 認証基盤運用主体

認証基盤運用主体は、次を担う。

- 認証要求の対象サービスを管理する。
- 認証結果の提供を許可したサービスを管理する。
- 認証要求に対応する本人確認結果を判定する。
- 通常認証・強化認証の方式差を対応サービスへ持ち込まない。
- 公開状態の失効または認証基盤障害時に、認証結果・失効結果を提供する。
- 重要な管理操作について、操作主体と対象を後から確認できる状態を維持する。

### 2.2 対応サービス

対応サービスは、次を担う。

- 自サービスを対象とする有効な認証結果だけを受け入れる。
- 認証成功を自サービスの認可・権限付与と同一視しない。
- 自サービスのセッション、認可、権限およびデータ責任を担う。
- 認証結果の失効を認識した場合、自サービスの認証状態またはセッションを継続利用させない。
- 認証成功未確認を独自に成功扱いしない。

### 2.3 サービス間の分離

- あるサービスへの認証成功は、別サービスのアカウント同一性、連携、統合または権限を意味しない。
- 共通識別子のサービス間共有を必須としない。
- あるサービスへの提供許可・停止を、別サービスへ暗黙に適用してはならない。
- サービス間で識別子、認証結果または認証記録を共有する場合、目的、範囲および責任主体を識別できるようにする。具体方式は未決定である。

## 3. 論理的な連携情報

認証結果は、少なくとも次の論理情報を識別できなければならない。実際のAPI、JSON名、トークン形式および搬送方式は未決定である。

| 論理情報 | 必須性 | 意味 |
| --- | --- | --- |
| 契約版 | 必須 | 対応サービスが解釈可能な認証契約を識別する。 |
| 対象サービス | 必須 | 結果を受け入れられるサービスを限定する。 |
| 認証主体識別子 | 必須 | 本人確認された認証主体を示す。サービス間共有を必須としない。 |
| 認証方式 | 認証基盤内部では必須 | 通常認証または強化認証を判定する。サービス向け結果で方式差を公開することは必須としない。 |
| 結果 | 必須 | 成立または不成立を明示する。 |
| 状態有効性 | 必須 | 結果が有効、失効または確認不能であることを示す。 |
| 対象ネットワーク | 必須 | Testnet/Mainnetを区別する。 |

認証結果にサービス固有のロール、権限または認可判断を含めてはならない。

## 4. 連携処理

1. 対応サービスが認証基盤へ認証要求を開始する。
2. 認証基盤は、サービスが提供許可を受けていることと、要求の対象サービスが一致することを確認する。
3. 認証基盤は [spec-authentication.md](./spec-authentication.md) に従って通常認証または強化認証を判定する。
4. 認証成立時、認証基盤は対象サービスに限定された認証結果を提供する。
5. 対応サービスは、結果の対象サービス、契約版、ネットワークおよび有効性を確認して受け入れる。
6. 認証結果が不成立、失効または確認不能の場合、対応サービスはログイン成功として扱ってはならない。

## 5. 通信と秘密情報

- 認証要求、署名結果、認証結果、公開状態の参照・変更およびSymbolノード・外部サービスとの認証関連通信はHTTPSで行う。
- 平文HTTPを認証関連通信に使用してはならない。
- TLS設定、接続先確認、証明書検証および障害・侵害時の責任主体を導入条件として識別できなければならない。
- 秘密鍵、ニーモニック、パスワードその他の署名用秘密情報を、認証結果またはサービス連携情報に含めてはならない。

## 6. OAuth/OIDCの扱い

補足メモはOAuth 2.0/OIDC Authorization Code Flow + PKCEを外部SSO方式の想定として示している。しかし、要件定義では具体的な方式、API、トークン形式および保存方式を確定していない。

したがって、本初版では次を規範仕様としない。

- `/authorize`、`/token`、`/userinfo`等の具体的なエンドポイント
- Authorization Code、Access Token、ID Token、Refresh Tokenの形式・claim・期限
- PKCEのパラメータとクライアント認証方式
- Tokenの失効、Introspection、保存およびセッション方式

採用方式が承認されるまで、実装者はOAuth/OIDCの採用を仕様上の確定事項として扱ってはならない。採用する場合は、対象サービス、契約版、署名認証結果、失効結果との対応を本書へ追記する。

## 7. 契約版と変更

- 認証契約の旧版と新版を識別できなければならない。
- 対応サービスと署名クライアントが、各契約版を処理可能か判定できなければならない。
- 非互換変更または廃止を行う場合、影響を受けるサービス・クライアント、周知責任、移行責任および提供停止の責任を識別する。
- 本仕様は、上流で承認されていない移行期間、フォールバック、互換層または廃止手順を追加しない。

版の表現、移行期間、通知方式および廃止手順は未決定である。

## 8. エラー分類

| 分類 | 条件 |
| --- | --- |
| `SERVICE_NOT_ALLOWED` | 認証結果の提供が許可されていないサービス |
| `SERVICE_SUSPENDED` | 提供停止済みのサービス |
| `SERVICE_MISMATCH` | 要求・結果・受入れ側の対象サービスが不一致 |
| `CONTRACT_UNSUPPORTED` | 契約版を処理できない |
| `AUTHENTICATION_FAILED` | 本人確認が成立しない |
| `AUTHENTICATION_REVOKED` | 認証状態が失効している |
| `AUTHENTICATION_UNCONFIRMED` | 認証の正当性を確認できない |
| `NETWORK_MISMATCH` | 対象ネットワークが不一致 |
| `SECURE_TRANSPORT_REQUIRED` | HTTPSでない通信 |
