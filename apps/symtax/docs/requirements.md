# SymTax 要件定義

## 1. 概要・目的

SymTaxはSymbol（XYM）のTransactionsとReceiptsを独立して参照・整理し、必要に応じてCryptactへ取り込めるデータを出力するWebツールである。長期間・大量の履歴を持つアカウントでも確認しやすくし、高頻度のHarvest関連Receiptについては個別履歴と価格評価の根拠を保持したまま、Cryptact向けの登録件数を削減できることを目指す。

SymTaxは税額計算、税務上の分類・判断、確定申告を行わない。履歴の取得・表示・整理と、利用者が確認できる出力データの作成を責務とする。

## 2. 要件の読み方

要件IDは本書および後続のSpecification・Reviewから参照するための一意な識別子である。要件の優先度を表す語は次の意味で用いる。

- **MUST:** 初期リリースの受け入れに必須。
- **SHOULD:** 初期リリースで満たすことを目指す。満たせない場合は理由と影響を記録し、対象範囲を誤認させない。
- **MAY:** 初期リリースに必須ではない任意の能力。

この区分は要件の適合性を表し、実装方式や品質の数値目標を定めるものではない。特段の記載がない要件はMUSTとする。

## 3. 対象範囲と責任境界

### 3.1 初期リリースの対象

- 対象チェーンはSymbol、対象資産はXYMとする。
- 利用者が指定したSymbolアドレスと期間について、TransactionsとReceiptsを参照する。
- 両カテゴリを月サマリー、日サマリー、個別明細の階層で確認する。
- bitbank Public APIのXYM/JPY 1分足を初期の市場価格ソースとし、Harvest関連Receiptの価格評価およびCryptact向け出力を支援する。
- Cryptact向けには個別明細出力とHarvest関連Receiptの日次集約出力を設ける。

### 3.2 初期リリースの対象外

- NEM（XEM）、複数アドレス・複数アカウント管理
- TransactionsまたはHarvest以外のReceiptの日次圧縮
- 税額計算、総平均法・移動平均法等の税務計算、税務上の分類や判断、確定申告書作成
- ウォレット機能、秘密鍵・ニーモニック管理、署名、トランザクション送信
- Symbolノードの管理
- Cryptact以外のサービス向け出力およびbitbank以外の価格Provider

これらの対象外は将来拡張の可能性を否定しない。

### 3.3 責任境界

| 主体 | 責任 |
|---|---|
| SymTax | 指定対象のオンチェーン履歴の参照・表示、価格データの保存・再利用、価格評価根拠と派生集計の追跡可能性、出力データの作成、取得・評価上の不完全性の明示 |
| 利用者 | アドレス・期間等の指定、履歴と価格評価の確認、出力データの採否、Cryptact等への取込、税務上の分類・申告判断 |
| Symbolノード運用環境 | SymTaxが参照できるSymbol MainnetまたはTestnetのデータ提供と、その保持・完全性に関する運用 |
| bitbank | 公開APIによる価格データの提供。過去データの将来にわたる可用性はSymTaxが保証できない |
| Cryptact | 受け入れるファイル形式、取引分類、価格・損益計算の規則とサービス動作 |

## 4. 利用者・関係者

- SymbolアカウントのTransactions、Receipts、Harvest状況を確認したい利用者
- Cryptactを利用し、Symbol履歴の照合や取込用データ作成を行いたい利用者
- 長期間または多量の履歴を持ち、特にHarvest関連Receiptの記録件数を抑えたい利用者
- Symbol MongoDBを参照可能な環境を提供・運用する担当者
- 価格データProviderおよび出力先であるbitbank、Cryptact

## 6. 主要ユースケース

| ID | 利用者の目的 | 主な結果 |
|---|---|---|
| UC-001 | Symbolアドレスと期間を指定してTransactionsを確認する | 指定範囲のTransaction一覧、月・日サマリー、個別明細を参照できる |
| UC-002 | 同じアドレス・期間のReceiptsをTransactionsと分けて確認する | Receipt一覧、月・日サマリー、Receiptの個別明細を参照できる |
| UC-003 | Harvest関連Receiptの価格評価を確認する | Receipt単位の数量、価格評価とその根拠を確認できる |
| UC-004 | Cryptactに取り込む履歴を出力する | 個別明細、または条件を満たすHarvest関連Receiptの日次集約を選んで出力できる |
| UC-005 | 日次集約結果を元履歴と照合する | 集約行から対象となった個別Harvest Receiptおよび各価格評価根拠を確認できる |

## 7. 機能要件

### 7.1 アドレス・期間指定と履歴取得

| ID | 要件 |
|---|---|
| FUNC-001 | 利用者はSymbolアドレスと参照期間を指定できなければならない。指定条件に対する履歴と、参照対象のネットワークを識別できなければならない。 |
| FUNC-002 | SymTaxはTransactionsとReceiptsを独立したカテゴリとして参照できなければならない。一方の表示・集計が他方を暗黙に含めたり、両者を単一の履歴として混在させたりしてはならない。 |
| FUNC-003 | TransactionカテゴリはTransfer、Aggregate、Metadata、Mosaic、Namespaceおよびその他のSymbol Transactionを扱う。具体的な型分類は後続のSpecificationで定める。 |
| FUNC-004 | ReceiptカテゴリはHarvestおよびその他のReceiptを扱う。Receipt Typeの詳細分類は後続のSpecificationで定める。 |

### 7.2 表示・集計

| ID | 要件 |
|---|---|
| FUNC-005 | TransactionsとReceiptsはそれぞれ、月サマリーから日サマリー、個別明細へ確認を進められなければならない。 |
| FUNC-006 | 月・日サマリーはJST基準でなければならず、各日の対象時刻はJSTの00:00以上、翌日00:00未満とする。価格評価のtimestamp対応と日付集約境界は区別する。 |
| FUNC-007 | 各カテゴリの日サマリーは、当該カテゴリに意味のある件数、数量、手数料、Harvest量、円換算額等を確認できること。表示項目の最終選択は後続のSpecificationで定める。 |
| FUNC-008 | サマリーから、その対象となる個別オンチェーン履歴を確認できなければならない。サマリーは個別履歴を置き換えず、元履歴から派生した情報として扱う。 |
| FUNC-009 | TransactionとReceiptの関連を利用者に示す場合も、独立したカテゴリ、一覧および集計を維持しなければならない。関連付けの範囲はOPEN-006に従い後続で決定する。 |

### 7.3 Harvest ReceiptとCryptact出力

| ID | 要件 |
|---|---|
| EXPORT-001 | Cryptact向け出力では、個別明細出力とHarvest日次集約出力を区別して選択できなければならない。 |
| EXPORT-002 | 個別明細出力はオンチェーン履歴に近い粒度で、利用者が元履歴と照合できる形で提供しなければならない。 |
| EXPORT-003 | 初期リリースの日次圧縮対象はHarvest関連Receiptのみとする。TransactionsおよびHarvest以外のReceiptsを日次圧縮してはならない。 |
| EXPORT-004 | Harvest日次集約はJST日単位を基礎とする。集約によって意味の異なる記録を混在させず、同日であることだけを集約条件として扱わない。集約可否に関わる未決事項はOPEN-001およびOPEN-005へ引き継ぐ。 |
| EXPORT-005 | 日次集約のために個別Harvest Receiptを削除・置換してはならない。利用者は集約行から構成Receiptの個別数量、個別価格評価および元履歴を追跡できなければならない。 |
| EXPORT-006 | Harvest日次集約は、数量合計だけで個別価格評価を失わせてはならない。各Receiptの価格評価根拠と日次評価の関係を保持し、個別出力との経済的な差が生じ得る場合はその可能性と制約を利用者に分かる形で示さなければならない。SymTaxは税務上の正しさや損益計算の同等性を保証しない。 |
| EXPORT-007 | 出力はCryptactが受け入れる形式と整合しなければならない。ただし、ファイル形式・Harvestの取引表現・集約行の計算上の扱いは、現行Cryptact仕様と照合した後に確定する（OPEN-005）。 |

## 8. 市場価格・データ要件

| ID | 要件 |
|---|---|
| PRICE-001 | 初期のXYM/JPY価格データはbitbank Public APIの1分足を利用対象とする。価格ソースと価格粒度を利用者が確認できなければならない。 |
| PRICE-002 | Harvest Receiptの市場価格評価は、Receiptを含むTransaction Statementが記録されたblockのtimestampを基準とする。これはReceipt自身に独立timestampがあることを前提としない。block timestampから1分足への対応方法およびOHLCの採用値はOPEN-002で決定する。 |
| PRICE-003 | 一度取得した過去価格をSymTax側で保存し、再利用できなければならない。価格データはアドレスごとではなくXYM/JPY市場に共通するデータとして扱い、保存済み価格は経過期間のみを理由に削除してはならない。 |
| PRICE-004 | 個別Harvest Receiptについて、数量、評価額、価格ソース、価格粒度、評価に用いた価格情報と元履歴を追跡できなければならない。価格評価根拠は後から検証・再現できる情報として保持する。 |
| PRICE-005 | 該当価格が得られない、取得不能、または価格根拠を確認できない場合、SymTaxは当該Receiptを確定した価格で評価済みであるかのように扱ってはならない。個別履歴を保持し、未評価または不完全であることを利用者が識別できるようにする。具体的な欠損補間・出力可否はOPEN-003、OPEN-004、OPEN-005に引き継ぐ。 |
| DATA-001 | オンチェーンTransactionとReceiptを原履歴として保持し、月次・日次サマリー、価格評価、Cryptact向け日次集約を原履歴から生成される派生情報として扱わなければならない。集約・出力によって元履歴を失ってはならない。 |
| DATA-002 | 利用者が選択した参照範囲について、取得結果が不完全、価格が未評価、またはデータ提供元の制約がある場合、その状態を正常に完全取得・評価できた結果と区別できなければならない。欠損を黙って補完または隠蔽してはならない。 |
| DATA-003 | SymTaxは公開アドレスに関連する参照履歴・価格・派生情報を、利用目的に必要な範囲を超えて保存することを前提としない。保持期間、利用者への説明、ログの扱いはOPEN-010で確定する。 |

## 9. 性能・品質要件

| ID | 要件 |
|---|---|
| PERF-001 | 参照期間が指定された場合、その期間外の不要な履歴を毎回全件取得することを前提としてはならない。 |
| PERF-002 | 数年分、多数のTransactions、月数百〜数千件規模のReceiptsを主要な利用条件として扱う。月700件程度のHarvest関連Receiptを代表負荷例として性能・利用性評価に含める。これはユーザー提供の事例であり、全アカウントの標準件数を意味しない。 |
| PERF-003 | 巨大な生データをブラウザへ一括転送することを前提としてはならない。ブラウザ側が全履歴を一括保持・解析する方式を必須とせず、大量履歴の確認が可能でなければならない。 |
| PERF-004 | 大量の明細を一度に画面要素として展開することを前提としてはならず、利用者が対象範囲の履歴を確認し続けられること。具体的な性能値、応答時間、メモリ上限、代表端末・ネットワーク条件はOPEN-008で決定する。 |
| QUAL-001 | 履歴取得、価格評価または出力の一部が失敗・欠損した場合、結果の完全性を誤認させず、利用者が未完了範囲または根拠不足を認識できること。再試行、補完、代替操作の具体方式は後続設計・仕様で定める。 |

## 10. Security・Privacy・ネットワーク境界

| ID | 要件 |
|---|---|
| SEC-001 | SymTaxは秘密鍵またはニーモニックを入力・保存・処理せず、トランザクション署名または送信を行わない。 |
| SEC-002 | Symbol MongoDBはブラウザから直接アクセスできず、DB接続情報をブラウザへ送信してはならない。SymbolノードのMongoDBを外部へ直接公開しない。アクセスは原則read-onlyとする。 |
| SEC-003 | TestnetとMainnetの接続先・データは明示的に分離し、異なるネットワークの履歴を一つの結果として混在させてはならない。開発・検証はTestnet、公開版はMainnetを対象とする。 |
| PRIV-001 | Symbolアドレスは公開情報であるが、SymTaxはアドレスと利用者の活動履歴の関連を慎重に扱い、利用者に履歴参照・価格保存・ログ等のデータ取扱いを説明できなければならない。保持範囲とログ方針の詳細はOPEN-010で決定する。 |
| SEC-004 | SymTax独自データを永続化する場合、SymbolノードDBの変更・書込みと分離しなければならない。 |

## 11. 外部サービス・相互運用性

| ID | 要件 |
|---|---|

## 14. Design / Specificationへの引継ぎ

### Designで扱う事項

- Symbol MongoDB参照の成立性、対象バージョン・履歴保持の検証およびデータ完全性の説明
- 大量・長期間履歴の性能目標と計測条件（OPEN-008）
- Testnet/Mainnetの運用分離・識別（OPEN-009）
- 価格データの保存、更新、再取得、欠損時の責任境界（OPEN-003、OPEN-004）
- アドレス関連情報の保持、Privacy、ログおよび利用者への説明（OPEN-010）
- TransactionsとReceiptsの独立した責務と、任意の関連付けの境界（OPEN-006）

### Specificationで扱う事項

- Transaction Type / Receipt Typeの具体的な分類と明細に必要な外部可視情報
- JSTサマリーと市場価格timestampの対応契約（集計境界はJSTで確定済み）
- Statementのblock timestampとbitbank 1分足の対応、OHLC選択、出来高0・価格欠損の扱い（OPEN-002、OPEN-003）
- Cryptact現行仕様に照らした個別出力とHarvest日次集約の形式、集約可能条件（OPEN-001、OPEN-005）
- 取得・評価が不完全な場合の表示・出力上の外部可視ルール

この引継ぎは、API path、MongoDB query・collection・schema、具体的な集約アルゴリズム、価格補間式、UIレイアウト、端数処理を本書で決めるものではない。

- `apps/symtax/docs/reviews/concept/concept-review-001.md` — 判定READY。Critical/Major/Minor指摘なし。Cryptact現行取込仕様、MongoDB実データ・スキーマ、bitbank再取得は未確認として後続に残している。

### 外部一次資料で確認した事実

- bitbank公式[Public API仕様](https://github.com/bitbankinc/bitbank-api-docs/blob/master/public-api.md)は、ローソク足種別に `1min` を含め、OHLCVとUnix時刻を返す形式を記載する。公式[取扱ペア一覧](https://github.com/bitbankinc/bitbank-api-docs/blob/master/pairs.md)には `xym_jpy` が記載されている。これらはAPI仕様上の対応を示すもので、特定過去日の取得成功を示さない。
- Cryptact公式[カスタムファイル作成方法](https://support.cryptact.com/hc/ja/articles/360002571312-%E3%82%AB%E3%82%B9%E3%82%BF%E3%83%A0%E3%83%95%E3%82%A1%E3%82%A4%E3%83%AB%E3%81%AE%E4%BD%9C%E6%88%90%E6%96%B9)は、カスタムファイルのCSV/XLSX、日時・種類・ソース・主軸通貨・取引量・価格・決済通貨・手数料等の項目と記載要領を案内する。公式[カスタムファイルのアップロード方法](https://support.cryptact.com/hc/ja/articles/7557126434457-%E3%82%AB%E3%82%B9%E3%82%BF%E3%83%A0%E3%83%95%E3%82%A1%E3%82%A4%E3%83%AB%E3%81%AE%E3%82%A2%E3%83%83%E3%83%97%E3%83%AD%E3%83%BC%E3%83%89%E6%96%B9%E6%B3%95)はアップロード時の帳簿タイムゾーンの扱いを説明する。これらだけでは、Harvest Receiptの適切な分類、日次集約値の受け入れ、個別登録と同一の計算結果を確認できないため、OPEN-005は未決のままとする。

### 利用者提供の確認結果と未確認事項

- `concept.md` に記録されたユーザーによるAPI取得確認として、bitbank XYM/JPY 1分足の2026-01-01および2025-01-01データが取得でき、確認時点で少なくとも2025-01-01まで取得可能とされている。本作業では日付別API応答を独立に再取得していない。この事実はbitbank公式仕様による保証とは区別する。
- Cryptactの現行仕様のうち、Harvest Receiptの税務上・計算上の分類、Harvest日次集約の許容性、個別明細との計算同等性は確認できていない。EXPORT-001〜007およびAC-005〜006に影響し、OPEN-005として後続で確認する。
- MongoDBの実データ、ノードごとの保持履歴、バージョン差異を本作業で検証していない。CON-001、FUNC-001、DATA-002、EXT-003に影響し、OPEN-007として成立性確認・Designへ引き継ぐ。
