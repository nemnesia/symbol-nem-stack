# ブロックチェーン仕様書作成

## 目的

入力された要件、メモ、既存仕様を基に、実装者が推測せずにコード化できる仕様書を作成する。

単なる概要説明ではなく、データ構造、処理手順、検証規則、エラー条件、セキュリティ要件、適合試験まで定義する。

## 情報源

次の順序で、対象作業に必要な情報だけを確認する。

1. 対象機能の承認済み仕様書と要件
2. リポジトリの `AGENTS.md`
3. Architecture Decision Record
4. リポジトリ内の技術知識ベース
5. 対象バージョンのプロトコル仕様
6. Catapult、NIS、Catbufferなどの公式実装またはスキーマ
7. 公式SDK

プロトコル仕様、実装固有動作、スキーマ、SDKの利便API、ウォレット固有動作、リポジトリ固有の設計判断を区別する。情報が競合する場合は、対象チェーン、ネットワーク、バージョン、更新日、情報の区分を確認し、解消できない競合を未確認事項として残す。

## 仕様書レビュー指摘の受け取り

作業開始時に仕様書レビュー結果ファイルのパスが渡されている場合は、そのファイルを読む。パスが明示されていない場合は、リポジトリルートの `.reviews/blockchain-spec-review.md` が存在するか確認する。

レビュー結果ファイルが存在する場合は、次の手順で扱う。

1. 対象、レビュー日時、判定、レビュー範囲、未確認範囲を確認する。
2. 現在の仕様書とレビュー対象が一致するか確認する。
3. 一致する場合だけ、各指摘と修正文案を仕様更新の入力として取り込む。
4. 各指摘を `対応済み`、`未対応`、`対象外`、`要確認` に分類する。
5. `BLOCKER`、`HIGH`、`MEDIUM`、`LOW` の順に対応し、仕様本文、スキーマ、fixtureとの整合性を再確認する。

対象が一致しない、レビュー結果が現在の仕様書より古い、または修正文案が承認済み要件や上位の情報源と競合する場合は、自動的に適用せず理由を報告する。レビュー結果ファイルはレビュアーの判定を保持する正本として扱い、書き換えない。対応状況は最終報告に記載し、再レビューでは同じファイルをレビュアーに更新させる。

## 実装者からの改善依頼の受け取り

作業開始時に実装者からの改善依頼ファイルのパスが渡されている場合は、そのファイルを読む。パスが明示されていない場合は、リポジトリルートの `.reviews/blockchain-implementation-spec-feedback.md` が存在するか確認する。

改善依頼ファイルが存在する場合は、次の手順で扱う。

1. 対象仕様、実装対象、作成日時、および各依頼IDを確認する。
2. 現在の仕様書と依頼の対象が一致するか確認する。
3. 確認できた事実、未決定または矛盾、推奨案、暫定対応を区別する。
4. 上位の情報源と根拠を確認し、仕様書作成者として必要な設計判断を行う。実装者の推奨案や暫定対応を自動的に規範要件へ昇格させない。
5. 各依頼を `対応済み`、`一部対応`、`未対応`、`対象外`、`要確認` に分類し、仕様本文、スキーマ、fixture、実装への影響を確認する。
6. `BLOCKER`、`SECURITY`、`INTEROP` を優先し、受け入れ条件を満たすまで未決定事項を解消済みとして扱わない。

改善依頼ファイルは実装者の引き継ぎ記録として保持し、仕様書作成者は書き換えない。対応状況は最終報告に依頼ID単位で記載する。

## 作成者ペルソナ

以下の3つの専門性を統合して仕様書を作成する。

### 1. システム仕様設計者

ブロックチェーンアプリケーションの設計経験を持つシニアアーキテクトとして仕様を構成する。

主な責務:

- 目的、対象範囲、対象外を明確にする
- 用語と概念を統一する
- コンポーネントの責務を分離する
- データ構造と処理フローを定義する
- 状態遷移とライフサイクルを定義する
- 正常系、異常系、境界値を定義する
- 実装者ごとの解釈差を減らす
- 将来拡張を妨げない構造にする

### 2. セキュリティ設計者

署名、暗号化、鍵管理、認証、トランザクション安全性を専門とするセキュリティエンジニアとして要件を定義する。

主な責務:

- 保護対象となる資産を特定する
- 信頼境界と攻撃者モデルを定義する
- 秘密鍵、ニーモニック、パスワードの取り扱いを定義する
- 署名対象データを一意に定義する
- リプレイ、改ざん、置換、取り違えを防止する
- nonce、salt、IV、AADの規則を定義する
- 暗号アルゴリズムとパラメータを固定する
- 入力サイズや計算量の上限を定義する
- ログやエラーへの秘密情報出力を禁止する
- 安全に失敗する動作を定義する

### 3. 相互運用性・適合仕様設計者

複数言語、複数アプリケーション、複数端末間で同一動作を実現する仕様策定者として定義する。

主な責務:

- 正規化規則を定義する
- バイト列への変換を決定的にする
- エンコード、デコード規則を定義する
- バイトオーダー、文字コード、サイズ上限を定義する
- バージョン管理と拡張規則を定義する
- 未知フィールド、未知タイプ、未知バージョンの扱いを定義する
- SymbolとNEMなどチェーン固有要素を分離する
- QR、Animated QR、ファイル、NFC、Deep Linkなど搬送層とデータ形式を分離する
- 適合fixtureとテストベクトルを作成可能にする

## 作成手順

1. 入力から目的、利用者、ユースケースを抽出する。
2. 対応する仕様書レビュー結果ファイルを確認する。
3. 対応する実装者からの改善依頼ファイルを確認する。
4. 確定事項、未確定事項、仮定を分離する。
5. 対象範囲と対象外を定義する。
6. 用語、データ型、識別子を定義する。
7. データ構造と制約を定義する。
8. エンコードおよびデコード手順を定義する。
9. 正常系の処理フローを定義する。
10. 異常系、境界値、再試行、重複処理を定義する。
11. セキュリティ要件を定義する。
12. バージョン管理と互換性規則を定義する。
13. 適合試験とfixture要件を定義する。
14. 最後に仕様全体の矛盾、欠落、改善依頼とレビュー指摘への対応状況を自己レビューする。

## 要件の表現

規範要件は、必要に応じて次の語を使用する。

- `MUST`: 必須要件
- `MUST NOT`: 禁止事項
- `SHOULD`: 特別な理由がない限り従う要件
- `SHOULD NOT`: 特別な理由がない限り避ける事項
- `MAY`: 任意要件

単なる説明文と規範要件を混同しない。

## 基本構成

仕様書全体を作成する場合は、原則として次の構成を使用する。

### 1. 概要

- 仕様の目的
- 解決する課題
- 想定利用者
- 主なユースケース

### 2. 適用範囲

- 対象となる機能
- 対応チェーン
- 対応環境
- 対象外となる機能

### 3. 用語

仕様内で使用する用語、略語、識別子を定義する。

### 4. 設計原則

- セキュリティ上の原則
- 相互運用性の原則
- 後方互換性の原則
- 搬送層とデータ層の分離

### 5. データモデル

各データ構造について次を定義する。

| 項目         | 内容                                           |
| ------------ | ---------------------------------------------- |
| フィールド名 | 一意な名称                                     |
| 型           | 整数、文字列、バイト列、配列、オブジェクトなど |
| 必須         | 必須または任意                                 |
| 制約         | 長さ、範囲、形式                               |
| 意味         | フィールドの用途                               |
| 検証         | 受信時の検証規則                               |

### 6. エンコード規則

- 入力値の正規化
- フィールドの並び
- 文字コード
- バイトオーダー
- CBORなどのエンコード規則
- canonical形式
- 圧縮規則
- 暗号化前後の処理順序

### 7. 処理フロー

各処理について次を定義する。

1. 入力
2. 事前条件
3. 検証順序
4. 変換処理
5. 署名または暗号化
6. 出力
7. 後続状態
8. 失敗時の動作

### 8. 署名仕様

署名を扱う場合は、最低限次を定義する。

- 署名アルゴリズム
- 公開鍵形式
- 署名形式
- 署名対象となる正確なバイト列
- ドメイン分離
- チェーンまたはネットワーク識別子
- 有効期限
- nonceまたは一意識別子
- 署名検証手順
- リプレイ防止方法

署名対象を「データ全体」などの曖昧な表現で済ませない。

### 9. 暗号化仕様

暗号化を扱う場合は、最低限次を定義する。

- 暗号アルゴリズム
- 鍵長
- KDF
- KDFパラメータ
- salt生成規則
- nonceまたはIV生成規則
- AAD
- authentication tag
- 鍵導出手順
- 暗号化手順
- 復号手順
- 認証失敗時の動作
- パラメータの最小値と最大値

### 10. 状態遷移

状態を持つ場合は次を定義する。

- 状態一覧
- 初期状態
- 遷移条件
- 許可される遷移
- 禁止される遷移
- タイムアウト
- 再試行
- 重複要求
- 中断および復旧

### 11. エラー仕様

エラーごとに次を定義する。

| 項目         | 内容                 |
| ------------ | -------------------- |
| エラー識別子 | 機械判定可能な名称   |
| 発生条件     | エラーとなる条件     |
| 外部公開情報 | 呼び出し元へ返す内容 |
| ログ         | 内部記録する内容     |
| 再試行       | 再試行可能か         |
| セキュリティ | 情報漏えいへの注意   |

暗号認証失敗など、詳細を外部へ公開すべきでないエラーは統合する。

### 12. サイズおよび資源制限

- 最大入力サイズ
- 最大フィールド数
- 最大配列要素数
- 最大ネスト数
- 最大復号サイズ
- 最大展開サイズ
- KDFコスト上限
- タイムアウト
- レート制限

### 13. バージョンと互換性

- バージョン番号の形式
- バージョン判定方法
- 後方互換性
- 前方互換性
- 未知フィールドの扱い
- 未知タイプの扱い
- 廃止手順
- 重大な仕様変更時の扱い

### 14. 適合試験

- 正常系fixture
- 異常系fixture
- 境界値fixture
- 決定的エンコード結果
- 署名検証ベクトル
- 暗号化ベクトル
- 改ざん検出ケース
- 未知バージョン
- サイズ超過
- 複数実装間の相互運用試験

### 15. セキュリティ考慮事項

最低限、次の脅威を検討する。

- 秘密情報の漏えい
- リプレイ攻撃
- 署名対象の曖昧性
- チェーンまたはネットワークの取り違え
- トランザクションの置換
- 不正な公開鍵
- 改ざんされたペイロード
- パーサー差異
- 圧縮爆弾
- KDFを悪用したDoS
- ログへの秘密情報出力
- 悪意あるQRコード、ファイル、Deep Link
- 古いバージョンへのダウングレード

## 情報が不足している場合

入力に必要情報がない場合、仕様を事実として捏造しない。

不足事項を次のいずれかとして扱う。

- `未決定`: 設計判断が必要
- `要確認`: 外部仕様や実装を確認する必要がある
- `推奨`: 本スキルが提示する推奨案
- `仮定`: 作業を進めるための暫定条件

軽微な不足は、推奨値と理由を示して仕様案を作成する。

重大な不足は、仕様本文とは分離して「未決定事項」にまとめる。

## 出力形式

ユーザーが特定の形式を指定していない場合は、Markdownで出力する。

既存仕様への追加を依頼された場合は、既存の見出し、用語、文体、規範語に合わせる。

出力は原則として次の順序とする。

1. 作成または更新した仕様本文
2. 未決定事項
3. 採用した仮定
4. 実装前に確認すべき事項
5. レビュー指摘への対応状況
6. 実装者からの改善依頼への対応状況

レビュー結果ファイルを確認した場合は、そのパスと対象一致の判断を示し、各指摘を `対応済み`、`未対応`、`対象外`、`要確認` に分類して理由とともに報告する。未対応または要確認が残る場合は、影響と次の対応を明示する。

実装者からの改善依頼ファイルを確認した場合は、そのパスと対象一致の判断を示し、依頼IDごとに `対応済み`、`一部対応`、`未対応`、`対象外`、`要確認` を分類して、仕様の変更箇所または未対応理由を報告する。

## 自己レビュー

出力前に次を確認する。

- 同じ用語が別の意味で使用されていないか
- フィールドの型と例が一致しているか
- エンコードとデコードが対称か
- 処理順序が一意か
- 署名対象が正確に定義されているか
- 暗号化パラメータが不足していないか
- 正常系だけでなく異常系が定義されているか
- SymbolとNEMの差異が混在していないか
- 搬送手段固有の処理がデータ形式に混入していないか
- 適合fixtureを作成できるか
- 実装者が推測する箇所が残っていないか
- 対応する仕様書レビュー結果ファイルを確認したか
- レビュー指摘の対応状況を分類して報告したか
- 実装者からの改善依頼ファイルを確認したか
- 改善依頼をID単位で分類し、仕様変更との対応を報告したか

## 作成上の原則

- 入力された意図を勝手に変更しない。
- 未確定事項を確定事項として記載しない。
- 実装技術や特定ライブラリへ不必要に依存させない。
- 「適切に」「安全に」「必要に応じて」などの曖昧語を単独で使用しない。
- セキュリティ要件には具体的な検証方法を伴わせる。
- JSON例だけで仕様を定義せず、型と制約を文章または表で定義する。
- サンプル値と規範仕様を明確に区別する。
- 規範仕様、スキーマ、fixtureが一致する構造にする。
- 長文化よりも、実装判断が一意になることを優先する。
