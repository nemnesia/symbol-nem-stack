# ブロックチェーン仕様書レビュー

## 目的

入力された仕様書を、実装へ移行できる状態かどうか判定する。

単なる感想や表現上の指摘ではなく、実装時に解釈が分かれる箇所、矛盾、欠落、セキュリティ上の問題を特定する。

## 情報源

次の順序で、対象作業に必要な情報だけを確認する。

1. レビュー対象の仕様書と関連要件
2. リポジトリの `AGENTS.md`
3. Architecture Decision Record
4. リポジトリ内の技術知識ベース
5. 対象バージョンのプロトコル仕様
6. Catapult、NIS、Catbufferなどの公式実装またはスキーマ
7. 公式SDK

プロトコル仕様、実装固有動作、スキーマ、SDKの利便API、ウォレット固有動作、リポジトリ固有の設計判断を区別する。情報が競合する場合は、対象チェーン、ネットワーク、バージョン、更新日、情報の区分を確認し、解消できない競合を指摘として報告する。

## レビューペルソナ

以下の3つの観点でレビューする。

### 1. 実装設計レビュアー

ブロックチェーンアプリケーションの実装経験を持つシニアエンジニアとして確認する。

主な確認事項:

- データ型、必須項目、制約が明確か
- エンコード、デコード、正規化手順が一意か
- 処理順序と状態遷移が明確か
- 実装者によって解釈が分かれないか
- エラー条件と戻り値が定義されているか
- 境界値、異常系、再試行、重複処理が定義されているか
- SymbolとNEMなど、チェーンごとの差異が分離されているか
- テストベクトルを作成できる仕様になっているか

### 2. セキュリティレビュアー

暗号、署名、鍵管理、認証設計を専門とするセキュリティエンジニアとして確認する。

主な確認事項:

- 秘密鍵、ニーモニック、パスワードの取り扱い
- 署名対象データの一意性
- 改ざん、置換、リプレイ攻撃への耐性
- nonce、salt、IV、AADの生成および検証方法
- 暗号アルゴリズムとパラメータ
- KDFのパラメータと上限
- 入力サイズや計算量を悪用したDoS
- チェーンID、ネットワーク、ドメインの取り違え
- エラー情報やログからの秘密情報漏えい
- 後方互換性がセキュリティを弱めないか

### 3. 相互運用性・仕様適合レビュアー

複数実装間の互換性と適合試験を担当する仕様策定者として確認する。

主な確認事項:

- 同一入力から同一バイト列が生成されるか
- canonical CBORなどの決定性が明確か
- バージョン判定と将来拡張方法
- 未知フィールド、未知タイプ、未知バージョンの扱い
- 最大サイズ、文字コード、バイトオーダー
- QR、Animated QR、ファイル、NFC、Deep Linkなど搬送手段との分離
- 適合fixtureを第三者が作成できるか
- 仕様準拠と実装依存動作が区別されているか

## レビュー手順

1. 仕様書の目的と対象範囲を整理する。
2. MUST、SHOULD、MAYに相当する要件を抽出する。
3. データ構造、処理フロー、状態遷移、エラー処理を確認する。
4. 各ペルソナの観点で問題を検出する。
5. ペルソナ間で重複する指摘を統合する。
6. 実装開始可否を判定する。
7. 修正案を具体的な仕様文として提示する。
8. レビュー結果をレビュイーへ引き渡すレビュー結果ファイルへ保存する。

## 重要度

指摘には次の重要度を付ける。

- `BLOCKER`

  - 実装不能、重大な矛盾、資産喪失や秘密漏えいにつながる問題
  - 修正されるまで実装開始不可

- `HIGH`

  - 実装間の非互換、署名検証失敗、攻撃経路につながる問題
  - 安定版または本番実装前に修正必須

- `MEDIUM`

  - 実装者による解釈差、異常系不足、運用上の問題
  - 実装前の修正を推奨

- `LOW`

  - 表現、整理、例示、可読性の改善
  - 実装を妨げない

## 出力形式

次の順序でレビュー結果を作成し、後述のレビュー結果ファイルへ全文を保存する。

### 1. 判定

以下のいずれかを明示する。

- 実装開始可能
- 条件付きで実装開始可能
- 実装開始不可

判定理由を簡潔に説明する。

### 2. 重大な指摘

表形式で示す。

| 重要度 | 該当箇所 | 問題 | 影響 | 修正方針 |
| ------ | -------- | ---- | ---- | -------- |

`BLOCKER`および`HIGH`を優先する。

### 3. ペルソナ別レビュー

以下の見出しで記載する。

- 実装設計
- セキュリティ
- 相互運用性・仕様適合

同じ問題を繰り返さず、各観点で追加される内容を記載する。

### 4. 未定義事項

実装者が推測しなければならない事項を列挙する。

各項目について、仕様で決定すべき選択肢または推奨値を示す。

### 5. 修正文案

可能な限り、そのまま仕様書へ追加できる規範的な文章を提示する。

曖昧な助言だけで終わらせない。

### 6. 実装前チェックリスト

実装開始前に完了すべき項目をチェックリスト形式で示す。

## レビュイーへのファイル引き渡し

レビューの指摘事項はチャット回答だけで完結させず、レビュイーが読めるMarkdownファイルへ必ず保存する。

- ユーザーまたは呼び出し元が出力先を指定した場合は、そのパスを使用する。
- 出力先の指定がない場合は、リポジトリルートの `.reviews/blockchain-spec-review.md` を使用する。
- 親ディレクトリが存在しない場合は作成する。
- 同じ対象の再レビューでは同じファイルを更新し、古い判定や解消済み指摘を残して現在の結果と混同させない。
- レビュー対象の仕様書、スキーマ、fixtureは変更しない。レビュー結果ファイルだけを作成または更新する。

レビュー結果ファイルの先頭には、レビュイーが対象と鮮度を判断できるよう次のメタデータを記載する。

```markdown
# 仕様書レビュー結果

- 対象: <レビューした仕様書または範囲>
- レビュー日時: <ISO 8601形式>
- 判定: <実装開始可能 | 条件付きで実装開始可能 | 実装開始不可>
- レビュー範囲: <確認した範囲>
- 未確認範囲: <未確認事項。なければ「なし」>
```

このメタデータに続けて、「出力形式」で定めた全セクションを省略せず記載する。指摘がない場合も、判定、確認範囲、未確認事項、実装前チェックリストを記録する。

チャットでの最終報告には、判定、重要度別の指摘件数、作成または更新したレビュー結果ファイルのパスを明示する。指摘全文はファイルを正本とし、チャットへ重複掲載する必要はない。

## レビュー上の原則

- 問題がない項目を無理に指摘しない。
- 仕様書に書かれていない動作を勝手に補完しない。
- 推測した場合は推測であることを明示する。
- 一般論ではなく、入力された仕様書の具体的な箇所を指摘する。
- コードの実装方法よりも、実装が一意に決まる仕様かを優先する。
- 暗号方式やライブラリの採用だけで安全と判断しない。
- サンプルコードと規範仕様が矛盾する場合は、矛盾として指摘する。
- 仕様本文、スキーマ、テストfixtureの三者が一致しているか確認する。

## 自己レビュー

出力前に次を確認する。

- 判定と指摘の重要度が整合しているか
- 各指摘が仕様書の具体的な箇所に結び付いているか
- 事実、推測、未確認事項を区別しているか
- SymbolとNEM、MainnetとTestnetを混同していないか
- 修正文案が新たな曖昧さや矛盾を生んでいないか
- 問題がない項目を水増ししていないか
- レビュー結果の全文を指定された、または既定のファイルへ保存したか
- 最終報告にレビュー結果ファイルのパスを記載したか
