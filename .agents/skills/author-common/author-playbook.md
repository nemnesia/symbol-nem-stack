# Author Playbook

作成系スキルに共通する指針。各スキルは、この文書と担当する成果物の責務を合わせて適用する。

## 対象プロジェクトの前提を確認する

- 作業前に、対象リポジトリで有効な作業指示（`AGENTS.md` など）があれば読む。
- 文書、コード、テスト、fixture、生成物の正本と保存先は、リポジトリ内の案内や既存構成から確認する。特定の言語、フレームワーク、ディレクトリ構成を前提にしない。
- 作業指示は作業方法の根拠、承認済み成果物はプロジェクト判断の根拠、公式資料は外部技術の根拠として区別する。
- 任意のフェーズ Context が作業指示から登録されている場合は、探索用の補助情報としてのみ使う。登録がなければ探したり新設したりしない。

## 参照順序

1. ユーザーの依頼と明示された判断
2. 対象リポジトリの作業指示
3. 対象文書とユーザーが指定した資料
4. 対象へ直接必要な承認済み上流資料、同一フェーズの成果物
5. 必要な場合に限り、関連設計判断、公式資料、実装、テスト、既存レビュー

Context や索引を読んでも、必要な正式資料の確認を省略しない。情報源の役割や適用範囲が異なる場合は、内容を混ぜず、競合と影響を記録する。

## 成果物の境界

成果物は確認済みの事実、要求、判断を、次の作業で使える形に整理する。入力にない機能、責任、制約、数値、方式、将来構想を網羅性のために追加しない。

- コンセプトは、目的、対象、価値、扱う範囲を説明する。
- 要件は、満たす必要のある結果、制約、責任、受け入れ条件を定める。
- 設計は、責務、境界、依存、主要な構成と判断理由を定める。
- 仕様は、外部から観測できる契約、データ、検証、失敗条件を定める。
- 実装は、承認済み契約をコードや設定へ反映する。
- 利用者向け文書は、現在利用できる機能と制約を正確に説明する。

上流の不足を下流の成果物で決めたり、下流の不足を上流へ逆流させたりしない。

## 対象と変更範囲

1. ユーザーが指定した対象、出力先、更新範囲を優先する。
2. 未指定なら既存構成から候補を探す。対象が一意でない、または既存構成が判断材料にならない場合は推測しない。
3. 既存ファイルの更新は依頼の範囲内に限り、無関係な改名や再構成をしない。
4. 依頼されていない成果物の種類を増やさず、後工程を先回りして同時作成しない。
5. ユーザーの変更、既存の固定名成果物、連番成果物を移動・削除・上書きしない。

## 根拠と安全な判断

- 各記述をユーザーの依頼、承認済み資料、適用される規格・公式資料のいずれかへ追跡できるようにする。
- 実装、テスト、SDK、既存文書は現状確認や互換性確認に使えるが、それだけで上流の要求や外部規則を確定しない。
- 技術的な挙動を記憶だけで断定しない。適用される製品、版、環境、規格、実装を確認する。
- 境界をまたぐ概念や環境を、根拠なく一つにまとめない。意味の違いが成果物に関係する場合は明記する。
- 秘密情報や個人情報を例、ログ、エラー、テスト出力へ含めない。数量や日時などの値は、対象分野で適切な表現を使う。
- 解消できない競合や不足は、仮定として明記するか未決定事項へ残す。仮定を確定事実として書かない。

## 作成手順

1. 対象、保存先、変更可否、適用される作業指示を確認する。
2. 必要な上流資料と対象文書を読み、事実、要求、制約、仮定、未決定事項を分ける。
3. 担当する成果物の責務に当たる内容だけを採用する。
4. 重要な記述を出典または上流項目へ追跡可能にする。
5. 後工程で決める事項は方式を発明せず、引継ぎまたは未決定事項にする。
6. 本文、図表、例、用語、リンクの整合性を確認する。
7. 指定された成果物だけを作成または更新し、差分と必要な形式を確認する。

## 検証と完了

検証範囲は実際の変更内容とリポジトリの作業指示に合わせる。文書のみの変更にコード検証を追加するなど、対象外の検証を慣例だけで実行しない。未実行の確認を成功として報告しない。

- 成果物が担当範囲に収まり、根拠へ追跡できる。
- 対象外の機能、方式、実装、将来構想を混入させていない。
- 未決定事項と仮定を確定事項から区別している。
- 差分に無関係な変更がなく、実行した検証と未実行の検証が明確である。
- 明示的な依頼がない限り、commit、push、tag、publish、外部サービスへの書き込みを行わない。
