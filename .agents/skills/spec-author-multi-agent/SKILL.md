# Specification Author Multi-Agent

## 目的

`spec-author` を基盤に、複数の独立したエージェントから仕様候補を集め、メインエージェントが上流根拠、設計境界、決定性、実装可能性、検証可能性を統合して仕様書を作成する。

分担は漏れ、矛盾、過剰設計を抑えるために行う。複数エージェントの一致や専門知識だけを、入力にない要求、機能、制約、方式、将来拡張を追加する根拠にしてはならない。

成果物は仕様書1つだけとする。サブエージェントは出力先ファイルを直接編集せず、レビュー結果、設計書、実装コード、fixture、下書きファイルを作成しない。

## 基盤ルール

作業開始時に `.agents/skills/spec-author/SKILL.md` を完全に読み、その内容を変更せず適用する。特に次を守る。

- 承認済み要件、明示された決定事項、既存の確定仕様、確認済みプロトコル仕様を根拠として区別する。
- 仕様は実装者が推測せず実装・検証できる粒度へ具体化するが、上流にない要求や将来構想を追加しない。
- 規範仕様、未決定事項、要確認事項、仮定、例、実装者からの提案を混同しない。
- 必要なデータ構造、エンコード、処理、状態、エラー、署名、暗号化、相互運用性だけを定義する。
- 既存要件を満たすために不可欠でない再試行、互換層、監査、レート制限、運用機構、抽象化を追加しない。
- レビュー指摘は根拠を確認し、対象仕様の修正に必要なものだけを採用候補にする。
- 文字による図解は、基盤スキルの `文字による図解` に従い、仕様本文を補助するものとして扱う。図解の対象が上流根拠または確認済み仕様に追跡できない場合は採用しない。

基盤スキルを読めない場合は仕様書を作成せず、参照できないことを報告する。

## 成果物の扱い

- ユーザーが出力先を指定した場合は、そのパスを使用する。
- 出力先が指定されない場合は、対象パッケージの `docs/specifications/specification.md` を新規作成する。対象パッケージは、ユーザーが指定したパッケージ、または入力資料・既存コードが属するパッケージのルートとする。
- 対象パッケージを特定できない、または複数のパッケージにまたがる場合は、出力先を推測せず対象パッケージの指定を確認する。
- 既存仕様書は、ユーザーが明示的に更新を依頼した場合だけ変更する。
- レビュー結果や実装者フィードバックを参照しても、それらを別成果物として作成しない。
- サブエージェントの返答、実行台帳、内部スコア、討議内容、採用しなかった案を仕様書へ記載しない。

## 上流資料とレビュー結果の扱い

1. ユーザーがコンセプトシート、要件定義書、既存仕様書、レビュー結果、実装者フィードバックのパスを指定した場合は、そのパスを優先する。
2. パスが指定されない場合の候補探索は `spec-author/SKILL.md` の規則に従う。候補が複数ある場合は自動選択しない。
3. 仕様書レビュー結果は、対象パッケージの `docs/reviews/specifications/` にある対象仕様書のベース名に対応するレビュー番号最大のファイル1件だけを確認する。連番レビューがない場合に限り、旧形式の固定名 `<ベース名>-review.md` または `<ベース名>-review-findings.md` を確認する。対象パス、確認日または版、判定、未解決指摘を照合する。
4. 実装者フィードバックは、指定パスまたは基盤スキルが定める `docs/reviews/implementation/implement-spec-feedback.md` だけを確認する。推奨ライブラリ、暫定実装、内部構造は規範仕様の根拠にしない。
5. レビュー結果やフィードバックが対象不一致、古い版、未確認の場合は、その状態を明記し、推測で補完しない。
6. レビュー関連の補助ファイル、手順書、レビュアーのメモ、レビュー結果からリンクされた資料は、対応ファイルの補足目的で辿らない。

レビュー結果がある場合は、第3担当だけに渡す。上流本文、ユーザー明示資料、対象仕様書は共通資料束として全担当へ渡す。

## エージェント編成

トップレベルのメインエージェントを編集担当とし、次の3役を別々かつ並列に起動する。役割数を減らしたり、メインエージェントがサブエージェントの代替分析を行ったりしてはならない。

### 1. 根拠・スコープ追跡担当 (`evidence-scope-traceability`)

- ユーザー依頼、承認済みコンセプト、要件、既存仕様、明示された決定事項、確認済み技術資料から根拠を抽出する。
- 確定事項、未決定事項、要確認事項、仮定、例、将来構想を分離する。
- 各仕様候補へ出典、根拠の種別、対象チェーン・ネットワーク・バージョン、影響する要件または章を付ける。
- 上流にない機能、制約、数値、方式、責任、互換性要件を発明しない。

必須返却内容は、候補ごとの「内容 / 分類 / 根拠 / 対応する上流項目 / 影響 / 未確認事項」とする。

### 2. 中心仕様候補担当 (`core-specification-candidates`)

- 上流要件を、実装者が推測せず扱える用語、データモデル、エンコード、処理フロー、状態、エラー、境界条件の候補へ具体化する。
- 外部動作または相互運用性に必要な箇所だけ、順序、必須性、型、制約、失敗条件を一意にする。
- 候補ごとに、規範仕様か例か、上流根拠、実装・検証上の必要性、未決定事項を示す。
- セキュリティ方式や相互運用方式を、根拠なしに追加・選定しない。
- API、クラス、関数、ライブラリ、内部構造など、仕様の範囲を超える実装設計を決めない。

必須返却内容は、候補ごとの「仕様項目 / 規範または例 / 根拠 / 必要性 / 影響する章 / 未決定事項」とする。

### 3. セキュリティ・相互運用性・レビュー指摘修正担当 (`security-interoperability-review-fix`)

- 上流要件と対象機能に実際に関係する署名、暗号化、認証、秘密情報、改ざん、リプレイ、相互運用性、互換性、適合試験だけを整理する。
- 仕様を一意に実装・検証するために必要な署名対象、暗号パラメータ、バイト列、識別子、fixture、失敗条件を候補として示す。ただし根拠のない方式やパラメータは決めない。
- 対応する仕様レビュー結果または実装者フィードバックがある場合、対象一致、鮮度、根拠、影響、修正候補、未解決理由を指摘ごとに整理する。
- 指摘の一部が過剰設計の場合は、既存要件を満たすための必要条件だけへ縮小する。
- 同じ規範内容が複数章に現れる場合の主定義箇所、参照化、矛盾、冗長性を確認する。
- レビュー指摘やフィードバックを無条件に仕様書へ反映せず、最終ファイルを直接編集しない。

必須返却内容は、候補または指摘ごとの「内容 / 対象箇所 / 根拠 / 既存要件との関係 / 影響 / 修正候補 / 未解決理由」とする。

### 起動時の共通要件

各起動プロンプトには、少なくとも次を明示する。

```text
あなたの割当て: <上表の割当て名>
目的: <その割当ての主目的>
入力: <他担当の結論を含まない共通資料束。第3役だけは対応するレビュー結果・実装者フィードバックを含む>
担当範囲: <必須の返却内容>
禁止事項: 入力にない要求・機能・制約・方式・将来拡張を追加しない。成果物を直接編集しない。
返却形式: 候補ごとに「内容 / 分類または対象箇所 / 根拠 / 必要性または影響 / 未確認事項」を記載する。
独立性: 他のサブエージェントの出力を参照せず、入力資料だけから判断する。
```

## 監査可能な起動

- 3役を3回の別々の `multi_agent_v1__spawn_agent` 呼び出しで起動し、各呼び出しに `fork_context: false` を指定する。
- 返却された3つの `agent_id` と割当て名を内部の実行台帳へ記録し、すべて存在し相互に異なることを確認する。
- 3つの起動が完了してから、各 `agent_id` を個別に `multi_agent_v1__wait_agent` で待機する。
- 1件でも起動失敗、重複、タイムアウト、未完了、返答不足があれば仕様書を生成しない。メインエージェントの代替分析をマルチエージェント成果物として扱わない。
- `multi_agent_v1__spawn_agent` または `multi_agent_v1__wait_agent` が利用できない場合は作成を中止し、実行できない理由だけを報告する。
- `agent_id` と実行台帳は仕様書へ記載しない。監査情報が必要な場合は、ユーザー指定の形式で別途提示する。

## 作成手順

1. 出力先、作成か更新か、対象チェーン・ネットワーク・バージョン、参照してよい資料を確定する。
2. `spec-author/SKILL.md` を読み、上流成果物、レビュー結果、実装者フィードバックを基盤スキルの規則で特定する。
3. ユーザー依頼、対象仕様書、上流資料、明示資料、必要な技術資料から共通資料束を作る。推測や編集方針は資料束へ含めない。
4. 対応するレビュー結果と実装者フィードバックの対象一致・鮮度を確認し、第3担当だけへ渡す。
5. 3役の割当てを実行台帳へ登録し、別々かつ並列に起動する。3つの `agent_id` の一意性を検証する。
6. 3役の返答を個別に待機する。返答が不足する場合は該当担当へ範囲内の補足だけを求め、メインエージェントが内容を推測して埋めない。
7. 返答を次の候補台帳へ正規化する。

   | ID | 内容 | 分類 | 根拠 | 必要性または影響 | 採用先または扱い |
   | --- | --- | --- | --- | --- | --- |
   | C-001 | <候補> | 規範/例/未決定/要確認/指摘修正 | <出典> | <実装・検証への影響> | <章または除外理由> |

8. 各候補へ、上流根拠、仕様としての必要性、実装・検証への影響、基盤スキルの責務境界を適用する。根拠がない候補、後工程で決められる候補、設計方式を過度に固定する候補は除外または未決定・要確認へ送る。
9. 担当間の矛盾を元資料へ戻って確認する。解消できない場合は一方を事実として選ばず、未決定事項または要確認事項として分離する。
10. 仕様レビュー結果または実装者フィードバックの各指摘を `対応済み`、`未対応`、`対象外`、`要確認` に分類し、根拠と理由を記録する。指摘を根拠に新しい要求を作らない。
11. 仕様書の各章を、基盤スキルの出力形式、既存の用語、規範語、対象範囲に合わせてメインエージェントだけが作成または更新する。
12. 仕様項目、データ表現、処理、エラー、署名、暗号化、fixture、適合試験の間で、実装・検証に必要な一意性と対称性を確認する。
13. 基盤スキルの自己レビューを実行し、重複・冗長性、上流根拠、過剰設計、未決定事項、対象チェーン差異を確認する。

## 統合ルール

- ユーザーの明示指示、承認済み要件、既存の確定仕様、確認済みプロトコル仕様を、エージェントの提案より優先する。
- 複数担当が一致しても、根拠がなければ採用しない。
- 仕様項目は実装・検証に必要な最小十分な内容にし、章を埋めるための記述を作らない。
- レビュー指摘や実装者フィードバックは、既存要件・仕様の欠陥を解消する場合だけ採用候補にする。新しい機能、制約、方式、将来拡張は追加しない。
- 規範要件、制約、検証規則が複数候補に重複する場合は、根拠、条件、パラメータ、例外、失敗条件を保ったまま統合または除外する。
- 同じ規範内容を複数章で説明する必要がある場合は、主となる定義箇所を一つに定め、他の章は参照または要約にする。
- 重複除去や短文化により、実装・検証に必要な規範情報、根拠、追跡可能性を削除しない。
- 文字による図解を採用する場合は、図の目的（規範図または説明図）、各要素・関係の根拠、主定義となる仕様章を候補台帳に記録する。図解は本文、表、エラー条件、署名・暗号化・適合試験の規範定義を代替しない。
- 用語、識別子、型、必須性、制約、規範語、例、fixture、エラー条件を章間で整合させる。
- データモデルとエンコード・デコード、署名・検証、暗号化・復号、正常系・異常系、仕様・適合試験の対応を確認する。
- 根拠が競合する場合は、チェーン、ネットワーク、バージョン、情報区分、更新日を確認し、解消できなければ未確認として残す。
- 未決定事項を仕様本文へ混在させず、実装者の提案を規範仕様として採用しない。
- サブエージェントの文章をそのまま貼り付けず、重複、粒度、用語、根拠、境界をメインエージェントが整える。

## 自己レビューと完了条件

`spec-author/SKILL.md` の自己レビュー項目をすべて実行し、さらに次を確認する。

- 3つの異なる `agent_id` を取得し、3役すべての返答を個別に確認している。
- 上流根拠、仕様項目、レビュー指摘対応、未決定事項、要確認事項の対応関係が追跡できる。
- 同じ規範要件、制約、検証規則を複数箇所で重複して定義していない。
- 意図的な反復は主定義箇所を参照または要約しており、規範語、条件、パラメータ、例外、失敗条件に矛盾がない。
- データモデル、エンコード、処理フロー、エラー、署名、暗号化、適合試験の間に不要な反復や意味の重複がない。
- 冗長性を削減しても、実装・検証に必要な規範情報、根拠、追跡可能性を失っていない。
- 各規範仕様が承認済み要件、明示された決定事項、既存の確定仕様、または確認済み技術資料へ追跡できる。
- 上流にない要求、機能、制約、責任、方式、将来拡張、運用機構を追加していない。
- 仕様書が対象チェーン、ネットワーク、プロトコル、バージョンを混在させていない。
- 未決定事項、要確認事項、仮定、例が規範仕様として誤読されない。
- 対応するレビュー結果または実装者フィードバックがある場合、各指摘の対応区分と理由を確認している。
- 仕様書以外の下書き、レビュー結果、設計書、実装コードを依頼なしに作成していない。
- 文字による図解を含めた場合、図解の目的と規範性が明示され、図の全要素・関係・順序・条件が仕様本文または参照資料へ追跡できる。図解から入力にない機能、方式、制約、アーキテクチャ、将来拡張を追加していない。

## 出力

ユーザーが別形式を指定しない場合は、`spec-author` の基本構成を使用する。不要な章は省略し、情報が不足する場合は「未決定」「要確認」「該当なし」と記載する。

サブエージェント機能の起動・完了を監査できない場合、マルチエージェント成果物として仕様書を生成せず、その理由を報告する。
