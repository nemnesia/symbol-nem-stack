# Review Process

必ず Phase 1、Phase 2、Phase 3 の順に実施する。内部討議は成果物へ出力しない。

## Phase 1: Individual Review

Reviewer A、B、C は互いの意見を参照せず、担当観点とコンセプトシートを独立してレビューする。Reviewer C は技術的または安全性上の前提を評価する必要がある場合に限り、`docs/knowledge` の関連資料を選んで参照してよい。

各指摘は仮 ID（`A-001`、`B-001`、`C-001`）を付け、次をすべて含める。

- 重大度（Critical、Major、Minor）
- 問題と対象箇所
- 根拠の種別と参照箇所
- 放置した場合の影響
- 必要な修正または確認

根拠の種別は「コンセプト本文」「ユーザー提供資料」「`docs/knowledge` の確認済み資料」のいずれかとする。未確認事項は未確認と明記し、外部事実を断定しない。

## Phase 2: Review Board Discussion

Phase 1 の終了後に限り、各 Reviewer は他の指摘を評価できる。評価は賛成、条件付き賛成、反対のいずれかとし、反対または条件付き賛成には根拠不足、範囲外、後工程で決める事項、重大度不適切などの理由を添える。

討議の目的は指摘を増やすことではなく、根拠と影響が十分な指摘へ絞り込むことである。各指摘を採用、却下、または重大度変更として確定する。次の場合は却下する。

- 問題、根拠、影響、必要な修正または確認を説明できない。
- 個人的好み、推測、設計・実装詳細、または後工程だけで決められる事項である。
- 確認済みの根拠と矛盾する。

## Phase 3: Chair Decision

Review Board Chair はコンセプト本文、明示された根拠、討議で採用された指摘を用いて品質ゲートを適用する。新しい指摘は追加せず、根拠不足の指摘は採用しない。

採用指摘を統合し、正式 ID（`CR-001` から連番）を付与する。重大度は次のとおりとする。

- Critical: 品質ゲートを不合格にし、要件定義の開始を妨げる問題。
- Major: 開始は妨げないが、後工程で問題になりやすく修正を推奨する問題。
- Minor: 開始を妨げない改善提案。

すべての品質ゲートが合格なら「要件定義へ進める」、1つでも不合格なら「コンセプト整理を優先する」と判定し、`.reviews/concept-review-findings.md` を生成する。
