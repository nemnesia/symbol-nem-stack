# 設計レビュー用セキュリティチェックリスト

対象の承認済み要求と設計判断に基づき、セキュリティ責任をシステム構造として成立させるための確認観点を示す。チェック項目だけを根拠に新しい脅威、要求、設計判断を作らない。対象外の攻撃者や環境へ scope を広げない。

## 1. 保護対象と信頼境界

- 対象の保護資産、重要な操作、信頼する主体と信頼しない主体が整理されているか。
- 入力、出力、保存、通信、管理経路を含む trust boundary が識別されているか。
- どのコンポーネントが検証、認証、認可、保護を担当するかが明確か。
- 境界をまたいで権限や秘密情報の責任が曖昧になったり逆流したりしていないか。

## 2. 所有とライフサイクル

- 保護資産の生成・取得、保持、利用、共有、更新、破棄の責任者が明確か。
- 保護対象データが不要な主体、ログ、例外、診断情報、永続領域へ流れない設計か。
- 交換、復旧、再起動、失敗、取消しなどの状態変化で保護責任が保たれるか。
- 保存・転送・削除の責任を外部へ委ねる場合、その境界と前提が明記されているか。

## 3. 認証、認可、重要操作

- 誰が主体を確認し、誰が操作を許可し、誰が実行するか分かるか。
- 権限の付与、縮小、失効と特権操作の責任が定義されているか。
- 操作主体や対象の取り違えが起きない責任・データフローになっているか。

## 4. 入力、状態、失敗

- 信頼されていないデータを検証する境界と担当が明確か。
- 失敗、部分処理、再試行、重複、競合、復旧時に安全性と状態整合性を保てるか。
- 失敗時に責任が不明なままデータや権限を引き継がないか。
- 必要なセキュリティ不変条件を、後続の仕様や運用へ伝えられるか。

## 5. 設計レビューの境界

ここでは責務、依存方向、trust boundary、所有、ライフサイクル、認可、失敗時の責任を確認する。暗号プリミティブ、鍵長、wire format、API field、特定言語のメモリ管理、具体的なテストフレームワークなどは、承認済み上流判断で設計が決める必要がある場合を除き、仕様や実装へ委ねる。

各 finding は既存要求、設計文書、明示された保護対象またはユーザー判断へ追跡し、影響、下流で安全に解消できない理由、必要な完了条件を示す。
