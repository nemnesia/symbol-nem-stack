# Requirements Author

要件定義書を作成または更新し、承認済みの上流判断を検証可能な要求へ整理する。このスキルは「何を満たす必要があるか」を明らかにし、「どう実現するか」は仕様・設計へ委ねる。

## 作業前の確認

1. 対象リポジトリの作業指示（`AGENTS.md` など）があれば読む。
2. `../author-common/author-playbook.md` と `scope-boundary.md` を読む。
3. ユーザーの依頼、対象の要件書、直接関係する承認済みコンセプト、関連要件を確認する。
4. 要件作成では、設計や仕様を通常の必須参照にしない。既存判断との衝突や互換性確認に必要な場合だけ補助的に参照する。

## 対象と出力

- ユーザーが指定した対象と出力先を優先する。
- 未指定なら、リポジトリの文書構成から候補と保存先を確認する。候補が複数ある場合は推測しない。
- 既存文書の変更は依頼範囲内に限る。既存の正本を複製・改名・上書きしない。
- 成果物は要件定義書に限る。仕様、設計、実装、レビューを同時に作成しない。

## 要件として整理する内容

入力と上流判断から、必要な範囲で次を整理する。

- 背景、課題、目的、利用者、関係者、主要な利用場面
- 対象範囲、対象外、責任境界、前提、制約
- 外部から観測できる機能要件
- 必要な品質、セキュリティ、プライバシー、相互運用性、データ保持の要求
- 第三者が合否を判定できる受け入れ条件
- 判断が必要な未決定事項、上流根拠、下流への引継ぎ

ID、優先度、MUST / SHOULD / MAY の規則が既存文書にあれば維持する。新たに導入する場合は意味を一貫して定義し、根拠のない優先度を付けない。

## 要件にしない内容

上流の承認や適用規格で定められていない限り、APIの詳細、field名、型、識別子、データ配置、具体的な直列化形式、アルゴリズム、状態遷移、暗号パラメータ、ライブラリ、データベース、インフラ、UI配置、内部テスト手順を新たに固定しない。達成に不可欠な性質や制約だけを要件化し、具体方式を適切な後工程へ渡す。

## 根拠の扱い

- ユーザーの依頼、承認済みコンセプト、適用される法令・標準・外部契約を確認する。
- 実装、テスト、SDK、既存の下流文書は現状や互換性の確認に使えるが、新しい要件の根拠にはしない。
- セキュリティ要求は既存の保護対象や責任へ結び付ける。一般的なベストプラクティスだけから新しい要求を作らない。
- 複数の製品、テナント、環境、バージョン、外部サービスが関係する場合、適用範囲と差異を明確にする。
- 資料間の競合は、資料の役割、版、適用範囲、影響を分けて記録する。解消できない場合は仮定や未決定事項として残す。

## 作成手順

1. 対象、出力先、上流資料、変更可否を確認する。
2. 入力を事実、要求候補、制約、仮定、未決定事項、将来構想に分類する。
3. 要求候補を上流根拠、対象主体、責任、外部可視性、境界へ対応付ける。
4. 要求を機能、品質、セキュリティ、相互運用性、データ、制約、受け入れ条件に整理する。
5. 各要求に対象、条件、期待結果、必要な場合は失敗時の結果を記す。
6. 未決定事項に、判断理由、時期、影響、必要な制約を記す。
7. トレーサビリティと文書内の一貫性を確認し、要件定義書だけを作成または更新する。

## 受け入れ条件

利用者または外部観測者が合否を判定できる形にする。対象、前提、観測可能な結果を示し、拒否・失敗・境界条件が要件に関係する場合はその結果も記す。内部ログや特定のテストランナーだけを受け入れ条件にしない。

## 自己確認

- 各要件が上流の目的や判断へ追跡できる。
- 対象、対象外、責任、前提、制約を区別している。
- 受け入れ条件が判定可能で、内部実装を指示していない。
- 必要なセキュリティ、プライバシー、相互運用性、失敗時の安全性を扱っている。
- API、schema、暗号、ライブラリ、アーキテクチャを根拠なく決めていない。
- 将来構想や一般的なベストプラクティスを確定要件にしていない。
- 競合、仮定、未確認事項を明示している。

独立した品質判定が必要な場合は `requirements-review` を使用する。このスキル自身はレビュー成果物を作成しない。
