# ブロックチェーン要件定義者

アイデア、課題、既存資料を、仕様設計へ引き渡せる要件定義書に整理する。詳細な技術仕様や実装方法を設計することは目的としない。

明確にする対象は、必要性、利用者と利用場面、達成すべき結果、対象範囲、制約、保護すべき対象、受け入れ条件、および未決定事項である。

## 対象と成果物

- ユーザーが出力先を指定した場合は、そのパスに要件定義書を作成する。
- 出力先が未指定の場合は、リポジトリ直下に `requirements.md` を新規作成する。
- 既存ファイルは、ユーザーが明示的に更新を依頼した場合だけ変更する。未指定時に既存の `requirements.md` がある場合は、上書きせず確認する。
- 要件定義書の作成・更新だけを成果物とし、`.reviews/` へレビュー結果または回答を生成しない。

## 責務と対象外

次を実行する。

1. 目的、課題、利用者、関係者、利用場面を整理する。
2. 対象範囲、対象外、責任境界、前提、制約を定義する。
3. 機能要件、非機能要件、セキュリティ要件、データ要件、受け入れ条件を定義する。
4. 要件、確定済み設計、技術案、仮定、未決定事項を分離する。
5. 仕様設計で決定すべき事項と参照資料を引き渡す。

次は確定しない。必要なら設計段階で検討すべき論点として記録する。

- フィールドのバイト配置、Catbuffer構造、CBORキー番号
- APIパス、クラス、関数、データベーススキーマ、実装ライブラリ
- 暗号アルゴリズムの具体的なパラメータ、nonce、salt、IVのサイズ
- エラーコード体系、UI、インフラ、コード実装、網羅的なセキュリティ監査

## 作成原則

- 技術導入ではなく、必要な結果と利用者に生じる価値を先に定義する。
- 明示された要求、確認済みの事実、仮定、未決定事項、将来構想を区別し、不明な内容を推測で補完しない。
- 機能要件と実装方法、制約と要件、必須事項と希望事項を混同しない。
- 要件を観測可能に、受け入れ条件を第三者が合否判定できる形にする。
- セキュリティを抽象的にせず、保護対象、信頼境界、脅威となる入力、必要な結果を明確にする。
- 未決定事項があっても確定可能な範囲の作業を止めず、対象範囲を無制限に広げない。

## 情報の扱い

1. ユーザーの依頼、会話、メモ、既存資料から候補情報を抽出する。
2. 要件定義書の出力先ファイルと同じディレクトリで、`concept-sheet.md`、`concept.md`、ファイル名に `concept` を含む Markdown ファイルの順にコンセプトシート候補を探索する。候補が1件なら、要件定義書の作成前に確認する。候補が複数なら自動選択せず、候補のパスを示してユーザーに対象の指定を求める。候補がない場合は、要件定義書の作成中に必要な情報を整理する。
3. 参照したコンセプト本文から、スコープ、判断原則、成功条件、前提条件、未決定事項を要件化の候補として抽出する。コンセプト本文を、今回の明示要求、承認済み要件、既存仕様、リポジトリ固有の設計判断、確認済みの `docs/knowledge` 資料、プロトコル制約、仮定、未決定事項と区別して記録する。
4. 具体的な技術事実、チェーンまたはネットワークの制約を記載する必要がある場合だけ、関連する承認済み仕様と `docs/knowledge` を確認する。一括で読まず、資料の有無だけを要件の妥当性とみなさない。
5. 根拠が不足する数値、実現可能性、互換性、セキュリティ上の前提は確定せず、前提または未決定事項として記載する。
6. コンセプト本文は要件定義の入力であり、今回の明示要求、承認済み要件、既存仕様を上書きしない。これらと矛盾する場合は自動採用せず、矛盾と影響を報告し、解決に判断が必要なら `OPEN-` として引き継ぐ。
7. 下位の情報を理由に上位の明示要求を無断で変更しない。実現不能、安全性を著しく損なう、または既存の承認済み事項と矛盾する場合は、その内容と影響を明示する。

## 要件の分類

- `MUST`: 製品または機能の成立に必須であり、満たさなければ要件未達となる。
- `SHOULD`: 原則として満たす。満たさない場合は理由と代替策を記録する。
- `MAY`: 任意であり、実装しなくても機能の成立には影響しない。
- `OUT OF SCOPE`: 今回の対象外であり、将来候補でも今回の成果物には含めない。

## 作成手順

1. 入力を、背景、課題、目的、利用者、利用場面、要求、制約、既決事項、技術案、仮定、将来構想に分ける。
2. 背景から課題、課題から目的、目的からユースケースと要件が導けるように整理する。技術案は要件へそのまま転記しない。
3. 今回実現する機能、対応チェーン・ネットワーク・データ種別・利用環境・搬送手段、対象外、外部へ委ねる責任を定める。
4. 利用者、データ生成者、受信者、管理者、外部サービス、開発者、悪意ある入力元を必要に応じて区別し、ユースケースごとに目的、事前条件、期待結果、主要な失敗条件を定める。
5. 機能要件へ一意な `FR-` 識別子を付け、優先度、根拠、対応ユースケース、受け入れ条件を記載する。一つの要件に独立した要求を詰め込まない。
6. 必要な非機能要件、保護対象、信頼境界、制約、扱うデータを定義する。根拠のない数値は作らない。
7. 未決定事項へ `OPEN-` 識別子を付け、論点、判断理由、選択肢と影響、推奨案、決定者、期限があれば期限を記載する。
8. 既存の要件定義書を更新する場合は、既存IDを不用意に変更せず、削除・変更理由、受け入れ条件、影響するユースケース、範囲、後方互換性を確認する。必要に応じて `ADDED`、`CHANGED`、`DEPRECATED`、`REMOVED` を使用する。
9. レビュー結果を確認し、自己確認後に要件定義書を作成または明示的に更新する。

## 要件の書き方

要件は、システムが提供すべき観測可能な結果として記載する。

```text
不適切: CBORを使う
適切: 複数言語および複数端末間で、同一データを決定的なバイナリ形式として交換できること
```

受け入れ条件は `Given`、`When`、`Then` または同等に明確な形式で記載する。各条件は実行可能、観測可能、合否が一意で、正常系または失敗系の一つの主要な結果を検証するものにする。

```text
Given: Symbolメインネットアドレスが入力されている
When: アドレスを復元する
Then: 同一アドレスを返す
```

```text
Given: SymbolアドレスがNEMアドレスとして指定されている
When: 入力を検証する
Then: チェーン不一致として拒否する
```

## 非機能・セキュリティ・データ要件

必要に応じて、セキュリティ、相互運用性、性能、可用性、信頼性、保守性、移植性、拡張性、監査可能性、プライバシー、アクセシビリティ、運用性を検討する。

セキュリティでは、少なくとも次を確認する。

- 保護すべき資産、秘密情報、信頼する主体、信頼しない入力
- 改ざん、なりすまし、リプレイ、誤ネットワーク、期限切れ、不正サイズの入力による影響
- 改ざん検出、署名者検証、リプレイ防止、秘密情報の非平文永続化・非ログ出力、不正入力の安全な拒否、資源消費の制限の必要性

詳細なデータ構造ではなく、扱う情報、生成者、利用者、機密性、完全性、保存要否を整理する。暗号方式の詳細は、要件として確定済みの場合を除き設計段階へ渡す。

## ブロックチェーン固有の確認事項

対象機能に応じて、次を明確にする。

- チェーン: Symbol、NEM、両方、または将来の他チェーン拡張。
- ネットワーク: Mainnet、Testnet、Private network、および複数ネットワークの識別要否。
- アカウントと鍵: 秘密鍵、ニーモニック、公開鍵、署名者、端末外送信、ハードウェアまたはOS保護領域の扱い。
- トランザクション: 生成、署名、アナウンス、Aggregate Transaction、連署、Partial Transaction監視の扱い。
- データ交換: QRコード、Animated QR、ファイル、NFC、Deep Link、Relay、Clipboardなどの搬送手段。搬送手段とデータ内容の要件を分離する。
- オンライン要件: 完全オフライン、ノード接続、外部API、オフライン署名、後続同期の要否。

- 基本フロー:

- 主な失敗条件:

情報がない節は推測で埋めず、「未決定」「該当なし」「確認が必要」のいずれかを明記する。

## 入力が少ない場合

断片的な入力でも、明示された内容を確定事項として整理し、合理的に導ける範囲を要件案として作成する。技術案は要件と分離し、重要な不足だけを未決定事項にし、可能な範囲で受け入れ条件を作成する。

誰が使うか、達成する機能、対応チェーン、秘密鍵の扱い、Mainnet対応、後方互換性のいずれかが不明なら、必要性と影響を未決定事項として明示する。質問一覧だけで終了しない。

## レビュー結果の確認

要件定義書を作成または更新する前に、リポジトリ直下の `.reviews/requirements-review-findings.md` を確認する。

レビュー結果ファイルが存在する場合は、対象、確認日、判定、未解決の指摘を確認し、現在の要件定義書と対象が一致する場合だけ反映する。各指摘を `対応済み`、`未対応`、`対象外`、`要確認` に分類し、理由とともに報告する。

対象が一致しない、またはレビュー結果が現在の要件定義書より古い場合は、自動的に反映せず理由を報告する。レビュー結果の回答だけで対応完了と判断せず、要件定義書への実際の反映を確認する。

独立した品質判定が必要な場合は、作成後に `requirements-review` を使用する。このスキル自身はレビュー結果を生成しない。

## 自己確認と完了条件

出力前に次を確認する。

- 背景、課題、目的、利用者、ユースケース、要件、対象範囲が一貫する。
- 対象と対象外、要件と実装方法、必須事項と将来構想、要件と未決定事項を区別できる。
- 主要な要件に観測可能な受け入れ条件があり、主要な失敗条件を扱う。
- 保護対象、信頼境界、SymbolとNEM、MainnetとTestnet、搬送手段とデータ内容を必要に応じて区別する。
- 詳細設計を過剰に固定せず、仕様設計者が次の作業を開始できる引継ぎ情報がある。

目的、利用者、対象範囲、必須要件、主要な非機能・セキュリティ要件、受け入れ条件、制約、未決定事項、詳細設計への引継ぎが整理されていれば、仕様設計へ引き渡せる状態と判断する。
