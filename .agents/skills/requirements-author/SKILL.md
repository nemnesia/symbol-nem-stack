# ブロックチェーン要件定義者

アイデア、課題、コンセプト、既存資料を、仕様設計へ引き渡せる要件定義書に整理する。

このスキルの責務は「何を満たす必要があるか」を定義することであり、「どう実現するか」を設計することではない。

要件候補を作成する前と成果物へ採用する前に、必ず `scope-boundary.md` を読む。

## 対象と成果物

- ユーザーが出力先を指定した場合は、そのパスに要件定義書を作成する。
- 出力先が未指定の場合は、対象パッケージの `docs/requirements/requirements.md` を新規作成する。対象パッケージは、ユーザーが指定したパッケージ、または入力資料・既存コードが属するパッケージのルートとする。
- 対象パッケージを特定できない、または複数のパッケージにまたがる場合は、出力先を推測せず対象パッケージの指定を確認する。
- 作成先が既に存在する場合は、更新依頼が明示されていない限り上書きせず、対象パスの指定または更新可否を確認して終了する。
- 既存ファイルは、ユーザーが明示的に更新を依頼した場合だけ変更する。未指定時に対象パッケージの `docs/requirements/requirements.md` がある場合は、上書きせず確認する。
- 成果物は要件定義書だけとし、レビュー結果、仕様書、設計書、実装コードを生成しない。

## 責務

次を整理する。

1. 背景、課題、目的、利用者、関係者、利用場面。
2. 対象範囲、対象外、責任境界、前提、制約。
3. システムが外部から観測可能な形で満たすべき機能要件。
4. 必要な非機能要件、セキュリティ要件、相互運用性、データ上の要求。
5. 主要要件の合否を判断できる受け入れ条件。
6. 仕様設計を始める前に決定が必要な要件レベルの未決定事項。
7. 上位要求、要件、既決事項、仮定、未決定事項、設計へ引き渡す事項の分離。

## 範囲外

次は、ユーザー要求、承認済み上位資料、外部規格等によって既に必須と確定している場合を除き、このスキルが新たに決定しない。

- API パス、HTTP メソッド、パラメータ、レスポンス構造、具体的なエラーコード
- フィールド名、型、キー番号、識別子の数値割当、バイト配置、スキーマ
- Catbuffer、CBOR 等の具体的プロファイルやシリアライズ詳細
- アルゴリズム、処理順序、状態遷移、クラス、関数、モジュール分割
- 暗号方式、KDF、nonce、salt、IV、tag、鍵長等の具体的構成
- ライブラリ、フレームワーク、データベース、インフラ、デプロイ構成
- UI レイアウト、画面遷移、具体的な操作手順
- 単体テスト、fixture、テストデータ、実装レベルの検証手順

範囲外事項について、要件定義書内で比較案、推奨案、候補一覧を新たに作成しない。必要なら「仕様設計で決定する」とだけ引き渡す。

## 作成原則

- 技術導入ではなく、必要な結果と利用価値を定義する。
- 要件定義書は、技術者が要件を正確に解釈し、仕様設計へ引き渡せる文章を基本とする。概要、目的、対象範囲などは、非技術者も過度な前提知識なしに概要を把握できるよう配慮する。専門用語、略語、英語・カタカナ表記を使う場合は、要件の理解に必要な範囲で意味を説明する。
- コンセプトまたはユーザー要求を具体化するが、無断で拡張しない。
- 「一般に必要」「安全のため」「将来便利」という理由だけで新機能を追加しない。
- 上位要求から論理的に不可欠な派生要件だけを追加し、根拠を追跡可能にする。
- 明示要求、確認済み事実、承認済み制約、仮定、未決定事項、将来構想を区別する。
- 不明な数値、方式、制約を推測で補完しない。
- 仕様設計で安全に決定できる余地が残っていること自体を不備とみなさない。
- 要件を観測可能にし、受け入れ条件を第三者が合否判定できる粒度にする。
- 受け入れ条件を単体テストや実装手順まで具体化しない。

## 情報の扱い

1. ユーザー依頼、会話、メモ、既存資料から候補情報を抽出する。
2. 対象パッケージの `docs/consept/` で `concept-sheet.md`、`concept.md`、ファイル名に `concept` を含む Markdown の順にコンセプト候補を探索する。`reviews/` と `*-review-findings.md` は除外する。対象パッケージが特定できない場合は、出力先とコンセプト候補を推測しない。
3. コンセプトが1件なら確認する。複数なら自動選択しない。存在しない場合は、明示された情報だけで整理する。
4. コンセプトから目的、対象利用者、提供価値、スコープ、判断原則、成功条件、前提、未決定事項を引き継ぐ。
5. コンセプト本文は入力であり、今回のユーザー要求や承認済み事項を上書きしない。
6. 技術的事実やプロトコル制約の確認が必要な場合だけ、関連する承認済み仕様や `docs/knowledge` の該当箇所を参照する。一括参照はしない。
7. `docs/knowledge` は技術的制約の確認に使い、新しい製品要件や機能を追加する根拠にはしない。
8. 対象チェーン、ネットワーク、プロトコルまたは実装のバージョンを、入力と参照資料から確認できる範囲で明示する。資料間でこれらが競合する場合は勝手に統合せず、競合と影響を未確認事項として扱う。
9. 根拠不足の数値、互換性、性能、安全性上の前提を確定しない。

### レビュー結果の探索

選択した要件定義書を対象パッケージの `docs/requirements/<base>.<ext>` とすると、対応する要件レビュー結果は
対象パッケージの `docs/reviews/requirements/` にある、対象要件定義書のベース名に対応するレビュー番号最大のファイル1件だけを確認する。連番レビューがない場合に限り、旧形式の固定名 `<base>-review.md` または `<base>-review-findings.md` を確認する。対応するコンセプトシートを選択した場合は、対象パッケージの `docs/reviews/concept/` にある、そのコンセプトのレビュー番号最大のファイル1件だけを確認する。

- ディレクトリ内を検索して別名のレビュー結果を自動選択しない。
- レビュー結果の対象パス、確認日または版が対象本文と一致するかを確認し、不一致または鮮度を確認できない場合は未確認として扱う。
- レビュー手順書、レビュアーのメモ、レビュー結果からリンクされた資料は、レビュー結果の補足目的では参照しない。
- レビュー結果は修正候補であり、ユーザー要求、承認済み資料、確認済み事実より弱い根拠として扱う。

## 要件候補の採用判定

各候補へ `scope-boundary.md` の境界テストを適用する。

特に次を確認する。

1. これは「何を満たす必要があるか」か、「どう実現するか」か。
2. 別の実装方法でも同じ結果を満たせるなら、具体方式を要件として固定する根拠があるか。
3. 根拠がなければ具体方式を削除し、観測可能な結果または制約へ書き換える。
4. 要件レベルへ書き換えられなければ成果物へ含めない。

## 要件の分類

- `MUST`: 成立に必須。満たさなければ要件未達。
- `SHOULD`: 原則として満たす。満たさない場合は理由が必要。
- `MAY`: 任意。実装しなくても成立に影響しない。
- `OUT OF SCOPE`: 今回の対象外。将来候補を今回の要件へ混入させない。

機能要件には `FR-` を付ける。非機能、セキュリティ、データ要件にも追跡が必要な場合は、それぞれ `NFR-`、`SEC-`、`DR-` を付け、要件IDは文書内で一意にする。目的、事実、仮定、将来構想などの非要件項目へ、要件用の優先度やIDを無理に付けない。

## 作成手順

1. 入力を、背景、課題、目的、利用者、利用場面、要求、制約、既決事項、仮定、将来構想へ分類する。
2. コンセプトの目的・スコープと整合させる。
3. 各候補へ `scope-boundary.md` を適用し、設計事項を除外する。
4. 今回実現する機能、対象チェーン・ネットワーク・データ種別・利用環境・搬送手段を、上位要求に存在する範囲で定める。
5. ユースケースは、利用者、目的、事前条件、期待結果、主要な失敗条件まで記載する。内部処理フローは設計しない。
6. 要件へ一意な識別子を付け、優先度、根拠、対応ユースケースまたは影響を記録する。機能要件は `FR-`、非機能・セキュリティ・データ要件は必要に応じて `NFR-`、`SEC-`、`DR-` を使う。
7. 必要な非機能・セキュリティ・データ要件を定義する。ただし一般的なチェック項目を理由に不要な要件を追加しない。
8. すべての `MUST` 要件と、外部契約または利用者価値に直接関係する `SHOULD` 要件へ、外部から合否を判断できる受け入れ条件を付ける。`MAY` や対象外には原則として付けない。
9. 要件レベルで未決定の事項だけを `OPEN-` として記録する。
10. 自己確認を行い、仕様設計へ引き渡す。

## 要件の書き方

要件は外部から観測可能な結果として記載する。

```text
不適切: CBORを使う
適切: 複数実装間で同一データを相互運用可能な形で交換できること
```

具体方式がユーザーまたは上位資料で既に確定している場合は、制約として保持できる。

```text
確定済み制約: 搬送形式は CBOR とする
```

この場合でも、キー番号、バイト配置、プロファイル等を要件作成者が追加決定してはならない。

## 受け入れ条件

受け入れ条件は、すべての `MUST` 要件と、外部契約または利用者価値に直接関係する `SHOULD` 要件の合否を、外部から判断できる粒度にする。`MAY` や対象外へは原則として付けない。

`Given / When / Then` または同等の形式を利用してよいが、必須ではない。

適切:

```text
Given: 対応対象のアドレスデータが入力される
When: データを交換し再取得する
Then: 元の意味を保持した同一データとして利用できる
```

不適切:

```text
Given: fixture 001 を読み込む
When: decoder.ts の decode() を呼ぶ
Then: 特定の内部オブジェクトになる
```

後者はテスト仕様・実装仕様である。

## 非機能・セキュリティ・データ要件

必要なカテゴリだけを記載する。カテゴリ一覧を埋めることを目的に要件を追加しない。

セキュリティでは、対象機能に必要な場合だけ、次のような要件レベルの事項を整理する。

- 保護対象と機密性
- 信頼境界
- 不正入力に対する必要な結果
- 改ざん、なりすまし、リプレイ等に対して必要な安全性特性
- 秘密情報の保存・ログ出力等に関する制約

暗号方式や内部検証手順は設計しない。

データ要件では、原則として次を扱う。

- データの種類
- 生成者
- 利用者
- 機密性
- 完全性
- 保存要否

フィールド構成や型は設計しない。

## ブロックチェーン固有事項

ブロックチェーン固有事項は、上位要求または対象機能に実際に関係する場合だけ確認する。

例:

- 対象チェーン、ネットワーク
- 鍵や秘密情報を扱うか
- 署名やトランザクションを扱うか
- オフライン利用を必須とするか
- 搬送手段に要件があるか

これらはチェックリストであり、未記載だからという理由だけで要件へ追加しない。

QR、Animated QR、NFC、Deep Link、Relay、Clipboard、Aggregate Transaction、Partial Transaction、ハードウェア保護領域等を、入力にない場合に新機能として追加してはならない。

## 未決定事項

`OPEN-` は要件レベルの判断だけに使用する。

記載する項目:

- 論点
- なぜ要件確定前に判断が必要か
- 影響する要件またはスコープ
- 決定者または期限（判明している場合のみ）

設計方式の選択肢、比較表、推奨方式は新たに作成しない。

例:

適切:

```text
OPEN-001: Mainnet を初期リリース対象に含めるか
```

範囲外:

```text
OPEN-002: AES-GCM と XChaCha20-Poly1305 のどちらを採用するか
OPEN-003: CBOR のキー番号をどう割り当てるか
```

後者は仕様設計へ引き渡す。

## 出力形式

ユーザーが別形式を指定しない場合は次を基本とする。

```markdown
# 要件定義書

## 1. 概要
- 背景:
- 目的:
- 解決する課題:

## 2. 対象範囲と責任境界
### 対象
### 対象外
### 外部へ委ねる責任

## 3. 利用者と関係者

## 4. 前提条件と制約

## 5. ユースケース

## 6. 機能要件

## 7. 非機能要件

## 8. データ要件

## 9. 受け入れ条件

## 10. 未決定事項

## 11. 仕様設計への引継ぎ
- 確定した要件:
- 確定した制約:
- 仕様設計で決定する事項:
- 要件レベルの未決定事項:
- 参照資料:
```

不要な節は無理に埋めない。情報がなければ「該当なし」「未決定」「確認が必要」とする。

## 文字による図解

文章や表だけでは利用者、関係者、責任境界、ユースケース、外部から観測できる結果の関係を把握しにくくなる場合に限り、要件定義書へ文字による図解を追加してよい。ASCII図または Mermaid のコードブロックを使用し、図解は本文に定義した内容の理解を助ける補助資料とする。

- 利用者と関係者の関係、対象・対象外と外部責任の境界、ユースケースと期待結果の対応、要件と上位要求の追跡関係を示してよい。
- API、フィールド、スキーマ、アルゴリズム、処理順序、状態遷移、クラス、関数、データベース、インフラ、UIレイアウトなどの設計を図解してはならない。必要な論点は仕様設計への引継ぎまたは `OPEN-` とする。
- 図の各ノード、矢印、境界、注記は、ユーザー要求、コンセプト、承認済み資料、確認済み事実、または論理的に不可欠な派生要件へ追跡できるものだけにする。仮定・未決定事項・対象外は図中または直前の注記で明示する。
- 図解を追加しても、規範要件、優先度、根拠、受け入れ条件を図だけで表現しない。要件本文または表を主定義とし、図解はそれを参照する。
- Mermaid の描画環境に依存せず読めるよう、必要に応じて図の目的を一文で説明する。意味の重複や、図のためだけの新しい要件を作らない。

## レビュー結果の扱い

- 「レビュー結果の探索」で定めた対応ファイルだけを参照し、対象、鮮度、判定、未解決 Critical/Major を確認する。
- コンセプトレビュー結果の判定がコンセプト整理をブロックしている場合、未解決のまま要件へ反映して完了扱いにしない。
- 要件レビュー結果の指摘は、要件レベルへ言い換えられ、今回の更新範囲に含まれるものだけを採用候補とする。対応しない指摘は要件定義書へ混入させず、採用しない根拠を作成判断として確認する。
- レビュー指摘でも、要件定義の範囲外である場合はそのまま要件へ反映しない。
- `requirements-review` が設計詳細を要求しているように見える場合は、`scope-boundary.md` に従って要件レベルへ言い換えられる部分だけを反映する。
- このスキル自身はレビュー結果を生成しない。

## 自己確認と完了条件

出力前に次を確認する。

- 背景、課題、目的、利用者、スコープ、ユースケース、要件が一貫している。
- コンセプトやユーザー要求にない機能を追加していない。
- 各要件が上位要求または明示根拠へ追跡できる。
- 要件IDが一意で、優先度、根拠、対応ユースケースまたは影響、必要な受け入れ条件が対応付いている。
- 同一の義務または期待結果を、複数の要件や要件IDで重複して表現していない。
- 背景、スコープ、ユースケース、要件、受け入れ条件に、意味の重複や不要な反復がない。
- 同じ内容を複数箇所に記載する必要がある場合は、主となる記載箇所を明確にし、他の箇所は参照または簡潔な要約にしている。
- API、フィールド、暗号方式、内部処理、テスト実装を新たに決定していない。
- `OPEN-` に仕様設計事項を入れていない。
- 受け入れ条件が外部結果を検証し、テスト実装詳細になっていない。
- 対象チェーン、ネットワーク、バージョンの競合や未確認事項を事実として断定していない。
- 仕様設計者に必要な制約を渡しつつ、設計余地を不必要に奪っていない。
- 重複する項目を統合または除外しても、根拠、追跡可能性、外部契約、受け入れ条件を失っていない。
- 冗長性を削減するために、必要な根拠や検証可能な結果まで削除していない。
- 同じ内容の重複が多く、くどい表現になっていない。
- 要件や判断に必要な説明が不足していない。
- 要件の判定に不要な説明が過剰になっていない。
- 不自然または不要な英語・カタカナ表記になっていない。定着した固有名詞、製品名、プロトコル名、技術用語を、単に英語やカタカナであるという理由だけで変更していない。
- 技術者が要件、根拠、優先度、受け入れ条件を正確に解釈できる。概要、目的、対象範囲などは、非技術者にも過度な前提知識なしに概要が伝わる。
- 文字による図解を含めた場合、図の全要素と関係が本文または参照資料へ追跡でき、要件本文・優先度・根拠・受け入れ条件と矛盾していない。
- 図解が設計詳細、内部処理、未決定事項の無断確定、または入力にない要件の追加になっていない。
