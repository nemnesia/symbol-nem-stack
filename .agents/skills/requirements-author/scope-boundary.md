# Requirements Scope Boundary

このファイルは、要件定義作成者が要件定義の範囲を超えて仕様・設計・実装を決めないための必須ゲートである。`SKILL.md` に従って要件候補を作成する前と、成果物へ採用する前の両方で適用する。

## 1. 要件定義で決めること

要件定義では、原則として次だけを決める。

- 解決する課題、目的、対象利用者、利用場面
- 今回の対象範囲、対象外、責任境界
- システムが外部から観測可能な形で満たすべき結果
- 必要な品質特性、セキュリティ特性、相互運用性、制約
- 扱う情報の種類、機密性、完全性、保存要否などのデータ上の要求
- 主要要件の合否を判断できる受け入れ条件
- 要件を追跡するための識別子、優先度、根拠
- 仕様設計を始める前に決定が必要な要件レベルの未決定事項

## 2. 要件定義で新たに決めないこと

次は、ユーザー、承認済み上位資料、外部規格等によって必須と確定していない限り、要件定義作成者が新たに決めてはならない。

- API のパス、HTTP メソッド、パラメータ、レスポンス構造、具体的なエラーコード
- フィールド名、型、キー番号、識別子の数値割当、バイト配置、スキーマ
- シリアライズ形式、Catbuffer/CBOR 等の具体的プロファイル
- アルゴリズム、内部処理順序、状態遷移、クラス・関数・モジュール構成
- 暗号アルゴリズム、KDF、nonce、salt、IV、tag、鍵長等の具体的構成
- データベース、ライブラリ、フレームワーク、インフラ構成、配置方式
- UI レイアウト、画面遷移、具体的な操作手順
- 単体テスト、fixture、テストデータ、実装レベルの検証手順

確定済みの技術選択を入力から受け取った場合は、その事実を制約として保持してよい。ただし、その周辺仕様を推測して補完してはならない。

## 3. スコープ拡張禁止

要件定義はコンセプトを具体化する工程であり、コンセプトを拡張する工程ではない。

- コンセプトまたはユーザー要求にない新機能を「あると良い」という理由で追加しない。
- セキュリティ、運用、互換性、将来拡張などの一般論だけを根拠に新機能を追加しない。
- 特定カテゴリのチェック項目が存在することを、そのカテゴリの要件を追加する根拠にしない。
- 上位の目的・スコープを実現するため論理的に不可欠な派生要件だけを追加できる。その場合は根拠を上位要求へ追跡可能にする。
- 新しい目的、利用者、ユースケース、対応チェーン、搬送手段、運用機能等が必要に見えても、上位要求から不可欠と導けなければ要件にせず、必要なら確認事項として扱う。

## 4. 要件候補の境界テスト

各要件候補について、次を順に判定する。

1. この記述は「何を満たす必要があるか」か、それとも「どう実現するか」か。
2. 別の実装方法でも同じ外部結果・制約を満たせるなら、その実装方法を要件として固定する必要があるか。
3. 固定する必要があるなら、その根拠はユーザー要求、承認済み上位資料、外部互換性、法令・規格などに存在するか。
4. 根拠がなければ、具体的な方式を削除して観測可能な結果または制約へ書き換える。
5. 観測可能な結果または要件レベルの制約へ書き換えられない場合は、その候補を要件定義から除外する。

## 5. 未決定事項の境界

`OPEN-` は要件レベルの判断が未決定の場合だけ作成する。

適切な例:

- Mainnet を初期リリース対象に含めるか
- 後方互換性を必須とするか
- オフライン利用を必須要件とするか

不適切な例:

- CBOR のキー番号をどう割り当てるか
- AES-GCM と別方式のどちらを採用するか
- API のエンドポイントをどう分割するか

後者は仕様設計で決められるため、要件定義の `OPEN-` にしない。

`OPEN-` に設計案の比較、推奨方式、具体的な実装候補を新たに作成してはならない。ユーザーが既に提示した設計候補がある場合も、要件定義では「要件として何を決める必要があるか」を記録し、詳細比較は後工程へ委ねる。

## 6. 最終判定

成果物へ記載する前に各項目へ次の一問を適用する。

> この項目を要件定義書から削除して仕様設計で初めて決めても、目的・スコープ・外部契約・必要な品質・受け入れ条件を損なわないか。

損なわないなら、その項目は原則として要件定義の範囲外である。
