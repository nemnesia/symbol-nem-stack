# Readme Author

READMEを、現在実装されている製品・パッケージの利用方法を利用者へ伝える文書として作成または更新する。

> README is documentation of the current product, not a place to design the product.

READMEは現在実装されている製品・パッケージの利用方法を説明する文書であり、仕様や設計を決定する文書ではない。

## 責務と境界

- READMEに必要な利用者向け情報だけを記載する。
- 実装されていない機能、確認できない対応環境、推測したAPIやサンプルを記載しない。
- READMEから仕様、公開API、デフォルト値、互換性、将来機能を新しく決めない。
- 設計思想、内部実装、詳細なプロトコル仕様、網羅的なAPI仕様は勝手に追加しない。
- 詳細仕様が必要な場合は、既存の `docs/` またはAPI仕様書へ誘導する。
- README専用の作業では、無関係なコード、仕様書、要件定義書、レビュー資料を変更しない。

## 事実源

対象を特定したうえで、次の情報を確認する。

1. 対象パッケージまたはアプリケーションの `package.json`
2. 公開エントリポイント、`exports`、公開関数・クラス・型定義および実装
3. 既存のREADMEと、対象に直接関係する既存ドキュメント
4. 実際のテスト、サンプル、ビルド設定、ライセンスファイル

情報源に矛盾がある場合は推測で統合せず、確認できた事実と未確認事項を分けて報告する。既存READMEの記載だけを、実装や公開APIより強い根拠として扱わない。

## 作成・更新手順

1. 対象パス、対象名、パッケージ管理方式、既存READMEの有無を確認する。
2. `package.json`、公開export、型定義、実装、既存ドキュメントからREADMEに必要な事実を抽出する。
3. 既存READMEがある場合は、内容と構成を尊重し、古い箇所や依頼された範囲だけを更新する。不要な全面書き換えを避ける。
4. 利用者が最初に理解すべき情報から並べ、根拠のない節は追加せず省略する。
5. サンプルコードを公開APIと照合する。パッケージ名、importパス、引数、戻り値、非同期処理、環境条件を実装と一致させる。
6. 書き終えたら、実装・`package.json`・公開export・既存ドキュメントとの不一致がないか確認する。

## 基本構成

必要な情報が確認できる場合に、次の順序を基本とする。対象に不要な節は省略する。

- 何のパッケージまたはアプリケーションか
- インストールまたはセットアップ
- 最小使用例
- 主要APIまたは主要な利用方法
- 対応環境
- 必要な注意事項、制約、既知の前提
- License

各節は利用者に必要な粒度に留める。主要APIは公開APIのすべてを機械的に列挙せず、入口となるものを記載する。対応環境は `engines`、ビルド設定、実際の依存関係など確認できる根拠がある場合だけ記載する。

## 表現とサンプル

- 既存READMEの言語、用語、見出し粒度、コードスタイルを可能な限り維持する。
- インストール方法は、`package.json`のパッケージ名とリポジトリで採用されているパッケージマネージャを根拠に記載する。
- 最小使用例は、実際に利用可能な公開APIだけで構成し、説明のための架空の関数や型を作らない。
- サンプルで使う値、ネットワーク、ホスト、環境変数、秘密情報の扱いは、既存の実装・テスト・ドキュメントで確認できるものに限る。
- 注意事項は、利用上の安全性や失敗条件に必要なものだけを記載する。一般論や未確認の保証を追加しない。
- 詳細な仕様、内部構造、プロトコル説明は、既存の資料へリンクしてREADMEに重複させない。

## 完成前の確認

- READMEが現在の実装の利用方法を説明し、仕様や設計を新たに決めていない。
- 記載した機能、API、対応環境、コマンド、ライセンスに根拠がある。
- 最小使用例のimport、API名、引数、戻り値、実行環境が公開APIと一致している。
- 実装されていない機能、将来構想、推測による互換性や保証を記載していない。
- 既存READMEがある場合、依頼に不要な全面書き換えをしていない。
- 詳細仕様をREADMEへ過剰に取り込まず、必要に応じて既存の `docs/` やAPI仕様書へ誘導している。
