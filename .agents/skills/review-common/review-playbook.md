# Review Playbook

レビュー系スキルに共通する実行指針。各スキルは、対象に必要な reviewer、gate、output format、security checklist だけを追加で参照する。

## 目的と責務

レビューは、対象の要求、設計、仕様、実装、公開文書、配布物が、適用される承認済み資料や契約を満たすか確認する。新機能や好みの設計を提案する場ではない。

レビュー担当は、対象の選定、根拠の確認、指摘の統合、gate 判定、依頼された成果物の作成を担う。委譲は依頼範囲と利用可能な仕組みに適合する場合だけ行う。委譲しない場合は、必要な観点を別々に確認し、行っていない作業を実施済みと記録しない。

## 根拠と Context

作業前に、対象リポジトリの作業指示（`AGENTS.md` など）があれば読む。技術的・製品上の根拠には、対象に適用される承認済み要求、設計、仕様、公開契約を用いる。標準、実装、SDK、既存コード、テスト、ユーザー提供資料は役割と適用範囲を区別する。

作業指示から任意の Phase Context が登録されている場合は、初期理解や正式資料の所在確認にのみ使う。Context を根拠として finding や Gate failure を確定しない。必要な正式資料は直接確認する。Context と正式資料の競合や鮮度の問題は、対象文書の欠陥と混ぜず必要に応じて別途報告する。

## レビューフロー

### 1. 対象と範囲を確定する

ユーザーが指定した対象と範囲を優先する。未指定なら、対象スキルが指示する方法で既存構成から候補を探す。候補がない、複数ある、または出力先を特定できない場合は推測で選ばない。

### 2. 独立に確認する

各観点について、対象箇所、確認した事実、適用される根拠、発生条件、影響、必要な修正・確認、未確認範囲を整理する。指摘候補は、根拠へ追跡でき、現在の対象範囲に具体的な影響があり、上流や下流で決める内容を先取りしない場合に限る。

### 3. 反証して統合する

重複指摘をまとめ、根拠、影響、完了条件、対象工程を再確認する。一般論、個人的な好み、将来機能、根拠のない hardening は finding にしない。

上流の正式資料や判断にある不足、曖昧さ、矛盾は `Upstream Feedback` に記録する。後工程、対象範囲外、追加検証へ渡す事項は `Deferred Findings` に記録する。Upstream gap が現在の成果物を安全に評価・完了できない場合は、現在の工程に対する finding と上流 feedback を関連付ける。同じ原因を二重計上しない。各専門スキルが異なる重大度や Gate 方針を定めている場合はそちらを優先する。

### 4. Gate と成果物を適用する

対象スキルで定められた Gate、重大度、判定値、出力形式を使う。既存のレビュー成果物を上書きせず、既存の保存先・命名規則を確認する。成果物の作成が依頼されていない場合は、指示された形式で結果を報告する。

実行していない検証を成功扱いにしない。Evidence、結果、未確認範囲、未実行の理由を分ける。

## 境界

- レビュー対象のコードや文書を、レビュー中に修正しない。
- 新しい要求、API、データ形式、エラー、fallback、互換動作、実装方式を発明しない。
- 既存コードやテストは現状確認・回帰確認の根拠になり得るが、単独で承認済み要求や外部標準の根拠にはしない。
- 技術的な競合は、対象、版、環境、資料の役割、適用範囲、影響を分けて記録し、根拠なしに統合しない。
- 秘密情報、個人情報、復号データをログ、成果物、例へ含めない。
- 作業指示に検証範囲が定められていればそれに従う。そうでなければ、変更・レビュー範囲に関連する検証だけを実施する。
- 明示的な依頼がない限り、commit、push、tag、publish、外部サービスへの書き込みを行わない。
