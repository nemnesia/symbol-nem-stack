# Review Process

必ず Phase 0、Phase 1、Phase 2、Phase 3 の順に実施する。内部討議は成果物へ出力しない。

## Execution Gate: Reviewer 起動の監査

Phase 1 の前に、トップレベルの Chair は Reviewer A、B、C をそれぞれ別の `spawn_agent` 呼び出しで起動する。サブエージェントを Chair として再委譲してはならない。各呼び出しに `fork_context: false` を指定し、返却された `agent_id` を役割ごとに記録する。3つの ID がすべて存在し、相互に異なることを確認できた場合だけ Phase 1 に進む。

ID の欠落、重複、起動エラー、サブエージェント機能の利用不能がある場合は、メインエージェントによる代替レビューを行わず、レビューを中止する。中止時は findings を生成せず、サブエージェントレビューを実行できなかったことを報告する。

## Phase 0: Scope Filter

各 Reviewer は指摘候補を作成する前に、その事項がコンセプトレビューの範囲内か判定する。

メインエージェントは Phase 0 の対象資料と判定条件を、Reviewer A、B、C の各サブエージェントへ個別に渡す。各サブエージェントは他の Reviewer と相談せず、自分の担当観点で範囲内かを判定する。

次のすべてを満たす場合だけ Phase 1 の指摘候補として扱う。

1. 課題、対象ユーザー、提供価値、スコープ、MVP、
   またはコンセプトそのものの成立性に直接関係する。
2. 要件定義へそのまま委譲できる事項ではない。
3. API、データモデル、アルゴリズム、通信形式、
   アーキテクチャ、実装方式等を決定しなくても修正できる。
4. 「より安全」「より保守しやすい」「将来問題になる」
   という理由だけの指摘ではない。

1つでも満たさない場合はレビュー対象外とし、
Phase 1 の指摘候補にも含めない。

レビュー対象外となった事項は成果物へ記載しない。

## Phase 1: Individual Review

Reviewer A、B、C は互いの意見を参照せず、担当観点とコンセプトシートを独立してレビューする。

メインエージェントは Reviewer A、B、C を別々のサブエージェントとして並列起動する。各サブエージェントは最終 findings ファイルを作成せず、下記の項目を含む指摘メモだけを返す。サブエージェントが参照できる根拠は、対象コンセプト本文とユーザーがレビュー対象として明示した資料に限る。

Chair は3つの `agent_id` それぞれについて Phase 1 の完了状態を待機して確認する。すべてが完了して指摘メモを返したことを確認できない場合は Phase 2 へ進まず、findings を生成しない。

各指摘は仮 ID（`A-001`、`B-001`、`C-001`）を付け、次をすべて含める。

- 重大度（Critical、Major、Minor）
- 問題と対象箇所
- 根拠の種別と参照箇所
- 放置した場合の影響
- 必要な修正または確認

根拠の種別は「コンセプト本文」「ユーザー提供資料」のいずれかとする。未確認事項は未確認と明記し、外部事実を断定しない。

Phase 1 の返答を受け取ったら、メインエージェントは仮 ID、対象箇所、根拠、影響、必要な修正または確認が揃っているかを確認する。不備がある場合は、該当するサブエージェントへ不足項目だけを補完させる。Chair が指摘内容を推測で補完してはならない。

## Phase 2: Review Board Discussion

Phase 1 の終了後に限り、各 Reviewer は他の指摘を評価できる。評価は賛成、条件付き賛成、反対のいずれかとし、反対または条件付き賛成には根拠不足、範囲外、後工程で決める事項、重大度不適切などの理由を添える。

メインエージェントは Phase 1 の全指摘メモを、同じ Reviewer A、B、C のサブエージェントへ渡す。各サブエージェントは自分の指摘を含む全指摘を評価し、他の Reviewer の指摘に対する判定と理由を返す。Phase 2 の評価が完了するまで、Chair は採用・却下・重大度を確定しない。

Chair は Phase 1 と同じ `agent_id` に対して Phase 2 の入力を送る。別の新規サブエージェントで置き換えてはならない。3つすべての Phase 2 完了状態を個別に確認できない場合は Phase 3 と findings の生成を中止する。

討議の目的は指摘を増やすことではなく、根拠と影響が十分な指摘へ絞り込むことである。各指摘を採用、却下、または重大度変更として確定する。次の場合は却下する。

- 問題、根拠、影響、必要な修正または確認を説明できない。
- 個人的好み、推測、設計・実装詳細、または後工程だけで決められる事項である。
- 確認済みの根拠と矛盾する。

## Phase 3: Chair Decision

Review Board Chair はコンセプト本文、明示された根拠、討議で採用された指摘を用いて品質ゲートを適用する。新しい指摘は追加せず、根拠不足の指摘は採用しない。

Chair はサブエージェントの Phase 1 メモと Phase 2 評価を統合し、重複をまとめて正式 ID を付ける。サブエージェントの討議内容、投票、個人意見、却下理由、思考過程は findings に出力しない。

Chair は findings の `Execution Audit` に、A/B/C の `agent_id`、Phase 1 の完了状態、Phase 2 の完了状態、Chair による統合完了を記載する。ID や完了状態を確認できない場合は、どの品質判定であっても findings を生成してはならない。

Chair は、対象パッケージの `docs/reviews/concept/` にある対象コンセプトの過去レビュー成果物を確認し、固定名の旧形式と連番形式を区別する。過去成果物は、対象コンセプトの正式ID、初出レビュー、前回状態、対応確認の根拠を把握する目的だけで参照する。Reviewerへ過去成果物を渡したり、新しいレビュー根拠として使用したりしてはならない。

対象コンセプトの連番レビュー成果物は、ベース名ごとに最大の3桁番号へ1を加えたファイル名で新規作成する。候補ファイルが存在する場合は、空き番号が見つかるまで番号を進める。固定名の `-review.md`、`-review-findings.md` および既存の連番成果物は変更しない。

採用指摘を統合する。過去指摘と同一問題であることを確認できる場合は既存の正式IDを引き継ぎ、新しい問題には過去成果物から抽出した最大の正式IDの次を付与する。正式IDは一度発行した番号を新しい問題へ再割当しない。

指摘状態は次の規則で決定する。

- `New`: 今回初めて採用した指摘。
- `Open`: 過去から継続して未対応の指摘。
- `Resolved`: 現在のコンセプト本文で問題が解消され、確認根拠を示せる指摘。
- `Deferred`: 問題を認識しているが、要件定義以降へ引き継ぐ指摘。
- `Reopened`: 過去に `Resolved` となった同一指摘が再び確認された指摘。

対応済み、後工程引継ぎ、再発を含む全正式指摘を `Finding Status` に一覧化し、`Resolved` は `Resolved Findings`、`Deferred` は `Deferred Findings` に整理する。現在対応が必要な指摘だけを `Required Changes` または `Optional Improvements` に記載する。

重大度は次のとおりとする。

- Critical:
  コンセプト自体の成立または要件定義開始を妨げる問題。
- Major:
  要件定義開始は可能だが、
  コンセプトの目的、対象ユーザー、提供価値、スコープ、
  MVPの解釈を大きく誤らせる可能性がある問題。
- Minor:
  コンセプトの理解を容易にする表現上の改善。
  新しい機能、制約、非機能要件、技術事項を追加する指摘には使用しない。

すべての品質ゲートが合格なら「要件定義へ進める」、1つでも不合格なら「コンセプト整理を優先する」と判定し、対象パッケージの `docs/reviews/concept/` に、コンセプトシートのベース名へ `-review-<3桁連番>.md` を付加した新規ファイルを生成する。
