# Concept Review Board

コンセプトを設計・実装・書き直すのではなく、要件定義を開始できる品質かを判定する。完璧さや Minor の解消を目的にレビューを継続してはならない。

## 対象と成果物

- レビュー対象は、ユーザーが明示したコンセプトシート1件とする。
- 対象パッケージは、ユーザーが指定したパッケージ、または対象コンセプトシートが属するパッケージのルートとする。対象パッケージを特定できない場合は、推測で選ばず対象を確認して終了する。
- コンセプトシートが明示されない場合は、対象パッケージ内で `concept-sheet.md`、`concept.md`、ファイル名に `concept` を含む Markdown ファイルの順で候補を探す。`reviews/` ディレクトリ、`*-review-*.md`、要件定義書、設計書、実装コード、過去のレビュー結果は除外する。
- 候補が0件または複数件なら、推測で選ばず対象を確認して終了する。
- 選択したコンセプトシートの拡張子を除いたベース名に `-review-001.md` 形式の3桁連番を付加し、対象パッケージの `docs/reviews/concept/` に成果物を作成する。たとえば対象パッケージの `docs/consept/concept-sheet.md` の初回成果物は `docs/reviews/concept/concept-sheet-review-001.md` とする。対象コンセプトに対応する連番ファイルが既にある場合は最大番号の次を使用し、候補ファイルが存在する場合は空き番号まで進める。既存の固定名 `-review.md` や `-review-findings.md` を含む成果物は移動・削除・上書きしない。`docs/reviews/concept/` が存在しない場合は作成する。
- 連番は対象コンセプトのベース名ごとに管理する。対象コンセプトの過去レビュー成果物（固定名の旧形式を含む）から正式な `CR-<番号>` を抽出し、新規指摘には最大番号の次を割り当てる。既存指摘は同一問題であることを確認できる場合に同じIDを引き継ぎ、新規指摘へ過去IDを再利用しない。
- 各正式指摘には `New`、`Open`、`Resolved`、`Deferred`、`Reopened` のいずれかの状態を付ける。`Required Changes` と `Optional Improvements` には現在対応が必要な指摘を、`Resolved Findings` には対応済み指摘と確認根拠を、必要に応じて `Deferred Findings` には後工程へ引き継いだ指摘を整理する。

## 実行主体と実行順序

1. `reviewers.md` を読む。
2. `review-process.md` を読む。
3. `review-gates.md` を読む。
4. `output-format.md` を読む。
5. メインエージェントを Review Board Chair 兼オーケストレーターとし、Reviewer A、B、C をそれぞれ別のサブエージェントとして起動する。
6. 定められた Phase 1 から Phase 3 を実施し、Chair だけが成果物を生成する。

## 監査可能な起動要件

- Reviewer A、B、C は、`multi_agent` の `spawn_agent` を3回の別々の呼び出しで起動する。各呼び出しでは `fork_context: false` を指定し、初期会話コンテキストを共有しない。
- このスキルは、サブエージェントではなく、`multi_agent` を利用できる現在のトップレベルエージェントが Chair として直接実行する。サブエージェントへ `concept-review` 全体を再委譲してはならない。
- Chair は各呼び出しから返された `agent_id` を、`A`、`B`、`C` の役割と対応付けて実行台帳へ記録する。
- Phase 1 を開始する前に、3つの `agent_id` がすべて存在し、相互に異なり、役割の重複がないことを検証する。検証できない場合はレビューを中止し、findings を生成しない。
- Phase 1 と Phase 2 は各 `agent_id` の完了状態を個別に待機して確認する。1つでも失敗、タイムアウト、未確認があればレビューを中止し、findings を生成しない。
- サブエージェント機能が利用できない場合に、メインエージェントが代替実行してレビュー済みと扱ってはならない。サブエージェントレビューを実行できない旨だけを報告する。
- findings には実行監査情報として、3つの `agent_id`、Phase 1/2 の完了状態、Chair が統合したことを記載する。プロンプト、内部討議、個人意見、思考過程は記載しない。

サブエージェントには、対象コンセプトシート、ユーザーがレビュー対象として明示した資料、該当するレビュー手順、担当役割だけを渡す。`docs/knowledge`、要件定義書、仕様書、設計書、実装コード、過去のレビュー結果は渡さない。サブエージェントはファイルを作成・編集せず、指摘メモを返す。

討議、投票、Reviewer 個人の意見、却下理由、思考過程は内部情報であり、成果物へ含めない。

## 共通原則

- 「何を作るか」を確認し、「どう作るか」の設計・実装判断はしない。
- 指摘は対象箇所、根拠、影響、必要な修正を示せる場合だけ採用候補とする。
- コンセプト本文、ユーザー提供資料の確認済み資料を根拠の種別として区別する。未確認の事実、推測、好みを事実として扱わない。
- レビュー根拠は、対象コンセプト本文およびユーザーがレビュー対象として明示した資料に限定する。
- `docs/knowledge`、要件定義書、仕様書、設計書、実装コードを、コンセプトレビューの根拠として参照しない。
- 技術的妥当性や方式の詳細確認が必要な事項は、要件定義または後続レビューへ委譲する。
- 正しい指摘であっても、コンセプト段階で解決する必要がなければ採用しない。
