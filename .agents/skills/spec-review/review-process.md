# Review Process

必ず Phase 1、Phase 2、Phase 3 の順に実施する。内部討議は成果物へ出力しない。

## Execution Gate: Reviewer 起動の監査

トップレベルのメインエージェントである Chair は、Reviewer A、B、C を `multi_agent_v1__spawn_agent` の別々の呼び出しで起動する。各呼び出しは `fork_context: false` とし、返却された `agent_id` を役割に対応付けて保存する。3件すべてが存在し、相互に異なることを確認できた場合だけ Phase 1 に進む。欠落、重複、起動失敗、ツール利用不可の場合は、代替起動や自己レビューを行わず中止し、findings を生成しない。

## Phase 1: Individual Review

Reviewer A、B、C は互いの意見を参照せず、担当観点と仕様書を独立してレビューする。Chair は各サブエージェントへ `multi_agent_v1__wait_agent` を個別に実行し、3件すべての Phase 1 完了とメモ返却を確認する。1件でも失敗、タイムアウト、未完了、メモ未返却なら Phase 2 と Phase 3 を実施せず、findings を生成しない。選択されたコンセプトシートまたは要件定義書がある場合は、各 Reviewer は `reviewers.md` の担当観点に必要な範囲で上流本文を照合する。対応するコンセプトレビュー結果または要件レビュー結果がある場合は、公開された判定、Required Changes、Review Gates だけを根拠として確認する。実装者からの仕様フィードバックがある場合は、対象仕様との一致を確認したうえで、確認済みの事実、未決定事項、実装への影響だけを参照する。推奨案、暫定対応、内部実装または未承認の判断は仕様の根拠にしない。Reviewer C は技術的または安全性上の前提を評価する必要がある場合に限り、承認済みのコンセプト・要件、レビュー結果、実装者からの仕様フィードバックまたはプロジェクト資料の関連箇所を参照してよい。

各指摘は仮 ID（`A-001`、`B-001`、`C-001`）を付け、次をすべて含める。

- 重大度（Critical、Major、Minor）
- 問題と対象箇所
- 根拠の種別と参照箇所
- 放置した場合の影響
- 必要な修正または確認

指摘を作る前に、次の最小十分性チェックを行う。

1. 既存のコンセプト、要件、仕様のどの要求・制約・判断原則に必要か。
2. 指摘を採用しなくても、現在の対象範囲を一意に実装し検証できるか。
3. 指摘は欠陥の修正か、それとも新しい機能・制約・設計の追加か。
4. 「将来必要かもしれない」「一般に望ましい」「より安全・柔軟になる」だけが根拠になっていないか。

1 の根拠を示せず、かつ 2 が「できる」、または 3 が新規追加、または 4 に該当する場合、その指摘は作成しない。

根拠の種別は「仕様本文」「コンセプト本文」「コンセプトレビュー結果」「要件本文」「要件レビュー結果」「実装者からの仕様フィードバック」「ユーザー提供資料」「承認済み要件またはプロジェクト資料」のいずれかとする。上流本文、レビュー結果または実装者からの仕様フィードバックがない、対象不一致、または古い場合は Evidence Used に「未確認」と記載する。未確認事項は未確認と明記し、外部事実を断定しない。

## Phase 2: Review Board Discussion

Phase 1 の終了後に限り、各 Reviewer は他の指摘を評価できる。評価は賛成、条件付き賛成、反対のいずれかとし、反対または条件付き賛成には根拠不足、範囲外、後工程で決める事項、重大度不適切などの理由を添える。

Chair は Phase 1 の全メモを、起動時と同じ Reviewer A、B、C の `agent_id` へ `multi_agent_v1__send_input` で個別に送信し、各返却 `submission_id` を保存する。その後、各送信の完了を `multi_agent_v1__wait_agent` で確認する。3件すべての完了を確認できない場合は Phase 3 へ進まず、findings を生成しない。

討議の目的は指摘を増やすことではなく、根拠と影響が十分な指摘へ絞り込むことである。各指摘を採用、却下、または重大度変更として確定する。次の場合は却下する。

- 問題、根拠、影響、必要な修正または確認を説明できない。
- 個人的好み、推測、具体的な実装詳細、または後工程だけで決められる事項である。
- 確認済みの根拠と矛盾する。
- 既存のコンセプト、要件、仕様にない新しい要求・機能・制約を追加する提案である。
- 現在のスコープを満たすためには不要な将来拡張、汎用化、抽象化、互換性、運用機能、防御機構の追加である。
- 問題の解消条件ではなく、Reviewer が好む具体的な解決方式を要求している。

指摘の一部だけが有効で、一部が過剰設計なら、過剰な部分を削除して既存要求を満たすための最小条件だけを残す。

## Phase 3: Chair Decision

Review Board Chair は仕様本文、確認された上流本文とレビュー結果、明示された根拠、討議で採用された指摘を用いて品質ゲートを適用する。3つの `agent_id`、Phase 1・Phase 2 の `multi_agent_v1__wait_agent` による完了、Chair の統合完了を確認し、成果物の `Execution Audit` に記録する。これらを確認できない場合は findings を生成しない。新しい指摘は追加せず、根拠不足の指摘は採用しない。

採用前に Chair は各指摘へ最終的な Anti-Overdesign Check を適用する。

- この指摘がなくても既存要件を実装・検証できるなら、原則として却下する。
- 修正内容が新しい設計を指定している場合、必要条件だけへ縮小できなければ却下する。
- 既存スコープ外の将来ケースだけを解決する指摘は却下する。
- より高度な安全性・柔軟性・拡張性を得るだけの指摘は却下する。

採用指摘を統合し、過去指摘との同一性を確認したうえで正式 ID（`SR-001` からの対象仕様書単位の連番）と状態を付与する。今回初めて確認した指摘は `New`、未解決の過去指摘は `Open`、一度 `Resolved` または `Deferred` とした同一指摘が再発・未解消と確認された場合は `Reopened`、対応済みの過去指摘は `Resolved`、後工程へ引き継ぐ指摘は `Deferred` とする。既存指摘を状態変更なく再確認した場合も、同じIDを保持する。重大度は次のとおりとする。

- Critical: 品質ゲートを不合格にし、実装開始を妨げる問題。
- Major: 開始は妨げないが、既存要件の実装または運用で具体的な問題になるため修正を推奨する問題。
- Minor: 既存要件または仕様の明確性・一貫性を改善する小さな問題。新機能や将来拡張の提案には使用しない。

すべての品質ゲートが合格なら「実装へ進める」、1つでも不合格なら「仕様の修正を優先する」と判定し、対象パッケージの `docs/reviews/specifications/` に、選択した仕様書の拡張子を除いたベース名へ `-review-<3桁連番>.md` を付加した新規ファイルを生成する。既存の固定名または連番成果物は変更しない。
