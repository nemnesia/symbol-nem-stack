# 仕様レビュー用セキュリティチェックリスト

このチェックリストは、承認済み要求・設計に定められた保護対象、責任、セキュリティ不変条件が、外部から判定でき、実装・検証できる仕様契約になっているか確認するための補助資料である。項目だけを根拠に要求、設計判断、脅威、暗号方針を新設しない。

## 1. 保護対象と公開範囲

- 仕様上の各操作で、保護対象を受け取る、返す、保存する、共有する条件が判定できるか。
- 認証情報、秘密鍵、個人情報、復号後のデータなど、上流資料が扱う資産を例外・警告・診断出力へ誤って含めないか。
- 外部への開示を制限する上流境界が、入力・出力・保存契約で維持されているか。

## 2. 認証・認可

上流資料で必要とされた場合、保護対象操作、必要な主体・権限、認証失敗・認可失敗時の観測可能な結果、状態が変更されない条件が明確か。画面、token方式など内部・UI方式は、仕様の責務でなければ決めない。

## 3. 対象、文脈、取り違え防止

操作対象、主体、tenant、接続先、環境、versionなどが結果に影響する場合、関連付けと不一致時の動作が一意か。複数対象を同じ値や処理として誤って扱わないか。適用対象にない区分を追加しない。

## 4. 暗号と完全性

上流要求・設計または適用標準が方式の具体化を求める場合に限り、algorithm、key、nonce、salt、AAD、tag、encoding、識別子、version、乱数の責任と失敗時の動作が複数実装で一意になるか確認する。推奨方式を好みだけで要求しない。nonce / salt / randomness の具体規則は、採用方式に必要な場合だけ仕様化する。

## 5. データと失敗時の契約

- validation、正規化、改ざん検知、未知値、期限切れ、重複、サイズ超過、不完全入力の外部結果が必要な範囲で定義されているか。
- 失敗時にデータ、権限、状態がどう保たれるか判定できるか。
- sensitive data がエラーや診断情報に含まれない境界が維持されているか。
- replay、再送、競合、復旧の対策が必要な根拠がある場合、仕様上の振る舞いが明確か。

## 6. 仕様と実装の境界

ここでは外部から観測できる契約を確認する。特定言語の関数構造、メモリ保持期間、具体的なゼロ化処理、parser実装、fuzz harness、ライブラリ呼び出しは実装へ委ねる。責任、trust boundary、許されるデータフロー、失敗時の責任が不足し、仕様が設計を推測する必要がある場合は上流設計への feedback とする。

指摘は対象仕様、承認済み要求・設計、適用規格へ追跡し、外部影響、安全性、再現条件、必要な完了条件を示す。
