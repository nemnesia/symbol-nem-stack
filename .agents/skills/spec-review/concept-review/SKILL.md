# Concept Review Board

コンセプトを設計・実装・書き直すのではなく、要件定義を安全に開始できる品質かを判定する。作業開始時に次の順で全文を読む。

1. `AGENTS.md`
2. ../review-common/review-playbook.md
3. `AGENTS.md` に対象フェーズの Phase Context が登録されている場合だけ、その Context
4. reviewers.md
5. review-gates.md
6. output-format.md

## 対象の確定

- ユーザーが明示したコンセプトシート1件を優先する。
- 未指定なら `docs/consept/` の候補から、`concept-sheet.md`、`concept.md`、ファイル名に `concept` を含む Markdown の順で探す。
- reviews、要件定義、仕様書、設計書、実装コード、過去レビュー成果物は候補から除外する。
- 候補が0件または複数件なら推測で選ばず、対象確認で終了する。
- 対象がリポジトリ全体か特定機能か不明な場合も推測で補わない。

成果物は `docs/reviews/concept/<ベース名>-review-NNN.md` に新規作成する。対象ベース名ごとに既存の最大番号の次を使い、固定名の旧形式を含め既存ファイルを上書きしない。

## 根拠の範囲

主な根拠はコンセプト本文、ユーザーが明示した資料、プロダクト範囲を定める承認済み資料とする。コード、詳細仕様、API、knowledge 資料を、コンセプト段階の欠陥を作る根拠として広げない。

下流資料との相違は、それだけで指摘にしない。用語、既に決まった責任境界、明示された前提の確認に使い、コンセプトの責務を越える論点は要件定義以降へ委譲する。

## レビュー観点

- 背景、課題、目的、対象ユーザー、利用場面、提供価値の因果
- v1、対象外、将来構想、外部責任の境界
- 判断原則、成功条件、根拠種別、前提、リスク、未決定事項
- 用語と本文内部の一貫性
- コンセプト自体を成立不能にする明白な外部制約や前提矛盾

API、データ形式、暗号、処理順序、アーキテクチャ、具体的な受け入れテストはレビューしない。

## 実行と判定

`../review-common/review-playbook.md` の Phase 0〜3 を適用する。Reviewer A、B、C の観点を独立して確認し、サブエージェントを使った場合だけその実行を成果物へ記録する。利用できない場合は自己レビューの観点別パスとして実施し、実施していない Board やエージェントを報告しない。

指摘は本文または確認済み資料へ追跡でき、要件定義で決めるだけでは解消できず、コンセプトの成立・解釈・境界に直接影響するものだけを採用する。

判定は READY または REVISE CONCEPT とする。Critical がなく品質ゲートを満たす場合、Major や Minor が残っていても、要件定義へ引き継げるなら READY とする。

レビュー中にコンセプト本文、仕様、コード、テスト、READMEを変更しない。未確認事項、未実行の検証、過去指摘の状態は output-format.md の規則で記録する。
