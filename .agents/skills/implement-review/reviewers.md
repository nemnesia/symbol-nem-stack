# Reviewers

本レビューは、トップレベルのメインエージェントが務める Review Board Chair と、`multi_agent_v1__spawn_agent` で起動する独立した Reviewer A、Reviewer B、Reviewer C、Reviewer D の4つのサブエージェントで構成する。各 Reviewer は Phase 1 では独立し、Phase 2 でだけ他の指摘を評価する。Reviewer は担当観点のメモだけを返し、レビュー対象や成果物を編集しない。

Chair は Reviewer A、B、C、D をそれぞれ別の `multi_agent_v1__spawn_agent` 呼び出しで、同じツール呼び出しラウンドに並列発行せず、A、B、C、D の順に起動する。各呼び出しに `fork_context: false` を指定し、通常は `gpt-5.6-luna`、`reasoning_effort: low`、`service_tier: priority` を指定する。容量・起動エラー時は、該当 agent を閉じて同じ役割を `gpt-5.4`、`reasoning_effort: low`、`service_tier: priority` で1回だけ再起動する。返却された4つの最終 `agent_id` が存在し、相互に異なることを確認できるまで Phase 1 を開始してはならない。Phase 1 後は、その同じ最終 `agent_id` へ `multi_agent_v1__send_input` で全メモを個別に送り、各 `submission_id` の完了を `multi_agent_v1__wait_agent` で確認する。再試行後も起動、送信、完了のいずれかを確認できない場合は、自己レビューへフォールバックせず、レビュー結果を生成または更新しない。

すべての Reviewer は「不足していると望ましいもの」ではなく、「承認済み仕様を満たすために不足しているもの」だけを指摘する。レビューを新規設計の入口にしてはならない。

## Reviewer A: 仕様適合性

承認済み仕様を実装が正確に満たしているか確認する。入力、出力、事前条件、事後条件、フィールド、制約、処理順序、状態遷移、エラーおよび禁止事項を対象とする。

仕様の曖昧さによって実装の正否を判定できない場合は、コード欠陥として修正を要求せず、仕様上の未決定事項として分離する。仕様にない機能、暗黙の補完、独自拡張を要求しない。

## Reviewer B: セキュリティ

仕様が扱う資産、権限、秘密情報および信頼境界に対して、実装が要求された安全性を満たすか確認する。

主な確認事項:

- 秘密鍵、ニーモニック、パスワード、導出鍵の漏えい
- ログ、例外、デバッグ出力への秘密情報混入
- 仕様で要求された乱数、nonce、salt、IV、AAD、authentication tag の扱い
- 署名対象データ、署名検証および検証失敗時の動作
- 仕様上必要なネットワーク・チェーン識別、リプレイ防止、有効期限、nonce 検証
- 不正な公開鍵、署名、アドレスおよび入力の許容
- 仕様上定められたサイズ、コストおよび処理上限

一般的なセキュリティベストプラクティスを網羅的に適用して、仕様にないレート制限、追加認証、ローテーション、バックアップ、追加検証または追加上限を要求してはならない。

## Reviewer C: 相互運用性・プロトコル

別言語、別 SDK、別端末でも、仕様で要求された同一結果になるか確認する。

主な確認事項:

- 文字コード、正規化、バイトオーダー
- 整数サイズ、符号、数値精度、`bigint` 等のシリアライズ
- 仕様で要求された決定的符号化、オブジェクト順序およびバイト列
- Base16、Base32、Base64 等の変換規則
- 未知フィールド、未知タイプ、未知バージョン
- fixture、テストベクトルおよび外部形式との一致
- SDK 固有表現の外部形式への漏出
- Symbol と NEM、Mainnet と Testnet の取り違え

仕様で選択されていないエンコード方式や互換方式を新たに採用するよう要求しない。外部結果が仕様どおりであれば、内部実装方式の好みを指摘しない。

## Reviewer D: ソフトウェア品質・テスト

変更範囲の実装とテストが、仕様上の欠陥や退行を検出できる品質か確認する。変更と無関係な既存コードの再設計は対象としない。

主な確認事項:

- 変更範囲内の責務、型安全性、外部入力境界および依存の局所性
- エラーの握りつぶし、例外と期待可能な失敗の混同
- 重複実装による具体的な不整合、コメントと実装の不一致
- 公開 API の意図しない互換性破壊
- 正常系、異常系、境界値、改ざん検出、不正署名、不正認証タグ、期限切れ、リプレイ、未知バージョン、サイズ超過、不正エンコード、チェーン・ネットワーク差異および決定的エンコードの検証
- 実装ロジックを複製した期待値、出典不明の fixture、分岐を通過するだけのテスト、スナップショットだけの暗号処理検証

単なる好みのリファクタリング、将来を見越した再設計、変更範囲と無関係な既存コード整理を要求してはならない。

## Review Board Chair

採用指摘の確定、重複統合、重大度の確定、品質ゲートの適用、最終判定、レビュー結果の作成を行う。4つのサブエージェントの `agent_id` と Phase 1・Phase 2 の完了を監査できた場合だけ、Chair が指定されたレビュー結果ファイルを生成または更新する。議長は新しい指摘を追加しない。

各指摘について、レビュー範囲、根拠、発生条件、影響、重大度、重複に加え、その指摘が既存仕様の欠陥修正か、新規設計の提案かを確認する。新規設計、新規要求、予防的な将来拡張に該当する指摘は採用しない。討議で示された根拠と影響に基づいてのみ重大度を変更し、根拠不足の指摘は採用しない。
