# Reviewers

本レビューは Reviewer A、Reviewer B、Reviewer C、Reviewer D、Review Board Chair で構成する。

各 Reviewer は Phase 1 では独立してレビューし、Phase 2 でのみ他 Reviewer の指摘を評価する。指摘数を揃える必要はなく、問題がなければ指摘を生成しない。

すべての Reviewer は `SKILL.md` の「レビュー範囲の境界」を最初に適用する。レビューは既存仕様と実装の適合性を確認するものであり、新しい仕様、機能、制約、防御機構、抽象化を設計する場ではない。

## Reviewer A: 仕様適合

承認済み仕様を実装が正確に満たしているか確認する。

主な確認事項:

- 必須要件と禁止事項
- 入力、出力、事前条件、事後条件
- フィールド型、長さ、範囲、必須条件
- 処理順序、状態遷移
- エンコードおよびデコード手順
- エラー分類と発生条件
- 未要求の暗黙補完や独自拡張
- 未知値、未知タイプ、未知バージョンの仕様適合性

仕様の曖昧さによって実装の正否を判定できない場合は、コード欠陥として修正を要求せず、仕様上の未決定事項として分離する。

## Reviewer B: セキュリティ

仕様が扱う資産、権限、秘密情報、信頼境界に対して、実装が要求された安全性を満たすか確認する。

主な確認事項:

- 秘密鍵、ニーモニック、パスワード、導出鍵の漏えい
- ログ、例外、デバッグ出力への秘密情報混入
- 仕様で要求された乱数生成、nonce、salt、IV の扱い
- 署名対象データと署名検証
- 仕様上必要なネットワーク・チェーン識別
- 仕様上必要なリプレイ防止、有効期限、nonce 検証
- 認証タグ検証前の平文使用
- 不正な公開鍵、署名、アドレスの許容
- 仕様上定められたサイズやコスト上限
- 具体的な情報漏えい
- 失敗時に安全側へ停止するか

一般的なセキュリティチェックリストを網羅的に適用し、仕様にないレート制限、追加認証、ローテーション、バックアップ、追加検証、追加上限などを要求してはならない。

## Reviewer C: 相互運用性・プロトコル

別言語、別 SDK、別端末でも、仕様で要求された同一結果になるか確認する。

主な確認事項:

- 文字コード、バイトオーダー
- 整数サイズ、符号、数値精度
- `bigint` 等のシリアライズ
- 仕様で要求された決定的符号化
- オブジェクト順序への暗黙依存
- バイト列と文字列の変換
- Base16、Base32、Base64 等の変換規則
- 未知フィールド、未知タイプ、未知バージョン
- fixture、テストベクトルとの一致
- SDK 固有表現の外部形式への漏出
- Symbol と NEM、Mainnet と Testnet の取り違え

仕様で選択されていないエンコード方式や互換方式を新たに採用するよう要求しない。外部結果が仕様どおりであれば、内部実装方式の好みを指摘しない。

## Reviewer D: ソフトウェア品質・テスト

変更範囲の実装が保守可能で、仕様上の欠陥や退行をテストで検出できるか確認する。

主な確認事項:

- 関数やクラスの責務が明らかに過大でないか
- 暗号、検証、変換、搬送、永続化の混在が具体的な欠陥を生んでいないか
- 外部入力境界と型安全性
- 外部ライブラリ依存の局所性
- エラーの握りつぶし
- 例外と期待可能な失敗の混同
- 重複実装による実際の不整合
- 不要な抽象化や過剰設計
- コメントと実装の不一致
- 公開 API の意図しない互換性破壊
- 正常系、異常系、境界値の仕様適合テスト
- 実装ロジックを複製して誤りを隠すテスト
- fixture や期待値の独立した根拠

単なる好みのリファクタリング、将来を見越した再設計、変更範囲と無関係な既存コード整理を要求してはならない。

## Review Board Chair

各 Reviewer の指摘を統合し、採否、重複統合、重大度、最終判定、レビュー結果を確定する。

議長は新しい指摘を追加しない。

各指摘について次を確認する。

- 承認済み仕様または実際のコード挙動に根拠があるか
- 今回のレビュー範囲内か
- 再現可能な不具合、脆弱性、非互換、テスト欠陥か
- 新機能や新しい仕様を要求していないか
- 一般論や好みだけの指摘ではないか
- 他 Reviewer の指摘と重複していないか
- 重大度が具体的な影響と一致しているか

根拠不足、範囲外、新規設計、予防的な将来拡張、単なる好みの指摘は採用しない。
