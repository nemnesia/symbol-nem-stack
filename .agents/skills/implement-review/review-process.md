# Review Process

必ず Phase 1、Phase 2、Phase 3 の順に実施する。内部討議は成果物へ出力しない。

## Execution Gate: Reviewer 起動の監査

トップレベルのメインエージェントである Chair は、Reviewer A、B、C、D を `multi_agent_v1__spawn_agent` の別々の逐次呼び出しで起動する。同じツール呼び出しラウンドで4件を並列発行してはならない。各呼び出しは `fork_context: false` とし、通常は `model: "gpt-5.6-luna"`、`reasoning_effort: "low"`、`service_tier: "priority"` を指定する。容量・起動エラーの場合だけ、agent_id が返っていれば該当 agent を `multi_agent_v1__close_agent` で閉じ、同じ役割を `model: "gpt-5.4"`、`reasoning_effort: "low"`、`service_tier: "priority"` で1回再起動する。返却された最終4件の `agent_id` を役割に対応付けて保存し、4件すべてが存在し相互に異なることを確認できた場合だけ Phase 1 に進む。欠落、重複、再試行後の起動失敗、ツール利用不可の場合は、代替起動や自己レビューを行わず中止し、レビュー結果を生成または更新しない。

## Phase 1: Individual Review

Reviewer A〜D は互いの意見を参照せず、担当観点とレビュー対象を独立して確認する。Chair は各サブエージェントへ `multi_agent_v1__wait_agent` を個別に実行し、4件すべての Phase 1 完了とメモ返却を確認する。容量・起動エラーだけは上記の代替モデルで1回だけ再試行できる。再試行後を含め、1件でも失敗、タイムアウト、未完了、メモ未返却なら Phase 2 と Phase 3 を実施せず、レビュー結果を生成または更新しない。承認済み仕様、実装、テストおよび必要な関連資料を、担当観点に必要な範囲で照合する。

各指摘は仮 ID（`A-001`、`B-001`、`C-001`、`D-001`）を付け、次をすべて含める。

- 重大度（Critical、Major、Minor）
- 問題と対象箇所
- 根拠の種別と参照箇所
- 発生条件
- 放置した場合の影響
- 必要な修正または確認

指摘を作る前に、次の最小十分性チェックを行う。

1. 承認済み仕様のどの要求・制約・判断原則に関係するか。
2. 指摘を採用しなくても、現在の対象範囲を安全に実装・検証できるか。
3. 指摘は欠陥の修正か、それとも新しい機能・制約・設計の追加か。
4. 「将来必要かもしれない」「一般に望ましい」「より安全・柔軟になる」だけが根拠になっていないか。

1 の根拠を示せず、かつ 2 が「できる」、または 3 が新規追加、または 4 に該当する場合、その指摘は作成しない。

根拠の種別は「実装コードまたは差分」「テストまたは fixture」「承認済み仕様」「プロトコル仕様」「公式実装・スキーマ」「公式 SDK」「ユーザー提供資料またはプロジェクト資料」のいずれかとする。未確認事項は未確認と明記し、外部事実を断定しない。

## Phase 2: Review Board Discussion

Phase 1 の終了後に限り、各 Reviewer は他の指摘を評価できる。評価は賛成、条件付き賛成、反対のいずれかとし、反対または条件付き賛成には根拠不足、範囲外、後工程で決める事項、重大度不適切などの理由を添える。

Chair は Phase 1 の全メモを、起動時と同じ Reviewer A、B、C、D の `agent_id` へ `multi_agent_v1__send_input` で個別に送信し、各返却 `submission_id` を保存する。その後、各送信の完了を `multi_agent_v1__wait_agent` で確認する。4件すべての完了を確認できない場合は Phase 3 へ進まず、レビュー結果を生成または更新しない。

討議の目的は指摘を増やすことではなく、根拠と影響が十分な指摘へ絞り込むことである。各指摘を採用、却下、または重大度変更として確定する。次の場合は却下する。

- 問題、根拠、発生条件、影響、必要な修正または確認を説明できない。
- 個人的好み、推測、具体的な実装方式、または後工程だけで決められる事項である。
- 確認済みの根拠と矛盾する。
- 承認済み仕様にない新しい要求、機能、制約、防御、互換性を追加する提案である。
- 現在のスコープを満たすためには不要な将来拡張、汎用化、抽象化、運用機能の追加である。
- 問題の解消条件ではなく、Reviewer が好む解決方式を要求している。

指摘の一部だけが有効で、一部が過剰設計なら、過剰な部分を削除して既存仕様を満たすための最小条件だけを残す。

## Phase 3: Chair Decision

Review Board Chair は、承認済み仕様、実装、テスト、確認された関連資料および討議で採用された指摘を用いて品質ゲートを適用する。4つの `agent_id`、Phase 1・Phase 2 の `multi_agent_v1__wait_agent` による完了、Chair の統合完了を確認し、成果物の `Execution Audit` に記録する。これらを確認できない場合はレビュー結果を生成または更新しない。新しい指摘は追加せず、根拠不足の指摘は採用しない。

採用前に Chair は各指摘へ最終的な Anti-Overdesign Check を適用する。

- この指摘がなくても既存仕様を実装・検証できるなら、原則として却下する。
- 修正内容が新しい設計を指定している場合、必要条件だけへ縮小できなければ却下する。
- 既存スコープ外の将来ケースだけを解決する指摘は却下する。
- より高度な安全性・柔軟性・拡張性を得るだけの指摘は却下する。

採用指摘を統合し、過去指摘との同一性を確認したうえで正式 ID（`IR-001` からの同一レビュー対象・成果物ベース名単位の連番）と状態を付与する。今回初めて確認した指摘は `New`、未解決の過去指摘は `Open`、一度 `Resolved` または `Deferred` とした同一指摘が再発・未解消と確認された場合は `Reopened`、対応済みの過去指摘は `Resolved`、後工程へ引き継ぐ指摘は `Deferred` とする。既存指摘を状態変更なく再確認した場合も、同じIDを保持する。重大度は次のとおりとする。

- Critical: 品質ゲートを不合格にし、実装の継続、マージまたはリリースを妨げる問題。
- Major: 品質ゲートは満たすが、現在の対象範囲で仕様適合性、安全性、相互運用性または検証可能性に具体的な問題があるため修正を推奨する問題。
- Minor: 既存仕様または変更範囲内の実装・テストの明確性、保守性、検証可能性に関する小さな具体的欠陥。新機能や将来拡張の提案には使用しない。

すべての品質ゲートが合格なら「公開可能」、1つでも不合格なら「修正後に再レビュー」と判定し、`output-format.md` に従って指定された出力先へレビュー結果を保存する。
