# Review Process

## Phase 1: 独立レビュー

Reviewer A〜D は互いの指摘を参照せず、それぞれの担当観点から独立して指摘候補を作成する。

各指摘候補には最低限次を含める。

- 対象ファイルと行
- 根拠となる仕様またはコード上の事実
- 発生条件
- 具体的な影響
- 重大度候補
- 最小限の修正方針
- 必要なら追加テスト

指摘候補がない場合は無理に作らない。

## Phase 2: 相互評価

各 Reviewer は他 Reviewer の指摘候補を評価する。

- `SUPPORT`: 根拠と影響が妥当
- `CHALLENGE`: 根拠不足、影響の誇張、仕様範囲外、または修正要求が過剰
- `DUPLICATE`: 他の指摘と同一原因

反論によって根拠または影響を維持できない指摘は採用候補から除外する。

討議ログ、個々の投票、却下理由、内部思考過程はレビュー成果物へ出力しない。

## Phase 3: 議長判定

Review Board Chair が Phase 1 と Phase 2 の結果から採用指摘を確定する。

1. 範囲外指摘を除外する。
2. 新機能、新仕様、将来拡張を要求する指摘を除外する。
3. 重複指摘を統合する。
4. 根拠と影響から重大度を確定する。
5. 採用指摘だけをレビュー結果へ記載する。
6. `review-gates.md` を適用して最終判定を決定する。
7. `output-format.md` に従って成果物を保存する。

## 差分レビュー

Pull Request やコミット差分でも、欠陥の判定に必要な範囲では呼び出し元と呼び出し先を確認する。

必要に応じて確認するもの:

- 変更された関数の呼び出し元
- 変更された型を利用するコード
- 公開 API の利用箇所
- 既存 fixture
- エラー処理
- 永続化形式
- エンコードとデコードの対になる処理
- 環境別実装
- Symbol と NEM の別実装
- Mainnet と Testnet の設定

変更されていない既存コードでも、今回の変更によって直接影響を受ける場合は指摘できる。変更と無関係な広範囲のリファクタリングや既存問題の一斉修正は要求しない。

## テストレビュー

テスト件数ではなく、仕様上のリスクを検出できるかを評価する。

対象仕様に該当する場合、正常系、異常系、境界値、改ざん検出、不正署名、不正認証タグ、期限切れ、リプレイ、未知バージョン、サイズ超過、不正エンコード、チェーン・ネットワーク差異、決定的エンコード、fixture、相互運用性を確認する。

テスト項目に存在するという理由だけで、仕様にない本番機能や制約を要求してはならない。

特に次を疑う。

- 実装コードと同じロジックで期待値を生成している
- 例外が発生しただけで合格としている
- 仕様で定義されたエラー種類を確認していない
- モックが確認対象のプロトコル制約を再現していない
- fixture の出典や生成方法が不明
- 分岐を通過するだけで結果を検証していない
- スナップショットだけで暗号処理を検証している

テスト成功だけで実装を正しいと判断しない。
