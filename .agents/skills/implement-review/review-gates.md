# Review Gates

## 重大度

### `BLOCKER`

次のように、マージまたはリリースを許容できない問題。

- 資産喪失につながる
- 秘密鍵、ニーモニック、パスワードが漏えいする
- 不正な署名やトランザクションを受理する
- 正しいデータを誤って署名する
- 実装が承認済み仕様と根本的に異なる
- データ破損や互換性破壊が確実に発生する
- 実装の正当性を判断できない重大な仕様欠落がある

### `HIGH`

本番投入前に修正が必要な問題。

- 仕様で防止すべき改ざん、リプレイ、取り違えが可能
- 複数実装間で互換性が失われる
- Mainnet で誤動作する可能性がある
- 認証や認可を回避できる
- 異常入力で不正状態へ遷移する
- 暗号処理の前提が破られている
- 仕様で要求された重要な検証が不足している

### `MEDIUM`

原則としてマージ前に修正する問題。

- 仕様上必要な境界値や異常系の扱いが不十分
- エラー分類が不正確
- 変更範囲内に具体的な保守上の欠陥がある
- テスト不足により重要な退行を検出できない
- 仕様上要求された性能・DoS 耐性を満たさない

### `LOW`

機能の正当性を直接損なわないが、具体的な保守・理解上のリスクがある問題。

### `NIT`

動作や安全性へ影響しない軽微な提案。スタイル上の好みだけで大量に作成しない。

## 最終判定

- `APPROVE`: マージを妨げる採用指摘がない
- `APPROVE WITH COMMENTS`: `LOW` または `NIT` のみ
- `REQUEST CHANGES`: `HIGH` またはマージ前修正が必要な `MEDIUM` が存在する
- `BLOCK`: `BLOCKER` が存在する

## Gate 適用原則

- 重大度はカテゴリ名ではなく、具体的な発生条件と影響で決める。
- セキュリティという理由だけで重大度を上げない。
- 可読性や好みをセキュリティ問題として誇張しない。
- 仕様範囲外の提案は重大度を付けず却下する。
- 仕様自体が未決定で実装の正否を判断できない場合は、コード欠陥と仕様欠落を分離する。
- Review Board Chair は新しい指摘を追加して判定を悪化させてはならない。
