# Output Format

Review Board Chair は採用された指摘だけをレビュー結果へ記載する。Phase 1/2 の個別指摘、討議ログ、投票、反論、却下理由、内部思考過程は出力しない。

## レビュー結果ファイル

ユーザーまたは呼び出し元が出力先を指定した場合はそのパスを使用する。指定がない場合はリポジトリルートの `.reviews/blockchain-code-review.md` を使用する。

同じ対象の再レビューでは同じファイルを更新し、古い判定や解消済み指摘を現在の結果と混同させない。

レビュー対象の実装、仕様書、fixture、テストは変更しない。レビュー結果ファイルだけを作成または更新する。

## メタデータ

```markdown
# コードレビュー結果

- 対象: <レビューしたファイル、差分、コミットまたはPull Request>
- レビュー日時: <ISO 8601形式>
- 判定: <APPROVE | APPROVE WITH COMMENTS | REQUEST CHANGES | BLOCK>
- レビュー範囲: <確認した範囲>
- 未確認範囲: <未確認事項。なければ「なし」>
```

## 1. 判定

`review-gates.md` に従った判定と、その理由を簡潔に記載する。

## 2. 重大な指摘

`BLOCKER`、`HIGH`、`MEDIUM` の順でまとめる。

| 重要度 | 場所 | 問題 | 影響 | 修正方針 |
| ------ | ---- | ---- | ---- | -------- |

問題がない場合は存在しないことを明示する。

## 3. 詳細レビュー

各採用指摘を次の形式で記載する。

```markdown
#### `[重要度] 指摘タイトル`

- 対象:
- 根拠:
- 問題:
- 発生条件:
- 影響:
- 修正方針:
- 追加テスト:
```

修正方針は欠陥を解消する最小範囲に限定し、新機能や大規模リファクタリングを混ぜない。

## 4. 仕様適合状況

- 適合している要件
- 不適合の要件
- 実装されていない要件
- 仕様が曖昧で判定できない要件

## 5. テスト評価

- 十分に検証されている範囲
- 不足しているテスト
- fixture または適合テストの問題
- 実行されていない検証

## 6. 残存リスク

修正後も残る可能性があるリスク、外部確認が必要な事項、仕様上の未決定事項を示す。

新しい機能や追加対策の提案一覧にはしない。

## 7. 推奨確認コマンド

リポジトリで実際に利用可能な場合だけ記載する。

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

実際に実行していないコマンドを実行済みとして報告しない。

## チャットでの最終報告

- 最終判定
- 重要度別の採用指摘件数
- 作成または更新したレビュー結果ファイルのパス

指摘全文はレビュー結果ファイルを正本とし、チャットへ重複掲載する必要はない。
