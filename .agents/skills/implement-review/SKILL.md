# Implementation Review Board

実装を設計・書き直すのではなく、承認済み仕様を正しく実装できているかを判定する。完璧さや軽微な指摘の解消を目的にレビューを継続してはならない。

## 対象と成果物

- レビュー対象は、ユーザーが明示した実装コード、テスト、差分、コミットまたは Pull Request とする。
- 対象の指定がない場合は、推測で選ばず対象を確認して終了する。
- 実装コード、テスト、承認済み仕様および必要な技術資料を照合し、複数の独立した Reviewer と Review Board Chair で判定する。
- レビュー結果の出力先と公開範囲は `output-format.md` に従う。実装、仕様書、fixture、テストは変更しない。

## 実行順序

1. `reviewers.md` を読む。
2. `review-process.md` を読む。
3. `review-gates.md` を読む。
4. `output-format.md` を読む。
5. 定められた Phase 1 から Phase 3 を実施し、成果物を生成する。

討議ログ、個々の投票、反論、却下理由、内部思考過程は成果物へ含めない。

## 共通原則

- レビューの目的は、承認済み仕様に対する実装の欠陥、脆弱性、非互換またはテスト欠陥の検出であり、新しい要求、機能、制約、設計原則を追加することではない。
- 実装者の意図や説明ではなく、実際のコード、テスト、承認済み仕様および確認済み資料を根拠とする。
- 仕様本文、コード、テスト、プロトコル仕様、公式実装・スキーマ、SDK、既存コードおよびサンプルコードを根拠の種別として区別する。未確認の事実、推測、好みを事実として扱わない。
- 技術的記述が競合する場合は、対象機能の承認済み仕様、Architecture Decision Record、対象バージョンのプロトコル仕様、公式実装またはスキーマ、公式 SDK、リポジトリ内の技術知識ベース、既存コード、サンプルコードの順に確認する。
- 下位資料は、仕様に記載された動作の実装方法を確認するために使用する。下位資料に存在するという理由だけで、仕様にない機能や制約をレビュー要求へ昇格させない。
- 変更差分だけで判断できない場合は、必要な範囲で呼び出し元・呼び出し先を確認する。
- 変更と無関係な既存問題や大規模リファクタリングを要求しない。
- テスト成功だけで実装を正しいと判断しない。
- 暗号ライブラリや公式 SDK を使用しているだけで安全・適合と判断しない。
- 確認できないことを断定しない。
- 実行していないテストやコマンドを実行済みとしない。
- 指摘には具体的な根拠、発生条件、影響、最小限の修正方針を持たせる。
- セキュリティ問題を可読性の問題として矮小化しない。
- 可読性や好みの問題をセキュリティ問題として誇張しない。

## 実装レビューの境界

指摘を生成する前に、必ず次の境界テストを適用する。

1. その問題は、承認済み仕様への違反、または今回のレビュー範囲に含まれる実装・テストの具体的な欠陥か確認する。
2. 一般に望ましい改善、新しい仕様、将来拡張、実装方式の好みにすぎる場合は、指摘を生成しない。
3. 仕様自体の不足によって実装の正否を判定できない場合は、コード欠陥として修正を要求せず、仕様上の未決定事項として分離する。
4. 既存の要求または再現可能な欠陥に基づく指摘へ言い換えられない場合は、採用候補にしない。

次の事項は、それ自体を実装レビューの欠陥として指摘してはならない。

- 仕様にない機能、公開 API、設定、フィールド、エラー種別、フォールバック、互換機能
- 一般的なベストプラクティスだけを根拠とする新しい防御機構
- 将来必要になる可能性だけを理由とする抽象化、拡張ポイント、互換レイヤー
- 「より安全」「より柔軟」「より保守しやすい」という理由だけの仕様範囲の拡張
- 問題がないコードへの形式的な指摘

レビュー対象は「承認済み仕様を正しく実装しているか」であり、「より良い仕様を設計できるか」ではない。

## ブロックチェーン固有確認

対象仕様に該当する場合だけ、次を確認する。

- 鍵、アカウント、秘密情報
- 署名対象と署名検証
- Symbol / NEM の差異
- Mainnet / Testnet の差異
- 通常 / Embedded Transaction
- Aggregate Complete / Aggregate Bonded
- 署名者 / 連署者
- fee、deadline、network、generation hash seed
- 暗号アルゴリズム、KDF、nonce、salt、IV、AAD、authentication tag
- エンコード、正規化、整数精度、決定性

この一覧に存在すること自体を、新しい仕様要求の根拠にしてはならない。

## TypeScript 固有確認

対象コードに該当する場合だけ、型安全性、`number` の精度、`bigint`、`Buffer` / `Uint8Array`、環境依存 API、非同期例外、列挙値・定数とプロトコル値の一致を確認する。

これらの確認から、仕様にない対応環境や新しい API を要求してはならない。
