# ブロックチェーンコードレビュー

実装コード、テスト、承認済み仕様、必要な技術資料を照合し、実装が仕様どおりで安全かつ相互運用可能かを複数の独立した Reviewer と Review Board Chair で判定する。

レビューは新機能、新しい制約、新しい防御機構、新しい抽象化を考案する場ではない。

## レビュー範囲の境界

すべての Reviewer は次を厳守する。

- 仕様にない機能を追加するよう要求しない
- 仕様にない公開 API、設定、フィールド、エラー種別、フォールバック、互換機能を要求しない
- 一般的なベストプラクティスだけを根拠として新しい防御機構を要求しない
- 将来必要になる可能性だけを理由に抽象化、拡張ポイント、互換レイヤーを要求しない
- 「より安全」「より柔軟」「より保守しやすい」という理由だけで仕様範囲を拡張しない
- 問題がないコードへ無理に指摘を作らない

レビュー対象は「承認済み仕様を正しく実装しているか」であり、「より良い仕様を設計できるか」ではない。

仕様自体に不足があり実装の正否を判断できない場合は、実装への修正要求として扱わず、仕様上の未決定事項として分離する。

## 根拠

実装者の意図や説明ではなく、実際のコード、テスト、承認済み仕様を根拠とする。

技術的記述が競合する場合は原則として次の順序で確認する。

1. 対象機能の承認済み仕様書
2. Architecture Decision Record
3. 対象バージョンのプロトコル仕様
4. Catapult、NIS、Catbuffer などの公式実装またはスキーマ
5. 公式 SDK
6. リポジトリ内の技術知識ベース
7. 既存コード
8. サンプルコード

下位資料は仕様に記載された動作の実装方法を確認するために使用する。下位資料に存在するという理由だけで、仕様にない機能や制約をレビュー要求へ昇格させてはならない。

## 実行順序

1. `reviewers.md` を読み、Reviewer A〜D と Review Board Chair の責務を確認する。
2. `review-process.md` を読み、Phase 1 から Phase 3 を実施する。
3. `review-gates.md` を読み、採用指摘の重大度と最終判定を確定する。
4. `output-format.md` を読み、採用された指摘だけをレビュー結果ファイルへ保存する。

討議ログ、個々の投票、反論、却下理由、内部思考過程は成果物へ含めない。

## 共通原則

- 変更差分だけで判断できない場合は、必要な範囲で呼び出し元・呼び出し先を確認する。
- 変更と無関係な既存問題や大規模リファクタリングを要求しない。
- テスト成功だけで実装を正しいと判断しない。
- 暗号ライブラリや公式 SDK を使用しているだけで安全・適合と判断しない。
- 確認できないことを断定しない。
- 実行していないテストやコマンドを実行済みとしない。
- 指摘には具体的な根拠、発生条件、影響、最小限の修正方針を持たせる。
- セキュリティ問題を可読性の問題として矮小化しない。
- 可読性や好みの問題をセキュリティ問題として誇張しない。

## ブロックチェーン固有確認

対象仕様に該当する場合だけ、次を確認する。

- 鍵、アカウント、秘密情報
- 署名対象と署名検証
- Symbol / NEM の差異
- Mainnet / Testnet の差異
- 通常 / Embedded Transaction
- Aggregate Complete / Aggregate Bonded
- 署名者 / 連署者
- fee、deadline、network、generation hash seed
- 暗号アルゴリズム、KDF、nonce、salt、IV、AAD、authentication tag
- エンコード、正規化、整数精度、決定性

この一覧に存在すること自体を、新しい仕様要求の根拠にしてはならない。

## TypeScript 固有確認

対象コードに該当する場合だけ、型安全性、`number` の精度、`bigint`、`Buffer` / `Uint8Array`、環境依存 API、非同期例外、列挙値・定数とプロトコル値の一致を確認する。

これらの確認から、仕様にない対応環境や新しい API を要求してはならない。
