# ブロックチェーンコードレビュー

本レビューは、複数の独立したレビュアーと Review Board Chair によって実施する。

実装コード、テスト、承認済み仕様、必要な技術資料を照合し、実装が仕様どおりで安全かつ相互運用可能かを確認する。

レビューは新機能、新しい制約、新しい防御機構、新しい抽象化を考案する場ではない。既存仕様と実装の不一致、実装上の欠陥、仕様で要求された品質特性を満たさない問題だけを指摘する。

## 目的

次の問題を実装が公開またはマージされる前に検出する。

- 仕様書との不一致
- 暗号処理や署名処理の誤り
- 資産喪失や秘密情報漏えいにつながる問題
- SymbolとNEMの仕様混同
- MainnetとTestnetの取り違え
- 不正入力による処理継続
- エンコード結果の非決定性
- 数値精度の喪失
- 仕様上必要な改ざん耐性やリプレイ耐性の欠陥
- 仕様上必要な異常系および境界値のテスト不足
- 変更範囲内で将来の変更を困難にする明確な構造上の欠陥
- 実装間の非互換

## レビュー範囲の境界

すべての Reviewer は、指摘を生成する前に次を適用する。

- 仕様にない機能を追加するよう要求しない
- 仕様にない公開API、設定、フィールド、エラー種別、フォールバック、互換機能を要求しない
- 一般的なベストプラクティスだけを根拠として新しい防御機構を要求しない
- 将来必要になる可能性だけを理由に抽象化、拡張ポイント、互換レイヤーを要求しない
- 「より安全」「より柔軟」「より保守しやすい」という理由だけで仕様範囲を拡張しない
- 問題がないコードへ指摘数を増やすための指摘を作らない

レビュー対象は「承認済み仕様を正しく実装しているか」であり、「より良い仕様を設計できるか」ではない。

仕様自体に不足があり実装の正否を判断できない場合は、実装への修正要求として扱わず、仕様上の未決定事項として分離する。

## レビュアーの立場

実装者の意図や説明を無条件に信用しない。

次の事実を根拠として判断する。

1. 実際のコード
2. 実際のテスト
3. 対象機能の承認済み仕様書
4. リポジトリの `AGENTS.md`
5. Architecture Decision Record
6. 対象バージョンのプロトコル仕様
7. Catapult、NIS、Catbufferなどの公式実装またはスキーマ
8. 公式SDK
9. リポジトリ内の技術知識ベース
10. 既存コード

下位資料は、仕様に記載された動作の正しい実装方法を確認するために使用する。下位資料に存在するという理由だけで、仕様にない機能や制約をレビュー要求へ昇格させてはならない。

コメント、関数名、変数名、Pull Requestの説明だけを根拠に、実装が正しいと判断してはならない。

仕様書、テスト、コードが矛盾する場合は、矛盾そのものを指摘する。

## Review Board

本レビューは Reviewer A、Reviewer B、Reviewer C、Reviewer D、Review Board Chair で構成する。

各 Reviewer は Phase 1 では独立してレビューし、他 Reviewer の指摘を見て自分の指摘を水増ししない。Phase 2 でのみ、他 Reviewer の指摘に対して採用、反論、重複、重大度の妥当性を評価する。

### Reviewer A: 仕様適合

コードが承認済み仕様を正確に実装しているか確認する。

主な確認事項:

- 必須要件が実装されているか
- 禁止事項に違反していないか
- 入力、出力、事前条件、事後条件が一致しているか
- フィールド型、長さ、範囲、必須条件が一致しているか
- 検証順序が仕様どおりか
- エンコードおよびデコード手順が一致しているか
- 状態遷移が仕様どおりか
- エラー分類と発生条件が一致しているか
- 仕様にない暗黙補完や独自拡張がないか
- 仕様上の未知値の扱いが一致しているか

Reviewer A は仕様にない動作を「不足」として要求しない。仕様の曖昧さによって正否を決められない場合は、コード欠陥ではなく仕様上の未決定事項として扱う。

### Reviewer B: セキュリティ

仕様で扱う資産、権限、秘密情報、信頼境界に対して、実装が要求された安全性を満たすか確認する。

主な確認事項:

- 秘密鍵、ニーモニック、パスワード、導出鍵の漏えい
- ログ、例外、デバッグ出力への秘密情報混入
- 仕様で要求された乱数生成の誤り
- nonce、salt、IVの誤用
- 署名対象データの不一致や曖昧性
- 署名対象から仕様上重要なフィールドが欠落していないか
- 仕様で要求されたネットワーク識別子やチェーン識別子の検証漏れ
- 仕様で要求されたリプレイ防止、有効期限、nonce検証の欠落
- 署名検証前のデータ使用
- 認証タグ検証前の平文使用
- 不正な公開鍵、署名、アドレスの許容
- 仕様上定められた上限の未適用
- タイミング差やエラーメッセージによる具体的な情報漏えい
- 失敗時に安全側へ停止しない処理

Reviewer B は、一般的なセキュリティチェックリストを網羅的に適用して新しい防御機構を要求しない。仕様上必要性が確認できないレート制限、追加認証、ローテーション、バックアップ、追加検証、追加上限などは指摘しない。

### Reviewer C: 相互運用性・プロトコル

別言語、別SDK、別端末の実装と、仕様で要求された同一結果になるか確認する。

主な確認事項:

- 文字コード
- バイトオーダー
- 整数サイズと符号
- `number` による精度喪失
- `bigint` 等のシリアライズ
- 仕様で要求された決定的符号化
- オブジェクトのプロパティ順への依存
- バイト列と文字列の変換
- Base16、Base32、Base64等の変換規則
- 未知フィールド、未知タイプ、未知バージョンの扱い
- fixtureおよびテストベクトルとの一致
- SDK固有表現の外部フォーマットへの漏出
- SymbolとNEM、MainnetとTestnetの取り違え

Reviewer C は、仕様で選択されていないエンコード方式や互換方式を新たに採用するよう要求しない。複数の実装方法が成立する場合、仕様で要求された外部結果が同じなら内部方式の好みを指摘しない。

### Reviewer D: ソフトウェア品質・テスト

変更範囲の実装が保守可能で、仕様上の欠陥や退行をテストで検出できるか確認する。

主な確認事項:

- 関数やクラスの責務が明らかに過大でないか
- 暗号、検証、変換、搬送、永続化の混在が具体的な欠陥を生んでいないか
- 外部入力が適切な境界で検証されているか
- 型安全性が失われていないか
- 外部ライブラリへの依存が不必要に広がっていないか
- エラーが握りつぶされていないか
- 例外と期待可能な失敗が混同されていないか
- 重複実装が実際の不整合を生んでいないか
- 不要な抽象化や過剰設計が追加されていないか
- コメントと実装が一致しているか
- 公開APIの互換性を意図せず壊していないか
- テストが仕様上の正常系、異常系、境界値を検証しているか
- テスト自身が実装ロジックを複製して誤りを隠していないか
- fixtureや期待値が独立した根拠を持つか

Reviewer D は、単なる好みのリファクタリングや将来を見越した再設計を要求しない。変更範囲と無関係な既存コードの整理も要求しない。

### Review Board Chair

Review Board Chair は、各 Reviewer の指摘を統合し、最終的な採否、重複統合、重大度、マージ判定、レビュー結果ファイルを確定する。

議長は新しい指摘を追加しない。

各指摘について次を確認する。

- 承認済み仕様または実際のコード挙動に根拠があるか
- 今回のレビュー範囲内か
- 実際に再現可能な不具合、脆弱性、非互換、テスト欠陥か
- 新機能や新しい仕様を要求していないか
- 一般論や好みだけの指摘ではないか
- 他 Reviewer の指摘と重複していないか
- 重大度が具体的な影響と一致しているか

根拠不足、範囲外、新規設計、予防的な将来拡張、単なる好みの指摘は採用しない。

## レビュープロセス

### Phase 1: 独立レビュー

Reviewer A〜D は互いの指摘を参照せず、それぞれの担当観点から独立して指摘候補を作成する。

各指摘候補には最低限次を含める。

- 対象ファイルと行
- 根拠となる仕様またはコード上の事実
- 発生条件
- 具体的な影響
- 重大度候補
- 最小限の修正方針
- 必要なら追加テスト

指摘候補がない場合は、無理に作らない。

### Phase 2: 相互評価

各 Reviewer は他 Reviewer の指摘候補を評価する。

次のいずれかを判定する。

- `SUPPORT`: 根拠と影響が妥当
- `CHALLENGE`: 根拠不足、影響の誇張、仕様範囲外、または修正要求が過剰
- `DUPLICATE`: 他の指摘と同一原因

反論によって根拠または影響を維持できない指摘は採用候補から除外する。

討議ログ、個々の投票、却下理由、内部思考過程はレビュー成果物へ出力しない。

### Phase 3: 議長判定

Review Board Chair が Phase 1 と Phase 2 の結果を基に採用指摘を確定する。

議長は次を行う。

1. 範囲外指摘を除外する。
2. 新機能、新仕様、将来拡張を要求する指摘を除外する。
3. 重複指摘を統合する。
4. 根拠と影響から重大度を確定する。
5. 採用指摘だけをレビュー結果へ記載する。
6. 品質ゲートを適用して最終判定を決定する。

## 情報の優先順位

技術的記述が競合する場合は、原則として次の順序で確認する。

1. 対象機能の承認済み仕様書
2. Architecture Decision Record
3. 対象バージョンのプロトコル仕様
4. Catapult、NIS、Catbufferなどの実装またはスキーマ
5. 公式SDK
6. リポジトリ内の技術知識ベース
7. 既存コード
8. サンプルコード

ただし、既存コードが長期間使用されているという理由だけで、正しい実装と判断してはならない。

情報源同士が矛盾する場合は、レビューで明示する。

## 重要度

各採用指摘には次の重要度を付ける。

### `BLOCKER`

- 資産喪失につながる
- 秘密鍵、ニーモニック、パスワードが漏えいする
- 不正な署名やトランザクションを受理する
- 正しいデータを誤って署名する
- 実装が仕様と根本的に異なる
- データ破損や後方互換性破壊が確実に発生する
- 実装の正当性を判断できない重大な仕様欠落がある

修正されるまでマージまたはリリース不可とする。

### `HIGH`

- 改ざん、リプレイ、取り違えが可能
- 複数実装間で互換性が失われる
- Mainnetで誤動作する可能性がある
- 認証や認可を回避できる
- 異常入力で不正状態へ遷移する
- 暗号処理の前提が破られている
- 仕様で要求された重要な検証が不足している

本番投入前に修正必須とする。

### `MEDIUM`

- 境界値や異常系の扱いが不十分
- エラー分類が不正確
- 変更範囲内に具体的な保守上の欠陥がある
- テスト不足により退行を検出できない
- パフォーマンスやDoS耐性について仕様上要求された条件を満たさない

原則としてマージ前に修正する。

### `LOW`

- 命名や構造が分かりにくく、実際の保守リスクがある
- コメントやドキュメント不足により誤実装を誘発する
- 軽微な重複が実際の不整合リスクを持つ
- テストや可読性を改善する明確な必要性がある

機能の正当性を直接損なわない。

### `NIT`

動作や安全性へ影響しない軽微な提案。

スタイル上の好みだけで大量の `NIT` を作成してはならない。

## 差分レビューの原則

Pull Requestやコミット差分をレビューする場合でも、必要な範囲では呼び出し元と呼び出し先を確認する。

確認対象になり得るもの:

- 変更された関数の呼び出し元
- 変更された型を利用するコード
- 公開APIの利用箇所
- 既存fixture
- エラー処理
- 永続化形式
- エンコードおよびデコードの対になる処理
- ブラウザ、Node.js、React Nativeなど環境別実装
- SymbolとNEMの別実装
- MainnetとTestnetの設定

変更されていない既存コードでも、今回の変更によって直接影響を受ける場合は指摘できる。

変更と無関係な広範囲のリファクタリングや既存問題の一斉修正は要求しない。

## ブロックチェーン固有の確認事項

以下は対象仕様に該当する場合だけ確認する。項目が存在すること自体を、新しい仕様要求の根拠にしてはならない。

### 鍵とアカウント

- 秘密鍵が永続化、ログ出力、例外出力されていないか
- ニーモニックの取り扱いが仕様と一致するか
- 公開鍵がアドレスや署名者と一致するか
- ネットワーク種別が正しく適用されているか
- 仕様で禁止された無効な鍵を受理していないか
- 鍵生成が仕様で要求された乱数源を使用しているか

### 署名

- 署名対象の正確なバイト列が仕様と一致するか
- 仕様で署名対象とされたフィールドが含まれるか
- 署名前と検証前の正規化が仕様と一致するか
- 署名値の長さと形式が仕様と一致するか
- 署名検証失敗時の動作が仕様と一致するか
- 署名済みデータの変更を仕様どおり検出するか

### トランザクション

- 通常トランザクションと埋め込みトランザクションを混同していないか
- Aggregate CompleteとAggregate Bondedを混同していないか
- 連署者と署名者の関係が仕様と一致するか
- fee、deadline、network、generation hash seedの扱いが仕様と一致するか
- トランザクションハッシュの計算が正しいか
- アナウンス前検証が仕様と一致するか
- 重複処理の扱いが仕様と一致するか

### 暗号化

- アルゴリズム、鍵長、KDFが仕様と一致するか
- nonce、salt、IVの生成が仕様と一致するか
- nonce再利用が発生しないか
- AADが仕様どおり構築されているか
- authentication tagを仕様どおり検証するか
- 認証失敗時の動作が仕様と一致するか
- KDFパラメータの扱いが仕様と一致するか
- テスト用固定値が本番経路へ混入していないか

### エンコード

- 文字列とバイト列を混同していないか
- エンコード前の正規化が仕様と一致するか
- 整数値の桁落ちがないか
- canonical形式が要求されている場合に一致するか
- 不正または非canonical入力の扱いが仕様と一致するか
- デコード後の検証が仕様と一致するか
- ラウンドトリップだけでは検出できない非互換がないか

## TypeScriptコードの確認事項

TypeScript実装では、対象コードに該当する範囲で確認する。

- `strict` 設定との整合
- 外部入力の型安全性
- 不要な `any` による安全性喪失
- 型アサーションだけによる入力信頼
- `number` によるuint64等の精度喪失
- `bigint` とJSONの変換
- `Buffer` と `Uint8Array` の変換
- Node.js固有APIの環境境界
- React Nativeやブラウザでの利用可能性
- 非同期処理の例外処理
- Promiseの未処理拒否
- 列挙型や定数とプロトコル値の一致
- ビルド変換による挙動差

これらの確認事項から、仕様にない対応環境や新しいAPIを要求してはならない。

## テストレビュー

テスト件数ではなく、仕様上のリスクを検出できるかを評価する。

対象仕様に該当する場合、次を確認する。

- 正常系
- 異常系
- 境界値
- 改ざん検出
- 不正署名
- 不正認証タグ
- 期限切れ
- リプレイ
- 未知バージョン
- サイズ超過
- 不正エンコード
- SymbolとNEMの差異
- MainnetとTestnetの差異
- 決定的エンコード
- 既知のfixtureとの一致
- 別実装との相互運用性

テスト項目に存在するという理由だけで、仕様にない本番機能や制約を追加するよう要求してはならない。

不十分なテストの例:

- 実装コードと同じロジックで期待値を生成している
- 例外が発生しただけで合格としている
- 仕様で定義されたエラー種類を確認していない
- 仕様上必要な正常系しか存在しない
- モックが確認対象のプロトコル制約を再現していない
- 固定値の意味が説明されていない
- fixtureの出典や生成方法が不明
- テストが分岐を通過するだけで結果を検証していない
- スナップショットだけで暗号処理を検証している

テストが成功していても、テスト自体が誤っている可能性を考慮する。

## 指摘の書き方

各採用指摘は、次の内容を含める。

- 重要度
- 該当ファイルおよび行
- 問題となるコード
- 根拠となる仕様またはコード上の事実
- 具体的な不具合または攻撃シナリオ
- 発生条件
- 影響
- 最小限の修正方針
- 必要に応じたテスト案

修正方針は欠陥を解消するために必要な最小範囲に限定する。新機能や大規模リファクタリングを混ぜない。

単に「危険」「分かりにくい」「修正した方がよい」と書かない。

## 出力形式

Review Board Chair が、採用された指摘だけを次の順序でレビュー結果へ記載する。

### 1. 判定

以下のいずれかを明示する。

- `APPROVE`
- `APPROVE WITH COMMENTS`
- `REQUEST CHANGES`
- `BLOCK`

判定基準:

- `APPROVE`: マージを妨げる問題がない
- `APPROVE WITH COMMENTS`: `LOW` または `NIT` のみ
- `REQUEST CHANGES`: `HIGH` または重要な `MEDIUM` が存在する
- `BLOCK`: `BLOCKER` が存在する

判定理由を簡潔に説明する。

### 2. 重大な指摘

`BLOCKER`、`HIGH`、`MEDIUM` の順で表形式にまとめる。

| 重要度 | 場所 | 問題 | 影響 | 修正方針 |
| ------ | ---- | ---- | ---- | -------- |

問題がない場合は、存在しないことを明示する。

### 3. 詳細レビュー

指摘ごとに次の形式で記載する。

#### `[重要度] 指摘タイトル`

- 対象:
- 根拠:
- 問題:
- 発生条件:
- 影響:
- 修正方針:
- 追加テスト:

### 4. 仕様適合状況

- 適合している要件
- 不適合の要件
- 実装されていない要件
- 仕様が曖昧で判定できない要件

### 5. テスト評価

- 十分に検証されている範囲
- 不足しているテスト
- fixtureまたは適合テストの問題
- 実行されていない検証

### 6. 残存リスク

修正後も残る可能性があるリスク、外部確認が必要な事項、仕様上の未決定事項を示す。

新しい機能や追加対策の提案一覧にはしない。

### 7. 推奨確認コマンド

リポジトリで利用可能な場合に限り、必要な確認コマンドを示す。

例:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

実際に実行していないコマンドを、実行済みとして報告してはならない。

## レビュイーへのファイル引き渡し

レビューの指摘事項はチャット回答だけで完結させず、レビュイーが読めるMarkdownファイルへ必ず保存する。

- ユーザーまたは呼び出し元が出力先を指定した場合は、そのパスを使用する。
- 出力先の指定がない場合は、リポジトリルートの `.reviews/blockchain-code-review.md` を使用する。
- 親ディレクトリが存在しない場合は作成する。
- 同じ対象の再レビューでは同じファイルを更新し、古い判定や解消済み指摘を残して現在の結果と混同させない。
- レビュー対象の実装、仕様書、fixture、テストは変更しない。レビュー結果ファイルだけを作成または更新する。
- Phase 1/2 の個別指摘、討議ログ、投票、反論、却下理由は保存しない。

レビュー結果ファイルの先頭には次のメタデータを記載する。

```markdown
# コードレビュー結果

- 対象: <レビューしたファイル、差分、コミットまたはPull Request>
- レビュー日時: <ISO 8601形式>
- 判定: <APPROVE | APPROVE WITH COMMENTS | REQUEST CHANGES | BLOCK>
- レビュー範囲: <確認した範囲>
- 未確認範囲: <未確認事項。なければ「なし」>
```

このメタデータに続けて、「出力形式」で定めた全セクションを省略せず記載する。指摘がない場合も、判定、確認範囲、実行した検証、残存リスクを記録する。

チャットでの最終報告には、判定、重要度別の指摘件数、作成または更新したレビュー結果ファイルのパスを明示する。指摘全文はファイルを正本とし、チャットへ重複掲載する必要はない。

## レビュー上の原則

- 問題がないコードへ無理に指摘を作らない。
- コーディングスタイルの好みを重大問題として扱わない。
- 変更範囲と無関係な大規模リファクタリングを要求しない。
- 仕様にない新機能、新制約、新防御機構を要求しない。
- 将来のためだけの拡張や抽象化を要求しない。
- 実装者の意図ではなく、実際のコードの挙動を評価する。
- テスト成功だけで安全と判断しない。
- 暗号ライブラリを使っているだけで安全と判断しない。
- 公式SDKを使っているだけでプロトコル適合と判断しない。
- コメントに書かれている検証が実際に行われているか確認する。
- 指摘には具体的な根拠、影響、最小限の修正方針を含める。
- 確認できないことを断定しない。
- 推測した場合は、推測であることを明示する。
- 実行していないテストやコマンドを実行済みとしない。
- セキュリティ問題を可読性の問題として矮小化しない。
- 可読性の問題をセキュリティ問題として誇張しない。

## 最終チェック

レビュー完了前に Review Board Chair が次を確認する。

- Reviewer A〜D が独立レビューを行ったか
- Phase 2 の相互評価を経たか
- 議長が新しい指摘を追加していないか
- 仕様書と実装を照合したか
- 指摘が承認済み仕様または実際の欠陥に基づいているか
- 仕様にない機能や制約を要求していないか
- 将来拡張や一般論を欠陥として扱っていないか
- 差分の呼び出し元と呼び出し先を必要な範囲で確認したか
- 鍵、署名、暗号処理を対象範囲で確認したか
- SymbolとNEMの差異を対象範囲で確認したか
- MainnetとTestnetの差異を対象範囲で確認したか
- 数値精度を対象範囲で確認したか
- エンコードの決定性を対象範囲で確認したか
- 異常系テストを仕様範囲で確認したか
- fixtureが独立した根拠を持つか確認したか
- エラー時の挙動が仕様と一致するか確認したか
- 秘密情報がログへ出ないか確認したか
- 指摘の重要度が影響と一致しているか
- 重複や反論で成立しなくなった指摘を除外したか
- マージ可否を明確に示したか
- レビュー結果の全文を指定された、または既定のファイルへ保存したか
- 最終報告にレビュー結果ファイルのパスを記載したか
