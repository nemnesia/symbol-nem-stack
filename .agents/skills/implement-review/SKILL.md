# Implementation Review Board

実装を設計・書き直すのではなく、承認済み仕様を正しく実装できているかを判定する。完璧さや軽微な指摘の解消を目的にレビューを継続してはならない。

## 対象と成果物

- レビュー対象は、ユーザーが明示した実装コード、テスト、差分、コミットまたは Pull Request とする。
- 対象の指定がない場合は、推測で選ばず対象を確認して終了する。
- 実装コード、テスト、承認済み仕様および必要な技術資料を照合し、複数の独立した Reviewer と Review Board Chair で判定する。
- レビュー結果の出力先と公開範囲は `output-format.md` に従う。既定の出力先は対象実装のソースコードがある `<source-root>/docs/reviews/implementation/` とし、リポジトリルートへ固定しない。実装、仕様書、fixture、テストは変更しない。
- レビュー結果は、対象実装のベース名に `-review-001.md` 形式の3桁連番を付加した新規ファイルとして作成する。既存の固定名 `implement-review.md`、`-review.md`、`-review-findings.md` および既存の連番成果物は移動・削除・上書きしない。
- 連番は同一レビュー対象と成果物ベース名ごとに管理する。過去レビュー成果物（固定名の旧形式を含む）から正式な `IR-<番号>` を抽出し、新規指摘には最大番号の次を割り当てる。同一問題であることを確認できる既存指摘は同じIDを引き継ぎ、新規指摘へ過去IDを再利用しない。各正式指摘には `New`、`Open`、`Resolved`、`Deferred`、`Reopened` のいずれかの状態を付ける。`Required Changes` と `Optional Improvements` には現在対応が必要な指摘を、`Resolved Findings` には対応済み指摘と確認根拠を、必要に応じて `Deferred Findings` には後工程へ引き継いだ指摘を整理する。

## 実行主体と実行順序

1. `reviewers.md` を読む。
2. `review-process.md` を読む。
3. `review-gates.md` を読む。
4. `output-format.md` を読む。
5. トップレベルのメインエージェントが Review Board Chair として、Reviewer A、B、C、D をそれぞれ独立したサブエージェントとして起動する。
6. 起動監査に合格した場合だけ、定められた Phase 1 から Phase 3 を実施し、Chair が成果物を生成する。

### 容量エラーに対する起動方針

- 4つの `spawn_agent` は同じツール呼び出しラウンドで並列発行せず、A、B、C、D の順に1件ずつ発行する。各呼び出しの返却を確認してから次を起動する。
- Reviewer は短い担当メモを返す役割であるため、通常は各起動に `model: "gpt-5.6-luna"`、`reasoning_effort: "low"`、`service_tier: "priority"` を指定する。これは本スキルの容量制限回避という明確な理由に基づくモデル指定であり、レビュー観点や独立性を変更しない。
- `spawn_agent` が容量・一時的なサービスエラーを返した場合、または起動した agent が Phase 1 の `wait_agent` で容量・起動エラーになった場合は、agent_id が返っていれば該当 agent を `close_agent` で閉じ、同じ役割を1回だけ `model: "gpt-5.4"`、`reasoning_effort: "low"`、`service_tier: "priority"` で再起動する。agent_id が返っていない起動失敗では閉じる操作を省略する。再試行は無制限に行わない。
- 再試行を含めて4役すべての起動と Phase 1 の完了を確認できない場合は、自己レビューや役割の統合を行わず中止する。失敗した起動を成功した `agent_id` として監査記録へ残してはならない。

## 監査可能な起動要件

- Reviewer A、B、C、D は、トップレベルのメインエージェントが `multi_agent_v1__spawn_agent` を4回の別々の逐次呼び出しで実行して起動する。各呼び出しは `fork_context: false` とし、役割ごとに独立した初期コンテキストを渡す。通常モデル、推論負荷、サービス層、および容量・起動エラー時の1回限りの代替モデルは「容量エラーに対する起動方針」に従う。
- このスキルを実行するトップレベルのメインエージェント自身が起動オーケストレーターであり、サブエージェントにスキル全体の再委譲をさせない。サブエージェントは担当レビューのメモだけを返し、ファイルを編集しない。
- 各呼び出しから返された `agent_id` を役割に対応付け、Phase 1 の開始前に4件すべてが存在し、相互に異なることを確認する。1件でも欠落、重複、起動未確認があれば直ちに中止し、レビュー成果物を生成しない。
- Phase 1 は各 `agent_id` に対して `multi_agent_v1__wait_agent` で完了を個別に確認する。容量・起動エラーだけは起動方針に従って1回だけ再試行できる。再試行後を含め、失敗、タイムアウト、未完了、またはメモ未返却が1件でもあれば Phase 2 以降へ進まず、成果物を生成しない。
- Phase 2 は Phase 1 の全メモを、起動時と同じ4つの `agent_id` へ `multi_agent_v1__send_input` で個別に送信する。返された `submission_id` を保存し、各送信に対応する `multi_agent_v1__wait_agent` の完了を確認する。別エージェントへの差し替えや単一エージェントへの代替をしない。
- `multi_agent_v1__spawn_agent`、`multi_agent_v1__send_input`、`multi_agent_v1__wait_agent` が利用できない場合に、メインエージェントの自己レビューへフォールバックしない。起動・完了を監査できないため、中止してその理由だけを報告する。
- Chair は、4つの `agent_id`、Phase 1 と Phase 2 の完了確認、Chair による統合完了を `Execution Audit` に記録できる場合だけ、指定されたレビュー結果ファイルを生成または更新する。プロンプト、討議内容、思考過程は記録しない。

討議ログ、個々の投票、反論、却下理由、内部思考過程は成果物へ含めない。

## 共通原則

- レビューの目的は、承認済み仕様に対する実装の欠陥、脆弱性、非互換またはテスト欠陥の検出であり、新しい要求、機能、制約、設計原則を追加することではない。
- 実装者の意図や説明ではなく、実際のコード、テスト、承認済み仕様および確認済み資料を根拠とする。
- 仕様本文、コード、テスト、プロトコル仕様、公式実装・スキーマ、SDK、既存コードおよびサンプルコードを根拠の種別として区別する。未確認の事実、推測、好みを事実として扱わない。
- 技術的記述が競合する場合は、対象機能の承認済み仕様、Architecture Decision Record、対象バージョンのプロトコル仕様、公式実装またはスキーマ、公式 SDK、リポジトリ内の技術知識ベース、既存コード、サンプルコードの順に確認する。
- 下位資料は、仕様に記載された動作の実装方法を確認するために使用する。下位資料に存在するという理由だけで、仕様にない機能や制約をレビュー要求へ昇格させない。
- 変更差分だけで判断できない場合は、必要な範囲で呼び出し元・呼び出し先を確認する。
- 変更と無関係な既存問題や大規模リファクタリングを要求しない。
- テスト成功だけで実装を正しいと判断しない。
- 暗号ライブラリや公式 SDK を使用しているだけで安全・適合と判断しない。
- 確認できないことを断定しない。
- 実行していないテストやコマンドを実行済みとしない。
- 指摘には具体的な根拠、発生条件、影響、最小限の修正方針を持たせる。
- セキュリティ問題を可読性の問題として矮小化しない。
- 可読性や好みの問題をセキュリティ問題として誇張しない。

## 実装レビューの境界

指摘を生成する前に、必ず次の境界テストを適用する。

1. その問題は、承認済み仕様への違反、または今回のレビュー範囲に含まれる実装・テストの具体的な欠陥か確認する。
2. 一般に望ましい改善、新しい仕様、将来拡張、実装方式の好みにすぎる場合は、指摘を生成しない。
3. 仕様自体の不足によって実装の正否を判定できない場合は、コード欠陥として修正を要求せず、仕様上の未決定事項として分離する。
4. 既存の要求または再現可能な欠陥に基づく指摘へ言い換えられない場合は、採用候補にしない。

次の事項は、それ自体を実装レビューの欠陥として指摘してはならない。

- 仕様にない機能、公開 API、設定、フィールド、エラー種別、フォールバック、互換機能
- 一般的なベストプラクティスだけを根拠とする新しい防御機構
- 将来必要になる可能性だけを理由とする抽象化、拡張ポイント、互換レイヤー
- 「より安全」「より柔軟」「より保守しやすい」という理由だけの仕様範囲の拡張
- 問題がないコードへの形式的な指摘

レビュー対象は「承認済み仕様を正しく実装しているか」であり、「より良い仕様を設計できるか」ではない。

## ブロックチェーン固有確認

対象仕様に該当する場合だけ、次を確認する。

- 鍵、アカウント、秘密情報
- 署名対象と署名検証
- Symbol / NEM の差異
- Mainnet / Testnet の差異
- 通常 / Embedded Transaction
- Aggregate Complete / Aggregate Bonded
- 署名者 / 連署者
- fee、deadline、network、generation hash seed
- 暗号アルゴリズム、KDF、nonce、salt、IV、AAD、authentication tag
- エンコード、正規化、整数精度、決定性

この一覧に存在すること自体を、新しい仕様要求の根拠にしてはならない。

## TypeScript 固有確認

対象コードに該当する場合だけ、型安全性、`number` の精度、`bigint`、`Buffer` / `Uint8Array`、環境依存 API、非同期例外、列挙値・定数とプロトコル値の一致を確認する。

これらの確認から、仕様にない対応環境や新しい API を要求してはならない。
