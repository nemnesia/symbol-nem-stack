# 実装レビュー用セキュリティチェックリスト

変更範囲と承認済み契約に関係する項目だけを適用する。実装方式の好みや一般論だけで finding を作らず、到達可能な欠陥、影響、根拠を確認する。

## 保護対象とデータフロー

- 認証情報、暗号鍵、個人情報、保護対象データなどが、承認済み境界を越えて漏れていないか。
- 入力、戻り値、例外、ログ、診断、永続化、クラッシュ情報を確認する。
- 必要な認可や主体確認を迂回して、保護対象の閲覧・変更・操作を許さないか。
- 秘密情報の不要な複製や保持が、具体的な漏えい・再利用経路につながっていないか。

## 入力と状態

- 外部入力の形式、長さ、範囲、文脈を検証してから使っているか。
- malformed、truncated、未知値、重複、改ざん、境界値、過大入力に安全に対処するか。
- 失敗や再試行で認可、完全性、状態整合性を破らないか。
- 外部標準や暗号契約に関係する場合、適用版と信頼できる参照値に適合しているか。

## 暗号・乱数・認証

対象が暗号や認証を使用する場合に限り、秘密鍵・乱数の扱い、認証結果の検査、nonceなどの再利用条件、署名・MAC対象データ、文脈分離、鍵用途、失敗時の扱いを確認する。実装言語、ライブラリ、定数時間処理については、具体的なセキュリティ欠陥または承認済み契約との不一致がある場合に指摘する。

## ランタイムと境界

- 型、所有権、メモリ安全性、並行性、シリアライズ境界、FFIやプラグイン境界が対象にある場合、その安全条件を確認する。
- 解放済みデータの参照、初期化漏れ、二重解放、競合、権限昇格など具体的な欠陥を探す。
- 特定言語機能や境界技術の存在だけを finding にしない。

## テストと判断

- セキュリティ上重要な正常系、拒否条件、失敗時、境界値を確認する。
- fixtureや期待値が独立した根拠を持つかを確認し、実装と同じロジックだけをoracleにしない。
- fuzzing、differential test、既知ベクトルは、対象の攻撃面や契約に見合う場合に評価する。
- 仕様不足で正否を決められない場合は、実装欠陥と断定せず上流への feedback として分ける。
- 重大度は到達可能性、影響、前提条件、緩和策、回復可能性で判断する。
