# Design Author

承認済み要求を実現可能な基本設計へ整理する。設計では責務、境界、依存、主要フロー、データ所有、運用前提と判断理由を明確にし、要件、外部仕様、詳細実装を混同しない。

## 作業前の確認

1. 対象リポジトリの作業指示（`AGENTS.md` など）があれば読む。
2. `../author-common/author-playbook.md` と `output-format.md` を読む。
3. 対象設計書、承認済み要求、直接関係する設計判断、ユーザーが指定した資料を確認する。
4. 仕様、コード、テストは、既存契約や実現可能性との整合確認に必要な場合だけ参照する。

## 対象と出力

- ユーザーが指定した対象、保存先、更新範囲を優先する。
- 未指定の場合は既存の文書構成と命名規則から判断する。候補が複数ある場合は推測しない。
- 既存文書の更新は依頼範囲に限り、正本を移動・改名・複製しない。
- 成果物は基本設計に限る。要求、仕様、実装、テスト、レビューを同時に作成しない。

## 設計に含める内容

対象に必要な範囲で、システムコンテキスト、外部主体、コンポーネント責務、依存方向、trust boundary、主要なデータフロー、状態とデータ所有、外部サービスとの関係、失敗・復旧、運用上の前提、品質特性、検証方針、重要な代替案と判断理由を整理する。

## 設計にしない内容

上流資料に根拠がない要求や責任を追加しない。APIの詳細、field、wire format、具体的な暗号パラメータ、class、function、module構成、特定ライブラリ、UI詳細は、承認済み要求や実現可能性から基本設計で必要とされない限り後続工程へ委ねる。重大な判断が未承認または不明確な場合は、仮定として固定せず未決定事項にする。

## 作成手順

1. 要求・設計判断を設計項目へ対応付ける。
2. システム境界、主体、責任、対象外を定める。
3. コンポーネントと依存方向を整理する。
4. 主要フロー、データ所有、状態遷移、失敗・復旧を記述する。
5. セキュリティ境界、運用前提、外部依存を必要に応じて記述する。
6. 重要な判断と代替案、未決定事項、仕様への引継ぎを整理する。
7. 追跡可能性と `output-format.md` に沿った一貫性を確認し、設計書だけを作成または更新する。

## 自己確認

- 責務、依存方向、境界、所有、主要フローが一貫している。
- 設計判断が承認済み要求や明示資料と整合する。
- セキュリティ、失敗、復旧、運用の責任が適切な境界にある。
- 仕様や実装の詳細を不必要に固定していない。
- 未決定事項、前提、外部依存を明示している。
- 各設計判断を根拠へ追跡できる。

独立した品質判定には `design-review` を使用する。このスキル自身はレビュー成果物を作成しない。
