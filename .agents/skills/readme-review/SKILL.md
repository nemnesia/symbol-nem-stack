# Readme Review

READMEを利用者向け文書としてレビューし、インストールから最初の利用までに支障がないか、記載内容が現在の実装と一致しているかを判定する。レビューは単一の技術ドキュメントレビュアーとして実施し、複数ペルソナ、討議、投票、会議方式は使用しない。

> README review evaluates the documentation, not the product design.

実装・仕様そのものに改善余地があっても、それがREADMEの誤りを生じさせていない限り、READMEレビューの指摘事項として扱わない。

## 対象と成果物

- ユーザーがREADMEのパスを指定した場合は、そのREADMEを対象にする。
- パッケージ、アプリケーション、機能が指定され、READMEのパスが指定されていない場合は、その対象に直接対応するREADMEを探す。候補が複数または見つからない場合は、推測で選ばず対象の確認を求める。
- 指定されたREADMEと同じディレクトリの `reviews/<READMEのベース名>-review-findings.md` にレビュー結果を作成する。出力先が指定されている場合はそれを使用する。
- `reviews/` が存在しない場合は作成する。既存の同名レビュー結果は、ユーザーが履歴保持を指定していない限り更新する。
- README、コード、`package.json`、仕様書、テスト、設定をレビューのために変更しない。修正依頼だけをレビュー結果に記載する。

## 確認する事実源

READMEを読んだ後、記載内容を次の資料と照合する。

1. 対象の `package.json`
2. 公開エントリポイント、`exports`、公開関数・クラス・型定義および実装
3. 対象に直接関係する仕様書、既存ドキュメント、ライセンスファイル
4. テスト、実例、ビルド設定、対応環境の設定

情報源に矛盾がある場合は、READMEの記載がどの事実と一致または不一致なのかを分けて記載する。READMEが誤っていない限り、実装や仕様の改善提案へ拡張しない。確認できない事項は未確認として扱い、推測で合否を決めない。

## レビュー観点

### 正確性

- インストールコマンド、パッケージ名、API名、引数、戻り値、importパスが実装と一致しているか。
- READMEに存在しない機能、API、オプション、対応環境、保証を書いていないか。
- サンプルコードが公開APIだけで構成され、実際の利用方法と一致しているか。

### 利用可能性

- 利用者がインストールから最初の実行まで辿れるか。
- サンプルコードが、記載された前提条件を満たせば成立するか。
- 必要な設定、環境変数、接続先、ビルド手順などが利用開始に必要な範囲で示されているか。

### 情報不足

- 必須設定、前提条件、対応環境、制約、重要な注意事項が抜けていないか。
- 利用者が誤った環境や手順を選ぶおそれのある欠落がないか。

### 過剰記載

- 内部設計、内部データ構造、実装詳細、詳細プロトコル仕様を書きすぎていないか。
- READMEで仕様、公開API、デフォルト値、互換性、将来機能を新規定義していないか。
- 将来構想や未実装機能を現在利用できる機能のように書いていないか。

### 整合性

- `package.json`、公開コード、仕様書、既存ドキュメント、READMEの間に矛盾がないか。
- 既存READMEの記述が古く、現在の公開APIやインストール方法を誤って説明していないか。

### 読みやすさ

- 利用者向けの順序で、概要、インストール、最小例が早い段階にあるか。
- 最初の利用に必要な情報が、詳細説明や内部仕様に埋もれていないか。
- 用語、見出し、コード例の粒度が対象の既存READMEやパッケージと大きくずれていないか。

## 明確な範囲外

次の事項は、READMEの誤りを直接生じさせていない限り指摘しない。

- API名や設計が分かりにくいので変更すべきという提案
- 実装に機能が足りないという提案
- 仕様書の要件、暗号方式、データ形式、アーキテクチャの改善提案
- READMEに記載されていない内部品質、性能、保守性、テストカバレッジの評価
- 将来機能、追加API、追加設定の提案

たとえば「API名が分かりにくいので変更すべき」は範囲外とする。一方、「READMEでは `createAccount()` と書かれているが、公開APIは `create()` である」はREADMEの正確性の問題として指摘する。

## 判定

- `READY`: `ERROR` と `WARN` の指摘がなく、利用者がREADMEを信頼して利用開始できる。`NIT` もない状態。
- `READY WITH MINOR FIXES`: `ERROR` と `WARN` はなく、表現や軽微な読みやすさに関する `NIT` だけがある。
- `REVISE README`: `ERROR` または `WARN` が1件以上ある。

重大度は次の3種類だけを使用する。

- `ERROR`: 実行不能、API・コマンド・パッケージ名の事実誤認、存在しない機能の記載など、READMEを信頼して利用すると失敗する問題。
- `WARN`: 必須情報の不足、重要な前提の欠落、誤解のおそれがある過剰記載など、利用開始や正しい理解を妨げる問題。
- `NIT`: 表現、順序、見出し、軽微な読みやすさの問題。事実誤認や利用不能には直結しない。

## レビュー手順

1. 対象READMEと対象パッケージまたはアプリケーションを特定する。
2. README全体を読み、インストール、最初の実行、主要API、対応環境、注意事項、Licenseを確認する。
3. `package.json`、公開export、型定義、実装、仕様書、既存ドキュメントと各記載を照合する。
4. 各問題について、READMEの誤りまたはREADMEに必要な情報の不足かどうかを範囲境界で確認する。
5. 対象箇所、根拠、利用者への影響、READMEに必要な修正を簡潔に記録する。
6. `ERROR`、`WARN`、`NIT`を分類し、判定を付けてレビュー結果を作成する。

テストやサンプルを実行した場合だけ実行結果を根拠にする。実行していないサンプルを「動作確認済み」と記載しない。レビューでコードを修正して成立させることは禁止する。

## 出力形式

レビュー結果は次の構成にする。

```markdown
# README Review Findings

- 対象README: <パス>
- 対象: <パッケージ、アプリケーション、またはモノレポ>
- 判定: READY | READY WITH MINOR FIXES | REVISE README

## Findings

### <ID>: <要約>

- 重大度: ERROR | WARN | NIT
- 対象箇所: <見出し、コード、行など>
- 確認できた事実: <READMEと照合資料の内容>
- 影響: <利用者が受ける影響>
- READMEに必要な修正: <READMEの修正内容。製品や仕様の変更は書かない>

## Evidence Used

- <確認した資料と用途>

## Review Summary

- <観点ごとの簡潔な結果>
```

指摘がない場合は `Findings` に「指摘なし」と記載する。レビュー対象外の実装・仕様改善案や、レビュアーの討議・思考過程は成果物へ含めない。
