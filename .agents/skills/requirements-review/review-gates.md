# Review Gates

目的は、要件定義書を完璧にすることではなく、仕様設計を安全に開始できるかを判断することである。各ゲートは合格または不合格とし、不合格は必ず Critical の採用指摘に対応付ける。

各ゲートは要件レベルで判定する。仕様書・基本設計・詳細設計で具体化できる事項が未確定であることだけを理由に不合格としてはならない。

## 品質ゲート

1. **目的と課題**: 解決する課題、達成する目的、および必要性を説明できる。
2. **利用者と関係者**: 利用者、影響を受ける関係者、利用場面、および責任を説明できる。
3. **対象範囲**: 要件定義書の「対象」と「対象外」として、今回実現する機能、対応するチェーン、対応するネットワーク、対応するデータ種別、対応する利用環境、対応する搬送手段、および今回対象外となる機能を明確にし、要件、ユースケース、受け入れ条件と矛盾なく区別できる。具体的な API、フィールド、画面、内部コンポーネントの列挙までは要求しない。
4. **要件と制約**: 機能、品質、制約、前提、および未決定事項を識別できる。実現方式の選択肢まで確定している必要はない。
5. **受け入れ条件**: 主要な要件の合否を、利用者または外部から観測可能な条件で判断できる。単体テスト、fixture、内部テスト手順など実装レベルの検証方法までは要求しない。
6. **内部整合性**: 用語、目的、範囲、要件、制約、例、関連資料の間に仕様設計を妨げる矛盾がない。設計詳細が未確定であることは矛盾とみなさない。
7. **不可欠な前提の現実性と安全性**: 仕様設計の開始に不可欠な技術、運用、外部連携、法務、ライセンス、セキュリティ上の前提が未確認のまま残っておらず、確認済み資料と矛盾しない。ここで確認するのは「必要な特性・制約・責任・外部契約」であり、暗号方式、データ構造、API 形式、ライブラリ、インフラ構成など具体的な実現方法ではない。
8. **コンセプト整合性と前段品質判定**: 選択されたコンセプトシートがある場合、目的、対象ユーザー、提供価値、スコープ、判断原則、成功条件、前提条件、未決定事項と、要件定義書の記述が仕様設計を妨げる形で矛盾していない。相違は、明示的な要件化、対象外、前提、または `OPEN-` として適切に引き継がれている。対応するコンセプトレビュー結果がある場合は、対象と鮮度が一致し、Review Result が「要件定義へ進める」であることを確認する。「コンセプト整理を優先する」の判定、または未解決 Critical がある場合は、要件定義書の内容にかかわらず不合格とする。Major または Minor だけでは自動的に不合格にせず、要件定義書への引継ぎ状況を確認する。コンセプトシートまたはレビュー結果がない場合は、Evidence Used にそれぞれ「未確認」と記録し、未確認だけを理由に不合格とはしない。

Gate 7 の技術的または安全性上の前提は、該当する場合に Reviewer C が承認済みのコンセプト・要件またはプロジェクト資料の関連箇所を選んで確認する。資料が存在しない、または範囲外で確認できないだけでは不合格にしない。前提が仕様設計の開始に不可欠で、確認が必要な理由と影響を示せる場合だけ不合格とする。

Gate 7 で「安全性」を理由に具体的な方式を要求してはならない。たとえば「AES-GCM を採用する」「KDF を scrypt にする」「salt を何 byte にする」等はゲート判定ではなく後工程の設計事項である。要件レビューで扱えるのは「機密情報は保存・搬送時に適切に保護される必要がある」「方式を交換可能にする必要がある」のような必要特性・制約までとする。

Gate 8 は Reviewer B が適用する。選択されたコンセプト本文との未解決の矛盾、コンセプトレビュー結果のブロック判定、または未解決 Critical が仕様設計の開始を妨げる場合だけ不合格とし、対応する Critical の採用指摘を付与する。開始を妨げない相違やコンセプトレビュー結果の Major/Minor は Major または Minor として記録する。レビュー結果がない、対象不一致、または古い場合は未確認として記録し、それだけを理由に不合格とはしない。

## 範囲外

次は原則として仕様書・設計書・実装で決める事項であり、要件定義の不足として指摘しない。

- データモデル、フィールド名、型、識別子の数値割当
- API エンドポイント、HTTP メソッド、パラメータ、レスポンス、エラーコード
- 使用技術、ライブラリ、フレームワーク、アーキテクチャ、インフラ、データベース設計
- UI レイアウト、画面遷移、具体的操作手順
- 暗号アルゴリズム、KDF、nonce、salt、tag 等の具体的構成
- アルゴリズム、内部状態遷移、処理順序、モジュール分割
- 単体テストケース、fixture、テストデータ、実装レベルの検証手順

ただし、それらに依存する要件レベルの特性、制約、責任、外部契約、互換性、性能水準、法的制約が欠落している場合は、その欠落だけを扱う。具体的な設計案を採用指摘へ含めてはならない。

## 判定と終了

- すべてのゲートが合格: **仕様設計へ進める**。
- 1つ以上のゲートが不合格: **要件の修正を優先する**。
- Major と Minor だけでは差し戻さない。

品質ゲートを満たした時点でレビューを終了する。より良い表現、代替案、残存 Minor、設計上の改善余地を理由に継続してはならない。
