# Reviewers

本レビューは、メインエージェントが務める Review Board Chair と、別々に起動する Reviewer A、Reviewer B、Reviewer C のサブエージェントで構成する。各 Reviewer は Phase 1 では独立し、Phase 2 でだけ他の指摘を評価する。Reviewer は最終成果物を作成せず、指摘メモだけを Chair に返す。

Chair は `multi_agent_v1__spawn_agent` を3回の別々の呼び出しで実行し、`fork_context: false` を指定して、3つの Reviewer サブエージェントを同じ対象資料に対して並列起動する。返された3つの `agent_id` を A/B/C に対応付け、値がすべて存在し相互に異なることを Phase 1 前に検証する。検証できない場合はレビューを中止し、findings を作成しない。

各 Reviewer に他の Reviewer の指摘や結論を Phase 1 の開始前に渡してはならない。Phase 1 完了後、Chair は同じ `agent_id` の Reviewer サブエージェントへ全指摘を渡し、Phase 2 の評価を依頼する。Phase 1/2 の完了状態は `agent_id` ごとに確認し、失敗・タイムアウト・未確認があれば findings を作成しない。

すべての Reviewer は、指摘を生成する前に `SKILL.md` の「要件レビューの境界」を適用する。仕様書・設計・実装で決められる事項を、その具体的方法の不足として指摘してはならない。設計詳細を見つけても、要件として必要な目的、制約、責任、外部契約、品質特性、受け入れ条件、または未決定事項の欠落に言い換えられない場合は指摘を生成しない。

## Reviewer A: 要件の明確性と完全性

背景、目的、用語、機能要件、非機能要件、制約、受け入れ条件、未決定事項を確認する。特定の技術、アーキテクチャ、実装方法の採用は指摘しない。

「詳細が不足している」という理由だけでは指摘しない。仕様設計を開始するために要件として確定または未決定事項として明示される必要がある情報だけを確認する。API 項目、データ構造、内部処理、具体的なテストケースなど、後工程で具体化できる情報の不足は対象外とする。

## Reviewer B: 利用価値とスコープ

課題、対象利用者、関係者、利用場面、提供価値、対象範囲、対象外、今回の優先事項を確認する。対象範囲は、要件定義書が定める今回実現する機能、対応するチェーン、対応するネットワーク、対応するデータ種別、対応する利用環境、対応する搬送手段、および今回対象外となる機能を確認する。選択されたコンセプトシートがある場合は、目的、対象ユーザー、提供価値、スコープ、判断原則、成功条件、前提条件、未決定事項と照合し、相違が明示的な要件化、対象外、前提、または `OPEN-` として適切に引き継がれているかを確認する。対応するコンセプトレビュー結果がある場合は、対象一致、確認日、Review Result、Required Changes、および Gate の判定を確認し、コンセプトレビューでブロックされた事項が要件定義書に未解決のまま残っていないかを確認する。UI、API、実装方法、技術選定は指摘しない。

スコープの明確化は「何を提供するか／しないか」までとし、「どの API、型、形式、画面、内部コンポーネントで提供するか」まで要求しない。

## Reviewer C: 実現性と安全性

実現に不可欠な技術的前提、外部連携、運用責務、データ保護、認可、可用性、保守性、法務・ライセンス上の前提を確認する。コーディング方法や詳細設計は指摘しない。

Reviewer C は「実現可能な設計が少なくとも存在するか」を要件レベルで確認し、最適な設計や安全な実装方法を提案する役割ではない。次のような内容は直接指摘しない。

- 暗号アルゴリズム、KDF、鍵導出パラメータ、nonce・salt・tag の構造
- データ構造、フィールド、型、識別子割当、エンコード方式の詳細
- API 契約の具体形、内部処理順序、ライブラリ、インフラ構成
- 具体的な防御実装、テスト手順、fixture

これらを確認する過程で、要件として必須の安全性特性、互換性、外部契約、責任分界、性能水準、法的制約等が欠落していることが判明した場合だけ、その欠落を指摘する。修正内容では実装方式を指定せず、必要な特性または制約を明文化するよう求める。

技術的または安全性上の前提を評価する必要がある場合だけ、承認済みのコンセプト・要件、コンセプトレビュー結果またはプロジェクト資料の関連箇所を参照する。コンセプトレビュー結果を参照する場合は、公開された指摘と判定だけを根拠とし、内部討議や思考過程を推測しない。要件本文、ユーザー提供資料、確認済み資料を区別し、未確認事項を断定しない。資料を確認できないこと自体を問題にせず、仕様設計の開始に不可欠な未確認前提だけを指摘候補とする。

## Review Board Chair

採用指摘の確定、過去指摘との同一性確認、IDと状態の引継ぎ、重複統合、重大度の確定、品質ゲートの適用、最終判定、findings の作成を行う。議長は新しい指摘を追加しない。3つの `agent_id` と Phase 1/2 の完了を検証できた場合だけ、Chair が対象パッケージの `docs/reviews/requirements/<要件定義書のベース名>-review-<3桁連番>.md` を新規作成する。既存の固定名または連番成果物は変更・上書きしない。findings には実行監査情報を記録する。

各指摘について、レビュー範囲、根拠、影響、重大度、重複を確認する。討議で示された根拠と影響に基づいてのみ重大度を変更し、根拠不足の指摘は採用しない。

さらに、各採用候補に対して「この修正は要件定義書に書くべき内容か、それとも仕様書・設計書で決める内容か」を最終確認する。後者なら却下する。要件レベルに言い換えた場合だけ採用できる。
