# Requirements Review Board

要件定義書を設計・実装・書き直すのではなく、仕様設計を開始できる品質かを判定する。完璧さや Minor の解消を目的にレビューを継続してはならない。

## 対象と成果物

- レビュー対象は、ユーザーが明示した要件定義書1件とする。
- 対象パッケージは、ユーザーが指定したパッケージ、または対象要件定義書が属するパッケージのルートとする。対象パッケージを特定できない場合は、推測で選ばず対象を確認して終了する。
- 要件定義書が明示されない場合は、対象パッケージの `docs/requirements/` で `requirements.md`、`requirement.md`、ファイル名に `requirements` または `requirement` を含む Markdown ファイルの順で候補を探す。`reviews/` ディレクトリ、`*-review-*.md`、`*-review-findings.md`、コンセプトシート、仕様書、設計資料、実装コードは除外する。
- 候補が0件または複数件なら、推測で選ばず対象を確認して終了する。
- 要件定義書を選択した後、対象パッケージの `docs/consept/` で `concept-sheet.md`、`concept.md`、ファイル名に `concept` を含む Markdown ファイルの順にコンセプトシート候補を探索する。`reviews/` ディレクトリと `*-review-*.md` は候補から除外する。候補が1件ならレビューの根拠として確認し、対応するコンセプトレビュー結果が対象パッケージの `docs/reviews/concept/` にある場合は、対象ベース名のレビュー番号最大のファイル1件だけを確認する。候補が複数なら自動選択せず、候補のパスを示してユーザーに対象の指定を求めて終了する。候補がない場合は、Evidence Used に「コンセプト本文: 未確認」「コンセプトレビュー結果: 未確認」と記録してレビューを続行する。
- 選択した要件定義書の拡張子を除いたベース名に `-review-001.md` 形式の3桁連番を付加し、対象パッケージの `docs/reviews/requirements/` に新規成果物を作成する。たとえば対象パッケージの `docs/requirements/requirements.md` の初回成果物は `docs/reviews/requirements/requirements-review-001.md` とする。対象要件定義書に対応する連番ファイルが既にある場合は最大番号の次を使用し、候補ファイルが存在する場合は空き番号まで進める。既存の固定名 `-review.md`、`-review-findings.md` および既存の連番成果物は移動・削除・上書きしない。`docs/reviews/requirements/` が存在しない場合は作成する。
- 連番は対象要件定義書のベース名ごとに管理する。対象要件定義書の過去レビュー成果物（固定名の旧形式を含む）から正式な `RR-<番号>` を抽出し、新規指摘には最大番号の次を割り当てる。同一問題であることを確認できる既存指摘は同じIDを引き継ぎ、新規指摘へ過去IDを再利用しない。各正式指摘には `New`、`Open`、`Resolved`、`Deferred`、`Reopened` のいずれかの状態を付ける。`Required Changes` と `Optional Improvements` には現在対応が必要な指摘を、`Resolved Findings` には対応済み指摘と確認根拠を、必要に応じて `Deferred Findings` には後工程へ引き継いだ指摘を整理する。

## 実行主体と実行順序

1. `reviewers.md` を読む。
2. `review-process.md` を読む。
3. `review-gates.md` を読む。
4. `output-format.md` を読む。
5. メインエージェントを Review Board Chair 兼オーケストレーターとし、Reviewer A、B、C をそれぞれ別のサブエージェントとして起動する。
6. 定められた Phase 1 から Phase 3 を実施し、Chair だけが成果物を生成する。

## 監査可能な起動要件

- Reviewer A、B、C は、実行可能なトップレベルの `multi_agent_v1__spawn_agent` を3回の別々の呼び出しで起動する。各呼び出しでは `fork_context: false` を指定し、初期会話コンテキストを共有しない。
- このスキルは、サブエージェントではなく、`multi_agent` を利用できる現在のトップレベルエージェントが Chair として直接実行する。サブエージェントへ `requirements-review` 全体を再委譲してはならない。
- Chair は各呼び出しから返された `agent_id` を、`A`、`B`、`C` の役割と対応付けて実行台帳へ記録する。
- Phase 1 を開始する前に、3つの `agent_id` がすべて存在し、相互に異なり、役割の重複がないことを検証する。検証できない場合はレビューを中止し、findings を生成しない。
- Phase 1 と Phase 2 は各 `agent_id` の完了状態を個別に待機して確認する。1つでも失敗、タイムアウト、未確認があればレビューを中止し、findings を生成しない。
- サブエージェント機能が利用できない場合、メインエージェントが代替実行してレビュー済みと扱ってはならない。サブエージェントレビューを実行できない旨だけを報告する。
- findings には実行監査情報として、3つの `agent_id`、Phase 1/2 の完了状態、Chair が統合したことを記載する。プロンプト、内部討議、個人意見、思考過程は記載しない。

実行呼び出しは次の順序に固定する。

1. `multi_agent_v1__spawn_agent` を A/B/C へ1回ずつ呼び出し、各戻り値の `agent_id` を保存する。
2. 3つの `agent_id` を検証してから、`multi_agent_v1__wait_agent` で Phase 1 の各エージェントを待機する。
3. Phase 1 の全結果を同じ A/B/C へ `multi_agent_v1__send_input` で送信し、各 `submission_id` を保存する。
4. `multi_agent_v1__wait_agent` で Phase 2 の各エージェントを待機する。
5. 全状態が完了であることを確認してから、Chair が findings を作成する。

サブエージェントには、要件定義書、選択されたコンセプトシート、対応する公開レビュー結果、ユーザー提供資料、承認済み資料のうち担当に必要なものだけを渡す。サブエージェントはファイルを作成・編集せず、指摘メモを返す。

討議、投票、Reviewer 個人の意見、却下理由、思考過程は内部情報であり、成果物へ含めない。

## 共通原則

- 要件が「なぜ」「誰のために」「何を満たすべきか」を定めているかを確認し、具体的な設計・実装方法は決めない。
- 指摘は対象箇所、根拠、影響、必要な修正を示せる場合だけ採用候補とする。
- 要件本文、コンセプト本文、コンセプトレビュー結果、ユーザー提供資料、承認済みの要件またはプロジェクト資料を根拠の種別として区別する。コンセプトレビュー結果は公開された findings の内容だけを参照し、内部討議や思考過程を推測しない。未確認の事実、推測、好みを事実として扱わない。
- 技術的または安全性上の前提は、必要な場合だけ関連する承認済み資料を選んで参照して評価する。資料を確認できないことだけを不合格理由にしない。

## 要件レビューの境界

指摘を生成する前に、必ず次の境界テストを適用する。

1. その問題は、仕様書・基本設計・詳細設計・実装で初めて決めても要件を満たせるか。
2. 満たせるなら、その事項は要件定義レビューの範囲外であり、指摘を生成しない。
3. 満たせない場合だけ、設計方法ではなく「要件として不足している目的、制約、責任、外部契約、品質特性、受け入れ条件、または未決定事項」に言い換えられるか確認する。
4. 要件レベルに言い換えられない指摘は採用候補にしない。

次の事項は、それ自体を要件定義の欠陥として指摘してはならない。

- API のエンドポイント、メソッド、パラメータ、レスポンス構造、エラーコード
- データモデル、フィールド名、型、数値割当、シリアライズ形式の詳細
- アルゴリズム、処理順序、内部状態遷移、クラス・モジュール分割
- 使用ライブラリ、フレームワーク、データベース、インフラ構成
- 暗号方式、KDF、nonce・salt・tag 等の具体的構成
- UI レイアウト、画面遷移、具体的な操作手順
- 単体テストケース、テストデータ、fixture、実装レベルの検証手順

ただし、これらについてプロダクトとして必須の互換性、セキュリティ特性、性能水準、外部契約、法令制約などが要件として必要なのに欠落している場合は、その「必要な特性または制約の欠落」だけを指摘する。具体的な実現方法を修正内容に含めてはならない。
