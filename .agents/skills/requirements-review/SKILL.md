# Requirements Review Board

要件定義書を設計・実装・書き直すのではなく、仕様設計を開始できる品質かを判定する。完璧さや Minor の解消を目的にレビューを継続してはならない。

## 対象と成果物

- レビュー対象は、ユーザーが明示した要件定義書1件とする。
- 明示されない場合は、`requirements.md`、`requirement.md`、ファイル名に `requirements` または `requirement` を含む Markdown ファイルの順で候補を探す。レビュー結果、コンセプトシート、仕様書、設計資料、実装コードは除外する。
- 候補が0件または複数件なら、推測で選ばず対象を確認して終了する。
- 要件定義書を選択した後、そのファイルと同じディレクトリで、`concept-sheet.md`、`concept.md`、ファイル名に `concept` を含む Markdown ファイルの順にコンセプトシート候補を探索する。候補が1件ならレビューの根拠として確認する。候補が複数なら自動選択せず、候補のパスを示してユーザーに対象の指定を求めて終了する。候補がない場合は、Evidence Used に「コンセプト本文: 未確認」と記録してレビューを続行する。
- 成果物はリポジトリ直下の `.reviews/requirements-review-findings.md` とし、レビューごとに上書きする。レビュイーへ公開するレビュー成果物はこのファイルだけとする。

## 実行順序

1. `reviewers.md` を読む。
2. `review-process.md` を読む。
3. `review-gates.md` を読む。
4. `output-format.md` を読む。
5. 定められた Phase 1 から Phase 3 を実施し、成果物を生成する。

討議、投票、Reviewer 個人の意見、却下理由、思考過程は内部情報であり、成果物へ含めない。

## 共通原則

- 要件が「なぜ」「誰のために」「何を満たすべきか」を定めているかを確認し、具体的な設計・実装方法は決めない。
- 指摘は対象箇所、根拠、影響、必要な修正を示せる場合だけ採用候補とする。
- 要件本文、コンセプト本文、ユーザー提供資料、承認済みの要件またはプロジェクト資料を根拠の種別として区別する。未確認の事実、推測、好みを事実として扱わない。
- 技術的または安全性上の前提は、必要な場合だけ関連する承認済み資料を選んで参照して評価する。資料を確認できないことだけを不合格理由にしない。
