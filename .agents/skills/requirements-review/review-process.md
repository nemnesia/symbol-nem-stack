# Review Process

必ず Phase 1、Phase 2、Phase 3 の順に実施する。内部討議は成果物へ出力しない。

## Execution Gate: Reviewer 起動の監査

Phase 1 の前に、トップレベルの Chair は Reviewer A、B、C をそれぞれ別の `multi_agent_v1__spawn_agent` 呼び出しで起動する。サブエージェントを Chair として再委譲してはならない。各呼び出しに `fork_context: false` を指定し、返却された `agent_id` を役割ごとに記録する。3つの ID がすべて存在し、相互に異なることを確認できた場合だけ Phase 1 に進む。

ID の欠落、重複、起動エラー、サブエージェント機能の利用不能がある場合は、メインエージェントによる代替レビューを行わず、レビューを中止する。中止時は findings を生成せず、サブエージェントレビューを実行できなかったことを報告する。

## Phase 1: Individual Review

Reviewer A、B、C は互いの意見を参照せず、担当観点と要件定義書を独立してレビューする。選択されたコンセプトシートがある場合、Reviewer B は `reviewers.md` の担当観点としてその本文を必ず照合する。対応するコンセプトレビュー結果がある場合、Reviewer B は公開された Review Result、Required Changes、Review Gates をコンセプト本文との照合に使用する。Reviewer C は技術的または安全性上の前提を評価する必要がある場合に限り、承認済みのコンセプト・要件、コンセプトレビュー結果またはプロジェクト資料の関連箇所を参照してよい。コンセプトレビュー結果がない、対象不一致、または古い場合は、Evidence Used に未確認として記録する。

メインエージェントは Reviewer A、B、C を別々のサブエージェントとして並列起動する。各サブエージェントは最終 findings ファイルを作成せず、下記の項目を含む指摘メモだけを返す。Chair は `multi_agent_v1__wait_agent` で3つの `agent_id` それぞれについて Phase 1 の完了状態を待機して確認する。すべてが完了して指摘メモを返したことを確認できない場合は Phase 2 へ進まず、findings を生成しない。

### Phase 1A: Scope Filter

各 Reviewer は指摘を書き起こす前に、候補となる問題へ次の順で判定を行う。

1. 問題を解消するために必要なのは、目的、対象範囲、制約、責任、外部契約、品質特性、受け入れ条件、前提、未決定事項の明確化か。
2. それとも API、データ構造、アルゴリズム、暗号方式、ライブラリ、インフラ、UI、内部処理、テストケース等の具体化か。
3. 2 だけで解消できるなら範囲外として破棄し、仮 ID を付けない。
4. 1 が必要なら、具体的な設計案を除去して要件レベルの問題に言い換えてから仮 ID を付ける。

「仕様設計で安全に決められる余地が残っている」こと自体は要件不備ではない。要件定義書は後工程の設計判断を残してよい。

各指摘は仮 ID（`A-001`、`B-001`、`C-001`）を付け、次をすべて含める。

- 重大度（Critical、Major、Minor）
- 問題と対象箇所
- 根拠の種別と参照箇所
- 放置した場合の影響
- 必要な修正または確認

「必要な修正または確認」は要件定義書で行う変更だけを書く。具体的なフィールド、API、アルゴリズム、ライブラリ、暗号方式、内部構造、テスト実装を指定してはならない。

根拠の種別は「要件本文」「コンセプト本文」「コンセプトレビュー結果」「ユーザー提供資料」「承認済み要件またはプロジェクト資料」のいずれかとする。コンセプトシート候補がない場合は、Evidence Used に「コンセプト本文: 未確認」「コンセプトレビュー結果: 未確認」と記載する。コンセプトレビュー結果がない、対象不一致、または古い場合も「コンセプトレビュー結果: 未確認」と記載する。未確認事項は未確認と明記し、外部事実を断定しない。

## Phase 2: Review Board Discussion

Phase 1 の終了後に限り、各 Reviewer は他の指摘を評価できる。評価は賛成、条件付き賛成、反対のいずれかとし、反対または条件付き賛成には根拠不足、範囲外、後工程で決める事項、重大度不適切などの理由を添える。

メインエージェントは Phase 1 の全指摘メモを、同じ Reviewer A、B、C のサブエージェントへ `multi_agent_v1__send_input` で渡す。各戻り値の `submission_id` を保存する。各サブエージェントは自分の指摘を含む全指摘を評価し、他の Reviewer の指摘に対する判定と理由を返す。Chair は Phase 1 と同じ `agent_id` に対して Phase 2 の入力を送り、別の新規サブエージェントで置き換えてはならない。`multi_agent_v1__wait_agent` で3つすべての Phase 2 完了状態を個別に確認できない場合は Phase 3 と findings の生成を中止する。

討議の目的は指摘を増やすことではなく、根拠と影響が十分な指摘へ絞り込むことである。各指摘を採用、却下、または重大度変更として確定する。次の場合は却下する。

- 問題、根拠、影響、必要な修正または確認を説明できない。
- 個人的好み、推測、具体的な設計・実装詳細、または後工程だけで決められる事項である。
- 要件レベルの目的、制約、責任、外部契約、品質特性、受け入れ条件、前提、未決定事項の不足に言い換えられない。
- 修正内容が仕様書・設計書・実装コードに対する変更要求になっている。
- 確認済みの根拠と矛盾する。

## Phase 3: Chair Decision

Review Board Chair は要件本文、明示された根拠、討議で採用された指摘を用いて品質ゲートを適用する。新しい指摘は追加せず、根拠不足の指摘は採用しない。

Chair はサブエージェントの Phase 1 メモと Phase 2 評価を統合し、重複をまとめて正式 ID と状態を付ける。対象要件定義書の過去レビュー成果物（固定名の旧形式を含む）を確認し、同一問題であることを確認できる指摘は過去の `RR-<番号>` を引き継ぐ。新規指摘には、その要件定義書の過去レビューで使用された最大番号の次から割り当て、過去IDを再利用しない。正式指摘の状態は `New`、`Open`、`Resolved`、`Deferred`、`Reopened` のいずれかとする。サブエージェントの討議内容、投票、個人意見、却下理由、思考過程は findings に出力しない。Chair は findings の `Execution Audit` に、A/B/C の `agent_id`、Phase 1/2 の完了状態、Chair による統合完了を記載する。ID や完了状態を確認できない場合は、どの品質判定であっても findings を生成してはならない。

採用前に Chair は各指摘へ最終 Scope Filter を適用する。「この指摘の修正先は要件定義書か」と問い、仕様書・設計書・実装コードが主な修正先になる指摘は却下する。

採用指摘を統合し、過去指摘との同一性を確認したうえで正式 ID（`RR-001` からの対象要件定義書単位の連番）と状態を付与する。今回初めて確認した指摘は `New`、未解決の過去指摘は `Open`、一度 `Resolved` または `Deferred` とした同一指摘が再発・未解消と確認された場合は `Reopened`、対応済みの過去指摘は `Resolved`、後工程へ引き継ぐ指摘は `Deferred` とする。既存指摘を状態変更なく再確認した場合も、同じIDを保持する。重大度は次のとおりとする。

- Critical: 品質ゲートを不合格にし、仕様設計の開始を妨げる要件レベルの問題。コンセプト本文との未解決の矛盾、またはコンセプトレビュー結果で示された未解決の前段ブロッカーが仕様設計の開始を妨げる場合を含む。
- Major: 開始は妨げないが、仕様化の前提や運用責務等が曖昧で、後工程の判断を不安定にする要件レベルの問題。
- Minor: 要件定義としての明確性・追跡性・検証可能性を改善する提案。設計上の改善案は含めない。

すべての品質ゲートが合格なら「仕様設計へ進める」、1つでも不合格なら「要件の修正を優先する」と判定し、対象パッケージの `docs/reviews/requirements/` に、要件定義書のベース名へ `-review-<3桁連番>.md` を付加した新規ファイルを生成する。既存の固定名または連番成果物は変更しない。
