# 要件レビュー用セキュリティチェックリスト

この一覧は、対象の承認済みコンセプト、ユーザー要求、要件文書が示す保護対象と責任に対し、必要なセキュリティ特性が要件として表現されているかを確認する補助資料である。一覧そのものを新しい要求や finding の根拠にしない。該当しない項目は適用せず、チェック項目を網羅するために scope を広げない。

## 保護対象と影響

- 何を保護するかが既存資料から特定できるか。例: 認証情報、暗号鍵、個人情報、業務データ、権限、サービス可用性。
- 想定する不正な閲覧、変更、削除、なりすまし、権限濫用、停止の影響が要件に関係するか。
- どの主体が保護対象を扱い、どの主体から守るかが明確か。

## 必要なセキュリティ特性

対象のリスクに応じ、次のうち必要な性質と外部から確認できる結果が定められているか。

- 機密性、完全性、可用性、真正性、否認防止、プライバシー
- 認証、認可、最小権限、職務分離
- 安全な初期状態、失敗時の保護、監査可能性、説明責任
- 保護対象データの収集、利用、保持、共有、削除
- 外部接続、相互運用、更新、復旧、運用に関する責任

## 境界と前提

- コンポーネント、利用者、外部サービス、テナント、環境、運用者の責任境界が要件に影響するか。
- 認証、権限判断、データ保護、インシデント対応など、外部へ委ねる責任が明示されているか。
- 対象外とする攻撃・環境・データがある場合、重要な前提として記録されているか。
- 法令、契約、業界標準の適用が要求される場合、その出典と適用範囲が確認できるか。

## 要件としての品質

- 要求は利用者、条件、期待される結果を示し、第三者が判定できるか。
- 要件にする必要のある失敗・境界時の安全な結果が明記されているか。
- API、暗号方式、鍵長、製品、ライブラリ、実装手順など下流で選ぶ詳細を先取りしていないか。
- 各セキュリティ要求が、承認済み資料の保護対象、リスク、責任、または適用規則へ追跡できるか。

## finding の基準

不足が下流の設計や実装で安全に選択できる詳細なら、要件の finding にしない。明確な責任、必要な安全性、利用者への影響、法的制約が欠けており、下流で推測すると異なる結果や受容できないリスクにつながる場合に限り、根拠と影響を示して指摘する。
