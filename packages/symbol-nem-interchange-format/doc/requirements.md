# Symbol/NEM Interchange Format（SNIF）要件定義書

## 文書情報

| 項目 | 内容 |
| --- | --- |
| 文書種別 | データ転送フォーマット要件定義書 |
| 対象 | Symbol/NEM Interchange Format（SNIF）v1 |
| 対象チェーン | Symbol、NEM、およびアプリケーション定義値 |
| ステータス | 仕様設計中 |

## 1. 目的

SNIFは、Symbol、NEMおよびチェーン非依存のデータを、特定の搬送手段やアプリケーション実装に依存せず受け渡すための共通データ転送フォーマットである。

本書は、SNIF v1が**データ転送フォーマットとして何を表現できる必要があるか、どこまでを形式として保証するか**を定義する。

本書ではライブラリの関数名、API構成、対応ランタイム、パッケージ配布形式、内部メモリ管理、ログ、error code、処理資源上限等の実装要件は定義しない。これらはフォーマット仕様を利用する実装側の設計事項とする。

## 2. 対象範囲

### 2.1 対象

SNIF v1では次を定義対象とする。

- JSONによるwire format。
- SNIFデータを識別する共通エンベロープ。
- Symbol、NEMおよび任意のチェーン識別値・ネットワーク識別値の表現。
- 標準データタイプと、そのタイプ固有payload。
- アプリケーション固有typeの搬送。
- byte列の文字列表現。
- `account` / `mnemonic` の平文状態と保護済み状態の表現。
- 機密payloadを保護するために必要な暗号メタデータの搬送。
- 要求と応答を関連付けるための識別情報。
- SNIFフォーマットとしての形式検証境界。
- 将来拡張および未知値の責任境界。

### 2.2 対象外

次はSNIFフォーマットの責任に含めない。

- QR、Animated QR、NFC、Deep Link、Clipboard、ファイル、HTTP、WebSocket、Bluetooth、Relay等の搬送処理。
- UI、表示、利用者承認、認証、認可。
- 接続セッションの確立、維持、失効、永続化。
- リプレイ防止、重複実行防止、要求の使用済み状態等の状態管理。
- アドレス、公開鍵、秘密鍵、トランザクション等のチェーン上・業務上の意味検証。
- トランザクションの作成、署名、連署、アナウンス、ノード選択。
- 秘密鍵、ニーモニック、パスワード等の永続保存・保管方法。
- dApp、URL、ドメイン、アイコン、送信者等の真正性・信頼性の保証。
- アプリケーション固有typeの意味的標準化。
- 一般的な入力サイズ、CPU、メモリ等の運用上限。
- ライブラリAPI、対応ランタイム、モジュール形式、依存ライブラリ等の実装方式。

## 3. 設計原則

### 3.1 搬送手段から独立する

SNIFデータの意味は、QR、ファイル、NFC、Deep Link、Relay等の搬送手段によって変化してはならない。

### 3.2 形式と意味を分離する

SNIFとして形式上正しいことは、格納データがチェーン上・業務上正しいこと、送信者が真正であること、または利用者が処理を承認すべきことを意味しない。

### 3.3 必要な情報だけを標準化する

v1で具体的な必要性がない将来拡張用フィールドを予約しない。用途固有の意味は標準フォーマットへ過剰に取り込まない。

### 3.4 保護状態を明示する

機密データは、平文payloadと保護済みpayloadを構造上明確に区別できなければならない。

### 3.5 未知値を標準値として推測しない

未知のtype、chain、network、action、permission等を既知の標準値として暗黙に解釈してはならない。未知値の利用可否は、フォーマットで意味を定義していない範囲について利用側が判断する。

## 4. フォーマット要件

| ID | 要件 |
| --- | --- |
| FMT-001 | SNIF v1のwire formatはJSONとし、JSON canonicalizationは要求しないこと。 |
| FMT-002 | byte列はhex文字列で表現し、`0x`等のプレフィックスやBase64等の別表現をv1標準として混在させないこと。 |
| FMT-003 | すべてのSNIFデータが、version、type、chain、networkを用いて形式・用途・対象を識別できる共通エンベロープを持つこと。用途に応じてgenerationHashSeed、id、replyToを付加できること。 |
| FMT-004 | chainの標準値として`symbol`と`nem`、networkの標準値として`mainnet`と`testnet`を定義しつつ、アプリケーション定義の文字列値も搬送できること。 |
| FMT-005 | v1標準typeとしてaddress、contact、account、mnemonic、transaction、connection-request、connection-responseを区別して表現できること。 |
| FMT-006 | 各標準typeについて、交換上必要なpayload項目、必須・任意、データ型およびbyte列表現を仕様で一意に定義できること。 |
| FMT-007 | 標準type以外のアプリケーション固有typeとJSON object payloadを搬送できること。SNIFはそのpayload内部の意味を標準化しないこと。 |
| FMT-008 | accountおよびmnemonicは、平文時の`payload`と保護時の`protectedPayload`を排他的に使用し、保護状態を構造だけで判別できること。 |
| FMT-009 | `protectedPayload`は元のtype固有payload全体を保護対象とし、復元に必要なcipher、KDF、salt、KDFパラメータ、nonce、ciphertext、認証tag等を選択した暗号プロファイルに応じて搬送できること。 |
| FMT-010 | transactionはトランザクション本体をhexで搬送でき、必要に応じて受信側への処理意図をactionとして表現できること。actionは処理命令や実行保証を意味しないこと。 |
| FMT-011 | connection-request / connection-responseは接続に関する要求内容と応答結果を搬送できること。ただし接続セッション、認証、認可、利用者承認を成立させるフォーマットとして扱わないこと。 |
| FMT-012 | id / replyToは要求・応答等を関連付けるための情報を搬送できること。ただし識別子の生成方式、存在確認、期限、使用済み状態、重複状態をSNIFフォーマット自身が管理しないこと。 |

## 5. 標準データ要件

| type | 交換する内容 | 機密性 |
| --- | --- | --- |
| `address` | 単一のアドレス | 低 |
| `contact` | 表示名、アドレス、公開鍵、補足情報等の公開連絡先情報 | 低 |
| `account` | 秘密鍵、公開鍵、アドレス | 高 |
| `mnemonic` | ニーモニック | 高 |
| `transaction` | Symbol/NEMトランザクションpayloadと任意の処理意図 | 低〜中 |
| `connection-request` | 接続要求元情報、要求permission等 | 低〜中 |
| `connection-response` | 許可・拒否結果と許可時に返却する情報 | 低〜中 |
| アプリケーション固有type | アプリケーションが定義するJSON object | 利用側定義 |

標準typeの具体的なフィールド構造はフォーマット設計書で定義する。要件定義では、これ以上の用途固有メタデータを必須化しない。

## 6. 機密payload保護要件

| ID | 要件 |
| --- | --- |
| SEC-001 | accountおよびmnemonicを、改変検出を伴う認証付き暗号で保護して搬送できる標準プロファイルをv1で定義すること。 |
| SEC-002 | 暗号方式を将来交換できるよう、暗号アルゴリズムおよびKDFを識別し、復元に必要なパラメータをprotectedPayload内で搬送できること。 |
| SEC-003 | パスワード、鍵、導出鍵等の供給・保存・管理方法をSNIFフォーマットに含めないこと。 |
| SEC-004 | protectedPayloadの認証成功を、外側の共通エンベロープ、送信者、dApp、URL等の真正性保証として扱わないこと。 |

標準暗号プロファイルの具体的なアルゴリズム、KDFパラメータ、nonce長、tag長等はフォーマット設計書で規定する。

## 7. 形式検証の責任境界

SNIFフォーマットとして検証対象とするのは、交換データの構造を一意に解釈するために必要な事項までとする。

### 7.1 形式として検証する事項

- JSONとして解釈可能であること。
- 対応するversionであること。
- 共通エンベロープおよび標準typeの必須項目が存在すること。
- 各フィールドが定義されたJSON型であること。
- byte列として定義された値がhex表現であること。
- `payload` / `protectedPayload` の使用規則が守られていること。
- フォーマット上で値が明示的に限定されている項目が、その限定に従っていること。

### 7.2 SNIFフォーマットでは検証しない事項

- アドレスのチェックサム、実在性、chain/networkとの対応。
- privateKey、publicKey、addressの相互関係。
- mnemonicからの鍵導出結果。
- トランザクションの構造・内容・署名状態・実行可能性。
- generationHashSeedの内容やnetworkとの一致。
- dApp、URL、アイコン、送信者等の真正性。
- permission要求とconnection-responseの返却内容の業務上の一致。
- replyToが実在する要求を参照しているかどうか。
- 期限、使用済み状態、リプレイ、重複実行。
- アプリケーション固有typeのpayload内部の意味。

形式検証の成功は、上記の意味的妥当性や安全性を保証しない。

## 8. 拡張方針

- v1で定義していないtype、chain、network、action、permission等の文字列値を、既知の標準値として推測しない。
- アプリケーション固有typeは標準typeと区別して扱う。
- 未知プロパティや未知値を受理するか拒否するかは、SNIFが意味を定義していない範囲について利用側が判断できる。
- 将来必要になった機能は、実際の用途が生じた時点で標準化を検討する。将来用途だけを理由として予約フィールドを追加しない。
- v1のJSON文字列について、プロパティ順や空白等の文字列表現を相互運用上の識別子として使用しない。

## 9. 受け入れ条件

| ID | 受け入れ条件 |
| --- | --- |
| AC-001 | 標準7typeについて、仕様に従った正常データをJSONとして表現し、同じ論理値として解析できる。 |
| AC-002 | Symbol、NEMおよびアプリケーション定義のchain/network値を共通エンベロープで区別して搬送できる。 |
| AC-003 | byte列を必要とするフィールドはhex表現のみで相互運用できる。 |
| AC-004 | account / mnemonicについて平文と保護済みを構造上区別でき、保護済みデータから使用暗号プロファイルと復元に必要なパラメータを取得できる。 |
| AC-005 | アプリケーション固有typeを標準typeとして誤解釈せず、そのJSON object payloadを搬送できる。 |
| AC-006 | 未対応version、必須項目欠落、不正なJSON型、不正hex、payload/protectedPayload競合等をフォーマット不正として識別できる。 |
| AC-007 | 形式検証成功がチェーン上の妥当性、送信者の真正性、利用者承認、処理実行の成立を意味しないことが仕様上明確である。 |

## 10. 仕様設計への引継ぎ

フォーマット設計書では、本要件を具体化するため次を定義する。

- 共通エンベロープの各フィールド、必須性、表現規則。
- 標準7typeのpayload構造。
- chain / network / action / permission等の標準値。
- protectedPayload構造とv1標準暗号プロファイル。
- 形式検証規則。
- 正常系・拒否系・暗号化系の適合テストデータ。

ライブラリAPI、対応ランタイム、ESM/CJS、内部メモリ処理、ログ、error code、provider interface等は、本要件定義ではなく実装・API仕様側で扱う。

## 11. 要件定義の完了条件

本要件定義は次を満たした時点で、フォーマット仕様設計へ進める。

- SNIFがデータ転送フォーマットとして扱う範囲と対象外が明確である。
- 標準type、共通エンベロープ、byte列表現、機密payload保護、拡張方針について必要な要件が定義されている。
- 形式検証と意味検証・認証・状態管理・処理実行の責任境界が明確である。
- 要件が特定の搬送手段、API、ランタイム、パッケージ実装へ依存していない。
- 受け入れ条件により、フォーマット仕様の充足を確認できる。
