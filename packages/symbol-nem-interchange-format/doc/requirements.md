| 項目           | 内容                                    |

## 1. 概要

### 背景

Symbol向けの既存QRライブラリは、交換データの表現とQR画像の生成を同じ責務として扱う。そのため、QR画像を必要としない利用、QR以外の搬送手段、異なる実行環境、およびNEMとの共通利用に制約がある。

また、dApp、ウォレット、署名専用アプリの間で、接続要求・応答、権限範囲、拒否時の開示量を共通に解釈する形式がない。

### 目的

SNIFは、Symbol、NEM、およびチェーン非依存のデータを、アプリケーション、ウォレット、署名アプリ、バックアップ／リカバリーアプリなどの間で、通常のJSONによるJSON wireとして交換できる共通形式を提供する。

SNIFが提供する価値は、搬送手段・UI・SDKから独立したデータ交換、JSONの意味同値性・構造検証・形式上の破損検出、機密ペイロードの保護、および接続時の最小権限・最小開示である。

### 解決する課題

- 交換形式がQR画像生成や特定の実行環境に依存する。
- SymbolとNEMで再利用できる共通形式がない。
- 外部アプリとの接続要求、許可権限、アカウント情報、拒否結果の開示範囲を一貫して扱えない。
- 各アプリケーションが形式検証、意味検証、搬送、UI、認証の責務を個別に判断している。

## 2. 対象範囲と責任境界

### 対象

v1では、次を対象とする。

- 共通エンベロープによるSNIFデータの識別、バージョン管理、タイプ識別、チェーン・ネットワーク識別。
- Symbol、NEM、およびチェーン非依存データの表現。
- 公開情報、機密バックアップ、トランザクション要求、接続要求・応答、署名要求・応答、任意データ。
- 構造、必須項目、型、解釈可能性、完全性、サイズおよび資源上限の検証。
- 同一論理入力を実装環境間で同じ意味構造として再現できるJSON wire表現。
- JSON wireの識別およびテキスト専用搬送手段からの復元。
- 機密ペイロードの認証付き暗号による保護、および交換可能な暗号化プロバイダー。
- 異なる実装間の適合性を確認する機械可読fixture。

### 対象外

次はSNIF v1の対象外とする。

- QR画像の生成・読取、Animated QRの分割・結合。
- NFC、Deep Link、Clipboard、HTTP、WebSocket、Bluetooth、Relayなどの通信・搬送処理。
- ウォレットUI、利用者認証、利用者への承認表示の実装。
- 秘密鍵、ニーモニック、パスワードの永続保存、OSキーストア連携。
- トランザクションの作成、意味検証、署名、アナウンス、ノード通信。
- 接続セッションの確立、維持、失効、永続管理。
- dApp、URL、ドメイン、アイコン、Relayの真正性・信頼性の保証。
- `symbol/qr-library` 形式との変換。
- 既存CBORデータの変換・受理・生成、JSON/CBOR併存、自動変換およびCBOR互換アダプター。
- 外部パッケージによるカスタムタイプ登録。

### 外部へ委ねる責任

| 責任                                               | 担当                                                  |
| -------------------------------------------------- | ----------------------------------------------------- |
| 配送方法、通信路の機密性・認証、再送               | 搬送層または上位アプリケーション                      |
| 送信者認証、能動的改ざん防止                       | 上位アプリケーション、署名、MAC、または認証済み通信路 |
| アドレス、公開鍵、署名、トランザクションの意味検証 | ウォレット、署名アプリ、対象チェーンの仕様・SDK       |
| dAppや外部表示情報の信頼判断                       | ウォレット、署名アプリ、利用者                        |
| 権限の許可、強制、利用者への提示                   | ウォレットまたは署名アプリ                            |

SNIFの構造検証に成功したことは、格納データの業務上・ブロックチェーン上の有効性、送信者の本人性、または利用者が承認すべき安全性を意味しない。

## 4. ユースケース

### UC-001: 搬送手段を選ばないデータ交換

- 利用者: アプリケーションおよび搬送層開発者
- 目的: 同一のSNIFデータをQR、ファイル、通信路など複数の搬送手段で利用する。
- 事前条件: 送信側と受信側が対象バージョン・タイプを扱える。
- 基本フロー: 送信側がデータをSNIFへ変換し、搬送層が運び、受信側が構造と完全性を検証して復元する。
- 期待結果: 搬送手段に依存せず、同じ論理データまたは定義済みエラーを得る。
- 主な失敗条件: 未対応形式、不正型、破損、上限超過、未知の必須機能。

### UC-002: 公開情報の交換

- 利用者: ウォレット、アプリケーション、連絡先管理アプリ
- 目的: 名前、アドレス、公開鍵などの公開情報を交換する。
- 事前条件: 交換対象に秘密鍵やニーモニックを含めない。
- 基本フロー: 送信側が公開情報を生成し、受信側がSNIFの構造を検証して表示または保存する。
- 期待結果: 公開情報を復元できる。公開情報の受領は接続承認や権限付与を意味しない。
- 主な失敗条件: 秘密情報の混入、不正な型、チェーン・ネットワークの解釈不能。

### UC-003: 機密バックアップの交換

- 利用者: バックアップ／リカバリーアプリ
- 目的: accountまたはmnemonicをバックアップまたは移行する。
- 事前条件: 利用者が機密情報の搬送・保存リスクを理解している。
- 基本フロー: 送信側が平文または暗号化表現を生成し、受信側が検証、必要に応じて復号して復元する。
- 期待結果: 平文表現または認証付き暗号で保護された表現を、定義済みの結果として扱える。
- 主な失敗条件: 認証失敗、復号失敗、未知の暗号方式、資源上限超過、秘密情報のログ出力。

### UC-004: dAppとウォレットの接続要求

- 利用者: dApp、ウォレットまたは署名アプリ
- 目的: 対象チェーン・ネットワークと要求権限を示し、接続承認を求める。
- 事前条件: 要求に不透明なrequestId、アプリケーションの自己申告情報、既知の権限が含まれる。
- 基本フロー: dAppが要求を生成し、ウォレットが内容と権限を提示し、承認または拒否を返す。
- 期待結果: 要求と応答を対応付け、承認された範囲だけを表現できる。
- 主な失敗条件: 期限切れ、未知または重複した権限、要求外のチェーン・ネットワーク、自己申告情報の信頼誤認。

### UC-005: 署名またはトランザクション要求の交換

- 利用者: dApp、ウォレット、署名アプリ
- 目的: 署名対象または作成済みトランザクションを、署名処理を担うアプリへ渡す。
- 事前条件: 要求と応答を対応付ける識別情報があり、署名対象の表示情報と実バイト列を区別できる。
- 基本フロー: 要求を生成・搬送し、受信側が内容を確認して署名または拒否の結果を返す。
- 期待結果: 署名対象を誤って別のデータとして扱わず、結果を元の要求へ対応付けられる。
- 主な失敗条件: 期限切れ、対象不一致、意味検証失敗、表示と署名対象の不一致。

### UC-006: 不正入力の拒否

- 利用者: SNIF受信側
- 目的: 不正なデータによる誤処理、情報開示、資源枯渇を防ぐ。
- 事前条件: 受信側が安全な既定のサイズ・資源上限を持つ。
- 基本フロー: 入力を構造、型、バージョン、完全性、上限の順に必要な範囲で検証する。
- 期待結果: 不正入力を安全に拒否し、秘密情報や内部詳細を不要に開示しない。
- 主な失敗条件: 未処理例外、無制限のメモリ・CPU消費、詳細な復号原因の漏えい。

### UC-007: 異なる実装間の適合確認

- 利用者: ライブラリ開発者、仕様実装者、レビュー担当者
- 目的: 複数言語・複数環境の実装が同じ入力を同じ結果として扱うことを確認する。
- 事前条件: 正常系と拒否系の機械可読fixtureがある。
- 基本フロー: 各実装でfixtureを処理し、JSON意味構造、復元結果、またはエラーを比較する。
- 期待結果: 実装差による意味構造または検証結果の揺れを検出できる。
- 主な失敗条件: 意味構造の不一致、エラー条件の不一致、秘密値を含むfixtureの不適切な再利用。

## 5. 前提条件と制約

- SNIF利用側は、受領データの意味検証、送信者認証、搬送路の保護の要否を判断する。
- SymbolとNEMは同一視せず、チェーン識別とネットワーク識別を明示する。
- Mainnet、Testnet、Private networkなどのネットワークの扱いは、対象データの要件として区別できるものとする。具体的な識別値は未決定とする。
- JSON wireのみを生成・受理する。既存CBORの生成・受理、JSON/CBORの併存、自動変換および互換アダプターはv1の対象外とする。
- accountおよびmnemonicの平文表現はv1で扱えるものとする。ただし、SNIFは平文の秘密性、保存安全性、搬送安全性を保証しない。
- 暗号化プロバイダーに必要な乱数および暗号処理環境が利用できる。
- v1では圧縮、搬送層の分割、カスタムタイプ登録を扱わない。
- 根拠のない性能値、サイズ値、暗号パラメータは要件として固定しない。

### 6.1 接続に関する明示的な境界

- `contact` は名前、アドレス、公開鍵などの公開情報交換であり、接続状態を確立しない。
- 接続要求の `origin`、アプリケーション名、アイコンなどは自己申告の表示メタデータであり、本人性・ドメイン所有・信頼性の証明ではない。
- ウォレットまたは署名アプリは、承認前に要求された権限を利用者へ確認可能な形で提示する責任を負う。
- 承認されたアカウント情報を利用する側は、対象チェーン・ネットワークの規則に従い、アドレスと公開鍵などの意味的整合性を別途検証する。

## 7. 非機能要件

### セキュリティ

| ID      | 優先度 | 要件                                                                                                             |
| ------- | ------ | ---------------------------------------------------------------------------------------------------------------- |
| SEC-001 | MUST   | 秘密鍵、ニーモニック、パスワード、導出鍵、復号済み機密ペイロードをログ、例外メッセージ、診断出力へ含めないこと。 |
| SEC-002 | MUST   | 未知入力、誤ネットワーク、期限切れ、重複権限、要求外権限、破損、認証失敗を安全側に拒否すること。                 |
| SEC-003 | MUST   | `origin`、URL、アイコン、Relay情報などの外部メタデータを認証または信頼の根拠として扱わないこと。                 |
| SEC-004 | MUST   | デコーダーおよび復号処理に、設定可能なサイズ、ネスト、要素数、暗号処理資源の上限を適用できること。               |
| SEC-005 | MUST   | 認証なし暗号を機密ペイロード保護の成功結果として扱わないこと。                                                   |
| SEC-006 | SHOULD | 機密情報の不要なメモリコピーを抑制し、実行環境で可能な範囲の消去方法と限界を文書化すること。                     |
| SEC-007 | MUST   | 予測困難性を必要とする値に、暗号学的に安全な乱数を使用すること。                                                 |
| SEC-008 | MUST   | 非暗号化の完全性検証を送信者認証と誤認させないこと。                                                             |

### 相互運用性・可搬性

| ID      | 優先度 | 要件                                                                                                                                                |
| ------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| NFR-001 | MUST   | SNIFのJSON wireの論理結果が複数言語および複数端末で同じ意味に解釈できること。                                                                       |
| NFR-002 | MUST   | 同じJSON意味構造または定義済みエラーを機械可読fixtureで再現できること。プロパティ順や空白の一致を必須条件としないこと。                             |
| NFR-003 | MUST   | QR画像生成、特定の搬送手段、特定のチェーンSDKまたは特定の通信サービスをSNIF本体の必須依存にしないこと。                                             |
| NFR-004 | MUST   | 対象環境を仕様設計で決定し、決定した環境の差異がSNIFのJSON wireの論理要件や検証結果を変更しないこと。対象環境の具体的な範囲はOPEN-010で定めること。 |
| NFR-005 | SHOULD | 配布形式、型情報、モジュール形式、依存関係を対象環境との互換性を保つ形で提供すること。具体的な形式は未決定とする。                                  |

### 保守性・検証可能性

## 11. 仕様設計への引継ぎ

### 確定した要件

- 搬送手段、UI、SDK、通信処理とSNIFの交換形式を分離する。
- Symbol、NEM、チェーン非依存データを区別する。
- 標準データタイプ、JSON構造検証、意味同値性、保証単位の分離、機密ペイロード保護、接続要求・応答、署名要求・応答をv1の要件対象とする。
- contactを接続承認や権限付与の代替にしない。
- 接続の承認は要求済み権限の部分集合に限り、拒否・エラー時の開示を最小化する。
- 外部アプリケーション情報は自己申告の表示メタデータとして扱う。
- accountおよびmnemonicの平文表現を扱えるが、SNIFはその保存・搬送安全性を保証しない。

### 確定した制約

- `@nemnesia/snif` は既存要件として維持する。JSON v1のMIME TypeはOPEN-002で決定する。
- JSON wireのみを生成・受理し、既存CBORの変換・受理・生成、JSON/CBOR併存、自動変換、互換アダプターはv1対象外とする。
- QR画像生成、通信、UI、ノード接続、セッション永続管理、既存QR形式変換、カスタムタイプ登録はv1対象外とする。
- SNIFはチェーン上・業務上の意味検証、送信者認証、dAppの真正性を保証しない。
- 既存CBOR利用者の移行、既存CBOR資料・fixtureの更新および廃止手順は、JSON v1の採用側が担う事項として仕様設計で具体化する。

### 詳細設計が必要な事項

- 共通エンベロープ、タイプ、チェーン、ネットワーク、拡張の論理構造とJSON wire表現。
- JSONの意味同値性、識別・配布方法、エラー表現、サイズ・資源上限。
- 暗号プロファイル、KDF、認証対象、provider境界、秘密情報のメモリ取り扱い。
- 接続権限語彙、requestId、期限、リプレイ防止、callbackおよびRelayの扱い。
- SymbolおよびNEMのデータ表現と、意味検証を外部へ委ねる境界。
- API、型定義、配布形式、対応環境、fixture manifestの構造。

### 未決定事項

`OPEN-001` から `OPEN-010` を仕様設計で決定し、決定理由、影響、適合fixtureを記録する。未決定事項を解消するまで、具体的なJSON正規化方式、暗号パラメータ、APIシグネチャ、エラーコードを要件から推測して追加しない。
