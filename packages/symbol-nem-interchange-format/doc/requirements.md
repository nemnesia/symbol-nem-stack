## 2. 背景

Symbolには、アカウント、ニーモニック、アドレス、トランザクションなどの情報をQRコードとして出力するための `symbol/qr-library` が存在する。

既存ライブラリは、交換対象となるデータ形式の生成に加えて、QR画像生成機能まで保持している。そのため、次の問題がある。

- データ交換フォーマットだけを利用したい場合でも、QR画像生成機能への依存が発生する
- QRコード以外の搬送手段へ適用しにくい
- Web、Node.js、React Nativeなど、異なる実行環境で利用する際の依存関係が増える
- Animated QR、NFC、Deep Link、ファイルなどへの展開が難しい
- dAppとウォレットまたは署名アプリ間の接続情報を交換する標準形式が存在しない
- Symbolを中心とした既存形式であり、NEMを含めた共通利用には適していない

このため、画像生成機能を持たず、データの生成、シリアライズ、暗号化および検証だけを担当する新しい交換フォーマットとライブラリを定義する。

---

## 3. 目的

SNIFの目的は、SymbolおよびNEMで使用するデータを、アプリケーション、ウォレット、署名デバイスおよび他の端末間で交換するための共通フォーマットを提供することである。

SNIFライブラリは、次の責務を持つ。

1. 交換データの構造を定義する
2. 交換データを決定的なバイナリ形式へ変換する
3. バイナリ形式から元のデータを復元する
4. データが破損または改変されていないことを検証する
5. 秘密鍵やニーモニックなどの機密情報を暗号化する
6. 暗号化アルゴリズムを交換可能にする
7. dAppとウォレットまたは署名アプリ間の接続要求および接続応答を表現する
8. QRコード以外の複数の搬送手段で利用できる形式を提供する

---

## 4. 基本方針

### 4.1 搬送手段からの独立

SNIFはQRコードそのものを仕様対象としない。

SNIFが生成したデータは、次のような搬送手段で利用できるものとする。

- 通常のQRコード
- Animated QR
- ファイル
- NFC
- Deep Link
- Clipboard
- Bluetooth
- WebSocket
- HTTP
- Relayサーバ
- その他のバイナリまたはテキスト搬送手段

SNIFライブラリは、QR画像、バーコード画像その他の視覚表現を生成しない。

### 4.2 内容物への非関与

SNIFは伝送フォーマットであり、格納されたデータの業務上またはブロックチェーン上の妥当性を保証しない。

例えば、次の検証はSNIFの責務外とする。

- 秘密鍵から公開鍵を導出できるか
- アドレスが公開鍵と一致するか
- トランザクションが対象ネットワークで実行可能か
- トランザクションの残高が足りているか
- トランザクションの期限が有効か
- 署名がトランザクションに対して正しいか
- 接続先dAppが安全であるか
- URLやドメインが信頼できるか
- ニーモニックの単語が特定の辞書に含まれているか

SNIFが行う検証は、次の範囲に限定する。

- SNIFデータとして構文が正しいこと
- 必須フィールドが存在すること
- フィールド型が正しいこと
- フォーマットバージョンが解釈可能であること
- データタイプが認識可能であること
- データ長が仕様上の制限以内であること
- 非暗号化データについて、伝送中の偶発的な破損を検出できること
- 暗号化データについて、認証付き暗号の認証範囲内で改変を検出できること
- 暗号化データが正常に認証および復号できること

非暗号化データのチェックサムまたはハッシュは、攻撃者が検証値を再計算できる能動的改ざんを防止または検出するものではない。能動的改ざんの検出および送信者認証は、電子署名、MAC、または認証済み搬送路を使用する上位アプリケーションの責務とする。

### 4.3 チェーン中立な共通構造

SymbolとNEMで共通する概念は、共通のデータ構造で表現する。

チェーン固有のデータが必要な場合は、チェーン識別子とタイプ固有ペイロードによって区別する。

### 4.4 決定的エンコード

同一の入力値からは、常に同一のバイナリデータが生成されなければならない。

マップのキー順序、整数表現、文字コードその他のエンコード規則を固定し、実装間で同一結果を再現できるものとする。

## 8. システム構成

SNIFは、概念上次のレイヤーに分割する。

```text
アプリケーション
    ↓
タイプ別SNIFペイロード
    ↓
SNIF共通エンベロープ
    ↓
暗号化レイヤー（任意）
    ↓
決定的バイナリエンコード
    ↓
搬送手段
    ├─ QR
    ├─ Animated QR
    ├─ NFC
    ├─ Deep Link
    ├─ File
    └─ Relay
```

SNIFライブラリが担当する範囲は、タイプ別ペイロードから決定的バイナリエンコードまでとする。

## 9. 共通エンベロープ要件

すべてのSNIFデータは、共通エンベロープに格納する。

### 9.1 論理構造

共通エンベロープは最低限、次の情報を保持する。

| フィールド |     必須 | 説明                                     |
| ---------- | -------: | ---------------------------------------- |
| magic      |     必須 | SNIFデータを識別する固定値               |
| version    |     必須 | エンベロープ仕様バージョン               |
| type       |     必須 | ペイロードのデータタイプ                 |
| chain      | 条件付き | Symbol、NEMまたはチェーン非依存          |
| network    |     任意 | Mainnet、Testnetなどのネットワーク識別   |
| flags      |     必須 | 暗号化などの状態                         |
| payload    |     必須 | タイプ別ペイロードまたは暗号化ペイロード |
| integrity  |     必須 | 完全性検証情報                           |
| extensions |     任意 | 将来拡張用領域                           |

### 9.2 識別子

`magic` は `snif` とし、SNIFデータを他のバイナリデータと区別する固定値とする。

デコーダーは、`magic` が一致しないデータをSNIFとして処理してはならない。

### 9.3 バージョン

バージョンは、少なくとも次の二つを区別できる設計とする。

- エンベロープ仕様バージョン
- ペイロードタイプ仕様バージョン

エンベロープ全体の互換性と、個別データタイプの互換性を独立して管理できるものとする。

### 9.4 チェーン識別

チェーン識別子は、最低限次を表現できるものとする。

- `symbol`
- `nem`
- `none`

`none` は、接続情報や任意オブジェクトなど、特定チェーンに依存しないデータに使用する。

独自チェーン識別子を自由文字列として直接格納する設計にはせず、仕様で管理された識別値を使用する。

`connection-request` および `connection-response` は複数チェーンの交渉を表現するため、共通エンベロープの `chain` は `none` とする。要求対象のチェーンおよびネットワークはタイプ別ペイロードで表現する。その他の標準タイプは、単一チェーンに属する場合、共通エンベロープの `chain` に当該チェーンを指定する。

### 9.5 ネットワーク識別

ネットワーク識別情報は、各チェーンのネットワークタイプを表現できなければならない。

ただし、SNIFはネットワーク識別子の実在性または有効性を保証しない。

接続要求では、各ネットワーク指定がどのチェーンに属するかを一意に解釈できる構造とし、単独のネットワーク一覧として曖昧に表現してはならない。接続応答では、承認されたアカウントごとに選択されたチェーンおよびネットワークを明示する。

### 9.6 拡張領域

将来の拡張のため、未認識フィールドを保持または安全に無視できる設計とする。

必須フィールドと任意フィールドを明確に区別する。

未知の必須機能を示すフラグが存在する場合、デコーダーは処理を中止しなければならない。

## 10. データタイプ要件

初期バージョンでは、最低限次のデータタイプを定義する。

| タイプ              | 用途                                 |     機密性 |
| ------------------- | ------------------------------------ | ---------: |
| address             | アドレス交換                         |         低 |
| contact             | 名前、アドレス、公開鍵などの交換     |         低 |
| account             | 秘密鍵を含むアカウント情報           |         高 |
| mnemonic            | ニーモニックの交換またはバックアップ |         高 |
| transaction-request | トランザクション署名または送信要求   |         中 |
| connection-request  | dAppからの接続要求                   |         中 |
| connection-response | 接続要求への応答                     |         中 |
| signing-request     | メッセージまたはデータの署名要求     |         中 |
| signing-response    | 署名結果                             |         中 |
| object              | 任意データの交換                     | 指定による |

## 11. アドレスフォーマット

アドレスフォーマットは、SymbolまたはNEMのアドレス情報を交換するために使用する。

最低限、次の情報を保持できるものとする。

| フィールド | 必須 | 説明                     |
| ---------- | ---: | ------------------------ |
| address    | 必須 | エンコード済みアドレス   |
| label      | 任意 | 表示名                   |
| publicKey  | 任意 | 対応する公開鍵           |
| message    | 任意 | 受取人向け補足           |
| metadata   | 任意 | アプリケーション固有情報 |

SNIFはアドレスのチェックサム、公開鍵との一致、ネットワークとの一致を保証しない。

ただし、フィールド長、文字列型および文字コードは検証してよい。

---

## 12. 連絡先フォーマット

連絡先フォーマットは、ユーザーまたはアカウントの公開情報を交換するために使用する。

最低限、次の情報を保持できるものとする。

- 表示名
- SymbolまたはNEMアドレス
- 公開鍵
- チェーン
- ネットワーク
- アイコンまたはアバターへの参照
- 任意の説明
- アプリケーション固有メタデータ

秘密鍵およびニーモニックは、連絡先フォーマットに格納してはならない。

---

## 13. アカウントフォーマット

アカウントフォーマットは、秘密鍵を含むアカウント情報のバックアップまたは移行に使用する。

最低限、次の情報を保持できるものとする。

| フィールド     | 必須 | 説明                 |
| -------------- | ---: | -------------------- |
| privateKey     | 必須 | アカウント秘密鍵     |
| publicKey      | 任意 | 公開鍵               |
| address        | 任意 | アドレス             |
| label          | 任意 | アカウント表示名     |
| derivationPath | 任意 | HDウォレット導出パス |
| metadata       | 任意 | 補助情報             |

アカウントフォーマットは機密データとして扱う。

暗号化された表現および平文の表現を仕様上許可する。平文アカウントは機密データであり、SNIFによる暗号化・安全な搬送・保存を保証しないことを利用者へ明示する。

---

## 14. ニーモニックフォーマット

ニーモニックフォーマットは、ニーモニックフレーズのバックアップまたは移行に使用する。

最低限、次の情報を保持できるものとする。

- ニーモニック
- 言語識別子
- ニーモニック方式
- 導出方式
- 既定導出パス
- アカウント数またはインデックス情報
- 任意メタデータ

ニーモニックフォーマットは機密データとして扱う。暗号化された表現および平文の表現を仕様上許可し、平文ニーモニックの機密性はSNIFによって保証しない。

SNIFは、ニーモニックの単語妥当性、チェックサムまたは導出結果を検証しない。

---

## 15. トランザクション要求フォーマット

トランザクション要求フォーマットは、作成済みトランザクションをウォレットまたは署名アプリへ渡すために使用する。

最低限、次の情報を保持できるものとする。

| フィールド         |     必須 | 説明                              |
| ------------------ | -------: | --------------------------------- |
| transactionPayload |     必須 | シリアライズ済みトランザクション  |
| generationHash     | 条件付き | Symbol署名に必要なGeneration Hash |
| requestId          |     必須 | 要求を一意に対応付ける識別子      |
| callback           |     任意 | 応答先情報                        |
| expiresAt          |     任意 | 要求期限                          |
| message            |     任意 | ユーザー向け説明                  |
| metadata           |     任意 | dApp固有情報                      |

SNIFは、トランザクションのCatbuffer構造、署名可能性、手数料、期限、残高または安全性を検証しない。

`transactionPayload` は不透明なバイト列として扱う。

---

## 16. 接続要求フォーマット

接続要求フォーマットは、dAppがウォレットまたは署名アプリに対して接続を要求するために使用する。

最低限、次の情報を保持できるものとする。

| フィールド      |     必須 | 説明                                     |
| --------------- | -------: | ---------------------------------------- |
| requestId       |     必須 | 接続要求の一意識別子                     |
| applicationName |     必須 | dApp名称                                 |
| applicationUrl  |     任意 | dAppのURL                                |
| applicationIcon |     任意 | アイコン参照                             |
| targets         |     必須 | 要求するチェーンとネットワーク条件の一覧 |
| permissions     |     必須 | 要求する権限一覧                         |
| callback        | 条件付き | 応答先                                   |
| relay           |     任意 | Relay接続情報                            |
| challenge       |     任意 | 応答確認用ランダム値                     |
| expiresAt       |     必須 | 要求期限                                 |
| metadata        |     任意 | dApp固有情報                             |

`targets` の各要素は、チェーン識別子と、そのチェーンに対する許容ネットワーク一覧またはネットワーク未指定を表現する。チェーン識別子は重複してはならない。接続要求の共通エンベロープでは `chain = none` とし、`network` は指定しない。

期限切れの接続要求は承認してはならない。要求に未知の権限、未知のチェーン、または解釈不能なネットワーク条件が含まれる場合、ウォレットまたは署名アプリは当該要求を承認してはならない。

### 16.1 接続権限

接続要求は、必要な権限を明示しなければならない。

初期仕様では、最低限次の権限を表現できるものとする。

- アドレス参照
- 公開鍵参照
- アカウント選択
- トランザクション署名要求
- メッセージ署名要求
- 署名済みトランザクション返却
- トランザクション送信要求

権限の意味はSNIF仕様で識別するが、権限の許可判断と強制はウォレットまたは署名アプリの責務とする。

要求権限は重複してはならない。承認応答の許可権限は、対応する接続要求に含まれる既知の要求権限の重複のない部分集合でなければならない。要求されていない権限を応答で追加してはならない。

### 16.2 接続要求の真正性

SNIFは、接続要求に記載されたアプリケーション名、URL、アイコンまたはRelayが真正であることを保証しない。

ウォレットは接続要求の内容を信頼済み情報として表示してはならない。

---

## 17. 接続応答フォーマット

接続応答フォーマットは、接続要求に対する承認、拒否またはエラーを返すために使用する。

接続応答の共通エンベロープでは `chain = none` とし、`network` は指定しない。選択されたチェーンおよびネットワークは、承認時の `accounts` に明示する。

最低限、次の情報を保持できるものとする。

| フィールド        |     必須 | 説明                                     |
| ----------------- | -------: | ---------------------------------------- |
| requestId         |     必須 | 元の接続要求識別子                       |
| status            |     必須 | approved、rejected、error                |
| sessionId         | 条件付き | 承認時のセッション識別子                 |
| accounts          | 条件付き | 公開を許可したアカウント情報。承認時のみ |
| permissions       | 条件付き | 実際に許可された権限。承認時のみ         |
| responseChallenge |     任意 | challengeに対応する値                    |
| expiresAt         |     任意 | セッションまたは応答期限                 |
| error             | 条件付き | エラー情報                               |
| metadata          |     任意 | 実装固有情報                             |

接続応答の状態は `approved`、`rejected`、`error` のいずれか一つとし、状態ごとのフィールド規則を次のとおりとする。

| 状態     | 必須フィールド                                      | 許可される追加フィールド                                     | 禁止フィールド                                                      |
| -------- | --------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------- |
| approved | requestId、status、sessionId、accounts、permissions | responseChallenge、expiresAt、metadata                       | error                                                               |
| rejected | requestId、status                                   | errorのうち利用者拒否を示す最小限のコード、responseChallenge | sessionId、accounts、permissions、expiresAt、アカウント由来metadata |
| error    | requestId、status、error                            | responseChallenge                                            | sessionId、accounts、permissions、expiresAt、アカウント由来metadata |

承認応答の `permissions` は、対応する接続要求の要求権限の部分集合でなければならない。`accounts` の各要素は、接続要求の `targets` に含まれるチェーンおよびネットワーク条件を満たさなければならない。要求外のチェーン、ネットワーク、権限またはアカウント情報を含む承認応答は不正とする。

拒否またはエラー応答は、元の要求との対応に必要な情報を除き、アカウント、公開鍵、許可権限、セッション識別子その他の不要な情報を開示してはならない。

秘密鍵またはニーモニックを接続応答に含めてはならない。

## 18. 署名要求フォーマット

署名要求フォーマットは、トランザクション以外のメッセージまたは任意バイト列への署名を要求するために使用する。

最低限、次の情報を保持できるものとする。

- requestId
- 署名対象データ
- 署名対象データの表現形式
- 署名方式または用途識別子
- 期待する署名者
- チェーン
- ネットワーク
- ユーザー向け表示文
- callback
- expiresAt
- metadata

署名対象データは、表示用文字列と実際の署名対象バイト列を明確に区別する。

ユーザーに表示される文字列と署名対象データが異なる場合、ウォレットまたは署名アプリが両者を確認できる構造とする。

SNIFは、署名要求が安全であること、署名対象の意味または署名後の用途を保証しない。

## 19. 署名応答フォーマット

署名応答フォーマットは、署名要求またはトランザクション要求に対する結果を返すために使用する。

最低限、次の情報を保持できるものとする。

| フィールド      |     必須 | 説明                    |
| --------------- | -------: | ----------------------- |
| requestId       |     必須 | 元の要求識別子          |
| status          |     必須 | signed、rejected、error |
| signerPublicKey | 条件付き | 署名者公開鍵            |
| signature       | 条件付き | 生成された署名          |
| signedPayload   |     任意 | 署名済みペイロード      |
| error           | 条件付き | エラー情報              |
| metadata        |     任意 | 実装固有情報            |

SNIFは返却された署名の暗号学的正当性を検証しない。

アプリケーションは、必要に応じてSymbol SDK、NEM SDKまたは暗号ライブラリを用いて署名を検証する。

## 20. 任意オブジェクトフォーマット

任意オブジェクトフォーマットは、標準タイプに該当しないアプリケーション固有データを格納するために使用する。

最低限、次の情報を保持する。

- namespace
- schema
- schemaVersion
- contentType
- data
- metadata

`namespace` は、異なるアプリケーション間でスキーマ名が衝突しないように使用する。

任意オブジェクトは、SNIF標準タイプの代替として使用することを推奨しない。

## 21. 暗号化要件

### 21.1 基本要件

SNIFは、秘密鍵およびニーモニックなどの機密情報を暗号化できなければならない。

暗号化方式は固定せず、交換可能な暗号化プロバイダーとして実装する。

### 21.2 認証付き暗号

暗号化方式は、機密性だけでなく完全性を保証する認証付き暗号方式を使用しなければならない。

暗号化プロバイダーは最低限、次の機能を提供する。

- 暗号化
- 復号
- 認証タグ検証
- パスワードからの鍵導出
- 暗号学的乱数生成
- アルゴリズム識別子の提供
- パラメーターのシリアライズ
- パラメーターの検証

### 21.3 暗号化メタデータ

暗号化エンベロープは最低限、次の情報を保持する。

| フィールド        |       必須 | 説明                        |
| ----------------- | ---------: | --------------------------- |
| algorithm         |       必須 | 暗号化アルゴリズム識別子    |
| kdf               |   条件付き | 鍵導出関数識別子            |
| kdfParameters     |   条件付き | salt、コストなど            |
| nonce             |       必須 | nonceまたはIV               |
| ciphertext        |       必須 | 暗号文                      |
| authenticationTag | 方式による | 認証タグ                    |
| aadDefinition     |       任意 | AADとして使用する領域の定義 |

### 21.4 パスワード方式

パスワードから直接暗号鍵を生成してはならない。

パスワード方式では、専用の鍵導出関数を使用する。

鍵導出パラメーターは、復号に必要な範囲で暗号化エンベロープに保存する。

### 21.5 プロバイダー交換

アプリケーションは、アルゴリズム識別子に対応する暗号化プロバイダーを登録できるものとする。

概念上、次のようなインターフェースを提供する。

```typescript
interface EncryptionProvider {
  readonly algorithm: string;

  encrypt(plaintext: Uint8Array, options: EncryptionOptions): Promise<EncryptedPayload>;

  decrypt(payload: EncryptedPayload, options: DecryptionOptions): Promise<Uint8Array>;
}
```

同期処理を強制せず、WebCrypto、ネイティブキーストアまたは外部暗号デバイスに対応できるよう、非同期APIを基本とする。

### 21.6 暗号化対象

暗号化は、共通エンベロープ全体ではなく、タイプ別ペイロードを対象とすることを基本とする。

これにより、復号前でも次の情報を判別可能にする。

- SNIFデータであること
- バージョン
- データタイプ
- 使用暗号方式
- 必要な復号プロバイダー

ただし、チェーンやデータタイプ自体を秘匿する必要がある用途に備え、将来的なエンベロープ全体暗号化を妨げない設計とする。

---

## 22. 完全性検証要件

### 22.1 非暗号化データ

非暗号化データについても、伝送中の偶発的な破損を検出できなければならない。非暗号化データの完全性検証値は、能動的な攻撃者による改ざんまたは送信者の真正性を保証しない。

完全性検証値は、少なくとも次の領域を対象とする。

- エンベロープバージョン
- データタイプ
- チェーン
- ネットワーク
- フラグ
- ペイロード

### 22.2 暗号化データ

暗号化データの改変検出は、認証付き暗号の認証タグによって行う。

暗号化エンベロープのうち暗号化されないヘッダー情報は、AADとして認証対象に含める。

### 22.3 完全性と真正性

チェックサムまたはハッシュによる完全性検証は、送信者の真正性を保証しない。

送信者認証または能動的改ざんの検出が必要な場合は、上位アプリケーションで電子署名、MAC、または認証済み通信路を使用する。SNIFの受入試験では、非暗号化完全性検証について偶発的破損の検出のみを適合対象とし、送信者認証の成立を適合条件としてはならない。

---

## 23. シリアライズ要件

### 23.1 成果要件と承認済み制約

成果要件は、決定的で言語中立なバイナリ形式により、同一の論理入力から実装言語に依存せず同一のバイト列を生成できることである。

初期バージョンでは、決定的CBORを採用することを承認済み制約とする。具体的なCBORプロファイル、タグ利用、マップキー規則および数値表現は仕様設計で確定する。

### 23.2 内部形式

標準バイナリ形式は、次の要件を満たさなければならない。

- 同一入力から同一バイト列が生成される
- 文字列はUTF-8で表現する
- バイナリデータを文字列へ変換せず保持できる
- 整数の表現が実装間で一致する
- マップキーの順序が決定的である
- 不要な浮動小数点数を使用しない
- 未知フィールドを処理できる
- JavaScriptの安全整数範囲を超える値を安全に表現できる

### 23.3 テキスト表現

URL、Deep Link、Clipboardなど、テキストのみを扱う搬送手段向けに、バイナリデータをテキストへ変換する機能を提供してよい。

テキスト表現は、次の要件を満たす。

- 大文字小文字の変換に影響されにくい
- 先頭にSNIFであることを示す識別子を持つ
- デコード時に不正文字を検出できる
- バイナリ形式との相互変換が可能である

テキストエンコードはSNIFの内容構造とは分離する。

### 23.4 圧縮

SNIF v1は圧縮を持たない。v1のエンコーダーは圧縮済みペイロードを生成してはならず、デコーダーは圧縮を示す入力をSNIF v1として受理してはならない。

将来バージョンで圧縮を導入する場合は、後方互換性および展開時の資源制限を含めて別途仕様化する。

---

## 24. API要件

ライブラリは、エンコード、デコード、検証、ヘッダー解析、暗号化プロバイダー登録の能力を提供する。以下のTypeScriptシグネチャは参照API形状であり、公開APIの最終的な命名、引数構造および同期・非同期の分割は仕様設計で確定する。

### 24.1 エンコード

```typescript
encode(value: SnifValue, options?: EncodeOptions): Uint8Array;
```

### 24.2 デコード

```typescript
decode(data: Uint8Array, options?: DecodeOptions): SnifValue;
```

暗号化データを処理する場合は非同期APIを提供する。

```typescript
decodeAsync(
  data: Uint8Array,
  options?: DecodeOptions,
): Promise<SnifValue>;
```

### 24.3 暗号化エンコード

```typescript
encodeEncrypted(
  value: SnifValue,
  options: EncryptEncodeOptions,
): Promise<Uint8Array>;
```

### 24.4 検証

```typescript
validate(data: Uint8Array): ValidationResult;
```

`validate` は、秘密鍵、ニーモニック、トランザクションなどの意味的妥当性を検証しない。

### 24.5 ヘッダー解析

復号せずにエンベロープ情報を取得するAPIを提供する。

```typescript
inspect(data: Uint8Array): SnifEnvelopeInfo;
```

### 24.6 プロバイダー登録

```typescript
registerEncryptionProvider(provider: EncryptionProvider): void;
```

### 24.7 データタイプ拡張

標準タイプに加えて、外部パッケージが独自データタイプを登録できる拡張機構を検討する。

ただし、標準タイプ識別子と独自タイプ識別子が衝突しない名前空間を設ける。

## 25. エラー要件

エラーは、少なくとも次のカテゴリーへ分類する。

| エラーカテゴリー       | 説明                         |
| ---------------------- | ---------------------------- |
| INVALID_MAGIC          | SNIF識別子ではない           |
| UNSUPPORTED_VERSION    | 対応していないバージョン     |
| UNSUPPORTED_TYPE       | 対応していないデータタイプ   |
| UNSUPPORTED_CHAIN      | 対応していないチェーン       |
| UNSUPPORTED_ALGORITHM  | 暗号方式に未対応             |
| MALFORMED_ENVELOPE     | エンベロープ構造が不正       |
| MALFORMED_PAYLOAD      | ペイロード構造が不正         |
| MISSING_REQUIRED_FIELD | 必須フィールドがない         |
| INVALID_FIELD_TYPE     | フィールド型が不正           |
| LIMIT_EXCEEDED         | サイズまたはネスト上限超過   |
| INTEGRITY_CHECK_FAILED | 完全性検証失敗               |
| DECRYPTION_FAILED      | 復号失敗                     |
| AUTHENTICATION_FAILED  | 認証タグ検証失敗             |
| INVALID_PASSWORD       | パスワードが不正である可能性 |
| EXPIRED                | 期限切れ                     |
| PROVIDER_ERROR         | 外部プロバイダーでエラー     |

暗号化データでは、パスワード誤りとデータ改変を外部へ詳細に区別して返すことで情報漏えいが生じないよう配慮する。

## 26. サイズおよびリソース制限

DoSおよびメモリ枯渇を防ぐため、デコーダーは次の制限を設定可能とする。

- エンベロープ最大サイズ
- ペイロード最大サイズ
- 文字列最大長
- バイナリ最大長
- 配列最大要素数
- マップ最大要素数
- 最大ネスト深度
- 暗号鍵導出パラメーターの最大値

ライブラリは安全な既定値を持つ。

利用者は用途に応じて制限値を引き下げられるものとする。

危険な上限緩和は明示的に行わなければならない。

## 27. セキュリティ要件

### 27.1 機密情報のログ出力禁止

ライブラリは、次の情報をログまたは例外メッセージへ出力してはならない。

- 秘密鍵
- ニーモニック
- 復号済みペイロード
- パスワード
- 導出済み暗号鍵

### 27.2 機密情報のコピー抑制

実装上可能な範囲で、機密情報の不要なメモリコピーを避ける。

利用終了後にバッファを上書きできるAPIまたは運用方法を提供する。

ただし、JavaScript実行環境では完全なメモリ消去を保証できないことを文書化する。

### 27.3 乱数

salt、nonce、requestId、challengeなど、予測困難性が必要な値には暗号学的安全性を持つ乱数生成器を使用する。

`Math.random()` を使用してはならない。

### 27.4 既定値

次の方針を安全な既定値とする。

- 秘密鍵およびニーモニックは機密データとして扱い、暗号化を利用できる
- 認証なし暗号を許可しない
- 未知の暗号方式を自動的にフォールバックしない
- 不明な必須フラグを無視しない
- デコードサイズに上限を設ける

### 27.5 エラーメッセージ

復号失敗時には、パスワード誤り、認証タグ不正、改変の詳細を攻撃者が判別できないエラー設計とする。

デバッグ用途の詳細情報は、明示的に有効化した場合のみ提供する。

---

## 28. 非機能要件

### 28.1 対応環境

最低限、次の環境を対象とする。

- Node.js
- モダンブラウザ
- React Native
- Expo

環境固有機能は抽象化し、Node.js専用APIへの直接依存を避ける。

### 28.2 モジュール形式

次の利用形態を考慮する。

- ESM
- TypeScript型定義
- Tree Shaking
- Browser Bundle
- React Native Bundle

CommonJSはサポートしない。

### 28.3 依存関係

画像生成ライブラリへ依存してはならない。

可能な限り依存パッケージを限定する。

暗号処理は、WebCryptoまたは交換可能なプロバイダーを使用し、特定のネイティブモジュールを必須としない。

### 28.4 性能

通常の静的QRコードで運べる程度のデータについて、参照実装の性能基準をベンチマークとして定義し、対象環境、入力サイズ、反復回数および許容時間を再現可能な形で公開する。具体的な閾値は仕様設計で確定し、受入試験では当該ベンチマークを使用する。

大容量データについては、SNIF本体で分割せず、Animated QRまたはストリーミング搬送レイヤーに委ねる。

### 28.5 可搬性

シリアライズ結果は、JavaScript以外の言語でも実装可能な仕様とする。

TypeScript固有の型やJSON固有の曖昧な数値表現を、ワイヤーフォーマットへ持ち込まない。

---

## 29. 互換性要件

### 29.1 後方互換性

同一メジャーバージョンでは、既存の必須フィールドの意味を変更しない。

任意フィールドの追加は許可する。

既存フィールドの削除、型変更または意味変更はメジャーバージョン変更とする。

### 29.2 未知フィールド

デコーダーは、未知の任意フィールドを安全に無視できるものとする。

再エンコード時に未知フィールドを保持するかどうかは、APIオプションとして定義する。

### 29.3 既存QRライブラリとの互換

既存 `symbol/qr-library` 形式との互換性は提供しない。同形式からSNIFへの変換アダプターおよびSNIFから同形式への変換アダプターは、本プロジェクトの成果物として提供しない。

新仕様本体および周辺パッケージに既存形式の制約を持ち込まない。

### 30.1 単体テスト

最低限、次をテストする。

- 各データタイプのエンコード
- 各データタイプのデコード
- エンコード後のデコード一致
- 決定的エンコード
- 必須フィールド検証
- 不正型検証
- バージョン検証
- サイズ制限
- 暗号化
- 復号
- パスワード誤り
- 認証タグ改変
- nonce改変
- ヘッダー改変
- 未知フィールド
- 未知タイプ
- 未知暗号方式
- プロバイダー交換

### 30.2 適合テストベクトル

異なる実装間で同一結果を確認するため、機械可読な適合fixtureを提供する。

各fixtureは最低限、次を含む。

- fixtureを一意に識別するID

- 正常系または拒否系の区分

- 暗号化ケースの固定salt
- 固定nonce
- 固定パスワード
- 導出鍵
- AAD
- ciphertext
- authentication tag

テスト専用の固定暗号値は、本番用途へ流用してはならない。

### 30.3 最低fixture matrix

| 対象             | 必須ケース                           |
| ---------------- | ------------------------------------ |
| データタイプ     | 標準タイプごとに正常系1件以上        |
| チェーン         | Symbol、NEM、none                    |
| ネットワーク     | Mainnet、Testnet相当                 |
| アカウント       | Symbol、NEM各1件以上（暗号化、平文） |
| ニーモニック     | 暗号化、平文                         |
| トランザクション | Symbol、NEM各1件以上                 |
| 接続             | 承認、拒否、エラー                   |
| 署名             | 成功、拒否、エラー                   |
| 暗号化           | 正常復号、誤パスワード、改変         |
| バージョン       | 対応、未対応                         |
| サイズ           | 上限内、上限超過                     |
| 拡張             | 未知任意フィールド、未知必須機能     |

### 30.4 Fuzzテスト

デコーダーおよび復号処理に対しFuzzテストを実施する。

不正入力によって次が発生しないことを確認する。

- プロセス停止
- 無制限メモリ消費
- 無制限CPU消費
- スタックオーバーフロー
- 機密情報漏えい
- 未処理例外

## 31. 要件トレーサビリティおよび適合判定

### 31.1 要件識別子

適合性の判定対象となる必須要件には、一意の要件IDを付与する。最低限、次の要件IDを管理する。

| 要件ID        | 要件                                                               |
| ------------- | ------------------------------------------------------------------ |
| ENV-REQ-01    | `snif` のmagic値により共通エンベロープを識別・バージョン管理できる |
| ID-REQ-01     | 正式名称、npmパッケージ名およびMIME Typeを確定値で使用する         |
| ENC-REQ-01    | 同一論理入力から決定的なバイト列を生成できる                       |
| INT-REQ-01    | 非暗号化データの偶発的破損を検出できる                             |
| CRYPTO-REQ-01 | 機密ペイロードを認証付き暗号で暗号化・復号できる                   |
| CRYPTO-REQ-02 | 暗号化プロバイダーをアルゴリズム識別子により交換できる             |
| PLAIN-REQ-01  | accountおよびmnemonicの平文表現をエンコード・デコードできる        |
| COMP-REQ-01   | SNIF v1で圧縮を生成または受理しない                                |
| MOD-REQ-01    | CommonJSをサポートしない                                           |
| LEGACY-REQ-01 | `symbol/qr-library` 形式との変換アダプターを提供しない             |
| CONN-REQ-01   | 承認権限は要求権限の部分集合であり、未知権限を承認しない           |
| CONN-REQ-02   | 拒否・エラー応答は最小開示に制限される                             |
| CONN-REQ-03   | 接続要求と応答のチェーン・ネットワーク条件を一意に照合できる       |
| LIMIT-REQ-01  | デコードおよび鍵導出の資源上限を適用できる                         |
| TEST-REQ-01   | 各必須要件を機械可読fixtureから追跡できる                          |

仕様設計では、その他の必須要件にも同じ規則で要件IDを付与する。

### 31.2 fixture manifest

適合fixtureは機械可読なmanifestで管理し、各fixtureに最低限次を記録する。

- `fixtureId`
- 対応する一つ以上の `requirementIds`
- 対象データタイプおよびバージョン
- 正常系または拒否系の区分
- 入力
- 期待される決定的バイト列、デコード結果、またはエラーカテゴリー
- 実行に必要な暗号プロファイル
- fixture仕様バージョン

各必須要件は、少なくとも一つの正常fixtureまたは拒否fixtureに対応付けられなければならない。検証可能な失敗条件を持つ要件は、少なくとも一つの拒否fixtureを持たなければならない。

### 31.3 必須適合ケース

| 要件ID        | 正常系                                          | 拒否・異常系                                                         |
| ------------- | ----------------------------------------------- | -------------------------------------------------------------------- |
| CONN-REQ-01   | 要求権限の部分集合を承認する                    | 未要求権限、重複権限、未知権限を拒否する                             |
| CONN-REQ-02   | rejected/errorが最小フィールドのみを含む        | rejected/errorにaccounts、permissions、sessionIdを含む入力を拒否する |
| CONN-REQ-03   | 要求targets内のチェーン・ネットワークを選択する | 要求外チェーン、要求外ネットワーク、曖昧なネットワーク対応を拒否する |
| INT-REQ-01    | 正常な完全性値を受理する                        | 一ビット破損を `INTEGRITY_CHECK_FAILED` とする                       |
| CRYPTO-REQ-01 | 正常復号する                                    | 認証範囲の改変を統一的な復号失敗として拒否する                       |
| PLAIN-REQ-01  | 平文accountおよび平文mnemonicを復元する         | 必須フィールドが欠落した平文機密データを拒否する                     |
| COMP-REQ-01   | 圧縮を示さないv1入力を処理する                  | 圧縮を示すv1入力を拒否する                                           |
| LIMIT-REQ-01  | 上限内入力を処理する                            | サイズ、ネスト、KDFコストの上限超過を拒否する                        |

## 33. 受入条件

初期バージョンは、次の条件をすべて満たした場合に受入可能とする。

- QR画像生成ライブラリに依存していない
- 正式名称が Symbol/NEM Interchange Format、npmパッケージ名が `@nemnesia/snif`、MIME Typeが `application/vnd.nemnesia.snif+cbor` として文書および配布物に使用されている
- `magic` が `snif` ではない入力をSNIFデータとして受理しない
- Symbol、NEMおよびチェーン非依存データを識別できる
- すべての標準データタイプについて正常なエンコード、デコードおよび決定的再エンコードfixtureが成功する
- すべての標準データタイプについて、必須フィールド欠落、不正型、未知列挙値および上限超過の拒否fixtureが定義済みエラーとなる
- 非暗号化データの一ビット破損を検出できる。ただし、送信者認証または能動的改ざん防止を保証事項として扱わない
- 秘密鍵およびニーモニックを認証付き暗号で暗号化・復号でき、平文表現もエンコードおよびデコードできる
- 圧縮を示すSNIF v1入力を拒否し、SNIF v1のエンコーダーが圧縮済みペイロードを生成しない
- 暗号化方式をプロバイダーとして交換でき、未知アルゴリズムへフォールバックしない
- 誤パスワード、認証タグ改変、nonce改変およびAAD対象ヘッダー改変が、情報漏えいを避けた定義済みエラーとなる
- 接続要求の `targets` と承認アカウントのチェーン・ネットワークを照合できる
- 承認応答の権限が要求権限の部分集合であることを検証できる
- 未要求権限、未知権限、要求外チェーンまたは要求外ネットワークを含む承認応答を拒否する
- 拒否・エラー応答に `accounts`、`permissions` または `sessionId` を含む入力を拒否する
- 期限切れの接続要求を承認しない
- 署名要求および署名応答を表現できる
- サイズ、ネストおよびKDFパラメーターの上限が実装されている
- fixture manifestから、各必須要件ID、入力、期待結果または期待エラーを追跡できる
- Node.jsおよびブラウザで同一fixtureを処理し、同一の決定的バイト列または期待エラーを得られる
- 主要APIにTypeScript型が付与されている
- CommonJSエントリポイントを配布しない
- `symbol/qr-library` 形式との双方向変換アダプターを提供しない
- 機密情報がログまたは例外メッセージへ出力されない
- QR、NFC、ファイルその他の特定搬送手段に依存していない

受入判定は、口頭確認または実装者の判断ではなく、公開された適合fixture、テスト結果および依存関係検査によって観測可能でなければならない。

## 36. 設計上の原則

SNIFの設計および実装では、次の原則を維持する。

1. フォーマットと搬送手段を分離する
2. フォーマットとUIを分離する
3. フォーマットとブロックチェーンSDKを分離する
4. 伝送検証と意味検証を分離する
5. 暗号方式を交換可能にする
6. 機密データを安全側の既定値で扱う
7. 実装言語に依存しないワイヤーフォーマットとする
8. 未知の入力を安全に拒否する
9. 互換性をバージョンで管理する
10. 適合fixtureを仕様の一部として管理する
