# Symbol/NEM Interchange Format（SNIF）

## 1. 概要

- 一言で説明: Symbol と NEM を扱うアプリケーションが、搬送手段や実行環境に依存せず、Draft v1でCBORを置換した通常の JSON による検証可能な共通形式でデータを交換するためのライブラリおよび交換フォーマット。
- 背景: 既存の Symbol 向け QR ライブラリはデータ形式と QR 画像生成をあわせて扱うため、画像を必要としない利用や QR 以外の搬送手段への適用で不要な依存と制約が生じる。また、Symbol と NEM を横断し、dApp・ウォレット・署名アプリ間で接続情報を表す共通形式がない。

## 2. 解決したい課題

- 対象者: Symbol または NEM 向けの dApp、ウォレット、署名専用アプリ、バックアップ／リカバリーアプリ、周辺ライブラリの開発者。
- 現在の課題: 交換データの表現が QR 画像生成や特定チェーン・実行環境に結び付き、アプリケーション間で一貫して安全に扱える再利用可能な形式がない。また、専用のバイナリエンコード方式を採用すると、対応実装の開発・保守負荷が高くなる。
- 課題の原因: データ交換形式、搬送手段、UI、SDK、通信、および業務上・チェーン上の意味検証の責務が分離されていない、または共通の取り決めが不足している。加えて、実装環境に標準的に備わる機能だけでは扱いにくい形式を前提にすると、利用開始までの負担が増える。
- 既存手段の不足: 既存形式は Symbol 中心であり、QR 画像以外への展開、NEM との共通利用、接続要求・応答の相互運用を直接の目的としていない。
- 放置した場合の影響: 各アプリケーションが独自形式と個別の安全判断を実装することになり、相互運用性、移植性、機密データの取り扱い、および利用者への説明の一貫性が損なわれる。

## 3. 目的

Symbol および NEM で利用するデータを、アプリケーション、ウォレット、署名デバイス、その他の端末の間で、特定の搬送手段・UI・SDKに依存せずに、標準ライブラリを利用しやすい通常の JSON で交換できる状態を実現する。あわせて、JSONの構造上の正しさ、形式上の偶発的破損の検出、機密データの認証付き暗号による改変検出、および接続時の最小限の情報開示を支える共通の基盤を提供する。

## 4. 対象ユーザーと主要利用場面

### アプリケーションおよびライブラリ開発者

- 利用目的: Symbol／NEM 対応アプリケーション間で、同じ解釈が可能なデータを生成・受領する。
- 前提知識: 対象チェーンおよび自アプリケーションで扱うデータの意味を理解している。
- 解決される課題: 搬送手段やランタイムごとに独自のデータ表現を設計・保守する負担を減らせる。

### ウォレットおよび署名専用アプリの利用者

- 利用目的: dApp からの接続・署名・トランザクション要求や、アカウント・ニーモニックの移行データを、利用中のアプリで確認して扱う。
- 前提知識: 表示された外部入力の意味と、承認・秘密情報の取り扱いを判断する責任は利用者またはウォレットにある。
- 解決される課題: 外部アプリとの情報交換に必要な構造と、拒否時に不要な情報を開示しない共通の基盤を得られる。

### 主要利用場面: 搬送手段を選ばないデータ交換

- 誰が: dApp、ウォレット、バックアップ／リカバリーアプリ、または周辺搬送ライブラリが。
- どのような状況で: QR、ファイル、NFC、Deep Link、Clipboard、通信路など、用途に応じた経路でデータを渡すとき。
- 何を行い: SNIF 形式へ変換したデータを搬送し、受領側が形式と対象データに応じた検証結果を確認して復元する。
- どのような結果を得るか: 搬送方式の実装を交換形式から独立して選べる。

### 主要利用場面: dApp とウォレットの接続

- 誰が: dApp とウォレットまたは署名専用アプリが。
- どのような状況で: dApp が対象チェーン・ネットワークと必要な権限を提示し、ウォレットが承認または拒否を返すとき。
- 何を行い: 要求と応答を対応付け、承認時だけ要求済み権限の部分集合と許可済みアカウント情報を表現する。
- どのような結果を得るか: 接続の意図、許可範囲、拒否時の最小開示を相互に解釈できる。

## 6. v1のスコープと責任境界

### v1で実施すること

Symbol、NEM、およびチェーン非依存データを識別できる共通交換形式を定義し、標準データ種別（公開情報、機密バックアップ、トランザクション・接続・署名の要求と応答、任意データ）を対象にする。Draft v1ではCBOR wire形式をJSONへ置換し、JSON wireのみを生成・受理する。通常の JSON によるwire表現、全データのJSON構文・型・構造・サイズの検証、公開データの形式上の破損検出、機密ペイロードの認証付き暗号、および意味的な適合性を確認する fixture を含める。

### v1では実施しないこと

QR 画像の生成・読取、Animated QR の分割・結合、NFC・Deep Link・HTTP・WebSocket・Relay の通信処理、ウォレット UI、秘密鍵やパスワードの永続保存、トランザクションの作成・署名・送信、ノード通信、接続セッションの永続管理、外部パッケージによるカスタムタイプ登録、既存 `symbol/qr-library` 形式との変換、既存CBORデータの変換、CBOR互換アダプター、およびJSON/CBORの併存は扱わない。カスタムタイプ登録は具体的な利用場面が未確認であり、これらはいずれも交換形式の価値を検証する最小範囲を超えるためである。

### プロジェクトとして扱わないこと

格納されたデータの業務上またはブロックチェーン上の意味的妥当性、残高・期限・署名などのチェーン上の成立、意味的に有効な公開JSONの改変検出、dApp・URL・ドメイン・アイコン・Relay の真正性、利用者認証および認可を保証しない。SNIF は Symbol SDK または NEM SDK の代替でもない。

### 外部へ委ねること

搬送層はデータの配送方法と通信路の保護を担う。上位アプリケーションは、送信者認証、公開データに対する追加の完全性対策、トランザクション・署名などの意味検証を担う。既存CBOR利用者はJSON v1への移行を担い、SNIF v1は既存CBORデータの変換や互換性を提供しない。ウォレットまたは署名アプリは、外部から自己申告された表示情報を信頼済み情報として扱わず、権限の許可・強制とユーザーへの提示を担う。利用者は承認および機密情報の取り扱いを判断する。

## 7. 判断原則

### 搬送手段・UI・SDKからの分離

- 原則: 交換形式は、特定の QR 実装、UI、通信方式、またはチェーン SDK を前提にしない。
- 理由: 同一形式を複数の実行環境と搬送手段で再利用するため。
- 判断への適用: 特定の搬送・表示・SDK 機能が必要な場合は、SNIF 本体ではなく周辺層の責務として扱う。

### 形式検証と意味検証の分離

- 原則: SNIF は形式、必須項目、型、解釈可能性、資源上限、形式上の完全性を検証し、チェーン上・業務上の意味や公開データの意味的に有効な改変を保証しない。
- 理由: フォーマットの相互運用性を保ちつつ、誤った保証範囲を設けないため。
- 判断への適用: データの意味を判定する要件は、必要に応じて上位アプリケーションまたは対象チェーンの仕様へ委ねる。

### 最小権限と最小開示

- 原則: 接続では要求された既知の権限だけを扱い、承認はその部分集合に限る。拒否・エラーでは要求との対応に不要な情報を返さない。
- 理由: アカウント、権限、セッションに関する不要な開示と権限拡大を避けるため。
- 判断への適用: 接続形式の拡張は、要求と応答の対応付け、権限範囲、開示量を明示できる場合に限る。

### 安全側の既定値と未知入力の拒否

- 原則: 機密データには認証付き暗号を用い、未知の必須機能、暗号方式、型、チェーン、上限超過の入力を自動的に受理・フォールバックしない。
- 理由: 相互運用上の曖昧さと、復号・デコード処理への不正入力リスクを抑えるため。
- 判断への適用: 互換性や利便性と衝突する場合は、安全な拒否と明示的なバージョン管理を優先する。

### JSONの意味同値性と検証可能性

- 原則: 同じ論理入力は実装言語に依存せず同じ JSON の意味構造と検証結果を再現できるようにし、プロパティ順や空白に依存する同一バイト列の生成は必須にしない。必須要件は機械可読な適合 fixture で追跡できるようにする。
- 理由: JSON の標準ライブラリを活用して開発・保守負荷を抑えながら、異なる実装間の相互運用を確認するため。
- 判断への適用: JSON の意味に影響しない表現差を不必要に wire 互換性の差とせず、型、数値、重複キー、文字列、byte 値など意味に影響する規則と検証結果を仕様化前に明確化する。

### 保証単位の分離

- 原則: JSON構文・型・構造・サイズの検証、公開データの形式上の破損検出、機密ペイロードの認証付き暗号による改変検出を、別の保証として扱う。
- 理由: JSONの意味同値性を保ちながら、公開データと機密データで異なる完全性の保証範囲を明確にするため。
- 判断への適用: 全データでは解析不能・型不正・構造不正・サイズ超過を拒否し、公開データについて意味的に有効なJSONの改変検出は保証しない。機密ペイロードは認証付き暗号の認証失敗を改変として拒否する。暗号・完全性検証で用いる具体的な判定単位は要件定義で定める。

### 原則間の優先順位

安全側の既定値と最小権限・最小開示を、未知入力の利便的な受理や互換性上の暗黙のフォールバックより優先する。搬送・UI・SDK からの分離を維持したうえで、JSON の意味同値性と検証可能性を満たす選択を採る。

## 8. 成功条件

- Draft v1がJSON wireのみを生成・受理し、CBOR wireを生成・受理せず、既存CBORとの併存や自動変換を行わないことを確認できる。
- 全データについてJSONの構文・型・構造・サイズを検証し、同じ論理入力が対象環境間で意味的に同値な JSON として解釈され、または同じ定義済みエラーになることを確認できる。
- 公開データについて、解析不能・型不正・構造不正・サイズ超過など形式上の破損を拒否できる一方、意味的に有効なJSONの任意の改変まで検出する保証を含まないことを確認できる。
- QR 画像生成ライブラリおよび特定の搬送手段に依存せず、SNIF データを周辺層で利用できることを確認できる。
- 機密ペイロードを認証付き暗号で保護でき、認証失敗または復号不能な入力を情報漏えいを抑えた定義済みエラーとして扱えることを確認できる。
- 接続の承認が要求済みの既知権限の部分集合に限られ、拒否・エラーが不要なアカウント・権限・セッション情報を含まないことを確認できる。
- 構造検証、公開データの形式不正拒否、機密ペイロードの認証失敗拒否、およびJSON意味同値性について、正常・拒否の適合 fixture を個別の判定単位で追跡できる。

## 9. 前提条件と主なリスク

### 前提条件

- SNIF 利用側が、受領データの意味検証、送信者認証、認証済み通信路の必要性を判断・実装する。
- 対象環境で、必要な暗号学的乱数および暗号化プロバイダーを利用できる。具体的な初期標準方式は未決定である。
- 各チェーンのデータの意味・署名・ネットワーク上の有効性は、対象チェーンの仕様、公式実装または SDK で別途確認する。
- 外部表示情報は自己申告のメタデータであり、信頼性の根拠とはしない。

### 主なリスク

- JSON の数値表現、重複キー、プロパティ順、空白、文字列、byte 値の扱いが未確定のままでは、異なる実装間で意味的な互換性を確立できない。
- JSON の表現と完全性検証・認証付き暗号をどのように結び付けるかが未確定のままでは、改変検出と暗号化データの相互運用を確立できない。
- JSON の fixture を意味構造で比較する範囲と、暗号・完全性に関わる入力をどの表現で固定するかが未確定のままでは、適合性を一貫して確認できない。
- 公開データの形式上の破損検出と意味的に有効な改変の検出を混同すると、SNIFが保証しない完全性を利用者が期待する可能性がある。
- 既存CBORとの互換性を想定した実装やfixtureが残ると、JSON v1の対象範囲と移行完了条件が分岐する可能性がある。
- QR、Relay、Deep Link 等の搬送層に求められる認証・機密性を SNIF の保証と誤認すると、安全でない運用につながる。
- 接続要求の外部メタデータを真正と誤認すると、利用者の判断を誤らせる可能性がある。
- 平文の秘密鍵・ニーモニックを許可する用途では、利用者・搬送・保存先の運用次第で漏えいする可能性がある。
- デコード・鍵導出の資源制限が不十分な場合、不正入力による可用性低下につながる。

## 12. 要件定義への引継ぎ

- 共通エンベロープ、標準データタイプ、JSON wire 表現、暗号プロファイル、およびサイズ・資源制限の具体的な規則を定義する。
- JSONの意味的同値性と構造保証について、数値、重複キー、プロパティ順、空白、文字列、byte 値、型、構造、サイズ、およびfixture比較の判定単位を定義する。
- 公開データでは形式上の破損を拒否し意味的に有効な改変を保証対象外とすること、機密ペイロードでは認証付き暗号の認証失敗を改変として拒否することを、別々の受入条件として定義する。
- 暗号・完全性検証で用いる表現、暗号対象、改変検出、および実装間の適合条件を定義する。暗号アルゴリズムや具体的な正規化方式はこの段階以降で決定する。
- JSON v1の識別・配布方法、MIME type、既存CBOR資料・fixtureの更新対象、既存CBOR利用者の移行責任、CBORの廃止手順を定義する。v1のCBOR受理・生成、JSON/CBOR併存、自動変換は対象外として扱う。
