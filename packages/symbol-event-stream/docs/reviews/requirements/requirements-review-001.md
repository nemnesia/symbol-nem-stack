## 要約

### 主要な価値

Symbol WebSocket Gateway への複数接続を、利用者アプリケーションから単一の論理的な監視として扱えること、同一対象・同一イベントの通知を通知レベルで重複排除できること、接続異常を観測し、利用可能な接続が残る間は監視を継続できること、明示的な終了後に処理を停止できることを価値として定義している。

### 対象範囲

Symbol WebSocket 通知、複数 Gateway の論理的な監視、候補接続の異常時の除外・補充・再利用、接続および最終監視状態の観測、明示的な終了を対象とする。NEM、非 Symbol WebSocket、トランザクション作成・署名・暗号化・アナウンス、秘密情報、履歴保存・リプレイ・ギャップ補償、フォーク判定などを対象外としている。

### 主なリスク

- 「複数接続」「継続」「リアルタイム」の保証境界と、接続数不足時の継続条件が明確でない。
- 初期接続時の状態差分、遅延・タイムアウト・通知が来ない状態の扱いが、外部状態として一貫して定義されていない。
- 一時除外した接続の復帰・再利用条件が、候補の補充状況と合わせて一意に定まらない。
- 対象とするイベント通知の範囲が抽象的で、受け入れ条件の適用対象を判定しにくい。
- 複数候補が同一監視に参加するための共通前提と、その確認責任が明示されていない。
- 接続切替・再利用・再接続をまたぐ重複排除の保証範囲が未定義である。

## Required Changes

### RR-001 [Major] 複数接続による継続条件と品質保証境界を明示する

- **該当箇所**: §1.2、§2.1、UC04、FR005、§7、AC005・AC006
- **問題**: 複数 Gateway を使う目的と、健全な接続が残れば継続し全て失えば異常とする方針はあるが、継続に必要な最低条件、接続数不足時の扱い、「リアルタイム」「継続」の保証範囲が定まっていない。§7 は性能・可用性の独立目標を置かないとしているため、機能上の継続条件と品質上の非保証事項の境界が曖昧になる。
- **要求する修正**: 最低限の継続条件または接続数に関する保証を定めるか、数値を保証しない場合は「健全な接続が1つ以上残る限り継続する」などの機能境界と、遅延・規模・復旧時間を保証しない範囲を明示する。接続プールの内部管理方法や具体的な性能値を要件で決める必要はない。
- **採用理由**: 複数接続、候補不足および継続を組み合わせたときの外部結果を一意に受け入れ判定できないため。

### RR-002 [Major] 初期状態、健全性、タイムアウトおよび通知なし状態の外部意味を統一する

- **該当箇所**: FR001、FR004〜FR006、AC001・AC004・AC006・AC016、§2.3
- **問題**: 初回接続時の状態差分は許容される一方、初回処理の終了点、そこから適用される遅延判定、通知が来ない状態、タイムアウトの責任主体および利用者に見える状態が明確でない。また「異常条件に該当しないこと」とする健全性の定義は、異常条件の範囲が閉じていない。
- **要求する修正**: 初期受入れと通常監視の境界を定め、遅延・初期接続失敗・タイムアウトを含む異常条件を要件上の分類として明示する。通知が一定期間ない場合を正常継続、異常、または保証対象外のいずれと扱うか、誰がその状態を観測・判断するか、最終状態へどう反映するかを定める。タイムアウト値や検出アルゴリズムは仕様へ委譲できる。
- **採用理由**: 同じ入力状態に対して健全・除外・継続・停止の結果が複数解釈でき、FR004〜FR006 の受け入れ判定が不安定になるため。

### RR-003 [Major] 一時除外した接続の復帰・再利用条件を明示する

- **該当箇所**: §2.3、UC04、FR005、AC005・AC006
- **問題**: Provider 候補を優先し、候補枯渇時には条件付きで遅延した確立済み接続を再利用する方針はあるが、「一時除外」の終了条件、候補が残っている場合の復帰可否、同一監視中の再利用範囲、再利用後の健全性確認が一意に定まっていない。
- **要求する修正**: 新しい候補がある場合とない場合を分け、除外から復帰・再利用できる外部条件、同一監視中に再利用できない失敗種別、再利用後に継続扱いとなる条件を明示する。ブラックリストのデータ構造や選択アルゴリズムを定める必要はない。
- **採用理由**: 部分障害時の継続性と停止条件に直結し、同じ障害状態でも接続管理の結果が分岐するため。

### RR-005 [Major] v1 のイベント通知範囲を明示する

- **該当箇所**: §2.1、UC02、FR003、§11、§12.2
- **問題**: 対象は「Symbol WebSocket 通知」「監視対象」「同一イベント」と抽象化され、具体的なイベント種別は仕様へ送られている。これでは受け入れ条件をどの通知に適用するか、Provider 依存の範囲と v1 の対象外を判定できない。
- **要求する修正**: v1 で扱うイベント通知の領域を要件レベルで列挙するか、Provider が提供する通知領域に依存すること、その場合の対象外・非保証範囲を明示する。通知のフィールド、シリアライズ、購読 API は仕様へ委譲できる。
- **採用理由**: 対象範囲と受け入れ条件の適用範囲に関わるため。コンセプトシートにある例を、要件上の確定範囲として扱うかどうかも明示が必要である。

### RR-006 [Major] 同一監視に参加する候補の共通前提と確認責任を明示する

- **該当箇所**: §2.2・§2.3、§4.1・§4.2、FR001〜FR003、AC016
- **問題**: Event Stream は候補の選択や互換性保証を行わず、利用者が利用可能な候補を準備すると定めている。一方、複数候補の通知を単一監視へ統合するために、同一チェーン・ネットワーク・対象・通知意味を共有することが前提なのか、前提を誰が確認するのかが明示されていない。
- **要求する修正**: Event Stream が互換性を保証しない責任分界は維持したまま、同一監視へ渡す候補に必要な共通前提と、その確認・不一致時の責任主体を明示する。候補を自動検証・選択する内部処理を要求するものではない。
- **採用理由**: 本件は Event Stream に互換性保証を追加する指摘ではなく、既存の「利用者が候補を準備する」「Provider が候補を提供する」という前提を、複数接続統合の受け入れ条件と接続するためのものだからである。

### RR-007 [Major] 接続ライフサイクルをまたぐ重複排除の保証範囲を定める

- **該当箇所**: FR003、FR005、AC003・AC005、§12.2
- **問題**: 同一対象・同一識別可能イベントの通知レベル重複排除は MUST とされているが、接続切替、候補の再利用、再接続および同一監視の再購読をまたいでも保証されるのかが不明である。重複識別方法や保持期間は仕様へ送られているものの、保証の適用範囲自体が未定義である。
- **要求する修正**: 「同一監視」のどのライフサイクル範囲で重複排除を保証するか、接続切替・再利用・再接続時の境界、保証しない境界を要件レベルで明示する。識別子の形式、保持期間、データ構造は仕様へ委譲できる。
- **採用理由**: FR003 の MUST を受け入れ試験で検証するために、適用範囲が必要だからである。アプリケーションの業務処理の二重実行を保証しないという既存の責任分界は維持する。

## Optional Improvements

### RR-004 [Minor] 候補準備・候補更新・終了操作の責任主体を要件内で一貫させる

- **該当箇所**: §3、§4.1、UC04・UC05、FR005〜FR007、§11、§12.2
- **問題**: 開発者、運用者、利用者アプリケーションの役割は概ね定義されているが、候補の更新、異常時の回復判断、明示的な終了を誰が実行するかは仕様・公開契約へ委譲されている。§11 の「要件レベルの未決定事項はない」との記述とも読み手によっては緊張関係がある。
- **改善案**: 操作を提供する主体と、継続・回復・停止を判断する主体を要件レベルで対応付ける。API 名、呼び出し形式、状態表現は仕様へ委譲する。
- **採用理由**: 現状でも責任分界の大枠は成立しているため、品質ゲートを阻害する指摘ではなく、仕様化時の解釈差を減らす改善とした。

## 採用しなかった指摘の扱い

認証方式、通知の個人情報・法務上の扱い、外部サービスのライセンス・再配布条件を追加で要求する指摘は、対象資料から必須要件である根拠を確認できなかったため採用しなかった。秘密情報を扱わないこと、通知を保存しないこと、アプリケーション側の検証・保存責任は既存要件の範囲で確認できる。これらを将来の利用環境やリリース条件で要求する場合は、別途根拠を明示して要件へ追加する。

## 残存する仮定・未確認事項

- Provider が提供する候補の具体的なイベント領域、ネットワーク識別および互換性情報は、現要件では確定していない。
- 「リアルタイム」「連続監視」が数値的な性能保証を意味するか、機能上の目的表現にとどまるかは、RR-001 で明確化が必要である。
- タイムアウトの値、遅延判定の計算、重複識別子、保持期間、候補選択・再利用アルゴリズムは要件レビューの対象外であり、要件の境界確定後に仕様で定める。
- 最新コンセプトレビューは必須修正なしで要件定義へ進める判定であり、今回の RR-004 はその任意改善に対応する。
