## Required Changes

### CR-001

- Priority: Major
- Status: Open
- 対象箇所: `9. 前提条件と主なリスク`、`11. 未決定事項`、`12. 要件定義への引継ぎ`
- 問題: 11章で「コンセプトレベルの未決定事項はない」と断定する一方、9章と12章では、保証境界、初期状態での接続受入れ・通知採用、遅延判定、接続除外後の復帰、候補不足・全接続不健全時の監視状態、異常情報、監視操作などを未確定の論点として扱っています。
- 根拠: 11章178行目は未決定事項を否定し、12章186〜195行目はv1の成立条件や保証範囲に関係する論点を要件定義へ引き継いでいます。
- 影響: コンセプトで決定済みの方針と、要件定義で初めて判断する事項の境界が読み手によって異なります。特に「重複通知を抑制する」「遅延接続の影響を抑える」という価値が、どの範囲でv1に成立するのかを過大・過小に解釈する可能性があります。
- 修正方針: 11章を、少なくとも「コンセプトとして決定済みの方針」「方針は決定済みだが要件定義で具体化する事項」「外部前提・保証対象外」に区分してください。コンセプトレベルの未決定事項を「なし」とする場合は、12章の論点が方針の再判断ではなく具体化であることを、論点ごとに誤解なく示してください。逆に、価値や責任境界を左右する事項を未決定と扱うなら、11章の表に明示してください。
- 修正完了条件: 6章・7章・9章・11章・12章を通読したとき、決定済みの価値・責任境界、未確認の外部前提、要件定義へ委譲する未決定事項が重複または矛盾なく区別できること。

## Resolved Findings

### CR-002 — Resolved

4章で、TypeScriptアプリケーション開発者とアプリケーション運用者が主対象ユーザーとして明示されています。通知監視・連携アプリケーションは利用形態、Gateway運用者・nodewatch運用主体・Providerは関係者とされ、主体の粒度が区分されています。

### CR-003 — Resolved

1章に監視対象、通知、接続、Gateway接続候補、健全な接続、初回、nodewatch、nodewatch情報、Providerの定義が追加され、詳細な判定方法は後続工程へ委譲されています。コンセプト理解に必要な用語の区分は本文から読み取れます。

### CR-004 — Resolved

3ブロック閾値、通知採用、接続除外後の復帰、異常情報の具体的な扱いは、現在は主として12章の引継ぎ事項に置かれています。6章では目的・責任境界として記述され、具体方式をv1の確定仕様として固定していません。

### CR-005 — Resolved

6章・9章でProviderを外部前提として位置付け、Event Streamが候補のチェーン・ネットワーク・Gateway適合性を保証しないこと、利用者が候補準備の責任を負うことが明記されています。12章でも信頼境界と確認責任を後工程で具体化する対象として示されており、旧指摘の責任境界の欠落は解消されています。パッケージ名の反復はCR-013で別途扱います。

### CR-011 — Resolved

5章は開発者・運用者が得る便益を表形式で示し、8章は監視の一元化、重複抑制、異常把握、終了後の残存処理なしという成立状態を列挙しています。両章には関連する表現が残りますが、役割の区別は現行本文で読み取れるため、追加の独立指摘とはしません。残る反復はCR-010で扱います。

### CR-012 — Resolved

4章の主要利用場面で、利用者、状況、困りごと、期待状態が別々に示されています。通常時・障害時・終了時をさらに別シナリオにすることは要件や利用シナリオで具体化できる範囲であり、コンセプト上の説明不足とは判断しません。
