# Symbol Event Stream 要件定義書

## 1. 概要

### 1.1 背景

Symbol WebSocket Gatewayを単一接続で監視すると、一時的な切断や遅延によって通知監視が不安定になる。複数Gatewayへ接続すると監視の継続性を高められる一方、同一監視対象に関する同一イベントが複数接続から届き、通知の重複を利用者側で扱う必要がある。

### 1.2 目的

Symbolを対象チェーンとするTypeScriptアプリケーションが、複数のSymbol WebSocket Gateway接続からの通知を一つの論理的なリアルタイム監視として扱えるようにする。監視対象の継続、通知レベルの重複抑制、接続状態と異常の把握、監視終了後の継続処理停止を、利用者が判断可能な責任境界で提供する。

ここでいう「一つの監視」は、複数接続を利用者から一つの論理的な監視として扱えることを意味する。完全配信、通知順序の保証、通知を利用した業務処理の一度だけの実行を意味しない。

### 1.3 解決する課題

- 単一Gatewayの一時障害による監視の不安定化
- 複数Gatewayから届く同一イベントの重複通知
- 接続間の状態差による遅延接続の影響
- 接続状態や監視上の異常を把握する負担
- アプリケーション終了後も接続や継続処理が残るリスク

## 2. 対象範囲と責任境界

### 2.1 対象

- Symbol WebSocket Gatewayからの通知監視
- 複数のGateway接続を利用した一つの論理的な監視
- 利用者が選択した監視対象の継続的な扱い
- 同一監視対象に関する同一イベントの通知レベルの重複抑制
- 接続状態および監視上の異常の観測
- 一部の接続障害または候補不足時の監視継続
- 全接続を監視に利用できない場合の異常把握
- 明示的な監視終了後の継続処理停止

### 2.2 対象外

- NEMチェーンへの対応
- Symbol WebSocket Gateway以外の通知方式への対応
- トランザクションの作成、署名、暗号化またはアナウンス
- 秘密鍵、ニーモニック、パスワードその他の秘密情報の管理
- Event StreamによるMainnet、Testnetその他のネットワークの選択・切替・自動判定
- Gateway接続候補のチェーン、ネットワークまたはGateway適合性の保証
- 通知の真正性、署名、完全性、業務上の意味または正当性の保証
- 通知の永続化、履歴取得、リプレイ、欠落・遅延の補償
- Gatewayやネットワークの可用性、通知生成および完全配信の保証
- 短時間フォークの発生有無または正当性の判定

### 2.3 用語と責任境界

| 用語・主体 | 本書での意味と責任 |
| --- | --- |
| Gateway接続候補 | Providerが提供し、利用者がEvent Streamで利用できるよう準備する接続先候補。候補であることは、実際の接続成立や健全性を意味しない。 |
| 接続 | Event Streamと一つのSymbol WebSocket Gatewayとの実際の接続。初回接続に失敗した候補は、接続として確立せず、接続候補として扱う。 |
| 健全な接続 | 本書で定める異常条件に該当せず、監視の継続に利用できる接続。追加の判定方法や公開表現は仕様設計で定める。 |
| ブラックリスト | 遅延または異常と判定された成立済み接続、または初回接続に失敗した接続候補を、原因と関連付けて一時的に除外する扱い。Providerの候補が枯渇した場合は、復旧条件を満たす成立済み接続だけを再利用候補とする。 |
| Event Stream | 複数接続の監視統合、監視対象の扱い、通知レベルの重複抑制、接続状態・異常の観測、監視終了を担う。候補の適合性や通知の業務上の正当性は保証しない。 |
| Provider | NodeWatch情報を利用してGateway接続候補を提供する外部のパッケージまたは候補供給者。監視で扱うネットワーク、ノードおよびそのGatewayのプロトコル・通知契約は、Providerが提供する候補と接続先に従う。候補の提供とEvent Streamの監視処理を同一視しない。 |
| NodeWatch運用主体 | ノード情報を収集・提供する外部主体。NodeWatch情報の正しさをEvent Streamが保証するものではない。 |
| 利用者アプリケーション | 通知を業務処理へ渡し、必要な真正性・完全性の確認、保存、欠落時の照合および復旧を担う。 |
| Gateway・ネットワーク | 通知の生成、接続サービスおよび配信を担う外部環境。 |

監視で扱うネットワークの選択・提示はProviderの責任範囲とし、Event Streamは独自にネットワークを選択、切替または判定しない。Event Streamは、Providerが提供する候補の対象チェーン・ネットワーク・Gatewayへの適合性を保証しない。利用者は、Providerが提示した候補をEvent Streamで利用できる環境と候補を準備する前提とする。

## 3. 利用者と関係者

| 利用者・関係者 | 目的または責任 |
| --- | --- |
| TypeScriptアプリケーション開発者 | Symbol通知の監視をアプリケーションへ組み込む。監視対象と利用候補を準備する。 |
| アプリケーション運用者 | 接続状態や異常を確認し、監視の継続・停止・復旧を判断する。 |
| 利用者アプリケーション | 受信通知を後続の業務処理へ渡し、必要な検証・保存・復旧を行う。 |
| Gateway運用者 | Gatewayの接続サービスと通知配信を提供する。 |
| NodeWatch運用主体 | ノード情報を収集・提供する。 |
| Provider・候補供給者 | Event Streamが利用できるGateway接続候補を提供する。 |

「利用者」は、文脈に応じて監視対象を選択する開発者、状態を判断する運用者、またはそれらが運用するアプリケーションを指す。候補の準備と監視終了の具体的な操作主体は、仕様設計で公開契約と合わせて確定する。

## 4. 前提条件と制約

### 4.1 前提条件

- 対象チェーンはSymbolである。
- 通知方式はSymbol WebSocket Gatewayである。
- 利用者は、利用可能なGateway接続候補を準備する。
- Providerは、NodeWatch情報を利用してGateway接続候補を提供する外部要素である。
- Providerは、監視で扱うネットワークに対応するGateway接続候補を提供する。
- 利用者は、Providerが提示した候補を利用できる環境と到達性を準備する。
- Event Streamは秘密情報を扱わない。
- 通知の業務利用に必要な検証、保存、欠落時の照合および復旧は利用者アプリケーションが担う。

### 4.2 確定した制約

- Event StreamはGateway接続候補のチェーン・ネットワーク・Gateway適合性を保証しない。
- Event Streamは、通知の完全配信、真正性、完全性、順序、一度だけの業務処理および欠落補償を保証しない。
- 短時間フォークの発生有無や正当性を判定しない。
- NEMチェーンおよびSymbol WebSocket Gateway以外の通知方式はv1の対象外である。
- 監視で扱うネットワークはProviderが提供する候補のネットワークに従い、Event Streamはネットワークを選択・切替・自動判定しない。
- 対象ノードのプロトコル・バージョン、Gatewayの通信契約およびWebSocket通知フォーマットは、Providerが提供するノードとそのGatewayに従い、Event Streamは独自に固定・選択・自動判定しない。
- 通知の形式、発生および連続通知の扱いはProviderが提供するノードとそのGatewayの契約を継承する。短時間フォークの解消などによりGatewayから連続して届く通知は、Event Streamが同一イベントだと判定できる根拠がない限り統合・排除しない。

## 5. ユースケース

### UC-01: 複数Gateway接続で監視する

- 利用者: TypeScriptアプリケーション開発者、利用者アプリケーション
- 事前条件: 利用者がGateway接続候補と監視対象を準備している。
- 目的: 複数接続からの通知を一つの論理的な監視として利用する。
- 期待結果: 選択した監視対象に関する通知を、接続ごとの統合処理を意識せず利用できる。
- 主な失敗条件: 初回接続に失敗する、またはタイムアウトによって切断され、監視を開始できない。

### UC-02: 通知の重複を抑制して利用する

- 利用者: 利用者アプリケーション
- 事前条件: 同じ監視対象を複数接続で監視している。
- 目的: 複数接続から届く同一イベントの通知重複を抑制する。
- 期待結果: 同一監視対象の同一イベントとして識別できる通知の重複が抑制される。
- 主な失敗条件: 同一イベントとして識別できる通知の重複が抑制されない。

### UC-03: 接続状態と監視上の異常を確認する

- 利用者: アプリケーション運用者
- 事前条件: Event StreamがGateway接続候補を利用して監視している。
- 目的: 接続の状態、利用可能性および監視上の異常を確認する。
- 期待結果: 運用者が監視の継続・停止・復旧を判断できる。
- 主な失敗条件: 最終的な接続状態または監視状態を確認できず、運用判断ができない。

### UC-04: 一部障害または候補不足の状態で監視を継続する

- 利用者: 利用者アプリケーション、アプリケーション運用者
- 事前条件: 複数候補または複数接続のうち、監視に利用できる健全な接続が残っている。
- 目的: 一部の接続障害や候補不足によって監視全体を停止させない。
- 期待結果: 遅延または異常な接続が監視から一時的に除外され、利用可能なProvider候補がある場合はそれで補充される。Providerの候補が枯渇した場合に限り、復旧条件を満たしたブラックリスト接続を再利用する。再利用できる接続もない場合は、残った健全な接続だけで監視対象の扱いを継続し、健全な接続がすべてなくなった場合は監視を停止する。
- 主な失敗条件: 利用可能な健全な接続がなく、監視継続の前提が失われる。

### UC-05: 監視を終了する

- 利用者: TypeScriptアプリケーション開発者、利用者アプリケーション
- 事前条件: Event Streamが監視を開始または継続している。
- 目的: アプリケーションのライフサイクルに合わせて監視を終了する。
- 期待結果: 終了後に監視に関係する継続処理が再開しない。再度監視する場合は、終了済みのインスタンスを再利用せず、初期化から開始する。
- 主な失敗条件: 終了後も監視に関係する処理が継続する。

## 6. 機能要件

### FR-001 監視対象の扱い

- 優先度: MUST
- 要件: Event Streamは、利用者が選択した監視対象を、継続的に通知を受ける対象範囲として扱える結果を提供しなければならない。
- 根拠: コンセプトシート §1「監視対象」、§3、§6
- 対応ユースケース: UC-01、UC-02、UC-04
- 受け入れ条件: 利用者が監視対象を指定したとき、その対象範囲に対応する通知を監視結果として扱えること。初回接続が成立したノードは、他のノードとの状態差にかかわらず直ちにその監視へ利用できること。

### FR-002 複数接続の論理的な統合

- 優先度: MUST
- 要件: Event Streamは、複数のSymbol WebSocket Gateway接続からの通知を、利用者からは一つの論理的なリアルタイム監視として扱える結果を提供しなければならない。
- 根拠: コンセプトシート §1、§3、§6、§8
- 対応ユースケース: UC-01
- 受け入れ条件: 複数の接続候補を利用した監視で、利用者が接続ごとの通知統合を個別に実装せず、選択した監視対象への通知を一つの監視として扱えること。完全配信、順序保証、一度だけの業務処理をこの要件から保証しないこと。

### FR-003 通知レベルの重複抑制

- 優先度: MUST
- 要件: Event Streamは、同一監視対象に関する同一イベントとして識別できる通知が複数接続から届いた場合、通知レベルで重複を抑制する結果を提供しなければならない。Gatewayが短時間フォークの解消などにより連続して送る通知について、Event Streamは同一イベントだと判定できる根拠がない限り統合・排除してはならない。これは利用者アプリケーションの業務処理そのものの二重実行を制御または保証するものではない。
- 根拠: コンセプトシート §1「重複通知」、§2、§6、§7、§8
- 対応ユースケース: UC-02
- 受け入れ条件: 同一監視対象に関する同一イベントとして識別できる通知が複数接続から届いたとき、重複通知が抑制されること。Gatewayが短時間フォークの解消などにより連続して送る通知は、同一イベントだと判定できる根拠がなければ別通知として扱い、監視対象が同じという理由だけで統合しないこと。Gateway由来の通知の完全配信、順序、欠落補償、再送、リプレイおよび一度だけの業務処理を保証しないこと。

### FR-004 遅延接続の影響抑制

- 優先度: MUST
- 要件: Event Streamは、初回接続後、各Gatewayから届いた最新通知のブロック進行を比較し、最大値から3ブロック以上の差がある接続を異常・遅延と扱わなければならない。一時的な差であっても遅延と扱い、判定材料はブロック進行の差だけとする。これは短時間フォークそのものの発生有無または正当性を判定するものではない。
- 根拠: コンセプトシート §2、§6、§7、§9、§11 CU-003・CU-004
- 対応ユースケース: UC-01、UC-04
- 受け入れ条件: 接続間に状態差がある場合、初回接続時はその状態差があっても接続成立済みのノードを監視へ利用できること。初回接続後、各Gatewayから届いた最新通知のブロック進行を比較し、最大値から3ブロック以上の差がある接続は、一時的な差であっても異常・遅延と扱うこと。判定にブロック進行以外の基準を加えず、短時間フォークの発生有無や正当性を判定しないこと。

### FR-005 異常接続の除外と候補補充

- 優先度: MUST
- 要件: Event Streamは、遅延または異常と判定した成立済み接続または接続候補を、原因と関連付けて監視から一時的に除外しなければならない。原因は、ブロック進行の遅延、初回接続の失敗およびタイムアウトによる切断を区別して扱う。減少した接続については、利用可能なProviderのGateway接続候補がある場合、それを優先して補充に利用しなければならない。Providerの候補が枯渇した場合に限り、原因がブロック進行の遅延であり、再利用時点で各Gatewayから届いた最新通知のブロック進行の最大値との差が3ブロック未満である成立済み接続を、再利用候補の中からランダムに選んで再利用しなければならない。初回接続の失敗またはタイムアウトによる切断を原因とする対象は、同じ監視中に再利用してはならない。補充または再利用できる接続がない場合は、残った健全な接続だけで監視対象の扱いを継続し、健全な接続がすべてなくなった場合は監視を停止しなければならない。
- 根拠: コンセプトシート §2、§6、§8、§11の決定済み方針
- 対応ユースケース: UC-04
- 受け入れ条件: 遅延または異常と判定した成立済み接続または接続候補が、原因と関連付けられて監視から一時的に除外されること。利用可能なProvider候補がある場合はそれで補充されること。Providerの候補が枯渇した場合、原因がブロック進行の遅延で、再利用時点の最大ブロック進行との差が3ブロック未満の成立済み接続だけが再利用候補となり、その中からランダムに選ばれて再利用されること。初回接続の失敗またはタイムアウトによる切断を原因とする接続候補は、同じ監視中に再利用されないこと。補充または再利用できる接続がなくても健全な接続が残る場合は、その接続だけで監視が継続すること。健全な接続がすべてなくなった場合は監視が停止すること。

### FR-006 接続状態と監視上の異常の観測

- 優先度: MUST
- 要件: Event Streamは、利用者へ、異常への対処後の最終的な接続状態および監視状態を知らせなければならない。監視に利用できる健全な接続が一つもない場合は、監視上の異常として知らせなければならない。ブラックリスト移動、候補補充およびブラックリスト接続の再利用などの途中経過は、個別通知の対象としない。
- 根拠: コンセプトシート §2、§4、§6、§8、§11 CU-005・CU-006
- 対応ユースケース: UC-03、UC-04
- 受け入れ条件: 異常への対処後、利用者が最終的な接続状態および監視状態を確認でき、健全な接続がすべてなくなって監視が停止した状態を監視上の異常として把握できること。初回接続の失敗またはタイムアウトによる切断も、対処後の状態として把握できること。初回接続時のノード間の状態差だけでは、監視開始の失敗または異常と扱わないこと。ブラックリスト移動、Provider候補による補充、ブラックリスト接続の再利用などの途中経過は、個別に知らせないこと。

### FR-007 監視終了後の継続処理停止

- 優先度: MUST
- 要件: Event Streamは、利用者が監視を終了した後、監視に関係する接続、購読その他の継続処理を停止し、同一インスタンスで監視を再開してはならない。再度監視する場合は、新しいインスタンスの初期化から開始する。
- 根拠: コンセプトシート §2、§6、§8、§11の決定済み方針
- 対応ユースケース: UC-05
- 受け入れ条件: 明示的な監視終了後に、監視に関係する接続、購読その他の継続処理が停止し、新たな監視を開始または再開しないこと。終了済みのインスタンスへ監視対象の追加・解除などを行っても監視は再開せず、再度監視する場合は新しいインスタンスの初期化から開始すること。

## 7. 非機能要件

コンセプトシートから、機能要件とは独立した性能値、可用性数値、処理時間、容量または運用目標は確認できない。監視継続性、観測可能性および終了後の停止は、機能要件FR-005〜FR-007で外部結果として定義する。根拠のない数値目標や一般的な品質要件は追加しない。

## 8. セキュリティ要件

### SEC-001 通知の信頼境界

- 優先度: MUST
- 要件: Event Streamは、Gatewayから受信した通知の真正性、署名、完全性または業務上の正当性を保証してはならない。必要な検証、保存、欠落時の照合および復旧は利用者アプリケーションの責任範囲として扱える境界を明示しなければならない。
- 根拠: コンセプトシート §6、§7、§9、§11 CU-007
- 対応ユースケース: UC-01、UC-02、UC-03
- 受け入れ条件: Event Streamが提供する監視結果と、通知の真正性・完全性・業務上の正当性の確認責任が区別されていること。Event Streamの能力として完全配信や欠落補償を示さないこと。

### SEC-002 秘密情報の非取扱い

- 優先度: MUST
- 要件: Event Streamは、通知監視の開始、継続または終了のために、秘密鍵、ニーモニック、パスワードその他の署名・認証用秘密情報を要求、保存または処理対象としてはならない。
- 根拠: コンセプトシート §6、§9
- 対応ユースケース: UC-01、UC-03、UC-05
- 受け入れ条件: 利用者が通知監視を開始・継続・終了する際、署名・認証用秘密情報をEvent Streamへ提供する必要がないこと。

## 9. データ要件

### DR-001 通知データの利用・保存境界

- 優先度: MUST
- 要件: Gatewayから受信する通知は、Event Streamが利用者アプリケーションへ渡す監視入力として扱う。Event Streamは、通知履歴の永続化、履歴取得、リプレイ、欠落・遅延の補償または業務データとしての保存を提供しない。
- 根拠: コンセプトシート §6、§7、§9、§11 CU-001・CU-007
- 対応ユースケース: UC-01、UC-02、UC-04
- 受け入れ条件: 利用者アプリケーションが通知を受信して利用できる一方、過去通知の取得、再生、欠落補償または業務データ保存をEvent Streamの機能として要求できないこと。Event Stream内部の一時状態の具体的な保持方式は本要件で決定しない。

## 10. 受け入れ条件

以下は各要件に記載した受け入れ条件を、外部結果の確認単位として整理したものである。

| ID | 対応要件 | Given | When | Then |
| --- | --- | --- | --- | --- |
| AC-001 | FR-001 | 利用者が監視対象を準備する | 監視を開始する | 選択した対象範囲に対応する通知を監視結果として扱え、初回接続が成立したノードは状態差にかかわらず直ちに利用できる |
| AC-002 | FR-002 | 複数のGateway接続候補と監視対象がある | 複数接続で監視する | 利用者は接続ごとの統合処理を個別に実装せず、一つの論理的な監視として扱える |
| AC-003 | FR-003 | 同一監視対象の同一イベントとして識別できる通知が複数接続から届く | 通知を扱う | 通知レベルの重複が抑制される。Gatewayが短時間フォークの解消などにより連続して送る通知は、同一イベントと判定できる根拠がなければ別通知として扱われる |
| AC-004 | FR-004 | 接続間に状態差があり、遅延接続が存在する | 初回接続または継続中の通知を監視結果へ反映する | 初回接続時は状態差があっても接続成立済みのノードを利用し、初回接続後は各Gatewayから届いた最新通知のブロック進行を比較して最大値から3ブロック以上の差がある接続を異常・遅延と扱う。判定はブロック進行の差だけで行い、短時間フォークの正当性判定は行わない |
| AC-005 | FR-005 | 遅延または異常と判定された成立済み接続または接続候補があり、利用可能なProvider候補がある | 異常対象を扱い、接続数を補充する | 対象が原因と関連付けられて監視から一時的に除外され、利用可能なProvider候補で補充される |
| AC-006 | FR-006 | 接続状態、全接続不健全、初回接続失敗またはタイムアウト切断が発生する | Event Streamが異常への対処を終え、利用者が状態を確認する | 最終的な接続状態と監視状態を確認でき、継続・停止・復旧を判断できる。途中のブラックリスト移動や候補補充の詳細は通知されず、初回接続時の状態差だけでは異常と扱わない |
| AC-007 | FR-007 | 監視が開始または継続している | 利用者が監視を終了する | 監視に関係する継続処理が監視を新たに開始または再開せず、再度監視する場合は新しいインスタンスの初期化から開始する |
| AC-008 | SEC-001 | Gatewayから通知を受信する | 通知を業務利用する | Event Streamが通知の真正性・完全性・業務上の正当性を保証せず、利用者側の確認責任と区別されている |
| AC-009 | SEC-002 | 利用者が監視を開始・継続・終了する | Event Streamを利用する | 署名・認証用秘密情報の提供を要求されない |
| AC-010 | DR-001 | 利用者アプリケーションが通知を受信する | 過去通知の取得や欠落補償を必要とする | それらがEvent Streamの機能として提供されず、利用者側の責任範囲として扱われる |
| AC-011 | FR-005 | Providerの候補が枯渇し、ブロック遅延を原因とする成立済み接続があり、再利用時点の最大ブロック進行との差が3ブロック未満である | 監視を継続する | 再利用条件を満たす接続の中からランダムに選ばれた接続が再利用される |
| AC-012 | FR-005 | Providerの候補が枯渇し、初回接続失敗またはタイムアウト切断を原因とする対象しかない | 監視を継続する | それらの対象は同じ監視中に再利用されない |
| AC-013 | FR-005 | Providerの候補が枯渇し、再利用できるブラックリスト接続がなく、健全な接続が残っている | 監視を継続する | 残った健全な接続だけで監視が継続する |
| AC-014 | FR-005、FR-006 | Providerの候補が枯渇し、再利用できるブラックリスト接続もなく、健全な接続がすべてなくなっている | 監視状態を確認する | 監視が停止し、利用者が監視上の異常として把握できる |
| AC-015 | 4.2、FR-001 | Providerがネットワークを含むGateway接続候補を提供する | Event Streamが監視を開始する | Event StreamはProviderの候補のネットワークに従い、独自にネットワークを選択・切替・自動判定しない |
| AC-016 | 4.2、FR-002、FR-003 | ProviderがノードおよびそのGatewayのプロトコル・バージョン、通信契約および通知フォーマットを提供する | Event Streamが候補へ接続して通知を扱う | Event StreamはProviderが提供するノードおよびGatewayの契約に従い、独自にプロトコル・バージョン・通知フォーマットを固定・選択・自動判定しない |

## 11. 未決定事項

要件レベルの未決定事項はない。確定した判断は、本文の制約、機能要件、セキュリティ要件、データ要件および受け入れ条件へ反映している。API、データ構造、アルゴリズム、ライブラリ、データベースなどの方式選択は、仕様設計へ引き継ぐ。

## 12. 仕様設計への引継ぎ

### 12.1 確定した要件

| 決定事項 | 主な対応要件 | 主な受け入れ条件 |
| --- | --- | --- |
| 監視ネットワークはProviderの候補に従い、Event Streamは独自に選択・切替・自動判定しない | 4.2、FR-001、FR-002 | AC-015 |
| ノードのプロトコル・バージョンとGatewayの通信契約・通知フォーマットはProviderの提供内容に従う | 4.2、FR-002、FR-003 | AC-016 |
| 初回接続時の状態差は許容し、初回接続の失敗またはタイムアウトによる切断は異常とする | FR-001、FR-004、FR-005、FR-006 | AC-001、AC-006、AC-012 |
| 初回接続後は最新通知のブロック進行を比較し、最大値から3ブロック以上の差を遅延とする | 4.2、FR-004 | AC-004 |
| 遅延・異常を一時除外し、Provider候補を優先して補充する。候補枯渇時は条件を満たすブロック遅延接続だけをランダムに再利用する | FR-005、FR-006 | AC-005、AC-011〜AC-014 |
| 利用者へ知らせるのは異常対処後の最終的な接続状態および監視状態とする | FR-006 | AC-006、AC-014 |
| Gateway由来の連続通知を継承し、識別できる同一イベントの通知だけを重複抑制する | 4.2、FR-003 | AC-003 |
| 終了後は継続処理を停止し、同一インスタンスで監視を再開しない | FR-007 | AC-007 |

### 12.2 仕様設計で決定する事項

- 監視対象の具体的な種類、表現、追加・解除の公開操作。
- Gateway接続候補、接続状態および健全性の具体的な公開表現。
- 通知の同一性を判断する方式と、重複抑制の保持範囲。
- 確定した3ブロック基準を用いた判定後の接続の切替・除外・補充・再利用の処理方式。
- 最終的な接続状態および監視状態の具体的な公開表現、通知経路および下位Gatewayとの責任境界。
- 終了処理の具体的な公開契約と、新しいインスタンスの初期化から再監視を開始する実装方式。
- API、データ構造、通知型、シリアライズ、ライブラリ、インフラおよび内部処理。
- ブラックリスト接続の原因情報の具体的な表現と、ブロック進行の差を再利用時に確認する具体的な方法。
