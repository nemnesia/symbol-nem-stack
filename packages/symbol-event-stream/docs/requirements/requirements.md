# Symbol Event Stream 要件定義書

## 1. 文書の位置付け

本書は、`@nemnesia/symbol-event-stream` の現行コード、README、CHANGELOG、テストおよび設計書から抽出した要件候補を整理したものである。

対象パッケージには、承認済みのコンセプトシート、既存要件定義書、要件レビュー結果、コンセプトレビュー結果および実装者フィードバックが存在しない。そのため、本書の要件は上位承認済み要件ではなく、現行実装と設計書から導出した要件候補として扱う。正式な製品要件として採用する前に、対象ネットワーク、対応バージョンおよび配信保証を確認する。

本書では、利用者が満たすべき結果を定義し、API名、通知フィールド、具体的な処理順序、クラス構成およびライブラリ内部の方式は決定しない。

## 2. 概要

### 2.1 背景

Symbol WebSocket Gatewayからのリアルタイム通知を複数ノードから受信すると、単一ノードの切断・遅延に依存しにくくなる一方、同じ通知が複数回届く可能性がある。

本パッケージは、複数のGateway接続を一つのイベント監視として利用できるようにし、通知購読、重複排除、接続障害時の候補切り替えおよび終了処理を提供する。

### 2.2 目的

TypeScriptアプリケーションが、複数のSymbol WebSocket Gatewayを用いて、対象通知を継続的に監視できるようにする。

### 2.3 解決する課題

- 複数ノードへの通知購読をアプリケーションごとに個別実装する負担
- 複数ノードから同一通知が届くことによる二重処理
- 接続障害時に監視対象を維持しながら別候補へ切り替える必要
- 接続状態、切断およびエラーを利用者が把握する必要
- アプリケーション終了時に接続や継続処理を確実に停止する必要

## 3. 対象範囲と責任境界

### 3.1 対象

- Symbol WebSocket Gatewayからのリアルタイム通知監視
- 複数の接続候補を利用した通知監視
- 通知種別および対象アドレスによる監視範囲の選択
- 同一監視対象への重複通知の抑制
- 接続状態、接続識別情報、切断およびエラーの観測
- 接続障害時の代替候補への切り替え
- 切り替え後の監視対象の継続
- 候補が不足した場合の任意の候補供給手段の利用
- 明示的な監視終了と一時状態の破棄

### 3.2 対象外

- トランザクションの作成、署名、暗号化、アナウンス
- 秘密鍵、ニーモニック、パスワードその他の秘密情報の管理
- MainnetまたはTestnetの自動選択・自動判定
- 接続候補が同一チェーン・同一ネットワークであることの自動検証
- 通知の署名、真正性、業務上の意味または完全性の検証
- 通知の永続化、履歴取得、リプレイ、欠落・遅延の補償
- REST APIによる履歴照合
- NEMのWebSocket、STOMPその他のSymbol Gateway以外の通知方式
- Gatewayの可用性、通知生成、完全配信およびネットワーク品質の保証

### 3.3 責任境界

| 主体 | 責任 |
| --- | --- |
| Event Stream | 通知監視の統合、購読範囲の管理、重複通知の扱い、候補切り替え、状態観測および終了 |
| 依存WebSocketクライアント | Gateway接続、受信通知の解析・振り分け、下位購読および接続エラーの提供 |
| 利用者・候補供給者 | 適切なチェーン、ネットワーク、Gatewayおよび実行環境に属する候補の提供 |
| 利用者アプリケーション | 通知の業務利用、必要な真正性・完全性確認、保存、欠落時の照合および復旧 |
| Gateway・ネットワーク | 通知の生成、接続サービスおよび配信 |

候補ノードのネットワーク適合性を誰が最終確認するかは未決定であり、利用者責任として確定しない。

## 5. 前提条件と制約

### 5.1 前提条件

- 利用者は到達可能なSymbol WebSocket Gateway候補を用意する。
- 候補は、利用者が対象とするチェーン・ネットワーク・Gateway互換性に適合していることが期待される。
- 通知の業務利用に必要な検証、保存および復旧は利用者アプリケーションが担う。
- Event Streamは秘密情報を扱わない。

### 5.2 確認済みの実装環境制約

- パッケージの実行環境はNode.js 20以上である。
- READMEはTypeScript 5以上を利用環境として記載している。
- 依存する `@nemnesia/symbol-websocket` の公開契約に依存する。
- 対象チェーンはSymbolであり、NEMは対象外である。

### 5.3 未承認の制約候補

接続候補URLの具体的な形式、数値設定の既定値・上限、対象Gatewayのプロトコルバージョンは現行コードで制約されているが、上位承認は確認できない。これらの具体値は仕様設計および正式要件の確認対象とする。

## 6. ユースケース

### UC-01: 複数ノードから通知を監視する

- 利用者: TypeScriptアプリケーション
- 事前条件: 利用可能なGateway候補が用意されている
- 目的: 複数候補を利用してSymbol通知を一つの監視として受け取る
- 期待結果: 対象通知を利用者アプリケーションへ届けられる
- 主な失敗条件: 候補が不正、到達不能または互換性不明で監視を開始できない

### UC-02: 通知種別・対象を選択して監視する

- 利用者: TypeScriptアプリケーション
- 事前条件: Event Streamが利用可能な状態である
- 目的: 必要な通知種別または対象アドレスだけを監視する
- 期待結果: 選択した監視範囲の通知を受け、不要になった監視を解除できる
- 主な失敗条件: 対象外の通知種別または不正な対象指定により監視が成立しない

### UC-03: 複数接続からの重複通知を扱う

- 利用者: 通知を処理するアプリケーション
- 事前条件: 同じ監視対象を複数接続で監視している
- 目的: 同一通知の二重処理を抑制する
- 期待結果: 同一監視対象への同一通知は、設定された重複排除方針に従って扱われる
- 主な失敗条件: 通知を識別できない、または実通知形式が想定と異なる

### UC-04: 接続障害時に監視を継続する

- 利用者: 通知監視アプリケーション
- 事前条件: 複数の候補または候補供給手段が利用可能である
- 目的: 接続障害後に、利用者が有効化した監視を継続する
- 期待結果: 利用可能な候補への切り替えを試み、切り替えに失敗した場合は既存の監視を不必要に失わない
- 主な失敗条件: 代替候補がない、候補供給に失敗する、または監視復元に失敗する

### UC-05: 接続状態と障害を把握する

- 利用者: 運用者または監視アプリケーション
- 事前条件: Event Streamが接続候補を管理している
- 目的: 接続中の候補、切断、接続識別情報およびエラーを把握する
- 期待結果: 利用者が継続・停止・復旧の判断に必要な状態を取得できる
- 主な失敗条件: 状態やエラーの責任境界が不明確で判断できない

### UC-06: アプリケーション終了時に監視を停止する

- 利用者: TypeScriptアプリケーション
- 事前条件: Event Streamが稼働中または初期化途中である
- 目的: 接続、購読および継続処理を終了する
- 期待結果: 終了後に新たな接続、購読復元または候補補充が発生しない
- 主な失敗条件: 終了後も接続またはタイマーが残る

## 7. 機能要件

### FR-001 複数接続による通知監視

- 優先度: MUST
- 要件: Event Streamは、利用者が指定した複数の接続候補を一つの通知監視として利用できる結果を提供しなければならない。
- 対応ユースケース: UC-01
- 受け入れ条件: 有効な候補と接続設定を与えたとき、候補数の範囲内で監視を開始でき、いずれかの接続から対象通知を受信できること。不正な候補または接続設定では監視が開始されないこと。

### FR-002 通知範囲の選択と解除

- 優先度: MUST
- 要件: Event Streamは、対応する通知種別および対象アドレスについて、利用者が監視を追加・解除できる結果を提供しなければならない。個別の受け手を解除しても、同じ監視範囲の他の受け手を不必要に解除してはならない。
- 対応ユースケース: UC-02
- 受け入れ条件: 監視を追加した範囲の通知を受信でき、個別解除後も残りの受け手が通知を受信でき、全解除後はその範囲の通知を受信しないこと。対象外の通知種別または不正な対象指定では監視が成立しないこと。

### FR-003 重複通知の抑制

- 優先度: MUST
- 要件: Event Streamは、同一監視対象に複数接続から届く同一通知を、利用者が設定した重複排除方針に従って一度だけ扱える結果を提供しなければならない。監視種別または対象が異なる通知は、同一通知として統合してはならない。
- 対応ユースケース: UC-03
- 受け入れ条件: 同一監視対象へ同一通知が重複して届いたとき、設定された期間内は一度だけ受信すること。監視種別または対象が異なる場合はそれぞれ受信できること。識別できない通知の扱いは、確定した通知識別方針に従うこと。

### FR-004 接続状態と障害の観測

- 優先度: MUST
- 要件: Event Streamは、利用者が管理中の接続状態、接続識別情報、接続成立、切断およびエラーを観測できる結果を提供しなければならない。
- 対応ユースケース: UC-05
- 受け入れ条件: 利用者が管理中の候補ごとの接続状態を確認でき、接続・切断・エラーを識別可能な通知として受け取れること。ある受け手のcallback異常によって、他の受け手への状態・エラー通知が停止しないこと。

### FR-005 障害時の候補切り替え

- 優先度: MUST
- 要件: Event Streamは、接続障害または再接続が継続した場合、利用可能で一時除外されていない候補への切り替えを試みなければならない。代替候補がない場合は、無効な切り替えによって既存の監視を失わせてはならない。
- 対応ユースケース: UC-04
- 受け入れ条件: 利用可能な代替候補がある場合は切り替えが試みられ、切り替え元候補が一時的に再利用対象から除外されること。代替候補がない場合または切り替え準備に失敗した場合、既存接続が不必要に失われないこと。

### FR-006 監視対象の継続

- 優先度: MUST
- 要件: Event Streamは、再接続または候補切り替えの後も、利用者が解除していない監視対象を継続して扱える結果を提供しなければならない。
- 対応ユースケース: UC-04
- 受け入れ条件: 接続先が変化した後も、解除されていない監視対象から通知を受信できること。復元に失敗した場合、部分的な新規監視だけを残さず、旧接続上の有効な監視を維持すること。

### FR-007 追加候補の利用

- 優先度: MAY
- 要件: 候補供給手段を利用する構成では、固定候補が不足した場合に追加候補を取得し、利用可能な候補として扱える結果を提供しなければならない。
- 対応ユースケース: UC-04
- 受け入れ条件: 追加候補が有効で未使用の場合だけ利用され、供給失敗・空結果・不正候補では既存接続が維持されること。同時に複数の補充要求があっても、同じ供給処理による重複追加が発生しないこと。終了後に解決した結果から新規接続が開始されないこと。

### FR-008 明示的な終了

- 優先度: MUST
- 要件: Event Streamは、利用者が監視を終了した後に、管理中の接続、購読および継続的な候補補充・再接続を停止できる結果を提供しなければならない。終了操作は繰り返し実行できなければならない。
- 対応ユースケース: UC-06
- 受け入れ条件: 終了後に新たな接続、購読復元または候補補充による接続が発生せず、終了済みであることを確認できること。終了操作を複数回行っても追加の失敗や副作用がないこと。

## 8. 非機能要件

### NFR-001 障害時の監視継続性

- 優先度: MUST
- 要件: 利用可能な代替候補が存在する場合、接続障害時に監視対象の継続を試みなければならない。切り替え準備に失敗した場合は、既存の監視を維持しなければならない。
- 対応ユースケース: UC-04
- 受け入れ条件: 代替候補ありの障害で監視継続を試み、代替候補の準備失敗時に旧監視が失われないこと。

### NFR-002 受け手の障害隔離

- 優先度: MUST
- 要件: 一つの通知・接続・切断・エラーcallbackの例外が、同一イベントの他callbackまたはEvent Stream全体の処理を中断してはならない。
- 対応ユースケース: UC-02、UC-05
- 受け入れ条件: 一つのcallbackが例外を送出しても、登録済みの他callbackが実行され、監視処理が継続すること。

### NFR-003 初期化整合性

- 優先度: MUST
- 要件: 入力検証または初期化に失敗した場合、部分的な接続・継続処理を残さず、失敗を利用者が認識できる状態にしなければならない。
- 対応ユースケース: UC-01
- 受け入れ条件: 初期化途中で失敗した場合、既に作成された接続および継続処理が残らず、発生した失敗を利用者が受け取れること。

### NFR-004 終了時の資源解放

- 優先度: MUST
- 要件: 明示的な終了後は、接続、購読、callback、タイマーおよび一時状態を解放し、終了後の非同期結果によって監視を再開してはならない。
- 対応ユースケース: UC-06
- 受け入れ条件: 終了後に時間経過または候補供給の解決があっても、新たな接続・購読復元・候補補充が発生しないこと。

## 9. セキュリティ要件

### SEC-001 接続候補の入力境界

- 優先度: MUST
- 要件: Event Streamは、許可された接続候補だけを接続対象として扱い、不正な形式、認証情報を含む候補または明示的に許可されない候補で接続を開始してはならない。
- 対応ユースケース: UC-01、UC-04
- 受け入れ条件: 不正な接続候補を与えた場合に接続を開始せず、候補供給から不正候補が返った場合に既存接続を損なわないこと。候補が正しいSymbolネットワークまたはGatewayであることの検証は本要件に含めない。

### SEC-002 通知の信頼境界

- 優先度: MUST
- 要件: Event Streamは、受信通知を認証済み、署名検証済み、真正または業務上正当なデータとして保証してはならない。通知の真正性・完全性が必要な利用者は、別の責任主体で確認できなければならない。
- 対応ユースケース: UC-01、UC-03、UC-05
- 受け入れ条件: 要件・利用者向け文書から、通知監視と通知の真正性・業務的妥当性の保証が分離されていること。

### SEC-003 秘密情報の非取扱い

- 優先度: MUST
- 要件: Event Streamは秘密鍵、ニーモニック、パスワードその他の署名・認証用秘密情報を入力、保存または処理対象として要求してはならない。
- 対応ユースケース: 全ユースケース
- 受け入れ条件: 利用者が通知監視を開始・継続・終了するために秘密情報を提供する必要がないこと。

## 10. データ要件

### DR-001 通知データの利用境界

- 優先度: MUST
- 要件: 通知データは、Gatewayから受信し、利用者の監視callbackへ渡す一時的な入力として扱わなければならない。Event Streamは通知内容の業務的意味を確定してはならない。
- 対応ユースケース: UC-01、UC-02、UC-03
- 受け入れ条件: 通知が監視callbackへ渡され、Event Stream自身が業務上の正当性や資産状態を保証しないことが確認できること。

### DR-002 重複排除情報の一時利用

- 優先度: MUST
- 要件: 重複排除に必要な通知識別情報は、一時的な重複判定のために利用し、明示的な終了時に破棄しなければならない。
- 対応ユースケース: UC-03、UC-06
- 受け入れ条件: 終了後に過去の重複判定情報が利用されず、次回利用時に過去インスタンスの一時状態が引き継がれないこと。

### DR-003 履歴・リプレイの非提供

- 優先度: OUT OF SCOPE
- 要件: Event Streamは、停止中または受信不能期間の通知履歴、リプレイおよび欠落補償を提供しない。必要な保存・照合・復旧は利用者アプリケーションが担う。
- 対応ユースケース: UC-04、UC-06

## 11. 受け入れ条件

主要要件に対する受け入れ条件は各要件に記載する。総合的には、次を満たすことを確認する。

1. 有効な接続候補を用いて、複数候補を一つの通知監視として利用できる。
2. 利用者が必要な通知範囲を選択・解除できる。
3. 同一監視対象への重複通知が、確定した重複排除方針に従って扱われる。
4. 接続状態、切断およびエラーを利用者が観測できる。
5. 障害時に代替候補への切り替えと監視継続を試み、失敗時に旧監視を不必要に失わない。
6. callback例外が他の監視やEvent Stream全体を停止させない。
7. 終了後に接続・購読・候補補充が再開せず、終了操作が冪等である。
8. 通知の真正性、履歴、リプレイおよび欠落補償を本パッケージの保証と誤認しない。

## 12. 未決定事項

### OPEN-001 対象ネットワーク

Mainnet、Testnet、その他のネットワークを対象に含めるか、異なるネットワークの候補混在を許可するかを決定する必要がある。候補の適合性と受け入れ範囲に影響する。

### OPEN-002 対象バージョン

対象Symbolプロトコル、Gatewayおよび通知スキーマのバージョンを決定する必要がある。公開通知型との相互運用性に影響する。

### OPEN-003 通知の検証責任

通知payload・topicの実行時検証、通知の真正性・完全性確認をどの責任主体が担うかを決定する必要がある。利用者が通知を業務判断へ利用できる条件に影響する。

### OPEN-004 配信保証

通知の欠落、重複、順序、遅延、再送、リプレイおよびバックプレッシャーについて、どの保証を必要とするかを決定する必要がある。重複排除を完全配信やExactly-once配信と混同しないために必要である。

### OPEN-005 候補ネットワークの責任主体

候補供給者、利用者またはEvent Streamのどの主体が、候補のチェーン・ネットワーク・Gateway適合性を確認するか決定する必要がある。

### OPEN-006 切り替えの成立条件

候補切り替えが成立したと判断する外部条件を決定する必要がある。切り替え後の監視継続、状態通知および受け入れ条件に影響する。

### OPEN-007 障害の利用者通知

候補切り替え、購読復元および候補供給の失敗を、利用者へどの粒度で通知するか決定する必要がある。運用上の復旧判断に影響する。

### OPEN-008 終了後の操作

終了後に監視追加・解除・callback登録などが呼び出された場合の公開契約を決定する必要がある。

### OPEN-009 実Gateway適合性

実Gateway、対象ネットワークおよび対象ノードバージョンを受け入れ対象へ含めるか決定する必要がある。現行テストは主にモックベースであり、実wire形式との適合性は未確認である。

### OPEN-010 NodeProviderのリリース状態

NodeProviderはCHANGELOGの未リリース欄に記載される一方、コード、READMEおよび設計書へ反映されている。正式な公開バージョンの要件範囲へ含めるかを決定する必要がある。

## 13. 仕様設計への引継ぎ

### 13.1 要件として確定候補の事項

- Symbol WebSocket Gatewayの通知を複数候補から一つの監視として扱う。
- 通知種別・対象を選択および解除できる。
- 同一監視対象への重複通知を、確定した方針に基づいて扱う。
- 接続状態、切断およびエラーを観測できる。
- 障害時に候補切り替えと監視継続を試みる。
- callback障害、初期化失敗、候補供給失敗および終了処理を適切に隔離する。
- 通知の真正性・完全性、履歴、リプレイおよび欠落補償は本パッケージの保証外とする。

### 13.2 仕様設計で具体化する事項

- 公開APIと通知型の詳細
- 対応通知種別、対象指定および依存WebSocketとの責任分担
- 接続候補の具体的な入力形式と拒否条件
- 通知識別と重複排除の具体的な判定規則
- 接続切り替え、購読継続、候補供給および終了の外部観測契約
- エラー分類、callback通知および失敗時の公開動作

これらは本書で方式を決定せず、OPEN項目の決定結果と上位要件に基づいて仕様化する。
