# Symbol Event Stream コンセプトシート

## 1. 概要

- 一言で説明: Symbol WebSocket Gatewayを利用するTypeScriptアプリケーションが、複数Gateway接続からの通知を一つの監視として扱い、接続障害や重複通知への対応負担を抑えるためのライブラリ。
- 背景: 単一接続の監視では一時的な切断や遅延の影響を受ける。複数Gateway接続を利用する場合も、同一監視対象に関する通知を利用側で統合する必要がある。

### 中心用語

- 監視対象: 利用者が選択し、継続的に通知を受ける対象範囲。
- 通知: 監視対象に関してSymbol WebSocket Gatewayから届くイベント情報。
- 接続: Event Streamと一つのSymbol WebSocket Gatewayとの接続。
- Gateway接続候補: Providerが提供し、利用者がEvent Streamで利用できるよう準備する接続先候補。候補の適合性はEvent Streamが保証しない。
- 健全な接続: Event Streamが監視の継続に利用できると扱う接続。具体的な判定条件は後続工程で定める。
- 初回: 監視開始後、接続間の状態を整理する前の段階。
- NodeWatch: 公式が開発・運用する、ノード情報を収集・提供するアプリケーションおよびWeb API。
- NodeWatch情報: Event StreamがGateway接続候補の情報源として利用する、NodeWatchから取得したノード情報。情報の正しさや詳細な判定方法は本書では保証・決定しない。
- Provider: `packages/symbol-nem-node-picker`（公開パッケージ名: `@nemnesia/symbol-nem-node-picker`）。NodeWatch情報を利用してGateway接続候補を提供するパッケージ。

## 2. 解決したい課題

- 対象者: Symbolのリアルタイム通知を監視・連携するTypeScriptアプリケーションの開発者および運用者。
- 現在の課題: 単一接続の一時障害で監視が不安定になり、複数接続を利用すると同一監視対象に対する重複通知の二重処理が発生しうる。複数接続の中にブロック進行が遅れている接続が含まれると、古い状態に基づく通知が監視へ混在するおそれがある。接続状態や障害の把握、終了時の後始末も利用側の負担になる。
- 課題の原因: Gateway接続は個別に状態を持ち、複数接続は同じ監視対象に関する通知を届ける可能性がある。また、Gateway接続候補や配信状態は外部環境に依存する。
- 既存手段の不足: 単一接続はノード障害への冗長性がなく、複数接続を利用側だけで統合すると重複抑制、切り替え、購読継続および終了処理を個別に実装する必要がある。
- 放置した場合の影響: 通知の二重処理や古い状態の混在、障害時の復旧判断の遅れ、アプリケーション終了後の不要な接続や継続処理が発生しうる。

これらは初期コンセプトとして整理した課題である。

## 3. 目的

複数Gateway接続を利用するアプリケーションが、接続ごとの差異や重複通知を個別に統合する負担を抑え、利用者が選択した監視対象を一つのリアルタイム監視として扱える状態を作る。

## 4. 対象ユーザーと主要利用場面

### 主対象ユーザー

#### TypeScriptアプリケーション開発者

- 利用目的: Symbolのブロック、ファイナライズ、トランザクションその他の対応通知をリアルタイムに監視する。
- 前提知識: TypeScriptアプリケーションの開発と、利用するSymbol Gateway接続候補の準備ができること。
- 解決される課題: 複数Gateway接続を一つの監視として扱い、重複通知や遅延接続への個別対応負担を抑えられる。

#### アプリケーション運用者

- 利用目的: 接続中の候補や接続障害を把握し、監視の継続・停止・復旧を判断するための材料を得る。
- 前提知識: Gateway、ネットワークおよび対象チェーンの運用条件を管理できること。
- 解決される課題: 接続障害や遅延接続の状態を把握し、監視の継続・停止・復旧を判断できる。

### 利用形態

#### 通知監視・連携アプリケーション

- 位置づけ: 主対象ユーザーが開発・運用するアプリケーションの利用形態であり、人間の対象ユーザーとは区別する。
- 利用目的: 受信した通知を後続の業務処理や連携処理へ渡す。
- 前提知識: 通知の業務上の意味、真正性、完全性および欠落時の照合を自ら判断すること。

### 関係者と責任境界

#### Gateway運用者・NodeWatch運用主体・Provider

- 位置づけ: Event Streamの主対象ユーザーではなく、Gateway接続候補と外部環境の責任境界に関係する主体・パッケージである。
- 関与する内容: Gateway運用者はGatewayの可用性、NodeWatch運用主体はノード情報の収集・提供、ProviderはNodeWatch情報を利用したGateway接続候補の提供に関係する。
- Event Streamとの関係: Event Streamが担う監視状態と、Gateway運用者・NodeWatch運用主体・Providerが担う外部情報や接続候補の責任を区別する。

### 主要利用場面

- 誰が: Symbol通知を扱うアプリケーションの開発者・運用者が。
- どのような状況で: 複数のGateway接続候補を使い、利用者が選択した監視対象への通知を継続したいとき。
- 何に困っており: 接続障害、重複通知および遅延接続の影響を、開発者・運用者だけで判断・処理する必要がある。
- どのような状態になることを期待するか: 接続状態や異常を把握して監視の継続・停止・復旧を判断でき、アプリケーションのライフサイクルに合わせて監視を終了できる。

## 6. v1のスコープと責任境界

### v1で扱う範囲

- Symbol WebSocket Gatewayからの複数接続を、一つのリアルタイム通知監視として扱う。
- 利用者が選択した監視対象を継続的に扱い、同一監視対象への重複通知を抑制する。
- 複数接続を活用し、接続間の状態差による遅延接続の影響を抑える。短時間フォークかどうかの判定は行わない。
- 候補不足または全接続不健全を監視上の異常として扱い、利用者が接続状態を把握できるようにする。
- ProviderがNodeWatch情報を利用して提供するGateway接続候補を前提とし、利用者がEvent Streamで利用できる候補を準備する。Event Stream側では候補の適合性を追加判定・保証しない。
- 候補が不足しても指定された接続数を無理に補充せず、健全な接続が残る場合はその接続で監視を維持する。
- 利用者が監視を終了した後は、監視に関係する継続処理を停止する。

### v1では実施しないこと

- トランザクションの作成、署名、暗号化、アナウンスおよび秘密情報の管理
- Mainnet、Testnetその他のネットワークの自動選択・自動判定
- 通知の真正性、署名、完全性、業務上の意味または正当性の保証
- 通知の永続化、履歴取得、リプレイ、欠落・遅延の補償
- 外部の履歴サービスを用いた欠落補完
- NEMまたはSymbol Gateway以外の通知方式への対応

### プロジェクトとして扱わないこと

Gatewayの可用性、通知生成、ネットワーク品質および完全配信は、Event Streamの責任範囲に含めない。候補が対象チェーン・ネットワーク・Gatewayに適合することの自動保証も行わない。
短時間フォークの発生有無や正当性の判定も、Event Streamの責任範囲に含めない。

### 外部へ委ねること

- 利用者: Providerが提供する候補を利用する環境を準備し、Event Streamで利用する候補が到達可能で対象に適合することを確認する。通知の業務利用、必要な真正性・完全性確認、保存、欠落時の照合および復旧も担う。
- Gateway・ネットワーク: 通知の生成、接続サービスおよび配信。
- NodeWatch運用主体: 公式のNodeWatchを開発・運用し、ノード情報を収集・提供する。
- Provider: NodeWatch情報を利用してGateway接続候補を提供する。Event Streamは候補の適合性を追加判定・保証しない。

## 7. 判断原則

### 監視の継続性と重複抑制を一体で考える

- 原則: 複数接続の価値は、接続数を増やすことではなく、監視の鮮度を保ちながら重複通知と接続障害の影響を抑えることに置く。
- 理由: 単一接続の障害、複数接続の重複および接続間のブロック進行差が、このプロジェクトで扱う課題だからである。
- 判断への適用: 監視の継続性と重複抑制を両立する範囲で方式を選び、完全配信や一度だけの処理保証など、未承認の保証を追加しない。接続状態や異常を把握したうえでの利用者の継続・停止・復旧判断と、具体的な通知採用、接続除外および異常情報の扱いは後続工程で定める。

### 保証範囲と外部責任を分ける

- 原則: Event Streamが提供する監視上の価値と、Gateway・ネットワーク・利用者アプリケーションの責任を混同しない。
- 理由: 通知の可用性、真正性、業務上の正当性および欠落復旧は、Event Streamだけでは確定できないからである。
- 判断への適用: 不足している保証をライブラリの能力として追加せず、必要な場合は外部責任または未決定事項へ送る。

### 未確認事項を確定仕様として扱わない

- 原則: ProviderがNodeWatch情報を利用して提供する候補を前提とし、配信保証、切り替え成立条件および公開範囲など、明示されていない保証は事実と仮定を分ける。
- 理由: ノード情報の収集・提供はNodeWatch運用主体に、候補の提供はProviderに委ねる一方、Event Streamが担う保証の境界は別途明確にする必要があるためである。
- 判断への適用: 上位承認または対象環境の確認がない事項は、v1の必須能力や保証として固定しない。

### 原則間の優先順位

責任境界と未確認事項の明示を優先し、その範囲内で監視継続と重複抑制の両立を目指す。継続性を高めるために、完全配信・真正性・ネットワーク適合性など未承認の保証を追加しない。

## 8. 成功条件

- 複数のSymbol Gateway接続候補を利用するアプリケーションが、監視対象への通知を一つの監視として扱える。
- 同一監視対象への重複通知による二重処理を抑制できる。
- 遅延接続や接続障害の影響を把握し、監視の継続・停止・復旧を判断できる。
- 候補不足時に健全な接続が残っていれば、その接続で監視を維持できる。
- 全接続不健全時に、監視上の異常を把握できる。
- 監視終了後に、監視に関係する接続や継続処理が残らない。

これらはコンセプトの成立を確認するための状態であり、具体的な確認方法は後続工程へ引き継ぐ。

## 9. 前提条件と主なリスク

### 前提条件

- 対象はSymbolであり、NEMは対象外である。
- Providerが提供する候補を利用者が準備し、Event Streamで利用する候補が到達可能で対象に適合することを確認する。
- 公式のNodeWatchから取得したノード情報をProviderがGateway接続候補の提供に利用する。
- Event Streamは、Providerが提供する候補のチェーン・ネットワーク・Gateway適合性を保証しない。
- 通知の業務利用に必要な検証、保存、欠落時の照合および復旧は利用者アプリケーションが担う。
- Event Streamは秘密情報を扱わない。

### 主なリスク

- NodeWatch情報またはそこから得たGateway接続候補が対象チェーン・ネットワーク・Gatewayに適合しない可能性がある。Event Streamはその適合性を保証しないため、監視結果を利用者が誤って解釈するおそれがある。
- 重複抑制が完全配信、順序保証、一度だけの処理保証または欠落補償と誤解される可能性。
- 実際の接続環境や通知形式が、利用者の想定と一致しない可能性。
- ブロック進行の遅れを誤って判定し、利用可能な接続を除外したり、遅れた接続を監視へ残したりする可能性。
- 短時間フォークに起因するブロック進行差を遅延として扱い、接続の除外に至る可能性。
- 監視開始直後は接続間の状態が整理されていないため、遅延接続の影響を受ける可能性がある。
- 新しいGateway接続候補が不足し、指定された接続数を維持できない可能性。
- 異常情報の具体的な内容や受け取り方が未確定で、復旧判断に影響する可能性がある。
- 監視終了後の継続処理停止方針と、監視追加・解除などの具体的な操作契約が一致しない可能性がある。

## 12. 要件定義への引継ぎ

ここに挙げる事項は、11章のCU-001〜CU-008に対応する。決定済みのコンセプト方針を再判断するものではなく、その方針を実現するために要件定義中に具体化する論点である。9章に記載した外部前提および保証対象外は、この引継ぎ事項には含めない。

- 監視継続、重複抑制、配信順序、欠落、再送および遅延について、必要な保証の境界を定める。
- NodeWatch情報の信頼境界、Providerが提供する候補の適合性の確認責任および候補を利用する責任範囲を具体化する。
- 初期状態での接続受入れと通知採用の規則、初回通知における遅延許容の範囲を具体化する。
- 遅延接続の判定基準として3ブロック閾値をどう扱うか、短時間フォークを判定しない責任境界を具体化する。
- 接続除外後の復帰方針、候補不足・全接続不健全時の監視状態および異常情報の扱いを具体化する。
- 異常情報を通常のイベント情報と同じ配信経路で扱う範囲と、利用者が受け取るかどうかを判断できる範囲を具体化する。
- 通知の検証、保存・復旧および完全配信に関する責任境界を具体化する。
- 監視終了後の追加・解除などの操作の扱いを定める。
