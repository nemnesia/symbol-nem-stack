# Symbol Event Stream コンセプトシート

## 1. 概要

- 一言で説明: Symbol WebSocket Gatewayを利用するTypeScriptアプリケーションが、複数ノードの通知を一つの監視として扱い、接続障害や重複通知への対応負担を抑えるためのライブラリ。
- 背景: 単一ノードの監視では一時的な切断や遅延の影響を受ける。複数ノードを監視すると継続性を高められる一方、同じ通知が複数回届くため、利用側で両方の問題を扱う必要がある。


## 2. 解決したい課題

- 対象者: Symbolのリアルタイム通知を監視・連携するTypeScriptアプリケーションの開発者および運用者。
- 現在の課題: 単一ノードの一時障害で監視が不安定になり、複数ノードを利用すると同じ通知の二重処理が発生する。接続状態や障害の把握、終了時の後始末も利用側の負担になる。
- 課題の原因: Gateway接続は個別に状態を持ち、複数接続は同じ監視対象へ同じ通知を届ける可能性がある。また、接続候補や配信状態は外部環境に依存する。
- 既存手段の不足: 単一接続はノード障害への冗長性がなく、複数接続を利用側だけで統合すると重複抑制、切り替え、購読継続および終了処理を個別に実装する必要がある。
- 放置した場合の影響: 一時的な通知停止、同じ通知の二重処理、障害時の復旧判断の遅れ、アプリケーション終了後の不要な接続や継続処理が発生しうる。

これらは初期コンセプトとして整理した課題である。

## 3. 目的

複数のSymbol WebSocket Gatewayを利用するアプリケーションが、利用者の監視対象を一つのリアルタイム監視として扱える状態を作る。

その状態では、複数接続による重複通知や一時的な接続障害の影響を利用側が個別に吸収する負担を抑え、接続状態を把握しながら監視を継続または終了できることを目指す。

## 4. 対象ユーザーと主要利用場面

### TypeScriptアプリケーション開発者

- 利用目的: Symbolのブロック、ファイナライズ、トランザクションその他の対応通知をリアルタイムに監視する。
- 前提知識: TypeScriptアプリケーションの開発と、利用するSymbol Gateway候補の準備ができること。
- 解決される課題: 複数Gatewayの監視を一つの監視として扱うための統合負担と、同一通知の二重処理への対応負担を抑えられる。

### 通知監視・連携アプリケーション

- 利用目的: 受信した通知を後続の業務処理や連携処理へ渡す。
- 前提知識: 通知の業務上の意味、真正性、完全性および欠落時の照合を自ら判断すること。
- 解決される課題: 接続障害時にも可能な範囲で監視対象の継続を試みつつ、監視基盤の接続状態を把握できる。

### 運用者・Gateway運用者

- 利用目的: 接続中の候補や接続障害を把握し、継続・停止・復旧の判断材料を得る。
- 前提知識: Gateway、ネットワークおよび対象チェーンの運用条件を管理できること。
- 解決される課題: Event Streamが担う監視状態と、Gateway・ネットワーク側が担う可用性や配信の責任を区別できる。

### 主要利用場面

- 誰が: Symbol通知を扱うアプリケーションが。
- どのような状況で: 複数のGateway候補を使って、ブロックやアドレスに関係する通知を継続的に監視したいとき。
- 何に困っており: 単一ノードの障害と複数ノードからの重複通知を、利用側だけで同時に扱う必要がある。
- どのような状態になることを期待するか: 利用可能な範囲で監視を続け、重複通知の扱いと接続状態を把握しながら、アプリケーションのライフサイクルに合わせて監視を終了できる。

## 5. 提供価値

| 対象ユーザー | 得られる価値 | 利用する理由 |
| --- | --- | --- |
| TypeScriptアプリケーション開発者 | 複数Gatewayを一つの監視として扱えるため、接続統合の実装負担を抑えられる | 単一ノード障害への依存を減らしつつ、複数接続を利用したいから |
| 通知監視・連携アプリケーション | 同一監視対象への重複処理を抑え、障害時も監視継続を試みられる | 通知処理の二重化や一時停止の影響を抑えたいから |
| 運用者 | 接続状態や障害を把握するための判断材料を得られる | 継続・停止・復旧の判断に監視状態が必要だから |
| Gateway運用者・候補供給者 | Event Streamと外部環境の責任境界を分けて扱える | Gatewayの可用性や候補の適合性をライブラリの保証と混同しないため |

本パッケージは、通知の完全配信、欠落補償、履歴・リプレイ、通知の真正性・完全性または業務上の正当性を保証する価値を提供しない。

## 6. v1のスコープと責任境界

### v1で扱う範囲

Event Streamは、Symbol WebSocket Gatewayからの複数接続を一つのリアルタイム通知監視として扱う能力と責任を持つ。利用者が選択した監視範囲を継続的に扱い、同一監視対象への重複通知を抑制する。また、接続障害時の候補切り替えと監視継続を試み、接続状態や障害を利用者が把握できるようにする。利用者が監視を終了した後は、監視に関係する継続処理を停止する。

候補が不足した場合の追加候補供給を行う。

### v1では実施しないこと

- トランザクションの作成、署名、暗号化、アナウンスおよび秘密情報の管理
- Mainnet、Testnetその他のネットワークの自動選択・自動判定
- 通知の真正性、署名、完全性、業務上の意味または正当性の保証
- 通知の永続化、履歴取得、リプレイ、欠落・遅延の補償
- 外部の履歴サービスを用いた欠落補完
- NEMまたはSymbol Gateway以外の通知方式への対応

### プロジェクトとして扱わないこと

Gatewayの可用性、通知生成、ネットワーク品質および完全配信は、Event Streamの責任範囲に含めない。候補が対象チェーン・ネットワーク・Gatewayに適合することの自動保証も行わない。

### 外部へ委ねること

- 利用者: 到達可能で対象に適合するGateway候補の準備、通知の業務利用、必要な真正性・完全性確認、保存、欠落時の照合および復旧。
- Gateway・ネットワーク: 通知の生成、接続サービスおよび配信。
- 候補供給者: 追加候補を提供する場合の候補の成立条件。ただし、候補の適合性を最終的に誰が確認するかは未決定である。

## 7. 判断原則

### 監視の継続性と重複抑制を一体で考える

- 原則: 複数接続の価値は、接続数を増やすことではなく、監視継続を試みながら同一監視対象への重複処理を抑えることに置く。
- 理由: 単一接続の障害と複数接続の重複が、このプロジェクトで同時に扱う課題だからである。
- 判断への適用: 新しい要件を検討するときは、監視継続の効果と重複通知の扱いを別々の価値として確認し、完全配信や一度だけの処理保証を暗黙に追加しない。

### 保証範囲と外部責任を分ける

- 原則: Event Streamが提供する監視上の価値と、Gateway・ネットワーク・利用者アプリケーションの責任を混同しない。
- 理由: 通知の可用性、真正性、業務上の正当性および欠落復旧は、Event Streamだけでは確定できないからである。
- 判断への適用: 不足している保証をライブラリの能力として追加せず、必要な場合は外部責任または未決定事項へ送る。

### 未確認事項を確定仕様として扱わない

- 原則: 対象ネットワーク、対応バージョン、配信保証、切り替え成立条件および公開範囲が確認できるまで、事実と仮定を分ける。
- 理由: 初期段階では、対象範囲や保証の境界が確定していないためである。
- 判断への適用: 上位承認または対象環境の確認がない事項は、v1の必須能力や保証として固定しない。

### 原則間の優先順位

責任境界と未確認事項の明示を優先し、その範囲内で監視継続と重複抑制の両立を目指す。継続性を高めるために、完全配信・真正性・ネットワーク適合性など未承認の保証を追加しない。

## 8. 成功条件

- 複数のSymbol Gateway候補を利用するアプリケーションが、通知を一つの監視対象として扱える。
- 複数接続によって同一監視対象へ届く通知について、合意した範囲の重複抑制を利用者が期待できる。
- 接続障害が発生したとき、利用可能な範囲で監視継続を試みたことと接続状態を利用者が把握できる。
- 利用者が監視を終了した後、接続や監視継続処理が残らないことを期待できる。
- Event Streamの監視上の価値と、Gateway・ネットワーク・利用者アプリケーションに委ねる責任が混同されない。
- 通知の欠落、完全配信、真正性、完全性および履歴・リプレイが本パッケージの保証外であることを関係者が理解できる。

これらはコンセプトの成立を確認するための状態であり、具体的な確認方法は後続工程へ引き継ぐ。

## 9. 前提条件と主なリスク

### 前提条件

- 対象はSymbolであり、NEMは対象外である。
- 利用者が到達可能なSymbol WebSocket Gateway候補を用意する。
- 候補が対象チェーン・ネットワーク・Gateway互換性に適合することを期待する。ただし、Event Stream自身がその適合性を保証することは未決定である。
- 通知の業務利用に必要な検証、保存、欠落時の照合および復旧は利用者アプリケーションが担う。
- Event Streamは秘密情報を扱わない。
- 実行環境の最低Node.jsは20である。

### 主なリスク

- 異なるネットワークや互換性のないGateway候補が混在し、監視結果を利用者が誤って解釈する可能性。
- 重複抑制が完全配信、順序保証、一度だけの処理保証または欠落補償と誤解される可能性。
- 実際の接続環境や通知形式が、利用者の想定と一致しない可能性。
- 切り替え、購読継続、候補供給の失敗を利用者へどの粒度で伝えるかが未確定で、復旧判断に影響する可能性。
- 終了後の監視追加・解除などの操作契約が未確定である。
