# Symbol WebSocket コンセプトシート

## 1. 概要

Symbol WebSocket は、Symbol WebSocket Gateway が提供するブロックチェーンのリアルタイム通知を、TypeScript アプリケーションから監視するためのクライアントライブラリである。

本パッケージの中心的な役割は、アプリケーションが必要とする通知の監視意図を保ちながら、Gateway との接続状態と通知監視の異常を扱えるようにすることである。トランザクションの作成・署名・送信、通知内容の真正性の保証、履歴の保存は本パッケージの目的に含めない。

## 2. 解決したい課題

### 対象者

- Symbol のリアルタイム状態やトランザクション通知を利用する TypeScript アプリケーション開発者
- 通知を継続的に監視する監視・連携アプリケーションの開発者

### 課題

対象者は、Symbol のリアルタイム通知をアプリケーションへ組み込む際に、次の課題に直面する。

1. Gateway から必要な通知だけを監視対象として扱いたい。
2. 接続の確立や一時的な切断によって、利用者が意図した監視対象を失いたくない。
3. 接続の成立、切断、再接続および通知受信時の異常を把握し、継続・停止を判断したい。
4. ある監視処理やコールバックの異常が、他の監視処理全体へ波及することを避けたい。

### 未導入時の影響

これらを利用側が個別に扱う場合、Gateway 接続の状態管理、監視意図の維持、異常の観測をアプリケーションごとに実装する必要がある。その結果、監視の継続性や障害時の判断がアプリケーションごとに不均一になる可能性がある。

なお、既存の代替手段との比較や、導入前の定量的な負担・損失は資料から確認できていない。

## 3. 目的

Symbol WebSocket は、TypeScript アプリケーションが Symbol WebSocket Gateway のリアルタイム通知を、必要な範囲に絞って監視できる状態を提供する。

一時的な接続状態の変化があっても監視の意図を維持し、接続や通知受信に関する異常を利用者が把握できるようにすることで、利用者が自身のアプリケーションの継続・停止・復旧方針を判断できるようにする。

## 4. 対象ユーザーと主要利用場面

### 4.1 対象ユーザー

| 対象 | 利用目的 |
| --- | --- |
| TypeScript アプリケーション開発者 | Symbol のリアルタイム通知をアプリケーションの処理へ取り込む |
| 監視・連携アプリケーションの開発者 | 特定の通知や対象を継続的に監視し、後続処理へ渡す |
| Gateway 運用者・上流システム担当者 | 通知提供側または通知利用側として、接続・配信の責任境界を把握する |

### 4.2 主要利用場面

1. Symbol のブロックチェーン状態やトランザクションに関するリアルタイム通知を監視する。
2. アプリケーションの目的に応じて、通知カテゴリや対象を選んで監視する。
3. 一時的な接続切断から復帰した後も、利用者が解除していない監視意図を継続する。
4. 接続・受信の異常を把握し、アプリケーション側で継続、停止、再処理などを判断する。
5. 監視を終了し、不要になった監視意図を取り除く。

## 5. 提供価値

| 価値 | 利用者にとっての意味 |
| --- | --- |
| リアルタイム性 | Symbol の状態変化を、アプリケーションの監視対象として扱える |
| 監視範囲の明確化 | 必要な通知カテゴリや対象に集中できる |
| 監視意図の継続 | 接続状態の一時的な変化で、利用者の監視方針が不用意に失われない |
| 障害時の判断可能性 | 接続・受信の異常を把握し、アプリケーション自身の復旧方針を選べる |
| 開発時の扱いやすさ | TypeScript アプリケーションから通知を型付きの開発者向け境界として利用できる |

## 6. v1 のスコープと責任境界

### 6.1 v1 で提供する能力

- Symbol WebSocket Gateway が提供するリアルタイム通知を、TypeScript アプリケーションが監視できるようにする。
- 利用者が選択した通知カテゴリおよび対応する監視対象を管理できるようにする。
- 接続の確立中または一時的な切断後も、解除されていない監視意図を維持できるようにする。
- 接続状態、再接続、接続異常および通知受信時の異常を、利用者が判断に使える形で観測できるようにする。
- 通知を TypeScript アプリケーションが扱うための型付きの公開境界を提供する。

### 6.2 v1 に含めないもの

- トランザクションの生成、署名、暗号化、アナウンスまたは秘密情報の管理
- アプリケーション認証、通知の真正性・署名の検証、通知内容の意味検証
- 通知の永続化、履歴管理、リプレイ、欠落・重複・遅延の補償、完全配信の保証
- Mainnet と Testnet の自動選択、ネットワーク整合性の自動判定
- NEM の WebSocket や STOMP など、Symbol Gateway 以外の通知方式
- 通知の機密性または完全性を本パッケージ単独で保証すること

### 6.3 本パッケージの責任外

- Gateway の可用性、通知の生成、通知配信および対象プロトコルとの互換性
- Gateway から受け取った通知が正当なものであることの保証
- 通知を用いた最終的な業務判断、資産保全、状態の永続化および復旧
- 通知の欠落・重複・遅延に対する利用側の回復処理
- 利用者が選択した Gateway とネットワークの適合性の判断

利用者は接続先、ネットワーク、実行環境および利用目的に適した検証・保存・復旧方針を担う。Gateway 運用者は、Gateway の稼働と通知の生成・配信を担う。TLS、証明書、プロキシおよび信頼設定の責任分担は未決定であり、要件定義で確定する。

## 7. 判断原則

1. 本パッケージの責任範囲は、Symbol WebSocket Gateway の通知監視に限定する。
2. 利用者が解除していない監視意図は、接続状態の変化によって不用意に失われないことを優先する。
3. 本パッケージが観測できる接続・受信状態と、Gateway の配信保証や利用者の業務責任を明確に区別する。
4. 通知の真正性、欠落・重複・遅延、ネットワーク整合性など、資料で決定されていない責任は推測で補完しない。
5. 未決定事項は、実装上の暗黙の保証にせず、要件定義で判断可能な論点として引き継ぐ。

## 8. 成功条件

v1 は、少なくとも次の状態を満たしたとき、コンセプト上の目的を達成したと判断する。

- 対応する環境に接続した TypeScript アプリケーションが、Symbol のリアルタイム通知を監視できる。
- 利用者が選択した監視範囲を維持しながら、一時的な接続状態の変化から監視を継続できる。
- 利用者が接続・受信の異常を把握し、アプリケーションの継続または停止を判断できる。
- 一つの監視処理やコールバックの異常が、他の監視処理の利用可能性を不必要に損なわない。
- 利用者が、本パッケージを通知の真正性、完全配信、履歴保存または業務上の安全性を保証する機能と誤認しない。

これらを満たす具体的な測定方法や適合条件は、要件定義および仕様書で定める。

## 9. 前提条件と主なリスク

### 9.1 前提条件

- 利用者は、到達可能で利用対象ネットワークに適合する Symbol WebSocket Gateway を用意する。
- 通知の生成と配信は Gateway の責任範囲であり、本パッケージはその通知を利用側へ届ける境界を担う。
- 通知を使った業務処理、検証、保存および復旧は、利用者または上流システムが担う。
- 本パッケージは秘密鍵、ニーモニック、パスワードなどの秘密情報を扱う機能を持たない。

### 9.2 主なリスク

| ID | リスク | 影響 |
| --- | --- | --- |
| R-001 | Gateway、WebSocket プロトコル、Symbol ネットワークまたは対象バージョンの互換性が未確定 | 接続・通知監視の成立条件を判断できない |
| R-002 | TLS、証明書、プロキシおよび信頼モデルの責任境界が未確定 | 安全な接続の前提を誤認する可能性がある |
| R-003 | 通知の真正性、内容の完全性および意味検証の責任が未確定 | 業務判断に不適切な通知を利用する可能性がある |
| R-004 | 通知の確認応答、再送、リプレイ、欠落、重複および遅延の扱いが未確定 | 監視結果の完全性や復旧方針を判断できない |
| R-005 | アドレスとネットワークの整合性を誰が確認するか未確定 | 意図しない対象を監視する可能性がある |
| R-006 | 再接続を継続できない場合の終端条件と観測方法が未確定 | 停止判断や運用設計が不明確になる |
| R-007 | 統合的な検証範囲が主に Symbol Testnet と限定された通知に依存している | 他ネットワーク・通知種別への適用範囲を誤認する可能性がある |

## 10. 将来コンセプト

現時点のコード、仕様書および要件定義書には、v1 の先に提供する価値や機能の明示的な合意がない。そのため、将来コンセプトは未定とする。

永続化、履歴・リプレイ、欠落補償、通知の真正性検証、ネットワーク整合性検証などは、必要性・責任主体・安全性を別途合意した後に検討する事項であり、本コンセプトから将来機能として確約しない。
