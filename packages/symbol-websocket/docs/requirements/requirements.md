# Symbol WebSocket 要件定義書

## 1. 概要

### 背景

Symbolノードは、ブロックチェーンの状態変化やトランザクション関連イベントをWebSocket Gatewayからリアルタイムに通知する。本パッケージは、アプリケーションがこれらの通知を監視するためのクライアント機能を提供する。

### 目的

Symbol Gatewayへの接続、通知の購読、接続状態およびエラーの把握、接続断後の監視継続を、TypeScriptアプリケーションから利用できるようにする。

### 解決する課題

- アプリケーションがSymbolのリアルタイム通知を利用できること
- 通知対象の登録・解除を管理できること
- 接続準備前や一時的な接続断によって、利用者の購読意図が失われないこと
- 通知処理の例外や接続エラーが監視全体へ波及しないこと

### 根拠の位置付け

承認済みの上流要件、コンセプトシートおよび既存要件定義書は確認できない。本書は、ユーザーが指定した対象パッケージのコードと設計書から、現行の外部契約を要件レベルへ整理したものである。実装方式、APIの詳細、wire形式および内部処理は仕様設計へ引き渡す。

## 2. 対象範囲と責任境界

### 対象

- Symbol GatewayへのWebSocket接続
- ブロック、ファイナライズ済みブロック、確定・未確定・部分トランザクション、連署、ステータスに関する通知の監視
- 通知全体または対応する対象に限定した購読
- 購読の登録、個別解除、対象単位の解除
- 接続状態、接続完了、再接続、エラーおよび切断の利用者向け通知
- 一時的な接続断後の購読継続

### 対象外

- トランザクションの作成、署名、暗号化およびannounce
- WebSocketのアプリケーション認証
- 通知の署名、真正性、意味的妥当性の検証
- 通知の永続保存、再送、欠落補償および履歴取得
- NEMのWebSocket/STOMP接続
- MainnetまたはTestnetの自動選択

### 責任境界

- 利用者は接続先ホストと、そのホストが提供するネットワークの適合性を管理する。
- Gatewayは通知の生成および配信を担う。本パッケージはGatewayが提供する通知の到達を超える保証をしない。
- 通知を業務判断、資産操作または永続データとして利用する場合の追加検証・保存は利用者または上位システムが担う。
- 本パッケージは秘密鍵を入力・保存・管理しない。

## 3. 利用者と関係者

| 区分 | 目的・関心 |
| --- | --- |
| TypeScriptアプリケーション開発者 | Symbolのリアルタイム通知を監視し、アプリケーション処理へ渡す。 |
| 通知監視アプリケーション | 通知対象を登録し、接続状態や障害を利用者へ示す。 |
| Symbol Gateway運用者 | GatewayのWebSocket接続と通知配信を提供する。 |
| 上位システム運用者 | 通知の業務利用、永続化、再送および秘密情報保護を管理する。 |

## 4. 前提条件と制約

- 対象チェーンはSymbolとする。
- 接続先ネットワークは利用者が指定するGatewayホストに依存する。本パッケージはMainnet / Testnetを自動選択または検証しない。
- 利用者はWebSocket接続可能なGatewayとネットワーク環境を用意する。
- 通知の正式な対象Gateway、Symbolプロトコルおよびネットワーク別対応バージョンは未確定である。
- 通信のTLS必須性、Gateway認証、証明書およびプロキシの責任範囲は未確定である。
- 設定可能な接続タイムアウト、自動再接続、再接続回数および再接続間隔を提供する。ただし、具体的な設定値と回数の意味は仕様設計で整合させる。

## 5. ユースケース

### UC-01: 通知監視を開始する

- 利用者: TypeScriptアプリケーション
- 事前条件: 利用可能なSymbol Gatewayの接続先がある
- 目的: Gatewayへ接続し、通知監視を開始する
- 期待結果: 接続の利用可否とGateway接続完了を利用者が判別できる
- 主な失敗条件: 接続先設定が不正、接続失敗、接続完了待ちの期限超過

### UC-02: 通知を購読する

- 利用者: 通知監視アプリケーション
- 事前条件: UC-01の接続開始後、監視対象が決まっている
- 目的: 必要な通知カテゴリを選択して受信する
- 期待結果: 登録した対象に一致する通知が利用者の受信処理へ渡る
- 主な失敗条件: 未対応カテゴリ、不正な対象指定、接続準備未完了

### UC-03: 通知の利用者処理を解除する

- 利用者: 通知監視アプリケーション
- 事前条件: 通知処理が登録されている
- 目的: 一部または全部の通知処理を停止する
- 期待結果: 個別解除では他の処理を維持し、対象単位の解除では対象の処理を停止する
- 主な失敗条件: 解除対象が存在しない場合でも、監視状態が不整合にならない

### UC-04: 接続断から監視を継続する

- 利用者: 通知監視アプリケーション
- 事前条件: 自動再接続が有効で、通知監視が登録されている
- 目的: 一時的な接続断後に監視を再開する
- 期待結果: 利用者が再登録しなくても、接続断前の監視対象が継続して利用できる
- 主な失敗条件: 自動再接続が無効、許容された再接続回数の上限到達、手動切断

### UC-05: 障害を処理する

- 利用者: 通知監視アプリケーション
- 事前条件: 接続または通知処理が実行中である
- 目的: 接続、通信、構文解析および接続完了待ちの障害を識別する
- 期待結果: 利用者が障害の区分と回復可能性を把握し、継続または停止を判断できる
- 主な失敗条件: エラー処理の未登録、利用者callbackの例外

### UC-06: 監視を終了する

- 利用者: 通知監視アプリケーション
- 事前条件: 接続または再接続が実行中である
- 目的: 接続と監視処理を明示的に終了する
- 期待結果: 自動再接続、購読および登録済み処理が終了する
- 主な失敗条件: なし

## 6. 機能要件

| ID | 要件 | 優先度 | 対応ユースケース |
| --- | --- | --- | --- |
| FR-001 | 利用者が指定した接続先設定に基づき、Symbol Gatewayへの通知監視接続を開始できなければならない。 | MUST | UC-01 |
| FR-002 | 接続先設定または通知対象設定が不正な場合、外部接続または購読要求を開始する前に利用者へ失敗を通知しなければならない。 | MUST | UC-01, UC-02 |
| FR-003 | 利用者は、WebSocket通信路の状態とGatewayとの接続完了状態を区別して把握できなければならない。 | MUST | UC-01, UC-05 |
| FR-004 | 利用者は、ブロック、ファイナライズ済みブロック、確定・未確定・部分トランザクション、連署およびステータスの通知を選択して購読できなければならない。 | MUST | UC-02 |
| FR-005 | 対応する通知カテゴリでは、利用者はSymbolアドレスまたはnamespace識別子に基づき監視対象を限定できなければならない。対象外カテゴリへの限定指定は受け付けてはならない。 | MUST | UC-02 |
| FR-006 | 接続完了前または再接続待機中に登録された購読は、利用者が解除していない限り、接続可能になった後も有効にならなければならない。 | MUST | UC-02, UC-04 |
| FR-007 | 同一の通知対象に複数の利用者処理を登録でき、個別解除では対象処理だけを解除できなければならない。対象に処理がなくなった場合は、その対象の購読を停止しなければならない。 | MUST | UC-02, UC-03 |
| FR-008 | 利用者が登録した通知対象に一致する通知だけを受信処理へ渡し、未登録または対象不明の通知を通常通知として渡してはならない。 | MUST | UC-02 |
| FR-009 | 予期しない接続断が発生した場合、自動再接続設定に従って監視の再開を試みなければならない。自動再接続が無効または許容回数に達した場合は、再接続を継続してはならない。 | MUST | UC-04 |
| FR-010 | 自動再接続後、接続断前に有効だった購読と、再接続待機中に登録された購読を、利用者の再登録なしに継続利用できなければならない。 | MUST | UC-04 |
| FR-011 | 利用者は、接続完了、再接続開始、接続クローズおよびエラーを外部から観測できなければならない。各通知処理は個別に解除できなければならない。 | MUST | UC-01, UC-04, UC-05 |
| FR-012 | 利用者は、接続、構文解析および接続完了待ちに関する障害を区別し、回復可能性を判断できなければならない。 | MUST | UC-05 |
| FR-013 | 利用者callbackが例外を発生させても、他のcallback、通知配送、接続状態管理および購読継続を妨げてはならない。 | MUST | UC-02, UC-04, UC-05 |
| FR-014 | 利用者が手動切断を選択した場合、自動再接続、購読および登録済みcallbackを終了しなければならない。手動切断後に同一インスタンスで接続を再開することを保証してはならない。 | MUST | UC-06 |

## 7. 非機能要件

| ID | 要件 | 優先度 | 影響 |
| --- | --- | --- | --- |
| NFR-001 | TypeScript利用者は、通知カテゴリに対応する公開型を用いて、通知データをコンパイル時に扱えなければならない。 | SHOULD | UC-02 |
| NFR-002 | 通知に含まれる高さ、時刻、ハッシュその他の大きな整数または識別値は、利用者が精度損失を避けて扱える必要がある。 | MUST | UC-02 |
| NFR-003 | 接続断、通知構文エラーおよび利用者callbackの例外が、監視全体の継続可能な処理を不必要に停止させてはならない。 | MUST | UC-04, UC-05 |

## 8. セキュリティ要件

| ID | 要件 | 優先度 | 影響 |
| --- | --- | --- | --- |
| SEC-001 | 接続先および通知対象の入力に、意図しない接続先、認証情報またはpathを混入させる形式を許容してはならない。不正入力時は外部通信および購読要求を行ってはならない。 | MUST | UC-01, UC-02 |
| SEC-002 | 本パッケージは、秘密鍵、署名、トランザクション作成およびannounceを扱ってはならない。 | MUST | 責任境界 |
| SEC-003 | 本パッケージが通知のJSON構文以外の意味的妥当性、署名、真正性またはアドレスのnetwork整合性を保証しない場合、その保証範囲を利用者が誤認しないようにしなければならない。 | MUST | UC-02, UC-05 |
| SEC-004 | 暗号化されない通信を利用できる場合、その通信について本パッケージが機密性および完全性を保証してはならない。TLS必須性は未決定事項として扱う。 | MUST | UC-01 |

## 9. データ要件

| ID | 要件 | 優先度 | 影響 |
| --- | --- | --- | --- |
| DR-001 | 本パッケージが扱うデータは、Gatewayから受信する通知、接続状態に関する情報、購読対象および利用者callbackへの一時的な配送情報に限定する。 | MUST | 全ユースケース |
| DR-002 | 通知データに永続保存、再送、欠落補償または履歴取得を保証してはならない。 | MUST | UC-04, UC-05 |

## 10. 受け入れ条件

| ID | 対応要件 | 受け入れ条件 |
| --- | --- | --- |
| AC-001 | FR-001〜FR-003 | Given: 有効なSymbol Gatewayと接続設定がある。When: 利用者が監視を開始する。Then: 接続が開始され、通信路の状態とGateway接続完了を利用者が区別して確認できる。 |
| AC-002 | FR-002, SEC-001 | Given: 接続先または通知対象に不正な値がある。When: 利用者が接続または購読を開始する。Then: 外部接続または購読要求が発生せず、入力不正を判定できる。 |
| AC-003 | FR-004, FR-005 | Given: 対応する通知カテゴリと有効な対象指定がある。When: 利用者が購読する。Then: 対象カテゴリの通知を全体または指定対象に限定して受信できる。対象外カテゴリの限定指定は受け付けられない。 |
| AC-004 | FR-006, FR-007 | Given: 接続完了前または再接続待機中に購読と解除が行われる。When: 接続が利用可能になる。Then: 解除済みの購読は有効化されず、残った購読だけが有効になる。同一対象の複数処理は個別に解除できる。 |
| AC-005 | FR-008 | Given: 登録済み対象と未登録対象の通知が到着する。When: 通知が処理される。Then: 登録済み対象に一致する通知だけが利用者処理へ渡る。 |
| AC-006 | FR-009, FR-010 | Given: 自動再接続が有効な状態で一時的な接続断が発生する。When: 接続が復旧する。Then: 既存および待機中の購読が利用者の再登録なしに継続する。自動再接続無効または上限到達時は再接続を継続しない。 |
| AC-007 | FR-011, FR-012 | Given: 接続完了、接続クローズ、network error、parse errorまたはtimeoutが発生する。When: 利用者がイベントを監視する。Then: 発生事象を区別して受け取り、回復可能性を判断できる。 |
| AC-008 | FR-013, NFR-003 | Given: 一つの利用者callbackが例外を発生させる。When: 同じ通知または後続の接続事象が処理される。Then: 他のcallback、通知配送および接続継続が停止しない。 |
| AC-009 | FR-014 | Given: 利用者が手動切断を選択する。When: 切断が完了する。Then: 自動再接続、購読および登録済みcallbackが継続せず、同一インスタンスの再接続が保証されない。 |
| AC-010 | NFR-001, NFR-002, DR-001〜DR-003 | Given: 通知データまたは秘密情報を扱う。When: 利用者が公開データを利用する。Then: 通知カテゴリに対応する型を利用でき、大きな値の精度が失われず、秘密鍵の要求・保存・ログ出力および通知の永続保存が発生しない。 |

## 11. 未決定事項

### OPEN-001: 対応するGateway・プロトコル・ネットワークの版

対象Gateway、Symbolプロトコル、Mainnet / Testnetの対応バージョンを確定する必要がある。確定しない場合、相互運用性の保証範囲を定められない。

### OPEN-002: TLSと接続先の信頼モデル

TLS必須性、証明書・プロキシの扱い、信頼できないhostを入力する用途に対する責任範囲を確定する必要がある。

### OPEN-003: 通知データの保証水準

JSON構文の確認だけで十分か、通知payloadのruntime schema、署名、真正性および意味的妥当性まで本パッケージが保証するかを確定する必要がある。

### OPEN-004: アドレスのネットワーク整合性

Symbolアドレスのchecksum、network byteおよび接続先ネットワークとの整合性を本パッケージの責務に含めるかを確定する必要がある。

### OPEN-005: 通知の信頼性

購読の受付確認、通知の再送、欠落および重複について、利用者へ保証する水準を確定する必要がある。

### OPEN-006: 再接続終了時の契約

再接続回数の単位、上限到達時の状態および利用者への通知結果を確定する必要がある。

## 12. 仕様設計への引継ぎ

### 要件として確定した範囲

- Symbol Gatewayのリアルタイム通知監視
- 通知カテゴリおよび対応対象の購読・解除
- 接続状態、エラー、切断および再接続の観測
- 接続断後の購読継続
- 不正入力の接続・送信前拒否
- callback例外の障害分離
- 秘密鍵・署名・トランザクション処理を対象外とする責任境界

### 仕様設計で決定する事項

- 公開APIの具体的なメソッド、型、フィールドおよびexport
- 接続先URL、Gateway接続完了判定、購読および解除のwire表現
- 通知データの具体的なスキーマと型対応
- 入力値の具体的な検証規則とエラー表現
- 接続断、再接続、購読復元および手動切断の具体的な状態・処理
- エラー分類、通知順序、ログの具体的な表現

### 参照した情報の区分

- ユーザー明示要求: コードと設計書から、指定ディレクトリへ要件定義書を作成すること。
- 現行設計・公開契約: `packages/symbol-websocket/docs/specifications/spec-websocket.md`、README、CHANGELOG。
- 実装事実: `packages/symbol-websocket/src/`、テストおよびE2Eテスト。
- 技術資料: `docs/knowledge/symbol-openapi3.yml`。WebSocket固有の新規要件は導出していない。
- 承認済み上流要件・コンセプト: 確認できていない。
